## 重构：统一前端模型列表数据源到 useModelsStore

**背景**：模型列表虽已通过 `/api/v1/chat/model/available` 动态查询后端，但前端数据源不统一——`LlmNode`/`FormNode` 用了 `useModelsStore`，而 `ChatInput.vue`、`ModelSelector.vue` 各自独立 fetch 并维护本地 localStorage 兜底，导致重复请求、缓存不一致。

**改动**（3 个文件）：
1. `frontend/src/stores/models.js`：新增 `buildFallbackModels()` 辅助函数；`loadModels` catch 块中，当接口失败且 `models` 为空时，从 `localStorage(chat_model_config)` 读取兜底配置，统一兜底逻辑供所有组件复用。
2. `frontend/src/components/ChatInput.vue`：移除自己的 fetch 与本地兜底；`availableModels`/`modelLoadingError` 改为 computed 指向 store；`loadAvailableModels(force)` 改为调用 `modelsStore.loadModels(force)` 并选默认模型；`defineExpose` 的 `reloadModels` 改为 `() => loadAvailableModels(true)` 强制刷新（`App.vue` 管理模型后无参调用）。
3. `frontend/src/components/ModelSelector.vue`：移除自己的 fetch 与 `buildFallbackModels`；`loading`/`models` 改为 computed（`models` 在 store 列表后追加 `__manage__` 虚拟项）；`loadModels(force)` 改为调用 store 并选默认。

**验证**：grep 确认 `/api/v1/chat/model/available` 的 fetch 现仅存在于 `stores/models.js`；`useModelsStore` 在 5 个组件（ChatInput、ModelSelector、LlmNode、FormNode、stores 定义）统一使用；无残留 `availableModels.value=` / `models.value=` 赋值。

**未改动**：`buildModelConfig()`（ChatInput 选中模型后从 localStorage 取完整 API Key 配置）逻辑保留——本次仅统一"列表数据源"，"选中模型取完整配置"属另一独立问题，待后续处理。

## 修复：点击"管理模型"按钮无反应（ChatInput → App 事件未触达）

**现象**：点击 ChatInput 模型菜单里的"管理模型"按钮，模型管理弹窗不弹出。
控制台日志显示 `[ModelDebug][ChatInput] open-model-config emit completed`，
但完全没有 `[ModelDebug][App]` 日志，说明 emit 执行了却没触达 App 的 `openModelConfigManager`。

**根因**：`frontend/src/components/ChatInput.vue` 的 `openModelManager` 函数里，
执行顺序是「先 `closeModelMenu()` 后 `emit('open-model-config')`」。
`closeModelMenu` 会把 `showModelMenu.value` 置 false，触发 `v-if="showModelMenu"` 的
DOM 卸载调度，在该调度时序下干扰了同步 emit 对父组件 handler 的查找，
导致 `instance.vnode.props.onOpenModelConfig` 查找失败，emit 静默不触发 handler。

**修复**（ChatInput.vue）：
1. 调整 `openModelManager` 顺序为「先 emit 后 closeModelMenu」
2. 用 `getCurrentInstance()` 拿到组件实例，emit 前检查 `vnode.props.onOpenModelConfig`
   是否存在，打印 `hasListener` 诊断日志，便于后续定位
3. import 加入 `getCurrentInstance`

**验证**：dist 产物（22:39 build）确认含旧版「先 close 后 emit」逻辑，用户需重新
`npm run build` 后刷新页面生效。修复后日志会多出 `hasListener` 字段：
- true → 事件绑定正常，emit 应能触达 handler
- false → App.vue 的 @open-model-config 没传到 ChatInput props（HMR/编译问题）

**涉及文件**：`frontend/src/components/ChatInput.vue`（openModelManager 函数，约 336 行）

### 更新（22:54）：顺序不是根因

HMR 推送「先 emit 后 close」改动后重新测试，日志确认顺序已变（emit 时
`showModelMenu: true`，close 在 emit 之后），但 `[ModelDebug][App]` 日志仍缺失——
**handler 仍未触发**。说明之前对「顺序干扰 emit」的根因判断错误。

App.vue 侧已确认无误：
- 第 231 行 `<ChatInput @open-model-config="openModelConfigManager" />` 绑定存在
- 第 672 行 handler 第一行即 `modelDebug('openModelConfigManager handler entered')`
- ChatInput 是 App.vue 直接子组件，无中间层阻隔

**待确认**：`hasListener` 字段（用户日志对象被 Chrome 折叠为 `…`，未展开）。
- `hasListener: false` → vnode.props 里没有 onOpenModelConfig，HMR 状态污染，需重启 dev server
- `hasListener: true` 但 handler 不触发 → 事件派发链路有更深问题，需查 emit/监听器匹配

### 更新（22:57）：真正根因——App.vue render 函数是旧编译缓存

改用纯字符串 `console.log` 打印（避免 Chrome 对象折叠）后，诊断结果明确：
```
hasListener=false
propKeys=["ref","modelValue","onUpdate:modelValue","placeholder","currentSkill",
"assistant-mode","onSend","onQuickAction","onSkillSelect","onRemoveSkill"]
```

ChatInput 的 vnode.props 里**完全没有 `onOpenModelConfig`**。对比 App.vue 源码
（行 216-232），`@stop`、`@file-upload`、`@image-upload`、`@voice-record`、
`@open-model-config`、`:disabled` 这些绑定全部缺失——它们都是某次修改后新增的，
但 Vite HMR 没有重新编译 App.vue 的模板，运行的是历史 render 函数。

**结论**：之前对「close/emit 顺序」的根因判断错误。真正根因是 **App.vue 的
render 函数编译缓存陈旧**，`@open-model-config` 绑定没编进 vnode.props，
导致 ChatInput emit 出去也找不到 handler。

**修复**：无需改代码，重启 dev server（Ctrl+C → npm run dev）+ 浏览器硬刷新
（Ctrl+Shift+R），让 Vite 重新编译 App.vue 模板即可。

**教训**：
1. Vue 3 父组件 `@event` 绑定编译成 `onEventName` 传入子组件 vnode.props，
   若该 prop 不存在，子组件 emit 该事件会静默失效（无报错）
2. 诊断这类问题，直接查 `getCurrentInstance().vnode.props` 的 keys 是最快路径
3. Vite HMR 偶尔会漏编译某个组件的模板（尤其大组件 + 频繁修改时），
   出现"源码对但运行行为不对"时，先重启 dev server 排除缓存问题
4. Chrome 控制台对象默认折叠，诊断日志用纯字符串 `console.log` 打印关键值，
   避免被 `…` 折叠看不到

### 更新（22:59）：最终根因——DashboardHome.vue 的 ChatInput 没绑 @open-model-config

重启 dev server 后 `hasListener` 仍为 false，propKeys 与 App.vue 源码不匹配——
推翻"编译缓存"假设。Grep 发现 **ChatInput 在两个文件被使用**：

1. `App.vue:216` — 绑定了 `@open-model-config`（一直被排查的这个，实际未渲染）
2. `DashboardHome.vue:140` — **实际渲染的实例**，绑定的 props/events 与 propKeys
   完全吻合：`ref/modelValue/onUpdate:modelValue/placeholder/currentSkill/assistant-mode/
   onSend/onQuickAction/onSkillSelect/onRemoveSkill`，唯独没有 `onOpenModelConfig`

App.vue:296 渲染 DashboardHome，但未绑 `@open-model-config`；DashboardHome 的
defineEmits 也未声明该事件。事件链路断裂：ChatInput emit → DashboardHome 无监听 → 静默失效。

**修复**（三处改动，打通事件链路 ChatInput → DashboardHome → App.vue）：
1. `DashboardHome.vue` defineEmits 加 `'open-model-config'`
2. `DashboardHome.vue` ChatInput 加 `@open-model-config="emit('open-model-config', $event)"`
3. `App.vue` DashboardHome 加 `@open-model-config="openModelConfigManager"`

**教训补充**：
1. 排查 Vue 事件失效，第一步就应 grep 组件的**所有使用位置**，不能只看一个父组件
2. `getCurrentInstance().vnode.props` 的 keys 是判断"实际父组件传了什么"的黄金标准，
   可直接锁定运行时渲染该实例的父组件
3. 之前两轮根因判断（close/emit 顺序、HMR 编译缓存）都错，根因是组件实例定位错误——
   教训是先确认"哪个实例在运行"再推断"为什么行为不对"

## 修复：输入框模型配置保存后模型列表不更新

**现象**：从 ChatInput 模型菜单点"管理模型"→保存配置后，输入框的模型下拉列表没有同步刷新。

**根因**（2 处）：
1. `App.vue` 的 `saveModelConfigFromManager` 保存成功后仅调用 `nextTick(() => chatInputRef.value?.reloadModels?.())`。但 `ChatInput` 在 `v-if="activeSessionId"`（已打开会话）下才渲染——首页/欢迎页配置时 `chatInputRef.value` 为 null，可选链短路，刷新被跳过；叠加 store 5 分钟缓存，进会话后也不重拉。
2. `stores/models.js` 的 `loadModels` 并发保护 `if (loading.value) return null` 会直接丢弃刷新请求，连 `force=true` 也被拦截。

**改动**（2 个文件）：
1. `frontend/src/App.vue`：引入 `useModelsStore`；`saveModelConfigFromManager` 成功后改为 `await modelsStore.loadModels(true)` 直接刷新 store（所有订阅 store 的组件 ChatInput/ModelSelector 响应式更新），保留 `chatInputRef.value?.reloadModels?.()` 同步选中项（已渲染时）。
2. `frontend/src/stores/models.js`：新增闭包变量 `loadingPromise`，`loadModels` 改为 promise 复用——进行中则返回同一 promise，不再 `return null` 丢弃请求；`force=true` 不再被并发保护拦截。

**验证**：`npx vite build` 成功（1720 modules，20.98s，0 error）。
**后端确认**：`_get_available_models()`（chat.py）实时查库无缓存；`/llm-config/save`（llm_config.py）正确停用旧激活配置、新建 `is_active=True` 记录并 commit，链路无问题。

## 调整：Spring Boot 后台日志级别 INFO → DEBUG

**需求**：用户反馈"后台日志太少，改为 debug"。

**排查关键**：项目有两个后端——`backend/`（Python FastAPI，端口 8000，已不在一键启动中，`start-backend.ps1` 已标记 `.deprecated`）和 `backend-app/`（Spring Boot，端口 6174，`start-all.ps1` 实际启动的"后台"）。`start-all.ps1` 明确标注 `Backend API: http://localhost:6174 (Spring Boot)`，故用户所说"后台"指 backend-app。

**根因**：`backend-app/src/main/resources/application.yml` 中 `logging.level.root: INFO`，全局 DEBUG 日志被过滤；`com.sitech.prodai` 虽已是 DEBUG，但框架层（Spring/Hibernate/Tomcat/HTTP）日志缺失，整体偏少。

**改动**（application.yml）：
- `root: INFO` → `root: DEBUG`
- 新增噪音抑制：`org.apache.catalina/coyote/tomcat: INFO`、`org.hibernate.orm.deprecation: WARN`、`org.springframework.context.annotation: WARN`，避免全开 DEBUG 刷屏淹没业务日志

**生效方式**：源码改的是 `src/main/resources`，`target/classes/` 下是编译产物。需重启 `start-backend-app.ps1`（mvn spring-boot:run 会重新编译）才生效。
