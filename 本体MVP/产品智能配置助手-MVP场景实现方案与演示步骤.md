# 产品智能配置助手 MVP：核心场景实现方案与演示步骤

> 依据：《中国移动新一代数智云原生省级业务运营系统规范-产商品中心子册@0126修订版》  
> 对齐规划：《产品智能配置助手 — 让配置回归业务本身，复杂逻辑交给 AI》（本体图谱 + 大模型）  
> 目标：基于**本体平台推理能力**，落地 2 个最有价值、可演示、可扩展的产商品**配置** MVP 场景

---

## 一、场景选型结论

### 1.1 推荐的 2 个 MVP 场景

| 优先级 | 场景名称 | 对应规划能力 | 本体推理价值 | 演示冲击力 |
|--------|----------|--------------|--------------|------------|
| **MVP-1** | **智聊·对话配置**（字段推理填报 + 全链路合规校验） | 场景 03：意图识别 → 业务匹配 → 字段推理与填报 | ★★★★★ 缺省补全 + 规则阻断 | 高（画布实时可见 + 冲突拦截） |
| **MVP-2** | **智读·批量生成**（方案文档 → 本体映射 → 多商品并行配置） | 场景 02：文档理解 → 信息抽取 → 本体映射批量生成 | ★★★★★ 非结构化到结构化映射 | 高（一文生成多套配置） |

### 1.2 为何暂不优先「智查·一键复制」

| 场景 | 暂缓原因 |
|------|----------|
| 智查·一键复制 | 核心是语义检索 + 结构化复制，本体推理占比偏低；可作为 MVP-1 的「相似模板推荐」子能力内嵌，不必单独做首期主演示 |

> **原则**：MVP 优先选「本体可推理 + 合规可拦截 + 结果可解释 + 5～8 分钟可讲清」的场景。  
> **智查**作为 Phase-2 / MVP-1 附属能力（对话中推荐相似历史配置）。

### 1.3 场景与规范 / 规划图谱映射

| MVP 场景 | 规范关键概念 | 配置本体图谱节点（规划图） |
|----------|--------------|----------------------------|
| MVP-1 智聊配置 | 商品、商品定价、销售规则、优惠规则、商品关系（互斥/依赖）、融合构成、业务服务模板 | 产品配置 ↔ 产品要素属性 ↔ 配置规则 ↔ 目标用户 ↔ 业务场景 ↔ 营销政策 |
| MVP-2 智读批量 | 同上 + 商品模板 / 产品模板 / 促销模板 | 文档要素抽取 → 映射到上述节点 → 批量实例化 |

### 1.4 选型一句话

- **MVP-1** 证明：配置员「说业务话」，本体负责**填字段、判冲突、保合规**（验证通过率 90%+ 的演示口径）。  
- **MVP-2** 证明：线下方案文档可**一键落库为多套合规配置**，效率提升 80%+ 的演示口径。

## 二、MVP 总体架构（共用底座）

```
┌──────────────────────────────────────────────────────────────┐
│              产品智能配置助手（演示层）                         │
│  对话区 / 实时配置画布 / 合规检查面板 / 文档上传 / 批量结果清单  │
└───────────────┬──────────────────────────────┬───────────────┘
                │ 自然语言 / 文档               │ 结构化配置草稿
┌───────────────▼─────────────┐   ┌────────────▼──────────────┐
│  大模型编排层（轻量）         │   │  本体推理引擎（核心）       │
│  - 意图/槽位抽取              │   │  - 字段缺省推理与补全       │
│  - 文档段落理解               │──▶│  - 资费冲突 / 规则漏洞校验  │
│  - 话术与引导追问             │   │  - 模板匹配 / 关系展开     │
│  - 不改写合规判定结果         │   │  - 证据链回传画布           │
└───────────────┬─────────────┘   └────────────┬──────────────┘
                │                                │
┌───────────────▼────────────────────────────────▼────────────┐
│                   产商品配置本体知识图谱                        │
│  OfferingConfig / Element / ConfigRule / TargetUser           │
│  BizScenario / MarketPolicy / PricePlan / FavRule / Relation  │
└──────────────────────────────────────────────────────────────┘
```

**分工约定（演示必须说清）**

| 角色 | 职责 |
|------|------|
| **本体平台** | 字段推理、关系展开、资费冲突/互斥依赖校验、模板匹配 —— **权威结论** |
| **大模型** | 理解自然语言与文档、追问澄清、把推理结果说成人话 —— **表达与交互层** |
| **配置画布** | 所见即所得展示草稿字段；红灯项必须来自本体校验，不可由模型「口头放过」 |

## 三、配置本体模型设计（MVP 最小集）

### 3.1 核心类（Class）

| 本体类 | 中文 | 对应规范 / 规划 | 说明 |
|--------|------|-----------------|------|
| `OfferingConfig` | 商品配置草稿 | 商品 / 商品创建 | 配置会话中的待落库商品实例 |
| `ProductElement` | 产品要素属性 | 产品属性 / 服务属性 / 业务服务模板参数 | 流量、语音、带宽、QoS 等可配置要素 |
| `ConfigRule` | 配置规则 | 销售规则 / 商品关系 / 定价关系 | 互斥、依赖、必选、M 选 N、渠道约束等 |
| `TargetUser` | 目标用户 | 目标客户群 / 销售规则 | 个人/家庭/政企、星级、校园等 |
| `BizScenario` | 业务场景 | 典型场景（融合/5G/校园等） | 驱动模板与缺省字段的场景标签 |
| `MarketPolicy` | 营销政策 | 促销 / 优惠规则 / 合约 | 折扣、赠送、协议期等 |
| `PricePlan` | 商品定价 | PD_GOODSPRC_DICT | 月费、一次性费、资费类型 |
| `GoodsRelation` | 商品关系 | PD_GOODS_REL | 互斥、依赖、连带订购等 |
| `ConfigTemplate` | 配置模板 | 商品模板 / 产品模板 / 融合业务模板 | 一键复制与批量生成的母版 |
| `ComplianceIssue` | 合规问题 | （配置扩展） | 资费冲突、规则漏洞、必填缺失等 |

### 3.2 核心对象属性

```
OfferingConfig --hasElement--> ProductElement
OfferingConfig --hasPricePlan--> PricePlan
OfferingConfig --constrainedBy--> ConfigRule
OfferingConfig --forTargetUser--> TargetUser
OfferingConfig --inScenario--> BizScenario
OfferingConfig --appliesPolicy--> MarketPolicy
OfferingConfig --basedOnTemplate--> ConfigTemplate
OfferingConfig --hasRelation--> GoodsRelation
OfferingConfig --hasIssue--> ComplianceIssue
ConfigRule --blocksCombination--> (OfferingConfig | PricePlan | ProductElement)
BizScenario --suggestsDefault--> ProductElement | PricePlan | MarketPolicy
ConfigTemplate --definesElement--> ProductElement
```

### 3.3 核心数据属性（节选）

| 属性 | 示例 | 用途 |
|------|------|------|
| `offeringName` / `offeringType` | 家庭融合畅享158 / 主套餐 | 草稿标识 |
| `monthlyFee` / `oneTimeFee` | 158 / 0 | 资费冲突判定 |
| `includeVoice` / `includeData` / `includeBroadband` | 500分钟 / 40GB / 500M | 要素完整性 |
| `channelScope` | 全渠道 / 仅电渠 | 销售规则 |
| `mutexGroup` / `dependOn` | 主套餐互斥组 / 需先订宽带 | 关系推理 |
| `issueType` / `issueLevel` | 资费冲突 / HIGH | 合规面板 |
| `fillSource` | scenario_default / template / user_said | 字段来源可解释 |

### 3.4 推理规则清单（MVP 必配）

#### 规则集 C：智聊字段推理与合规（MVP-1）

| 规则ID | 规则语义 | 推理动作 |
|--------|----------|----------|
| R-C01 | 业务场景=`家庭融合` 且未指定宽带带宽 → 缺省补全 `broadband=500M`（来自场景默认） | 自动填字段，标记 fillSource=scenario_default |
| R-C02 | 目标用户=`校园` 且月费为空 → 推荐对标模板价 `59` 或追问确认 | 填报建议 / 追问槽位 |
| R-C03 | 同一互斥组内已选主套餐 A，再选主套餐 B → **资费/关系冲突** | 生成 ComplianceIssue，阻断提交 |
| R-C04 | 订购附加包但缺失依赖的主服务/宽带 → **规则漏洞：缺少依赖** | 阻断并提示补依赖商品 |
| R-C05 | `monthlyFee=0` 且无合约且场景≠权益赠送白名单 → **高风险资费** | 警告或阻断（可配置） |
| R-C06 | 必填要素（名称、定价、目标用户、渠道）存在空值 → **必填缺失** | 画布标红，引导追问 |
| R-C07 | 优惠折扣=100% 且可重复订购=true → **异常优惠漏洞** | 警告 + 建议改不可重复 |
| R-C08 | 字段均由本体补全/用户确认且无 HIGH 问题 → `compliancePass=true` | 允许「提交配置草稿」 |

#### 规则集 D：智读映射与批量生成（MVP-2）

| 规则ID | 规则语义 | 推理动作 |
|--------|----------|----------|
| R-D01 | 文档抽取到「套餐名+月费+包含要素」三元组 → 映射为 `OfferingConfig` 候选 | 生成草稿骨架 |
| R-D02 | 抽取到的场景关键词命中 `BizScenario` → 绑定场景并继承缺省要素 | 模板/缺省展开 |
| R-D03 | 一文出现 N 个套餐段落 → 并行生成 N 条 `OfferingConfig` | 批量实例化 |
| R-D04 | 对每条草稿执行规则集 C（R-C03～C07） | 批量合规筛查 |
| R-D05 | 仅 `compliancePass=true` 的草稿进入「待确认入库」清单 | 人机协同确认 |

## 四、MVP-1：智聊·对话配置

### 4.1 场景目标

配置人员用自然语言描述需求，助手在 **对话 + 实时画布** 中完成：

1. 意图识别与槽位抽取  
2. 基于场景/模板的**字段推理填报**  
3. 基于配置规则的**全链路合规校验**（自动拦截资费冲突、规则漏洞）  
4. 输出可落库的商品配置草稿（含证据：字段来源 + 命中规则）

### 4.2 业务价值（对齐规划口径）

- 「让配置回归业务本身，复杂逻辑交给 AI」  
- 支撑「效率提升 80%+」「验证通过率 90%+」的演示叙事  
- 本体负责合规，避免大模型「编造可过审配置」

### 4.3 演示数据准备（Mock）

| 实体 | Mock 要点 |
|------|-----------|
| 业务场景 | `家庭融合`、`校园体验`、`5G个人主套餐` |
| 配置模板 | `TPL-HF-128` 家庭融合畅享128（含语音/流量/宽带缺省、月费128、互斥组 MAIN_PKG） |
| 在架商品 | `OF-HF-128`（已上架主套餐，用于演示互斥冲突） |
| 配置规则 | 主套餐互斥；宽带依赖；校园 0 元须合约；必填：名称/月费/目标用户/渠道 |
| 对话脚本 | 见 4.6 |

### 4.4 推理链路（演示时投影）

```
用户话术：「给家庭用户配一个融合套餐，月费158，含500M宽带，全渠道可卖」
        │
        ├─ LLM：意图=创建商品配置；槽位={scene:家庭融合, fee:158, bb:500M, channel:全渠道}
        ├─ 本体 R-C01：补全语音/流量缺省（来自家庭融合场景）
        ├─ 本体 R-C06：检查必填 → 缺「商品名称」→ 追问
        ├─ 用户：「就叫家庭融合畅享158」
        ├─ 本体 R-C03：检查与 OF-HF-128 是否同互斥组冲突（若用户又要再挂一个主套餐则拦截）
        └─ 合规通过 → 画布绿灯 → 生成配置草稿 JSON
```

**冲突演示支路（高潮）**：用户追加「顺便再加一个畅享128主套餐一起上」→ R-C03 命中互斥 → 画布红灯 + 证据链。

### 4.5 接口与能力清单

| 能力 | 输入 | 输出 | 实现方 |
|------|------|------|--------|
| 解析配置意图 | 自然语言 | intent, slots | 大模型 |
| 字段推理填报 | slots + scenarioId | filledFields[], fillSource | **本体推理** |
| 合规校验 | OfferingConfig 草稿 | issues[], passFlag | **本体推理** |
| 相似模板推荐 | slots | templateId[] | 本体检索（内嵌智查） |
| 画布刷新 | 草稿增量 | UI 状态 | 前端 |
| 提交草稿 | passFlag=true 的草稿 | draftId | Mock 落库 |

### 4.6 演示步骤（约 7 分钟）

#### 步骤 0：开场（40 秒）

- 展示配置助手首页：对话区 + 空白配置画布 + 合规面板  
- 金句：「大模型听懂人话，**本体负责填对字段、拦住冲突**」

#### 步骤 1：自然语言发起配置（50 秒）

- 输入：`给家庭用户做一个融合套餐，月费158，带500M宽带，全渠道销售`  
- 期望：意图=`创建商品配置`；画布出现部分字段；合规面板提示「缺商品名称」

#### 步骤 2：展示字段推理来源（70 秒）**【高潮 1】**

- 高亮自动补全项：语音分钟、国内流量（来自场景 `家庭融合` 缺省）  
- 打开「字段来源」：`fillSource=scenario_default` / `user_said`  
- 强调：不是模型瞎填，是本体场景缺省推理

#### 步骤 3：追问补全与画布所见即所得（50 秒）

- 助手追问名称 → 用户回复 `家庭融合畅享158`  
- 画布实时更新；必填红点消失

#### 步骤 4：主动制造冲突并拦截（90 秒）**【高潮 2】**

- 用户：`再绑一个已有的家庭融合畅享128当主套餐一起卖`  
- 本体命中 R-C03（主套餐互斥）  
- 合规面板：`HIGH | 资费/关系冲突 | 规则R-C03`  
- 提交按钮禁用；展示证据三元组（草稿—互斥组—OF-HF-128）

#### 步骤 5：修正后合规通过（40 秒）

- 用户：`那不加128了，就单独上158`  
- 冲突解除；`compliancePass=true`；一键「生成配置草稿」

#### 步骤 6：收束（30 秒）

- 展示草稿 JSON / 可导入产商品中心的字段清单  
- 金句：「冲突不是事后稽核，而是**配置当下被本体拦住**」

### 4.7 验收标准

- [ ] 对话 3 轮内形成完整草稿骨架  
- [ ] 至少 2 个字段标明本体推理来源  
- [ ] 互斥/依赖类冲突 100% 可拦截并展示规则 ID  
- [ ] 大模型话术不得把 `passFlag=false` 说成可提交

## 五、MVP-2：智读·批量生成

### 5.1 场景目标

上传一份线下**产品方案 / 营销方案文档**，助手自动：

1. 解析文档并抽取产商品要素  
2. **按配置本体映射**为多条商品配置草稿  
3. 对每条草稿跑合规规则（复用规则集 C）  
4. 输出「通过 / 待修正」批量清单，支持逐条确认入库

### 5.2 业务价值

- 对齐「智读·批量生成」：文档理解 + 本体映射 + 多商品并行生成  
- 把专家方案从 Word/PPT 变成可执行配置资产  
- 演示「一文多包」效率与「批量合规」质量

### 5.3 演示文档准备（Mock）

准备一份短文档 `校园迎新产商品方案_2026.md`（或 PDF/Word），含 3 个套餐段落：

| 段落 | 内容要点 | 预期结果 |
|------|----------|----------|
| 套餐 A | 校园青春 59 元；含 20GB+200 分钟；目标校园；电渠+厅店 | 合规通过 |
| 套餐 B | 校园体验 0 元流量包；无合约；可重复订购 | 命中 R-C05/R-C07，待修正 |
| 套餐 C | 校园融合加装包；依赖宽带；未写月费 | 命中 R-C06 必填缺失 + 可补依赖提示 |

### 5.4 推理链路

```
上传方案文档
   │
   ├─ LLM：分段抽取 {name, fee, elements, target, channel, constraints}
   ├─ 本体 R-D01/D02：映射 OfferingConfig + 绑定 BizScenario=校园
   ├─ 本体 R-D03：生成 3 条草稿
   ├─ 本体 R-D04：逐条执行 R-C03～C07
   └─ R-D05：清单 = [A通过] [B待修正-零元无合约] [C待修正-缺月费]
```

### 5.5 演示步骤（约 6 分钟）

#### 步骤 0：切到「智读批量」页（20 秒）

- 展示上传区、本体映射说明、历史批量任务

#### 步骤 1：上传方案文档（40 秒）

- 上传 `校园迎新产商品方案_2026`  
- 动画：文档解析 → 识别到 3 个产商品段落

#### 步骤 2：展示本体映射结果（80 秒）**【高潮 1】**

- 同屏三列：原文摘录 | 映射字段 | 命中场景/模板  
- 点开套餐 A：字段与 `BizScenario=校园`、模板推荐对齐

#### 步骤 3：批量合规筛查（90 秒）**【高潮 2】**

- 自动跑规则后清单：  
  - A：通过（绿）  
  - B：HIGH 零元无合约 + 异常优惠（红）  
  - C：必填缺失月费（黄）  
- 点开 B 的证据链：`monthlyFee=0` ∧ `hasContract=0` → R-C05

#### 步骤 4：人机协同修正（50 秒）

- 对 B：勾选「补协议期 12 个月」或「转内部验证渠道」后重跑校验 → 降级或通过  
- 对 C：确认月费 19 元 → 通过

#### 步骤 5：批量确认入库（30 秒）

- 一键「确认通过项入库（Mock）」  
- 展示 2～3 条 draftId；强调未通过项不会入库

### 5.6 验收标准

- [ ] 单文档稳定识别 ≥3 条产商品草稿  
- [ ] 每条草稿可回溯到原文段落  
- [ ] 高风险/缺字段项必须进入「待修正」，不可静默通过

### 7.1 开场（通用）

> 「产品智能配置助手用产商品配置本体把要素、规则、场景、客群、政策结构化。大模型负责听懂配置员的话和方案文档，**字段补全、冲突拦截、批量合规由本体推理完成**，保证配置可解释、可审计。」

### 7.2 MVP-1 收束金句

> 「配置员只需说业务意图，画布上的字段由场景本体推理填报；主套餐互斥、依赖缺失、零元无合约等问题在提交前就被拦住——复杂逻辑交给本体，而不是交给记忆和经验。」

### 7.3 MVP-2 收束金句

> 「线下方案文档一键映射为多条配置草稿，并自动做全量合规筛查；通过的确认入库，有漏洞的当场修正，实现从“写文档”到“可上架配置”的最短路径。」

## 八、风险与应对

| 风险 | 应对 |
|------|------|
| 文档解析不稳定 | MVP 先用结构化 Markdown/表格方案书；解析失败时允许人工圈选段落 |
| 大模型补全错误字段 | 所有自动字段必须带 fillSource；HIGH 级不可由模型覆盖 |
| 规则过严导致演示卡死 | 准备「演示模式」白名单开关，但默认展示真实拦截 |
| 与产商品中心字段不一致 | 草稿字段对齐规范：商品/定价/销售规则/优惠/关系/渠道 |
| 智查能力被追问 | 说明已内嵌为「相似模板推荐」，完整智查放 Phase-2 |
