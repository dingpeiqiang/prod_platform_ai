# 后端接口缺陷单：审批流程发起出参结构与约定不符

- **缺陷等级**：P0（阻塞需求工单审批环节及后续上线审批链路）
- **发现方式**：`wf_runner.py --demo` 实时联网端到端演示（幕2「发起需求审批」）
- **接口**：`POST /api/v1/appstore/approval/submit`
- **提出日期**：2026-09-27
- **状态**：✅ 已修复（2026-09-27 当日后端 `backend-app` 落码 + 契约测试锁定；见第 8 节）

## 1. 问题描述

接口 `POST /api/v1/appstore/approval/submit` 的**出参结构**与《多商品批量接口契约.md》§3.6 不一致：
- 工单级单值 `approval_id` 未在**顶层**返回，被放在了每个 `offers[]` 元素内；
- 顶层 `status` 恒为 `"FAIL"`，与实际提交成功的业务结果矛盾。

导致下游工作流（`wf_sub_11` / `wf_sub_06` / `wf_sub_08`）按约定读取顶层 `approval_id` 时取到空值，误判审批发起失败。

## 2. 权威约定

《多商品批量接口契约.md》§3.6（`POST /api/v1/appstore/approval/submit`）：

| | 改造前 | 改造后 |
| --- | --- | --- |
| 入参 | `{req_id, offer_id, report_url, approval_flow, execution_id}` | `{req_id, approval_flow, offers:[{offer_seq, offer_id, report_url}]}` |
| 出参 | `{approval_id, req_id, approval_type, status, approval_matrix}` | `{approval_id, req_id, status, offers:[{offer_seq, approval_type, status, approval_matrix}]}` |（✅ 已于 2026-09-27 修正为顶层 `approval_id`）

**业务口径确认（产品/后端）**：一个审批工单编号（`approval_id`）对应**一个审批工单**，工单内可包含**多个商品**。因此 `approval_id` 属于**工单级字段，应为顶层单个值**；`offers[]` 仅承载各商品自身的业务状态。

> 说明：约定 §3.6 第145行「改造后」列原先将 `approval_id` 写入 `offers[]` 内，与业务口径矛盾，**已于 2026-09-27 修正为顶层 `approval_id`，并新增「多商品口径」说明条目**。

## 4. 期望报文

按业务口径（工单级 `approval_id` 在顶层，`offers[]` 仅带商品级状态）：

```json
{
  "resultCode": "0",
  "resultMsg": "success",
  "approval_id": "AP202609272237380019",
  "req_id": "PLAN20260927223807124",
  "approval_type": "requirement",
  "status": "SUCCESS",
  "offers": [
    {
      "offer_seq": 1,
      "offer_id": "PLAN20260927223807124",
      "status": "通过"
    }
  ]
}
```

要求：
1. `approval_id`：**顶层**返回工单级单值（一次提交多个商品时，仍为**单个**工单号）；
2. 顶层 `status`：反映**工单提交结果**（成功应为 `SUCCESS`/`OK` 等成功口径，而非恒 `FAIL`）；
3. `offers[]`：承载各商品自身业务状态，不再重复携带 `approval_id`（或至少保证顶层同步返回）。

| 工作流 | 影响 | 说明 |

| `wf_sub_11` 需求工单审批发起 | 直接阻塞 | 读顶层 `approval_id` 为空 → 误报失败（走失败分支） |

跨工作流上下文键 `approval_id`（见 `wf_runner.py:1535 CHAIN_CARRY_KEYS`）约定为**顶层单值**，需后端对齐。

## 6. 修复落地（2026-09-27）

后端 `backend-app` 已按下述方案落码，并新增契约测试锁定口径：

| 文件 | 修复点 |
| --- | --- |
| `OfferSimV16Service.approvalSubmitBatch` | ①工单级 `approval_id` 提升到**顶层信封**；②`offers[]` 元素**移除** `approval_id`；③元素 `status` 保留**审批单域状态**（审批中/通过/NOT_CONFIRMED）供逐品展示；④顶层 `status` 改由 `batchAggStatus(成功数, 总数)` 聚合（成功判据=已生成 `approval_id`），修正原恒 `FAIL` |
| `OfferSimV16Service.approvalStatusBatch` | ①无 `offers[]` 时按 `req_id` 经 `resolveOffersByReqId` 解析**全量商品**；②各元素冗余携带**同一**工单级 `approval_id`；③元素 `status` 保留审批单域状态（通过/审批中/驳回）；④顶层 `status` 同法聚合 |
| `OfferSimV16Service.batchAggStatus`（新增） | 整批态聚合：全成功=SUCCESS / 全失败=FAIL / 其余=PARTIAL，与元素中文域状态解耦 |
| `AppStoreV16Controller`（接口9/10 `@Operation`） | Swagger 描述同步为「工单级 `approval_id` 仅顶层，工单含多商品」新口径 |
| `ApprovalBatchContractTest`（新增） | 2 条用例锁定 §3.6/§3.7 契约（顶层 `approval_id` 单值、元素不再携带、整批 `status=SUCCESS`、按 `req_id` 返回全量品且 `approval_id` 一致） |

> **关键设计点**：元素 `status` 是**审批单域状态**（中文「审批中/通过/驳回」），前端与工作流（`wf_sub_08`）据此逐品展示并按 `status=通过` 触发衔接；**顶层 `status`** 才是批量结果（SUCCESS/PARTIAL/FAIL）。两者解耦，避免以中文域值参与字符串相等聚合导致恒 `FAIL`。

**验证**：`mvn -o test -Dtest=ApprovalBatchContractTest` → 2/2 PASS；全量后端单测 26 条仅 `InterfaceAdapterTest.b4SqlQuery` 1 条失败（**既有失败，与本次无关**，经 `git stash` 复现确认）。

 "offers":[{"offer_seq":1,"offer_id":"...","status":"success","approval_type":"requirement","approval_matrix":[...]}]}
