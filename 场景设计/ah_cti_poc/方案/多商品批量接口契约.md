# 产销品加载 AI 应用 · 多商品批量接口契约（V3.12 草案）

> **状态**：**已评审通过（V3.12）**，据此改造后端（Java）与工作流生成器（`gen_workflows_v2.py`），并重新生成 14 个子工作流 JSON。
> **决策记录**：① 入参/出参数组字段统一为 `offers[]`（彻底替换单品字段）；② 含旁路只读子流（07/08/09/10/11）在内**全部子流**改数组；③ 单品字段（`offer_id`/`offerId`/`globalId` 等顶层标量）**删除**，不再兼容；④ **对接 EOP 真实接口的入参不可改动**（稽核 B1~B4、测试 C1~C4 的 real 契约冻结）。

---

## 0. 分层边界（关键）

多商品改造**只发生在工作流面（`/api/v1/appstore/*` 面向 workflow 的控制器端点）**；对接 EOP 真实接口的适配层契约冻结：

```
工作流（offers[] 批量）
    │  POST /api/v1/appstore/test/offer/start   {req_id, offers:[{offer_seq, offerId}]}
    ▼
Controller / OfferSimV16Service  ← 批量拆解在此层（server 端 for 循环逐品）
    │  逐品调 InterfaceFacade.testOfferStart({offer_id})   ← 入参冻结（EOP real 同构）
    ▼
InterfaceFacade（MockInterfaceAdapter / EopInterfaceAdapter）
    │  单体 EOP 报文（B1~B4、C1~C4 入参不变）
    ▼
EOP 现场
```

- **冻结层**：`InterfaceFacade` 及其实现（`MockInterfaceAdapter`/`EopInterfaceAdapter`）的 9 个方法签名与入参**一律不动**（`{offer_id}`/`{global_id}` 单体）。
- **改造层**：`AppStoreV16Controller` 面向 workflow 的端点 + `OfferSimV16Service` 的批量编排——收 `offers[]`，**服务端逐品调用冻结层**，再聚合为 `offers[]` 返回。
- **工作流层**：一次 HTTP 调用传/收 `offers[]`，无需跨节点循环。

---

## 1. 背景与目标

现状：14 个子工作流均为**单品粒度**——顶层标量 `offer_id`/`offerId`，每环节接口一次处理一个商品；一份需求只能承载一个销售品。

目标：**一份需求 → N 个商品**。接口统一收/发 `offers[]` 数组，工作流**一次调用**处理 N 品，无需跨节点循环（平台无循环节点）。

核心原则：
- **数组即契约**：所有涉及商品的入参用 `offers[]`，出参用 `offers[]`（元素内保留原字段名，如 `offer_id`/`globalId`/`product_config`）。
- **父键不变**：`req_id` 仍为需求级父键（`PLAN\d{17}` 校验零改动），落库寻址 `req_id + node_name` 不变，多品结果以数组内嵌于单键。
- **原子性口径**：整批调用返回 `status`（`SUCCESS`/`PARTIAL`/`FAIL`）+ 逐品 `offers[].status`；写入性键（`spec`/`fee`/`test`）仅当**全部品通过**才写入（由工作流判定）。

## 2. 通用数组元素定义

### 2.1 入参元素（`offers[]`）

调用方按品传入，字段按接口需要选用：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `offer_seq` | int | 商品序号 1..N（与解析产物一致），**必填**，整批唯一 |
| `offer_id` | string | 商品编码（9 位 900 编码）；配置落地/测试/审批传 |
| `offerId` | string | 同 `offer_id`（测试类接口沿用驼峰，见 §3.4） |
| `offer_name` | string | 商品名称（可选，回显/报告用） |
| `plan_json` | string | 落地执行方案 JSON（配置落地传） |
| `config_json` | string | 落地配置 JSON（资费校验传） |
| `report_url` | string | 报告下载链接（审批传，可选） |

### 2.2 出参元素（`offers[]`）

后端按品返回：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `offer_seq` | int | 回显入参序号，用于调用方对齐 |
| `offer_id` | string | 后端确定的商品编码（含新生成） |
| `status` | string | 单品态 `success`/`partial`/`fail` |
| …（各接口专有字段） | — | 如 `product_config`/`group`/`script_url`/`globalId`/`pass`/… |

### 2.3 整批外层信封（出参顶层）

```
{
  "resultCode": "000000",       // 或 "0"（各接口沿用原标记）
  "resultMsg":  "...",
  "req_id":     "PLAN20260913143025087",   // 有则回显
  "status":     "SUCCESS|PARTIAL|FAIL",    // 整批态（无单品失败=SUCCESS）
  "offers":     [ { ... }, ... ]           // 逐品结果数组
}
```

失败口径：单元素失败时该元素带 `status:"fail"` + `error_msg`；整批 `status=PARTIAL` 或 `FAIL`。参数级失败（如 `req_id` 空）仍走 `resultCode`（`PARAM_MISSING`/`5001` 等）且不返回 `offers[]`。

## 3. 逐接口契约

### 3.1 配置落地 `POST /api/v1/appstore/product/config/save`

| | 改造前 | 改造后 |
| --- | --- | --- |
| 入参 | `{req_id, plan_json, offer_id}` | `{req_id, offers:[{offer_seq, plan_json, offer_id}]}` |
| 出参 | `{offer_id, save_result, status, saved_at, product_config, script_url, group?}` | `{req_id, status, offers:[{offer_seq, offer_id, save_result, status, saved_at, product_config, script_url, group?}]}` |

- 幂等：由 `plan_json` 幂等改为**逐品幂等**（每元素按 `plan_json` 查重放）。
- `group`（融合组）随所属品元素内嵌，语义不变。

### 3.2 规格稽核发起（4a）

> **边界**：`audit/realtime` 为 POC 侧稽核入口，改造为批量；其内部若经 B1~B4（现场真实接口）则**逐品调冻结的单体契约**，B1~B4 入参不动。

| | 改造前 | 改造后 |
| --- | --- | --- |
| 入参 | `{offer_id, config_json}` | `{req_id, offers:[{offer_seq, offer_id, config_json}]}` |
| 出参 | `{pass, error_list, audit_summary}` | `{req_id, status, offers:[{offer_seq, pass, error_list, audit_summary}]}` |

> B1~B4（`audit/file/upload`、`audit/async/notify`、`audit/result/insert`、`audit/sql-query`）为**现场真实接口代理，入参冻结不变**（`{fileName,bytes}`/`{sales_id,...}`/`{records[]}`/`{sql_id,params}`）；批量由服务端逐品调用。

### 3.3 规格稽核轮询（4b）

> **边界**：`CODE_POLL_AUDIT` 节点内嵌轮询若经 B4（`audit/sql-query`）则**入参冻结**（`{sql_id, params}`）；工作流面轮询入口承载 `offers[]`。

| | 改造前 | 改造后 |
| --- | --- | --- |
| 入参 | `{requestIds: "..."}`（逗号串） | `{req_id, offers:[{offer_seq, requestIds[]}]}` |
| 出参 | `{pass, error_list, ...}` | `{req_id, status, offers:[{offer_seq, pass, error_list, ...}]}` |

### 3.4 测试发起 / 场景 / 进度 / 结果（C1~C4）

> **边界**：C1~C4 的 EOP real 入参**冻结不变**（`{offer_id}`/`{global_id}`）。工作流面端点收 `offers[]` 后，服务端**逐品调用冻结的 C1~C4** 并聚合。

| 接口 | 改造前入参 | 改造后入参（工作流面） | 改造后出参（工作流面） | 冻结层入参 |
| --- | --- | --- | --- | --- |
| `test/offer/start` | `{offerId}` | `{req_id, offers:[{offer_seq, offerId}]}` | `{req_id, status, offers:[{offer_seq, globalId}]}` | `{offer_id}`（不变） |
| `test/offer/scenes` | `{globalId}` | `{req_id, offers:[{offer_seq, globalId}]}` | `{req_id, status, offers:[{offer_seq, testScenes[]}]}` | `{global_id}`（不变） |
| `test/offer/progress` | `{globalId}` | `{req_id, offers:[{offer_seq, globalId}]}` | `{req_id, status, offers:[{offer_seq, done, failed, failIndex, ...}]}` | `{global_id}`（不变） |
| `test/offer/result` | `{globalId}` | `{req_id, offers:[{offer_seq, globalId}]}` | `{req_id, status, offers:[{offer_seq, testScenes[], orderId, offerInstId, offerName, report_url, testCases[], offer_group_check?}]}` | `{global_id}`（不变） |

- 防重复发起：逐品判断进行中任务（按元素内 `offerId`）。
- `CODE_POLL_PROGRESS`（节点内嵌轮询）改为**批量轮询**：一次 HTTP 传 `offers[{offer_seq, globalId}]`，聚合整批 `done/failed`；单次窗口 5s×60 不变。

### 3.5 资费校准 `POST /api/v1/appstore/billing/rules/verify`

| | 改造前 | 改造后 |
| --- | --- | --- |
| 入参 | `{config_json, check_scene}` | `{req_id, check_scene, offers:[{offer_seq, config_json}]}` |
| 出参 | `{pass, risk_list, compare_list, resultCode}` | `{req_id, status, offers:[{offer_seq, pass, risk_list, compare_list}]}` |

### 3.6 上线审批推送 `POST /api/v1/appstore/approval/submit`

| | 改造前 | 改造后 |
| --- | --- | --- |
| 入参 | `{req_id, offer_id, report_url, approval_flow, execution_id}` | `{req_id, approval_flow, offers:[{offer_seq, offer_id, report_url}]}` |
| 出参 | `{approval_id, req_id, approval_type, status, approval_matrix}` | `{approval_id, req_id, status, offers:[{offer_seq, approval_type, status, approval_matrix}]}` |

- 四环节硬校验（config/spec/fee/test 齐全）改为**逐品**校验（每元素独立判定），元素级 `status=NOT_CONFIRMED` + `reason`。
- **多商品口径**：一个 `approval_id` 对应**一个审批工单**，工单内可包含**多个商品**；`approval_id` 为**工单级**字段，仅出现在**顶层**（单值），`offers[]` 只承载各商品自身的业务状态，不再重复携带 `approval_id`。
- 幂等：按 `offer_id` 幂等不变，逐品判重。

### 3.7 审批进度查询 `GET /api/v1/appstore/approval/status`

| | 改造前 | 改造后 |
| --- | --- | --- |
| 入参 | `req_id`（+ chat_id/approval_id/offer_id 兜底） | `{req_id, chat_id}`；返回该需求**全部品**审批单 |
| 出参 | 单审批单字段 | `{req_id, chat_id, status, offers:[{offer_seq, approval_id, offer_id, approval_type, status, current_node, approver, opinion, submit_time, update_time, approval_matrix}]}` |

> **多商品口径**：一次需求仅对应**一张审批单**（一个工单级 `approval_id`），工单内承载该需求**多个商品**。为便于前端逐品展示与节点级进度渲染，`offers[]` 每元素**冗余携带**同一 `approval_id`（即同一需求下各元素 `approval_id` **相同**）；`status`/`current_node`/`approver`/`opinion` 等为**工单级**进度，各元素一致。

### 3.8 监控查询 `GET /api/v1/appstore/product/monitor`

| | 改造前 | 改造后 |
| --- | --- | --- |
| 入参 | `offer_id` / `req_id` | `{req_id}`（或 `offers:[{offer_seq, offer_id}]`） |
| 出参 | 单品指标 | `{req_id, status, offers:[{offer_seq, offer_id, offer_name, order_count, order_trend, error_count, error_trend, fee_error_rate, fee_trend, metric, alarm_list[]}]}` |

### 3.9 需求文档解析 `POST /api/v1/appstore/requirement/parse-xlsx`

| | 改造前 | 改造后 |
| --- | --- | --- |
| 入参 | multipart `file` | multipart `file`（不变） |
| 出参 | `{resultCode, resultMsg, count, offers[], relations[], source_sheets[]}` | **不变**（已天然数组） |

> 本接口已是 `offers[]` 形态，作为全链路「数组化」的输入源头与命名基准。

### 3.10 节点结果存储/查询（`result/save`、`result/query`）

**契约不变**：`{req_id, node_name, result_json}` / `{req_id, node_name}`。多品结果以 `offers[]` JSON 字符串内嵌于 `result_json`。

## 6. 影响面与风险

- **破坏性**：删除单品顶层字段将导致**现有单品调用/回归用例全部失效**，需同步重写（18 销售品兼容核对表须逐品按单元素 `offers[]` 重跑）。
- **平台校验**：新增代码节点出参须显式声明（返回键 ⊆ 声明出参，E41 教训）；节点 type 仍限 0/1/2/3/6/9/13。
- **生成器**：`gen_workflows_v2.py` 唯一真源，禁手改 JSON；改后重跑生成 14 JSON。
- **旁路子流**：07/08/09/10/11 改数组后须核对「智能体一次调用取全品」的提示词口径。
- **验证**：四档样本《新增四档5G畅享融合套餐销售品.xlsx》端到端（解析 → 提报 → 4 品逐环节 → 审批），验收点见统一方案 6.6.5.7。

## 7. 决议记录（已定）

1. **稽核批量入口**：`audit/realtime` 改造为批量入口（**不新增端点、不改名**）；B1~B4 入参冻结，服务端逐品调用。
2. **去驼峰**：`test/offer/start` 工作流面入参由 `offerId` 改为 `offer_id`（冻结层 C1 的 `offer_id` 不受影响）；全链路统一 snake_case（`offerId` camelCase 特例废除）。
3. **写入门禁**：`spec`/`fee`/`test` **全品通过才写**（工作流 selector 判定整批 `status==SUCCESS`）。
4. **`result/save`/`result/query` 契约不变**：`{req_id, node_name, result_json}` / `{req_id, node_name}`；多品结果以 `offers[]` JSON 字符串内嵌 `result_json`（通用字符串载体，改之无收益且增风险）。
