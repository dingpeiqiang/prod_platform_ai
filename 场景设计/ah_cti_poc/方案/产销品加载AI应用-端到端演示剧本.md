## 幕1 需求提报与需求分析（执行方案生成）

**演示话术（输入）：**
```
我要上新一个 5G-A 套餐，月费 199 元，包含 60GB 国内流量和 1000 分钟国内通话，
流量可结转至次月，支持副卡，营业厅和 APP 渠道可办理，10月1日生效。
请帮我分析需求并生成执行方案。
```

**系统预期输出：**
1. 需求理解（1~2 句话）；
2. 分析结果：已识别要素 + 匹配相似产品（`cpcp_api.py similar_offer` 命中 900102308 5G-A套餐199元，相似度 ≈0.92，offerInfo 同构合并）+ AI补全字段说明（如付费方式=后付费、退订规则=允许退订次月生效）+ 待补充字段提示（仅价格类套餐档位维持待补充，由本体推理引擎判定；套餐编码不补全，显示"系统待生成"）；
3. 《加载方案》五列模块表格（模块/分类/字段名称/字段值/备注，24 字段由 `build_plan` 子命令代码生成，同模块/同分类合并展示）；
4. req_id（如 `PLAN20260913143025087`，统一键，由程序A `build_plan` 子命令以系统时钟生成（LLM 不参与），已通过 `save_node_result` 存入节点结果存储）；
5. 确认提示：【确认配置】/ 修改意见。

**要点强调：** 字段来源备注为【原始需求】/【AI补全】两种；仅价格类（套餐档位）未提取到时"待补充"，价格禁止推理；套餐编码不补全（由智能配置生成）；按 24 字段模板提取（月费→套餐档位、流量→国内通用流量、通话→本地语音、支持副卡→是否允许办理副卡=允许、营业厅/APP→销售渠道=实体渠道、电子渠道、流量可结转→流量结转规则=结转），禁止输出旧口径字段名（产品名称/套餐固定费/渠道类型等）。

**验收映射：** 需求要素映射准确率 ≥95%；AI推理字段标记正确率 100%。

## 幕2 用户确认门禁（先反向，后正向，SKILL.md 语义识别；V2.2 门禁移除）

**幕2.1 反向演示（未确认不配置）：**
```
输入：帮我直接配置落地
预期：SKILL.md 意图路由拒绝——"请先确认执行方案后再触发智能配置"；flow-B 未加载，
      save_product_config 未被调用，CRM 无写入记录。
说明（V2.2）：确认与否由 SKILL.md 核心纪律3 语义识别保证（后端已移除 CONFIRMED 门禁），
未识别到确认类回复时不得加载 flow-B 执行智能配置。
```

**幕2.2 正向演示：**
```
输入：确认执行
预期：SKILL.md 意图路由命中【确认执行】→ 加载 flow-B-execution.md，程序B 串行执行——
  ① 取上下文中执行方案存储键 req_id（沿用原值，不新生成——req_id 由程序A build_plan 生成，LLM 任何环节均不生成 req_id）；
  ② 一次串行跑完四环节（智能配置→稽核→资费→测试，进入幕3，不等用户再发消息）。
  说明（V2.2）：无需写 node_name=CONFIRMED 确认标记——后端 save_product_config
  已移除该门禁，确认语义由 SKILL.md 核心纪律3 识别保证，流程少一次工具调用、更快。
```

**⚠️ 幕2.3 故障排查（联调常见问题）：若输入"确认执行"后系统再次输出执行方案表格（重复需求分析）**
```
现象：SKILL.md 意图路由误判，未加载 flow-B 执行主干，
      仅原样重发需求文本重复运行程序A。
排查：1) 检查 SKILL.md【意图路由表】是否含"确认执行/重新执行失败环节→加载 flow-B"行，
         及核心纪律3 确认语义识别约定（V2.2：识别确认语义后直接串行执行程序B，无需写标记）；
      2) 新会话无 req_id 时，应先运行 query_node_result 检索最近执行方案取回 req_id；
      3) V2.2 门禁已移除：save_product_config 不再校验 confirmed/CONFIRMED 标记，
         NOT_CONFIRMED 状态不再出现；若落地仍失败，检查 plan_json 是否为执行方案
         对象原文（须先 extract_record 提取 list[0].result_json 原文，
         禁止将 query_node_result 的 list 出参数组整体透传）。
```

**验收映射：** 确认门禁有效性（SKILL.md 核心纪律3 语义识别，V2.2）——未确认时配置落地触发率 = 0%。

## 幕3 执行主干程序B 串行执行

**演示观察点：** 确认后程序B 一次运行连打四环节结果，**中途不停顿、无多余人工询问、无并行调用**（每环节返回后打印结果，再执行下一环节脚本）。

**预期输出序列：**
```
【环节1/智能配置】✅ 执行成功
- 关键数据：product_id={...}，offer_id=9001023xx，四类字段写入结果：基础信息✓ 资源配置✓ 营销资源✓ 销售规则✓
- 已自动进入下一环节……

【环节2/配置规格稽核】✅ 执行成功
- 关键数据：稽核通过 + {audit_summary}
- 已自动进入下一环节……

【环节3/资费校准】✅ 执行成功
- 关键数据：资费校准通过，未发现叠加/互斥冲突
- 已自动进入下一环节……

【环节4/销售品自动测试（含受理验证）】✅ 执行成功
- 关键数据：场景 3 个（套餐新装/副卡加装/套餐退订）、测点 N 个全部一致；
  受理验证：orderId={...}，offerInstId={...}，各受理场景均通过
- 执行主干全部完成
```

**技术口径（V1.8 Skills 版）：** SKILL.md 意图路由命中确认意图 → 加载 `references/flow-B-execution.md` → 按程序B 串行运行环节1~4 脚本（`cpcp_api.py save_product_config` → `spec_audit` → `billing_verify` → `offer_test`/`test_scenes`/`poll_test_progress.py` 轮询/`test_result`）；每环节结果由 `save_node_result` 存储落库（req_id=统一键、node_name=config/spec/fee/test，后端持久化），打印后进入下一环节；稽核为实时接口同步返回；测试为"发起→场景→轮询脚本（5s/30min）→结果"。

**验收映射：** 程序B 串行纪律（无并行/无跳步）；每环节结果打印率 100%。

## 幕3A 异常中断与引导（可选彩排，反向演示）

**操作：** 换用预构造的含缺陷需求（互斥优惠叠加）重新走一遍需求分析 → 确认执行。

**预期输出：**
```
【执行中断】❌ 环节：配置规格稽核
- 异常原因：稽核驳回（pass=0）
- 关键明细：error_list——[互斥] 叠加优惠 X 与优惠 Y 互斥不可同订（error）
- 整改建议：移除互斥优惠之一后重新执行……
请选择下一步：
① 回复【重新执行】：将自动从失败环节继续（已成功环节不重复执行）
② 回复【修改执行方案】：请说明修改意见，将重新生成执行方案并再次确认
```

**续跑演示：**
```
输入：重新执行
预期：从稽核环节续跑；环节1 不重复落地（CRM 无重复记录）；已成功环节结果回放打印。
```

**修改方案演示：**
```
输入：修改执行方案，去掉优惠 Y
预期：回到需求分析重新生成执行方案（覆盖写同 req_id），再次等待确认。
```

**验收映射：** 异常处置完整性；续跑正确性（写接口不重复调用）。

## 幕3B 成功详情汇总与审批发起确认（第二次中断，程序B 末步引导）

**预期输出（四环节全部成功后）：**
```
【执行主干全部完成】✅ 共4个环节执行成功：
1. 智能配置：product_id={...}，offer_id={...}，四类字段全部写入成功；
2. 配置规格稽核：通过，{audit_summary}；
3. 资费校准：通过，未发现叠加/互斥冲突；
4. 自动测试（含受理验证）：场景 3 个、测点 N 个全部一致；
   受理验证：orderId={...}，offerInstId={...}，各受理场景均通过。

是否发起上线审批？回复【发起审批】将汇总以上结果提交审批流；
回复【暂不】可稍后发送"发起审批"继续。
```

**反向演示（审批门禁）：**
```
输入：帮我直接上线
预期：系统提示先确认发起审批；flow-C 未加载，submit_release_approval 未被调用。
```

**正向演示（Skills 版）：**
```
输入：发起审批
预期：SKILL.md 意图路由命中【发起审批】→ 加载 flow-C-approval.md（req_id 入参）
→ 程序C 串行自查 5 类环节结果（query_node_result 依次查 config/spec/fee/test/requirement）
→ 按内嵌模板生成 7 章节报告（需求摘要/配置落地/稽核结论/资费结论/测试统计/
受理验证/上线建议）→ 报告存入节点结果存储（save_node_result，node=report）
→ submit_approval 审批推送（后端硬校验 req_id 四环节结果齐全）
→ 输出审批单号 approval_id。
```

**验收映射：** 审批发起门禁（未确认时审批推送触发率 0%）。
