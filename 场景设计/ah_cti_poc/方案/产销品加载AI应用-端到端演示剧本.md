## 幕1 需求提报与需求分析（执行方案生成）

**演示话术（输入）：**
```
我要上新一个 5G-A 套餐，月费 199 元，包含 60GB 国内流量和 1000 分钟国内通话，
流量可结转至次月，支持副卡，营业厅和 APP 渠道可办理，10月1日生效。
请帮我分析需求并生成执行方案。
```

**系统预期输出：**
1. 需求理解（1~2 句话）；
2. 分析结果：已识别要素 + 匹配相似产品（`query_similar_offer` 命中 900102308 5G-A套餐199元，相似度 ≈0.92）+ AI 补全字段说明（如收费方式=月付、退订生效规则=次月生效，来源"AI补全"）+ 待补充字段提示（仅当套餐固定费未提取到或三类资源全部未提取到；产品编码不补全，显示"由智能配置生成"）；
3. 《产销品加载执行方案》Markdown 表格（4 列：字段分类/字段名称/字段值/来源）；
4. req_id（如 `PLAN20260913143025087`，V1.8 统一键，由 wf_sub_01 拆分代码节点以系统时钟生成（LLM 不参与），已存入节点结果存储）；
5. 确认提示：【确认执行】/ 修改意见。

**要点强调：** 字段来源只有"原始需求/AI补全"两种；仅当套餐固定费未提取到或三类资源全部未提取到时"待补充"，不推理；产品编码不补全（由智能配置生成）。

**验收映射：** 需求要素映射准确率 ≥95%；AI 补全字段标记正确率 100%。

## 幕2 用户确认门禁（先反向，后正向，V1.7 LLM 智能调度）

**幕2.1 反向演示（未确认不配置）：**
```
输入：帮我直接配置落地
预期：智能体拒绝——"请先确认执行方案后再触发智能配置"；CRM 无写入记录（save_product_config 未被调用）。
```

**幕2.2 正向演示（V1.7）：**
```
输入：确认执行
预期：智能体 LLM 执行确认流程——
  ① 取上下文中执行方案存储键 req_id（沿用原值，不新生成——req_id 由 wf_sub_01 代码节点生成，LLM 任何环节均不生成 req_id）；
  ② 写确认标记（save_node_result：req_id=执行方案存储键、node_name=CONFIRMED）；
  ③ 立即串行直调 wf_sub_02→wf_sub_03→wf_sub_05→wf_sub_04（进入幕3，不等用户再发消息）。
```

**⚠️ 幕2.3 故障排查（联调常见问题）：若输入"确认执行"后系统再次输出执行方案表格（重复需求分析）**
```
现象：智能体识别到确认意图，但未执行"写确认标记+串行直调子流"流程，
      仅原样重发需求文本重复调用需求分析。
排查：1) 检查智能体提示词是否包含主方案 3.2【意图→子工作流智能调度映射表】
         及【技能2】确认标记写入约定；
      2) 确认"确认执行"触发时 LLM 先调 save_node_result（req_id=执行方案存储键、
         node_name=CONFIRMED），再按映射表串行直调子工作流；
      3) 新会话无 req_id 时，LLM 应先调 query_node_result 检索最近执行方案；
       4) 硬校验兜底：即使 LLM 跳步直调 wf_sub_02，后端 save_product_config
          因存储中无 CONFIRMED 标记返回 NOT_CONFIRMED，不会误写入 CRM。

  V2.1 诊断增强：NOT_CONFIRMED 返回体 save_result.diagnose 字段会列出该 req_id
  已有的环节记录，直接区分两类根因：
  - diagnose="该 req_id 下无任何环节记录……" → req_id 传错（LLM 重新生成而非沿用
    执行方案存储键），需检查 req_id 是否沿用；
  - diagnose="该 req_id 已有环节: requirement/config……确认标记缺失" → LLM 跳步，
    未按【技能2】先写 node_name=CONFIRMED。

  手动兜底修复（验证门禁放行，PowerShell 示例，端口默认 6174）：
    # 1. 手动写确认标记（req_id 换成实际执行方案存储键）
    curl.exe -X POST http://localhost:6174/api/v1/appstore/result/save `
      -H "Content-Type: application/json" `
      -d '{\"req_id\":\"PLAN20260913182110931\",\"node_name\":\"CONFIRMED\",\"result_json\":\"{\\\"confirmed\\\":true,\\\"req_id\\\":\\\"PLAN20260913182110931\\\"}\",\"status\":\"ok\"}'
    # 2. 重新调 save_product_config（同报文）应返回 SUCCESS
    #    注意：plan_json 应传执行方案对象本身（wf_sub_01 的 result_json 原文），
    #    而非 query_node_result 的 list 出参数组。
```

**验收映射：** 确认门禁有效性（工具层硬校验）——未确认时配置落地触发率 = 0%。

## 幕3 执行主干 LLM 串行直调（V1.7）

**演示观察点：** 确认后 LLM 一次运行连打四环节结果，**中途不停顿、无多余人工询问、无并行调用**（每环节返回后打印结果，再直调下一子工作流）。

**预期输出序列：**
```
【环节1/智能配置】✅ 执行成功
- 关键数据：product_id={...}，offer_id=9001023xx，四类字段写入结果：基础信息✓ 资源配置✓ 营销资源✓ 销售规则✓
- 已自动进入下一环节……

【环节2/配置规格稽核】✅ 执行成功
- 关键数据：稽核通过 + {audit_summary}
- 已自动进入下一环节……

【环节3/资费校准】✅ 执行成功
- 关键数据：资费校准通过，未发现叠加/互斥冲突
- 已自动进入下一环节……

【环节4/销售品自动测试（含受理验证）】✅ 执行成功
- 关键数据：场景 3 个（套餐新装/副卡加装/套餐退订）、测点 N 个全部一致；
  受理验证：orderId={...}，offerInstId={...}，各受理场景均通过
- 执行主干全部完成
```

**技术口径（V1.7）：** 智能体 LLM 串行直调 8 个子工作流中的 4 个执行环节子流（wf_sub_02→03→05→04）；每环节结果由子流内部 save_node_result 节点存储（req_id=入参统一键、node_name=config/spec/fee/test，后端落库持久化），LLM 打印结果后直调下一环节；稽核为实时接口同步返回；测试为"发起→场景→代码节点轮询（5s/30min）→结果"。

**验收映射：** LLM 串行调度纪律（无并行/无跳步）；每环节结果打印率 100%。

## 幕3A 异常中断与引导（可选彩排，反向演示）

**操作：** 换用预构造的含缺陷需求（互斥优惠叠加）重新走一遍需求分析 → 确认执行。

**预期输出：**
```
【执行中断】❌ 环节：配置规格稽核
- 异常原因：稽核驳回（pass=0）
- 关键明细：error_list——[互斥] 叠加优惠 X 与优惠 Y 互斥不可同订（error）
- 整改建议：移除互斥优惠之一后重新执行……
请选择下一步：
① 回复【重新执行】：将自动从失败环节继续（已成功环节不重复执行）
② 回复【修改执行方案】：请说明修改意见，将重新生成执行方案并再次确认
```

**续跑演示：**
```
输入：重新执行
预期：从稽核环节续跑；环节1 不重复落地（CRM 无重复记录）；已成功环节结果回放打印。
```

**修改方案演示：**
```
输入：修改执行方案，去掉优惠 Y
预期：回到需求分析重新生成执行方案（覆盖写同 req_id），再次等待确认。
```

**验收映射：** 异常处置完整性；续跑正确性（写接口不重复调用）。

是否发起上线审批？回复【发起审批】将汇总以上结果提交审批流；
