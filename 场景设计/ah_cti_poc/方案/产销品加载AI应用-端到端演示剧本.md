### 1.5.4 本轮发现的差异点（演示与后续整改须知）

1. **渠道落地**：需求「APP 渠道可办理」未显性落地，渠道字段来源标注为"模型推测"（落为营业前台/实体渠道）。演示时应对 APP 渠道口径做人工确认，或补充渠道映射规则。
2. **自动测试与资费校准顺序**：本文档各幕按演示口径写为 `wf_sub_02 → wf_sub_03 → wf_sub_05（资费）→ wf_sub_04（测试）`，但**本轮 wf_runner 实际串行顺序为 `02 → 03 → 04（测试）→ 05（资费）`**。因自动测试先于资费校准执行，wf_sub_04 读取 fee 环节结果为空，导致受理类场景 `S_O_TC`/`S_U_TC` 判定「未执行」，测试整体结论退化为「⚠️ 评估风险后上线」。**整改建议**：串行执行应恢复为"资费校准先于自动测试"，或在 wf_sub_04 内对 fee 结果缺失做显式容错。
3. **受理验证数据缺失**：wf_sub_04 本轮未调用 `test/offer/scenes`，`testScenes`/`orderId`/`offerInstId` 均为空，报告第四章受理验证无实际凭证。演示前需确认 `test/offer/scenes` 端点连调、补齐受理凭证。
4. **模型推测/AI补全字段**：销售开始日期 `system_date`、权益"10 分钟+10 条短信"等字段来源为模型推测/相似品补全（相似品 900102308），演示时应如实标注为 AI 补全，避免被误认为需求原文。

## 幕1 需求提报与需求分析（wf_sub_00 → wf_sub_01）

**系统预期输出：**

【子工作流 0 · 需求提报（wf_sub_00）】
1. 智能体（助手）按提示词【意图→工作流映射表】语义识别 intent=REQ_REPORT → 直调 `wf_sub_00`；
2. LLM 需求字段抽取（snake_case 平面 JSON，未提及项空串）→ 代码节点 `render_requirement_report` 确定性渲染《销售品需求提报单》；
3. 生成需求单号 `req_id` + 待补充判定；无待补充 → 保存需求工单（node_name=requirement_report）+ 触发**需求工单审批**（approval-type=requirement，`submit_release_approval`）→ 进入需求分析。

【子工作流 1 · 需求分析（wf_sub_01，模板轨六步：①识别→②相似→③模板→④提取→⑤合并→⑥渲染）】

5. 步骤④ 要素提取：LLM 按模板叶子清单提取嵌套要素 → `validate_elements` 质量校验代码节点（六项校验 + E31 可提取命中率门禁 ≥0.30）；
6. 步骤⑤ 合并：`merge_nested` 代码节点（JSONPath 对位，schema 骨架）——需求值 source=原始需求、相似品补全 source=AI补全、schema default source=默认值；**价格字段需求未提供时留空（禁止从相似品照搬）**；随后 `validate_nested` **本体校验闸**代码节点（HTTP 调用 `/api/v1/appstore/validate-nested`，R-C04/C06，不可达回退占位）；
7. 《加载方案》**分节多表**（`render_table` 代码节点渲染业务分节表格）：概览卡片置顶（资费名称/套餐月费/包含资源）+ "1. 基础信息 / 2. 发布信息 / 3. 可选配置…" 独立小节 + 小节内二级分组加粗子标题 + 三列表格（字段名称/字段值/备注），**纯 x-label 中文，无技术键名**；
8. 保存 requirement（延续 req_id，衔接 wf_sub_02~05 自查链路）+ round trip 输出方案 + 待补充字段 + 要素质量 + 本体校验结论；
9. 确认提示：【确认配置】/ 修改意见。

**要点强调：**
- 需求提报（环节1）为新增独立子工作流：需求工单审批 approval-type=requirement 双轨之一，req_id 全程贯穿衔接；
- **LLM 仅在"翻译"环节做"自然语言→结构化"转换**，合并/校验/渲染/路由全部代码节点执行（输出逐字节可回归）；

- 同输入输出逐字节稳定（幂等），禁止为"展示好看"加工渲染结果。

**验收映射：** 需求要素映射准确率 ≥95%；模板轨六步全链路可回归（同输入逐字节一致）；AI补全字段标记正确率 100%；需求提报/需求工单审批闭环。
