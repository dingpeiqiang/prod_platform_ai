# 端到端演示剧本验证与异常问题清单

> **验证对象**：《产销品加载AI应用-端到端演示剧本.md》V5.1 所描述的全部演示场景
> **执行器**：`工作流配置/wf_runner/wf_runner.py`
> **模式**：`--demo`（真实 LLM 编排回放）为主 + `--chain`（串行全链路）为辅
> **环境**：真实联网（LLM 网关 + 插件后端网关 `http://10.86.13.201:31281` 均可达）
> **日期**：2026-09-28
> **最终结论**：`--demo` **32/32 断言 PASS、15 回合全绿**；连带修复串行模式「异常不中止」的逻辑缺陷

---

## 1. 验证结论（一句话）

演示剧本的**正常主干全链路**已可通过 `--demo` 完整走通（LLM 编排 32/32 PASS）与 `--chain` 走通（10/10 环节 PASS）；验证过程中发现并修复了 **4 类编排层缺陷**（A~D）与 **1 类串行执行逻辑缺陷（E，本轮新增修复）**，另存 1 项**演示覆盖度缺口**（异常分支回合未纳入脚本回放）。

## 2. 验证方法与基线

| 模式 | 作用 | 判定口径 |
| --- | --- | --- |
| `--demo` | 以主智能体提示词驱动真实 LLM，逐条回放剧本用户回合，LLM 自主决定「直调哪个子流 / 拒绝 / 纯回复」，runner 本地执行并回灌结果；每轮做确定性语义断言 | 断言级 PASS/FAIL + 回合级结论 |
| `--chain` | 按 `CHAIN_ORDER`（00→01→02→03→12→05→04→13→06→07）串行执行，全程同一 `req_id` | 环节级 PASS/FAIL/中止 |
| `--verify` | 逐个工作流独立执行 | 环节级 PASS/FAIL |

- **LLM**：`qwen3-30b-a3b`（`max_tokens` 种子值 4096，temperature 0.3）。
- **提示词权威来源**：统一方案 §2.2 围栏代码块（见缺陷 A 修复）。
- **日志**：`wf_runner/logs/demo_*/demo_report.md`（回合→断言明细）、`wf_runner/logs/<环节>_*.log.md`（逐节点）、`wf_runner/logs/_chain_*_out.txt`（命令输出）。

## 3. 缺陷清单与修复

### 缺陷 A【P0，已修复】编排者提示词缺失导致意图误路由

- **现象**：首轮 `--demo` 断言 32 项中 FAIL 9 项；回合 1「我要新增…」被误路由到 `wf_sub_02`（应为 `wf_sub_00`），需求从未提报 → 后端该 `req_id` 下 `requirement`/`config` 全空 → 全链路环节空转。
- **根因**：`_load_orchestrator_prompt()` 读取 `logs/_prompt_22.txt`，文件缺失时回退到**内置精简提示词**，该精简版**不含「意图→工作流映射表」**，LLM 无法正确路由。
- **修复**：
  1. 新增 `_extract_orchestrator_prompt_from_plan()`，从 `方案/产销品加载AI应用-统一方案.md` §2.2 的围栏代码块**自动抽取**主智能体提示词全文（含映射表与限制），作为权威、可随仓库持久化的来源（`logs/` 已被 `.gitignore` 忽略，原 `_prompt_22.txt` 无法入库）。
  2. `_load_orchestrator_prompt()` 来源优先级：① `logs/_prompt_22.txt` 覆盖文件（临时调参）→ ② 统一方案 §2.2 自动抽取 → ③ 内置精简兜底。
  3. 抽取结果与手工提取的 `_prompt_22.txt` **逐字节一致**（6056 字符，`equal True`）。
- **验证**：修复后回合 1 正确路由 `wf_sub_00`。

### 缺陷 B【P0，已修复】编排层 JSON 被截断，决策整条丢失

- **现象**：回合 4「生成加载方案」LLM 返回的 JSON 解析失败（`action` 为空），该回合**未执行 `wf_sub_01`** → 执行方案未落库 → `wf_sub_02/05/04` 级联业务失败（回合 9/10/11 连锁 FAIL）。
- **根因**：LLM 把整份《加载方案》markdown 表塞进 JSON 的 `reply` 字段，`max_tokens=4096` 不足以容纳 → JSON 被截断/转义非法 `_extract_json_object` 返回 `None`。
- **修复（三管齐下）**：
  1. **提示词协议**：在输出协议中新增「reply 长度铁律」——严禁将完整方案/大段 markdown 表塞入 `reply`，表格概括为一两句话或 ≤3 行小结。
  2. **提额**：新增 `ORCHESTRATOR_MAX_TOKENS = 8192`，仅对编排者「决策 / 结果表达」两次调用生效，不影响子流内部节点。
  3. **容错解析**：新增 `_salvage_truncated_json()`，当整体解析与平衡扫描均失败时，按顶层字段逐字段抢救（优先 `action`/`workflow`，再 `reply`/`reason`），避免单个超长字段截断导致整条决策丢失。
- **验证**：修复后回合 4 正确调用 `wf_sub_01`（15 节点 PASS），下游 02/03/12/05/04/13/06 全绿。

### 缺陷 C【P1，已修复】串行模式不中止：上游异常后剩余环节照跑

- **现象**（用户指出）：`--chain` 串行时，某环节**业务层未达成**（命中异常结束分支 / 待补充阻断），**其余环节仍继续执行**，属“带病空跑”，逻辑不合理。
- **根因**：`_run_chain` 无条件遍历 `CHAIN_ORDER`；`ChainResult.passed` 仅依据**节点级** `error/fallback`，而工作流的成功/失败体现在**结束节点业务分支**上（如 `结束(有待补充)`、`结束(方案质量未通过)`、`结束(配置未通过-未写config)`），与节点级 PASS 并不等价。
- **修复**：
  1. `ChainResult` 新增 `end_title`（实际到达的结束节点标题，权威业务分支）与 `skipped`（被跳过）。
  2. `_chain_one` 捕获结束节点标题。
  3. 新增 `chain_business_halt(cr)`：节点级报错，或结束标题含 `失败/未通过/未写/缺失/有待补充` 即判定业务未达成（成功分支名 `…完成/已发起/已生成/已提报/正常…` 不含这些词，无误伤；`结束(异常-已告警并闭环)` 为监控正常闭环，不在标记内）。
  4. `_run_chain` 一旦中止，后续环节全部标记 `SKIP` 并显示原因，汇总区分「执行 / 跳过」，退出码非 0。
- **验证**：
  - 稀疏需求（`我要新增一个套餐。`）→ `wf_sub_00` 命中 `结束(有待补充)` → **串链中止**，`wf_sub_01~07` 共 9 环节全部 SKIP，`exit=1`。修复前该场景会继续跑完 10 环节。
  - 完整需求（剧本第一幕原文）→ 10/10 环节 PASS，**无误中止**，且日志新增「结束分支」列（如 `结束(审批已提交)`、`结束(正常-运营报告)`）。

### 缺陷 D【P2，保留观察】演示脚本回放未覆盖异常/补录回合

- **现象**：`DEMO_TURNS`（15 回合）仅覆盖**正常主干**；剧本头部（需求四要素必带、缺月费/资源会触发「待补充」阻断）与附 B（异常与兜底话术）描述的**异常分支未纳入回放**。
- **影响**：`--demo` 无法证明编排者在异常分支下的行为（如「需求分析不通过需补录信息」时是否正确阻断并引导补录）。
- **现状**：异常分支已在**工作流层**证明可达（见第 4 节），本轮按用户确认口径「异常分支只需经日志分析指出」处理，暂不注入 `DEMO_TURNS`。

### 缺陷 E【P2，已修复】`reporter` 入参占位符泄漏到演示输出

- **现象**：`wf_sub_00` 结束正文出现 `提报人 | 【样例】reporter（可 --set reporter=... 覆盖）`。
- **根因**：`wf_sub_00` 开始节点 `reporter` 声明默认占位符。
- **建议**：`--demo`/`--chain` 运行时注入真实会话用户（或留空），避免占位符出现在面向客户的输出中。**（本轮为可选项，未强制改动）**

## 4. 异常分支可达性证据（工作流层已支持）

各子工作流结束节点均区分**成功 / 失败**分支，串行模式现据此中止：

| 环节 | 子流 | 成功结束分支 | 异常/阻断结束分支 |
| --- | --- | --- | --- |
| 需求提报 | wf_sub_00 | `结束(无待补充-止于确认点)` | `结束(有待补充)` |
| 需求分析 | wf_sub_01 | `结束(方案已生成)` | `结束(需求工单缺失-失败)`、`结束(方案质量未通过)` |
| 智能配置 | wf_sub_02 | `结束(配置落地完成)` | `结束(配置未通过-未写config)` |
| 规格稽核 | wf_sub_03/12 | `结束(稽核已发起)`、`结束(稽核查询完成)` | `…未写audit_pending`、`结束(稽核处理中-未写spec)`、`结束(稽核未通过-未写spec)` |
| 自动测试 | wf_sub_04/13 | `结束(测试已发起)`、`结束(测试查询完成)` | `…未写test_pending`、`结束(测试处理中-未写test)`、`结束(测试未通过-未写test)` |
| 资费校准 | wf_sub_05 | `结束(资费校准完成)` | `结束(资费未通过-未写fee)` |
| 上线审批 | wf_sub_06 | `结束(审批已提交)` | —（前置守卫在编排层） |
| 监控运维 | wf_sub_07 | `结束(正常-运营报告)`、`结束(异常-已告警并闭环)` | —（异常告警闭环即成功终态） |
| 存量合规 | wf_sub_10 | `结束(合规扫描)` | `结束(合规服务未就绪-失败)` |

**「需求分析不通过需补录信息」场景证据链**（`wf_sub_01`）：

1. 节点 `0108 要素校验与方案合并` 产出 `quality_gate`（命中率 ≥ 阈值 0.30 为「通过」）、`pending_required`、`ve_stats`。
2. 节点 `0117 方案质量门禁`：`quality_gate=="通过"` → `-1` 分支进 `0112 面板 → 0111 结束(方案已生成)`；否则 `0` 分支进 `0118 结束(方案质量未通过)`，正文明确「**暂不引导进入配置**，请补充/修正后回复【重新分析】」。
3. 若需求稀疏至**提报阶段**即不满足（缺月费/套内资源）：`wf_sub_00` 直接命中 `结束(有待补充)`，不再落 `requirement_report`，故 `wf_sub_01` 读到 `list:[]` 并命中 `结束(需求工单缺失-失败)`——**示例实测**：`--chain --chain-text "我要新增一个套餐。"` → `wf_sub_00 结束(有待补充)` 即中止。
4. 命中率实测：完整需求（含月费/资源/规则）= **38.5%**（> 30%，通过）；仅「月费+资源」= 通过；稀疏需求 = 提报阶段即阻断。

> 结论：异常分支在**工作流层与串行执行层均已可触发且可观测**；`--demo` 回放脚本尚未覆盖，属演示脚本覆盖度问题（缺陷 D）。

## 6. 覆盖度缺口与后续建议

| 项 | 说明 | 建议 |
| --- | --- | --- |
| 异常分支未纳入 `--demo` 回放 | `DEMO_TURNS` 仅正常主干 | 新增「稀疏需求→待补充→补录→重新分析」异常回合链（可加开关，避免影响主基线），覆盖剧本头部四要素约束与附 B 话术 |
| `reporter` 占位符 | 面向客户输出出现 `【样例】reporter` | 运行时注入会话用户或留空 |
| 需求描述四要素 | 剧本头部要求；缺月费/资源直阻断 | 已在 `--demo` 回合 1 文本中保证要素齐备；建议在 `DEMO_TURNS` 注释中固化该约束 |
| 高风险阈值敏感 | 质量门禁命中率 38.5% vs 阈值 30%，余量有限 | 关注 `wf_sub_01:0107/0108` 抽取完整性与命中率统计口径（另见《多品工作流全链路验证与优化改进方案》P2-1） |
