## 3. 问题清单与整改方案

### P0-1【契约§4 未实现】写入门禁缺失：spec/fee/test 未做「全品通过才写」

**证据**：`wf_sub_02/03/04/06`（写 `config`/`audit_pending`/`test_pending`/`report`）**type-2 selector 数量为 0**；`wf_sub_05` 边为直线 `0401→…→0410→0408→0405→…`，节点 `0405 环节结果存储` **无条件执行**。即 `pass=0`/`status=FAIL` 时仍写入 `spec`/`fee`/`test`。

**契约**：§1 原子性口径、§4 写入门禁、§7 决议 3——“仅当全部品通过才写入（selector 判定 `status==SUCCESS`）”。

**整改**：
1. 在写库节点（02-0105、03-0205、04-0305、05-0405、06-0614）**前**各插入 1 个 type-2 selector「写入门禁」。
2. 判定源用**聚合后**的整批 `status`（02/03/04 用接口返回 `status`；05 用 `0410.pass`；06 用 `0612` 汇总结论），条件 `等于 SUCCESS`（05 为 `pass 等于 1`）。
3. 「通过」分支→写库并继续；「未通过」分支→写临时态（如 `*_pending`）并走独立的「未写库」结束节点，在 flowRemark/正文标注未写原因。

> 注：§4 落库键为 `req_id+node_name`，未通过时**不覆盖已有正式键**即可保证“全品通过才有正式记录”。

### P0-2【契约§2.2/§4】`status` 字段未在写入节点校验，仅靠 API 侧隐含

**证据**：节点 `0410` 已产出 `pass`（全品聚合），但下游未消费该值做门禁；`0108` 产 `status`/`quality_gate` 却无消费方。

**整改**：与 P0-1 合并——selector 的判定左值**必须引用聚合 `status`/`pass`**，禁止硬编码常量 `1`。

---

### P1-1【契约§3.12/删标量】`CHAIN_CARRY_KEYS` 仍携带废弃单品标量 `offer_id`

**证据**：`wf_runner.py:1539` `CHAIN_CARRY_KEYS = ("req_id", "offer_id", "approval_id", "globalId")`。契约明确顶层单品标量 `offer_id`/`globalId` 应删除，多品靠 `req_id` 传递。

**整改**：改为 `("req_id", "approval_id")`（`globalId` 亦为单品标量）；在 `:1554/1713/1731` 三处透传点同步核对，确保 `offers[]` 作为整块 JSON 原样跨环节携带（已在各提取节点实现，无需逐字段）。

### P1-2【契约§2/显式出参】结束节点面板 URL 为空 `offer_id=&name=`

**证据**：`wf_sub_01:0112 构建页面地址面板` 仅接线 `chat_id`、`req_id` 两个入参，代码读取 `offer_id`/`offer_name` 恒为空 → `biz_url` 中 `offer_id=&name=`。

**整改**（二选一）：
- **A（推荐，契合多品）**：面板 URL 去掉 `offer_id`/`name`，改用 `req_id`（列表页按父键展示 N 品）；代码删除 `offer_id`/`offer_name` 读取。
- **B（兼容单入口）**：将上游 `0103.offers[0].offer_id`/`offer_name` 接入 0112 入参，取首品回显。
- 各子流面板节点（02-0109、03-0209、04-0321、05-0409 等）统一口径。

### P2-1【质量门禁未消费→已改为软门禁】wf_sub_01 抽取质量低仍继续

**证据**：`wf_sub_01` 唯一 selector 为 `0115 需求工单有效性判定`，`0108` 产出的 `quality_gate:"不通过"`/`ve_result:"不通过"` **无消费方**，流程照常 `0109 渲染→0110 保存→结束`，且结束正文**无条件**引导「回复【确认执行】」。

**整改（已实施）**：保存后新增 selector `0117 方案质量门禁`（判定 `108.quality_gate=="通过"`）：
- `-1`（通过）→ `112` 面板 → `111 结束(方案已生成)`，正常引导【确认执行】；
- `0`（不通过）→ `118 结束(方案质量未通过)`，**保留 requirement 落库**（待补充场景必需），但**阻断引导**，要求先补充/整改。

**整改即暴露的深层问题（新发现）**：启用门禁后复跑，`wf_sub_01` 门禁恒为**不通过**——
```
第N档：提取字段总数 13，有效 5，无效剔除 8；必填字段 48（可提取 34，命中 3，可提取命中率 8.8%）；门禁阈值 0.30
```
即 LLM 要素抽取仅命中 3/34（8.8%），远低于 30% 阈值。此前因无消费方被完全掩盖。

**后续（非本次范围）**：需排查 `0107 配置要素提取` LLM 抽取完整性与 `0108` 命中率统计口径（48 必填 / 34 可提取的合理性、schema 必填项是否过严），属抽取质量调优，与多品链路结构无关。阈值 30% 已在 `0108` 入参集中定义。

### P2-2【非缺陷·已澄清】4 品 payload 字段差异化

**初判**：`billGprsCfg.theshold=100` 等除费用外 4 品完全一致。

**复核结论（2026-09-28）**：**非缺陷**。初判基于非差异化测试文本（四档均写「100GB流量、1000分钟语音」），故一致正确。改用真实样本差异化输入复跑（79/99/139/169 元、20/40/60/80GB、100/150/200/250 分钟）后，逐品差异字段正确：

```
optionalInfo.acctMonth.fixFee        = 79 / 99 / 139 / 169
optionalInfo.printContent.prcMonthFee= 79 / 99 / 139 / 169
optionalInfo.billGprsCfg.theshold    = 20GB / 40GB / 60GB / 80GB
optionalInfo.billVoiceCfg.theshold   = 100分钟 / 150分钟 / 200分钟 / 250分钟
optionalInfo.printContent.containResource = 20GB,100分钟 / ... 逐品
```

**唯一残留**：套外流量阶梯单价（5元→3元/GB）在样本中随档位变化，但当前 schema 的 `billGprsCfg` 无对应阶梯单价叶子（属独立「超出资费」配置项），未映射。若需覆盖阶梯单价，须扩展 schema/模板字段，列为后续增强（非多品链路问题）。

**整改**：无需改代码。
