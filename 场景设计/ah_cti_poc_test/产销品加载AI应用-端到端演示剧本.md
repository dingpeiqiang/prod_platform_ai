# 产销品加载 AI 应用 · 端到端演示剧本设计
> 用途：现场演示 / 验收评审 / 宣传展示。完整走通"需求提报→需求分析→智能配置→规格稽核→资费校准→自动测试→受理验证→上线审批→监控运维"9 环节。
> 配套示例产品：流量包-畅享5G通用包-30GB-24个月（product_id: P20260010）
> 剧本角色：**演示员**（业务/验收方）、**数字员工**（智能体）、**系统动作**（插件/工作流后台执行）、**旁白**（讲解要点）

---

## 0. 演示准备

| 项 | 内容 |
| --- | --- |
| 环境 | 智能体 `cpcp_product_worker` 已发布；接口环境 uat；测试环境 uat |
| 预置数据 | 存量产品可查（含互斥产品"流量畅享包"）；测试账号 3 个（新入网/存量/携转）；监控库预置 P20260001 数据 |
| 演示时长 | 全流程约 15 分钟（可按环节分段演示） |
| 演示模式 | 对话驱动（用户在对话框输入）+ 旁白讲解后台工作流节点 |

## 幕1：需求提报（对应环节：需求提报 + 需求分析 wf_sub_01）

**旁白**：过去上新一个套餐，需求文档要人工流转给配置、计费、测试多个团队。现在，只需一段话。

**演示员输入：**
> 我们要上一个新流量包：名称"流量包-畅享5G通用包-30GB-24个月"，月租29元，含30GB通用流量，超套后3元/GB，安徽全省，营业厅、APP、网厅都能办，新入网和存量用户都可以订，10月1日生效，可以和话费返还优惠叠加，不能和其他流量包同时订购。

**数字员工（内部动作）：**
1. 调用主工作流 `wf_cpcp_main` → 子工作流 `wf_sub_01`
2. 大模型节点：结构化解析需求 → 输出 `parsed_json`

```json
{
  "product_name": "流量包-畅享5G通用包-30GB-24个月",
  "product_id_apply": "P20260010",
  "fee": {"monthly": 29.0, "once": 0, "over_price": {"unit": "GB", "price": 3.0}, "contained": {"general_data_GB": 30}},
  "sale_scope": {"province": "anhui", "channel": ["营业厅","APP","网厅"], "user_group": ["新入网","存量"]},
  "effect_date": "2026-10-01",
  "expire_date": "2099-12-31",
  "discount": {"allow": ["话费返还类"], "exclude": ["流量畅享包"]},
  "term": "24个月"
}
```

**数字员工输出：**
> 已完成需求解析，要素如下——
> - 产品：流量包-畅享5G通用包-30GB-24个月
> - 资费：月租 29 元 / 含 30GB 通用 / 超套 3 元/GB
> - 范围：安徽全省，营业厅/APP/网厅，新入网+存量
> - 生效：2026-10-01，有效期 24 个月
> - 叠加：允许话费返还类；与其他流量包互斥
>
> 要素完整 ✅，是否继续生成 CRM 与计费配置？（请确认）

**演示要点**：展示"追问补全"反向用例——可先故意漏说资费，数字员工会追问"月租与超套单价是多少？"补全后继续。

## 幕2：销售品智能配置（wf_sub_02）

**演示员输入：**
> 确认，继续。

**数字员工（内部动作）：**
1. 插件节点 `query_product_config`：keyword="畅享 通用包" → 返回 3 个存量流量包
2. 大模型节点：比对差异，判定无重复产品、确认互斥关系应写入 exclude_list
3. 插件节点 `gen_crm_config` → 生成 `crm_config_json`（含目录挂载、订购规则、互斥清单）
4. 插件节点 `gen_billing_config` → 生成 `billing_config_json`（月租/超套/优惠/账期）

**数字员工输出：**
> 存量比对完成：未发现重复产品；发现互斥产品"流量畅享包"（P20260001），已写入互斥清单 ✅
> 已生成配置数据——
> - **CRM 配置**：目录 CATL_FLOW_001，允许新订/续订，退订月末生效，禁止重复订购
> - **计费配置**：月租 29 元（按天分摊），超套 3 元/GB，生效次月，优惠组：允许话费返还、互斥流量包
> - 配置编号：CRM-C20260010 / BILL-C20260010
> 是否提交规格稽核与资费校准？

**演示要点**：旁白强调"数字员工查了存量、做了冲突比对，这一步原来人工要在 CPCP 里翻半天"。

## 幕3：配置规格稽核 + 资费校准（wf_sub_03 / wf_sub_04）

**演示员输入：**
> 提交稽核。

**数字员工（内部动作）：**
1. 插件节点 `check_product_spec`：五项稽核（必填属性/命名/时间逻辑/范围合法性/三侧一致性）→ **pass=1**
2. 选择器节点：通过 → 进入资费校准
3. 插件节点 `check_billing_rule`（check_scene=all）：红线检查、叠加互斥检查 → **pass=1**，提示 1 条非阻断建议

**数字员工输出：**
> **规格稽核 ✅ 通过**（5/5 项）：必填属性完整、命名合规、生效时间合法、销售范围合法、三侧一致。
> **资费校准 ✅ 通过**，1 条提示：
> - [提示] 超套单价 3 元/GB 高于套内折算单价 0.97 元/GB，无套利风险，符合规则。
> 两个环节均通过，是否生成测试用例并执行？

**演示要点**（关键反向演示，评审最关注）：插入"稽核拦截"环节——
**演示员输入：**
> 我把月租改成 0 元，再跑一次校准。

**数字员工输出：**
> **资费校准 ❌ 未通过**，风险清单：
> - [高危] 月租为 0 且无自动转常规资费规则，命中红线"禁止零元月租长期产品"
> - 整改建议：恢复 29 元，或配置 ≤3 个月免费体验 + 自动转常规
> 流程已拦截，不进入测试环节。已按原配置（29元）继续？还是您重新给出资费？

**演示员输入：**
> 用回 29 元的，继续。

**旁白**：演示"资费漏洞被自动拦截"，替代过去人工核对易漏配的最大风险点。

## 幕4：销售品自动测试（wf_sub_05）

**演示员输入：**
> 继续测试。

**数字员工（内部动作）：**
1. 插件节点 `gen_test_cases`：case_type=all → 生成 16 条用例（受理4/变更3/退订3/计费6）
2. 插件节点 `run_test_cases`：env=uat, async → task_id=T20260910001，轮询回查
3. 选择器节点：passed=16, failed=0 → 全部通过

**数字员工输出：**
> 已生成 **16 条测试用例**并执行完成（uat 环境）——
> - 受理：4/4 ✅（新订成功、重复订购拦截、互斥拦截、依赖拦截）
> - 变更：3/3 ✅（升级补差、降级次月生效、三侧一致）
> - 退订：3/3 ✅（月末生效、无次月计费、无合约限制）
> - 计费：6/6 ✅（整月 29.00、月中15日订购分摊 15.47、优惠生效、无双重优惠、超套计费、31日跨月边界）
> **通过率 100%**，是否发起受理验证？

**演示要点**：旁白说明"16 条用例是按测试规范模板自动设计的，包含边界用例——过去测试组手写要 1-2 天"。可插播反向：若计费用例 fail（如分摊金额差 0.01），数字员工会定位到"按天分摊取整规则配置"并要求回归。

## 幕5：受理验证（wf_sub_06）

**演示员输入：**
> 继续受理验证。

**数字员工（内部动作）：**
1. 插件节点 `verify_acceptance`：verify_type=new → 验证环境自动发起模拟订购单
2. 回读订单结果：pass=1, order_id=OD20260910001；追加验证 change/cancel → 均 pass

**数字员工输出：**
> **受理验证 ✅**：模拟新订购（订单号 OD20260910001）、变更、退订三类流程均验证通过，受理界面展示正常。
> 下一步将汇总全部结论生成报告并推送上线审批，是否确认？

## 幕6：上线审批（wf_sub_07）

**演示员输入：**
> 确认，推送审批。

**数字员工（内部动作）：**
1. 大模型节点[报告汇总]：按报告模板生成《销售品上线测试与稽核报告》
   - 需求摘要 / 配置摘要 / 稽核结论 ✅ / 资费结论 ✅ / 测试 16/16 ✅ / 受理验证 ✅ / 上线建议：通过
2. 插件节点 `submit_release_approval`：approval_flow=standard → 返回审批单号

**数字员工输出：**
> 报告已生成并推送审批 ✅
> - 审批单号：**AP20260910-001**
> - 审批链：配置组 → 计费 → 市场部 → 分管领导
> - 结论摘要：稽核 5/5 通过，资费校准通过，测试 16/16 通过，受理验证通过
> 审批结果我将持续跟踪。产品生效日 2026-10-01，上线后我会纳入每日监控。

**旁白**：过去上线材料人工汇总至少半天，现在审批单自动生成，材料完整可溯。

## 幕7：监控运维（wf_sub_08）

**演示员输入（上线一周后场景）：**
> 查一下 P20260010 最近 7 天的运行情况。

**数字员工（内部动作）：**
1. 插件节点 `query_product_monitor`：date_range=近7天, metric=all
2. 模拟数据：order_count=2,843，error_count=9（成功率 99.7%），fee_error_rate=0.03%，alarm_list 含 1 条"10-06 APP 渠道瞬时下单失败 4 起（网络抖动，已恢复）"
3. 选择器：error_count 未超阈值 → 无需升级告警；但 alarm_level=low 的异常自动生成巡检记录

**数字员工输出：**
> **P20260010 近 7 天监控**：
> - 订购量 2,843 笔，成功率 **99.7%**（阈值 95% ✅）
> - 计费差错率 0.03%（阈值 0.1% ✅）
> - 异常事件：10-06 APP 渠道 4 起瞬时下单失败，网络抖动导致，已自恢复
> 结论：运行平稳，无需下线评估。已生成巡检记录并同步运维群。

**演示要点（可选加时幕）**：演示员输入"假如计费差错率飙到 0.5% 会怎样？"→ 数字员工演示告警链路：send_alert（high）→ 建议"冻结新订购 + 立即排查 + 2 小时内上报"。

## 幕8：收尾总结（旁白）

| 对比项 | 传统人工 | 数字员工 |
| --- | --- | --- |
| 需求解析与流转 | 文档多人传递，1-2 天 | 对话即达，分钟级 |
| 配置生成 | 3 系统手工录入，易错 | 自动生成三侧一致数据 |
| 稽核/资费核对 | 人工抽查，易漏 | 全量规则校验，漏洞即拦截 |
| 测试 | 手写用例+回归，2-3 天 | 16 条用例自动生成执行 |
| 审批材料 | 人工汇总半天 | 报告自动生成推送 |
| **整体周期** | **约 5-7 天** | **约 0.5 天** |

**结束语**：以上即产销品加载全流程闭环。数字员工承担了 80% 的重复操作性工作，人只在"确认"与"审批"两个决策点介入。
