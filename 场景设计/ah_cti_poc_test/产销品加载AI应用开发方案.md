## 1. 方案总览

### 1.1 建设目标
以数字员工替代产销品上架全流程人工操作，实现：

**需求提报 → 需求分析 → 销售品智能配置 → 配置规格稽核 → 资费校准 → 销售品自动测试 → 受理验证 → 上线审批 → 监控运维** 的端到端闭环。

### 1.2 总体架构（平台能力映射）

| 平台能力 | 在本场景中的角色 |
| --- | --- |
| 智能体（助手） | 产销品数字员工统一入口（对话式 + 流程式调度中枢） |
| 工作流 | 承载 9 个业务环节的主流程编排（start→…→end） |
| 插件/工具 | 封装 CPCP、CRM、计费、订单等系统接口的原子能力 |
| 知识库 | 存储业务规范、资费规则、测试规范、存量产品资料 |
| 大模型节点 | 需求解析、配置生成、稽核判定、测试报告生成 |
| 选择器节点 | 稽核通过/驳回、测试通过/失败、审批通过/拒绝等分支控制 |

### 1.3 设计原则
1. **一个主工作流 + 多个子工作流**：主流程控制环节顺序与分支，每个环节封装为子工作流，便于独立调试与复用。
2. **插件先行**：所有系统交互必须封装为插件工具（HTTP 接口），大模型只做"理解与生成"，不直接触碰生产系统。
3. **知识库兜底**：业务规范类判断（如资费叠加约束）以知识库检索增强 + 大模型节点共同完成，降低幻觉。
4. **人机协同**：稽核不通过、审批等关键节点保留人工确认（通过对话反馈或工作流分支回退实现）。

## 3. 智能体设计（产销品数字员工）

### 3.1 基本信息
| 项 | 值 |
| --- | --- |
| 助手代码 | `cpcp_product_worker` |
| 助手名称 | 产销品数字员工 |
| 功能介绍 | 面向产销品域的数字员工，支持从需求提报、需求分析、销售品配置、规格稽核、资费校准、自动测试、受理验证到上线审批、监控运维的全流程自动化操作。 |
| 发布范围 | 所有人可见 |
| 图标 | 默认/上传产销品图标 |

### 3.2 提示词（角色 + 技能 + 限制 模式）

```
【角色】
你是安徽电信产销品域的数字员工，精通 CPCP 产销品管理、CRM 配置、计费规则、
订单受理与测试验证，负责支撑销售品从需求到上线的端到端自动化加载。

【技能】
1. 需求提报与分析：接收用户上传的需求文档或口述需求，解析出销售品名称、
   套餐规则、资费信息、销售范围、生效时间等要素；缺失要素时逐项追问补全。
2. 销售品配置：调用产销品配置查询工具比对存量产品，调用 CRM 配置生成、
   计费配置生成工具输出标准配置数据。
3. 稽核与校准：调用配置规格稽核、计费规则校验工具，输出稽核结果与整改建议；
   稽核不通过时不得进入测试环节。
4. 自动测试：调用测试用例生成与执行工具，覆盖受理、变更、退订、计费场景，
   输出测试报告。
5. 上线与运维：调用受理验证、上线审批推送工具完成上线；调用监控工具持续
   查询运行状态并主动告警。

【限制】
1. 仅回答产销品加载相关业务，其他问题按答案为空提示回复。
2. 涉及生产系统写入类操作（配置生成、审批提交）前，必须向用户复述关键要素
   并获得确认。
3. 稽核或测试不通过时，明确给出失败原因与整改建议，不得跳过环节。
4. 输出遵循结构化格式：环节名称、执行结果、关键数据、下一步动作。
5. 不得泄露资费、配置等敏感数据的明细，仅展示摘要。
```

## 4. 插件设计（工具清单）

### 4.1 插件创建
- 插件名称：`产销品加载插件集`
- 每个工具统一走「工具代码/名称/描述/接口协议(http/https)/接口地址/出参归纳」配置流程。

### 4.2 工具定义（关键示例）

**工具1：产销品配置查询 `query_product_config`**
| 项 | 内容 |
| --- | --- |
| 接口 | GET `https://{cpcp-gateway}/api/v1/products/config/query` |
| 描述 | 按产品编码/名称/关键字查询存量产销品配置、规格与资费 |
| 入参 | `keyword`(string,选填) `product_id`(string,选填) `status`(string,枚举: online/offline/all) |
| 出参 | `total`(int) `list`(array: product_id, product_name, spec_json, fee_json, sale_scope, status) |
| 是否提参 | 是（keyword 必填） |

**工具2：CRM 配置数据生成 `gen_crm_config`**
| 项 | 内容 |
| --- | --- |
| 接口 | POST `https://{cpcp-gateway}/api/v1/crm/config/generate` |
| 入参 | `product_name`(string,必填) `fee_json`(string,必填) `sale_scope`(string,必填) `effect_date`(date) `expire_date`(date) |
| 出参 | `crm_config_id`(string) `crm_config_json`(string) `status`(string) |

**工具3：计费配置数据生成 `gen_billing_config`**
| 项 | 内容 |
| --- | --- |
| 接口 | POST `https://{cpcp-gateway}/api/v1/billing/config/generate` |
| 入参 | `product_id`(string,必填) `fee_json`(string,必填) `discount_rules`(string,选填) |
| 出参 | `billing_config_id`(string) `billing_config_json`(string) `status`(string) |

**工具4：计费规则校验 `check_billing_rule`**
| 项 | 内容 |
| --- | --- |
| 接口 | POST `https://{billing-check}/api/v1/rules/verify` |
| 入参 | `billing_config_json`(string,必填) `check_scene`(string,枚举: fee/overlay/superposition/all) |
| 出参 | `pass`(int: 1/0) `risk_list`(array: risk_type, risk_desc, suggest) |

**工具5：配置规格稽核 `check_product_spec`**
| 项 | 内容 |
| --- | --- |
| 接口 | POST `https://{cpcp-gateway}/api/v1/spec/audit` |
| 入参 | `crm_config_json`(string,必填) `billing_config_json`(string,必填) `audit_template`(string,选填: 默认规范模板) |
| 出参 | `pass`(int: 1/0) `error_list`(array: item, level, desc, suggest) |

**工具6：测试用例生成 `gen_test_cases`**
| 项 | 内容 |
| --- | --- |
| 接口 | POST `https://{test-platform}/api/v1/cases/generate` |
| 入参 | `crm_config_json`(string,必填) `billing_config_json`(string,必填) `case_type`(string,枚举: acceptance/change/cancel/billing/all) |
| 出参 | `case_count`(int) `case_ids`(array) `case_list_json`(string) |

**工具7：测试用例执行 `run_test_cases`**
| 项 | 内容 |
| --- | --- |
| 接口 | POST `https://{test-platform}/api/v1/cases/execute` |
| 入参 | `case_ids`(array,必填) `env`(string,枚举: sit/uat/pre) `execute_mode`(string,枚举: sync/async) |
| 出参 | `task_id`(string) `total`(int) `passed`(int) `failed`(int) `fail_detail`(array) |

**工具8：受理验证 `verify_acceptance`**
| 项 | 内容 |
| --- | --- |
| 接口 | POST `https://{crm-gateway}/api/v1/order/verify` |
| 入参 | `product_id`(string,必填) `verify_type`(string,枚举: new/change/cancel) |
| 出参 | `pass`(int) `order_id`(string) `fail_reason`(string) |

**工具9：上线审批推送 `submit_release_approval`**
| 项 | 内容 |
| --- | --- |
| 接口 | POST `https://{oa-gateway}/api/v1/approval/submit` |
| 入参 | `product_id`(string,必填) `report_url`(string,必填) `approval_flow`(string,枚举: standard/urgent) |
| 出参 | `approval_id`(string) `status`(string) |

**工具10：监控查询 `query_product_monitor`**
| 项 | 内容 |
| --- | --- |
| 接口 | GET `https://{monitor}/api/v1/product/monitor` |
| 入参 | `product_id`(string,必填) `date_range`(string,选填) `metric`(string,枚举: order/error/fee/all) |
| 出参 | `order_count`(int) `error_count`(int) `fee_error_rate`(float) `alarm_list`(array) |

**工具11：异常告警 `send_alert`**
| 项 | 内容 |
| --- | --- |
| 接口 | POST `https://{monitor}/api/v1/alert/send` |
| 入参 | `product_id`(string,必填) `alarm_level`(string,枚举: high/middle/low) `content`(string,必填) |
| 出参 | `alert_id`(string) `status`(string) |

## 6. 工作流设计

### 6.1 主工作流 `wf_cpcp_main`（产销品加载主流程）

**节点编排（开始 → 结束）：**

```
开始节点
  ├─ 输入参数：requirement_text(string,必填,需求描述/文档摘要)
  │            requirement_file(string,选填,需求文档地址)
  │            product_id(string,选填,已有产品ID，用于续流程)
  ▼
大模型节点 [需求分析] wf_sub_01
  ▼
选择器节点 [要素完整性判断]：解析要素是否完整
  ├─ 不完整 → 大模型节点 [补全追问] → 结束（返回追问清单）
  └─ 完整 ↓
插件节点 query_product_config [存量比对与冲突检查]
  ▼
插件节点 gen_crm_config + gen_billing_config [配置生成]
  ▼
插件节点 check_product_spec [规格稽核]
  ▼
选择器节点 [稽核判定]
  ├─ 不通过 → 插件节点 send_alert / 结束（返回整改建议，流程可重入）
  └─ 通过 ↓
插件节点 check_billing_rule [资费校准]
  ▼
选择器节点 [资费判定]
  ├─ 不通过 → 结束（返回资费风险清单）
  └─ 通过 ↓
插件节点 gen_test_cases → run_test_cases [自动测试]
  ▼
选择器节点 [测试判定]
  ├─ 失败 → 结束（返回失败明细与定位建议）
  └─ 通过 ↓
插件节点 verify_acceptance [受理验证]
  ▼
大模型节点 [报告汇总]
  ▼
插件节点 submit_release_approval [上线审批]
  ▼
结束节点：输出 product_id / 各环节结果 / 审批单号 / 下一步指引
```

### 6.2 子工作流拆分（每个环节一个子工作流）

| 子工作流 | 编码 | 输入 | 输出 | 关键节点 |
| --- | --- | --- | --- | --- |
| 需求分析 | `wf_sub_01` | requirement_text/file | parsed_json（品名/资费/范围/生效期） | 开始 → 大模型(结构化解析+知识库参照) → 选择器(完整性) → 结束 |
| 智能配置 | `wf_sub_02` | parsed_json | crm_config_json / billing_config_json | 开始 → query_product_config → 大模型(复用与差异决策) → gen_crm_config → gen_billing_config → 结束 |
| 规格稽核 | `wf_sub_03` | crm/billing_config_json | pass / error_list | 开始 → check_product_spec → 大模型(整改建议生成) → 结束 |
| 资费校准 | `wf_sub_03` | billing_config_json | pass / risk_list | 开始 → check_billing_rule → 大模型(风险解读) → 结束 |
| 自动测试 | `wf_sub_04` | crm/billing_config_json | task_id / passed / failed / fail_detail | 开始 → gen_test_cases → run_test_cases → 选择器(全通过?) → 结束 |
| 受理验证 | `wf_sub_05` | product_id | pass / order_id / fail_reason | 开始 → verify_acceptance → 选择器 → 结束 |
| 上线审批 | `wf_sub_06` | product_id / report | approval_id / status | 开始 → 大模型(报告生成) → submit_release_approval → 结束 |
| 监控运维 | `wf_sub_06` | product_id / date_range | 指标与告警 | 开始 → query_product_monitor → 选择器(异常?) → send_alert → 结束 |

> 说明：主工作流中"大模型节点 [需求分析]"等环节，实际采用"插件节点调用子工作流"或按平台版本直接编排子节点；若平台子工作流不支持嵌套，则将子工作流节点在主画布上平铺展开（节点逻辑不变）。

### 6.3 关键节点配置要点

**① 需求分析大模型节点**
- 温度值：0.2
- 输入：`requirement_text`
- 提示词要点：`你是产销品需求分析师，请从需求中解析：product_name、fee_json（含月租/单价/赠送/有效期）、sale_scope（省份/渠道/用户群）、effect_date。仅输出JSON，无多余文字。`
- 输出：`parsed_json`(string)

**② 选择器节点（通用）**
- 条件模板：`{环节结果字段} 等于 通过值` → 走"通过"分支；否则走"驳回"分支。
- 支持且/或多条件（如 pass==1 且 failed==0）。

**③ 报告汇总大模型节点**
- 输入：引用前面各环节输出（稽核结果、资费结果、测试结果、受理结果）
- 提示词要点：`请按标准模板汇总生成《销售品上线测试与稽核报告》，包含：需求摘要、配置摘要、稽核结论、资费结论、测试统计与失败明细、受理验证结论、上线建议。`
- 输出：`report`(string) → 传给 `submit_release_approval` 的 `report_url/report` 字段。

## 8. 测试与验收

### 8.1 分层测试
1. **插件级**：逐工具在"预览与调试"中验证接口连通、入参提取、出参归纳正确。
2. **工作流级**：
   - 正向用例：完整合规需求 → 全环节通过 → 审批单生成；
   - 反向用例：构造资费冲突（如叠加优惠互斥）→ 资费校准拦截；构造配置缺失 → 稽核驳回；
   - 分支用例：追问补全分支、测试失败分支、告警分支。
3. **智能体级**：多轮对话体验（追问、确认、结构化输出）、引导问题命中、FAQ 回答准确率。

### 8.2 验收标准（建议）
| 指标 | 目标 |
| --- | --- |
| 端到端流程贯通率 | 100%（给定需求→审批单生成） |
| 需求要素解析准确率 | ≥95% |
| 稽核/资费问题拦截率 | ≥95%（构造缺陷样例集） |
| 测试用例覆盖（受理/变更/退订/计费） | 4类场景全覆盖 |
| 全流程耗时 | 相比人工缩短 ≥60% |

### 8.3 端到端演示剧本（V1.1 新增）
- 剧本文件：《产销品加载AI应用-端到端演示剧本.md》
- 用途：现场演示、验收评审、宣传展示；按 8 幕走通 9 环节（示例产品 P20260010"畅享5G通用包"）。
- 剧本与验收的映射关系：
| 剧本环节 | 对应验收内容 | 演示方式 |

## 9. 上线与运维

1. **发布**：智能体发布到小思页面；工作流、插件保持版本可回退（平台支持保存草稿/发布双状态）。
2. **监控**：每日定时（或由运维对话触发）运行 `wf_sub_06` 监控子工作流，对 error_count 超阈值、fee_error_rate 异常的销售品调用 `send_alert` 告警。
3. **迭代机制**：
   - 知识库持续更新（新规范、新资费政策）；
   - 提示词与选择器阈值按稽核/测试误判情况调优；
   - 插件接口按系统升级同步维护。
4. **运维报表**：每周汇总全流程执行量、拦截量、测试通过率，评估数字员工效能。

## 10. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 接口不稳定/字段变更 | 插件层隔离；出参加必填校验；维护接口版本 |
| 大模型解析幻觉 | 知识库增强 + 温度调低 + 结构化 JSON 输出 + 稽核兜底 |
| 生产误操作 | 写入类插件前置用户确认；测试仅打 sit/uat/pre 环境 |
| 资费漏洞漏检 | 知识库规则持续运营 + `check_scene=all` 全量校验 |
| 流程环节被跳过 | 选择器节点强制分支，不通过即终止并返回原因 |
