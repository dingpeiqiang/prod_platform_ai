# 专利申请书

## 一、发明名称

一种基于大语言模型的动态表单字段智能推断与零代码扩展方法

---

## 二、所属技术领域

本发明涉及计算机技术领域，特别是涉及人工智能驱动的动态表单处理技术，具体涉及一种基于大语言模型（LLM）的表单字段智能推断与零代码扩展方法。

---

## 三、背景技术

随着企业数字化转型的深入，表单系统在政务审批、金融数据录入、通信业务管理等场景中得到广泛应用。传统表单系统通常采用以下方式实现：

**1. 静态预定义表单模式**

开发人员预先定义表单模板，包含固定数量的字段及其类型、校验规则。当业务需求变更或新增表单类型时，需要修改代码、重新部署，扩展周期通常为3-5个工作日。这种方式存在以下缺陷：
- 新增表单类型需要前后端配合修改代码，开发成本高
- 业务人员无法自主定义新表单，依赖技术团队支持
- 表单类型的管理和维护复杂度随着数量增长而指数级上升

**2. 规则引擎驱动的动态表单模式**

部分系统引入规则引擎（如Drools、EasyRules），通过配置规则实现字段的动态提取和校验。虽然在一定程度上降低了代码修改频率，但仍然存在以下不足：
- 规则的定义和维护需要专业技术人员，业务人员难以参与
- 复杂业务场景下规则数量庞大且相互冲突，维护成本高
- 规则引擎无法处理模糊的自然语言输入，用户仍需按照结构化格式填写

**3. AI辅助填表模式**

近年来出现了利用AI模型辅助填表的技术方案，通常思路是将用户输入与预定义字段映射进行匹配。现有方案存在以下局限：
- 字段映射规则仍然需要预定义，新增表单类型需要配置映射关系
- AI仅作为辅助工具，字段提取的核心逻辑仍依赖规则引擎
- 不同类型字段的推断（编码类、枚举类、数值类、日期类等）需要分别编写提示词和映射规则
- 无法实现"新增表单类型零代码"——即便使用AI，扩展一个新表单仍然需要写代码或配置复杂规则

**4. 当前技术的核心矛盾**

现有技术在实现动态表单时面临一个根本矛盾：**灵活性和扩展成本之间的权衡**。越是灵活的表单系统，其扩展新表单类型的成本越高。传统方式中，灵活性来自于代码的复杂度，扩展成本也随之升高。迫切需要一种既能保持高度灵活性，又能实现零代码扩展的技术方案。

综上所述，现有技术中缺乏一种能够通过本体定义驱动、由大语言模型完全接管字段推断逻辑、实现新增表单类型零代码的方法。

---

## 四、目的

本发明旨在解决现有技术中存在的如下技术问题：

1. **新增表单类型开发成本高**：解决传统表单系统扩展新表单类型需要修改代码、重新部署、耗时数日的技术问题
2. **字段推断逻辑维护困难**：解决规则引擎模式下规则数量庞大、相互冲突、难以维护的技术问题
3. **自然语言输入处理能力弱**：解决现有系统无法从非结构化自然语言输入中准确提取结构化字段值的技术问题
4. **不同类型字段提取缺乏统一框架**：解决编码类、枚举类、数值类、日期类、关联类、文本类字段需要分别编写不同提取逻辑的技术问题

本发明的目的在于提供一种基于大语言模型的动态表单字段智能推断与零代码扩展方法，实现只需通过配置本体定义（JSON Schema）和场景提示词即可支持新表单类型，无需修改任何代码，将表单系统的扩展成本从"开发工作"降为"配置工作"。

---

## 五、技术方案

### 5.1 设计思路

本发明的核心设计思路是：**由大语言模型完全接管表单字段的提取和推断逻辑，代码只负责流程编排和数据传递**。通过构建"本体定义层→场景提示词层→LLM推断层→推荐引擎层"的四层架构，实现表单类型的新增完全通过配置文件驱动，无需编写或修改任何代码。

### 5.2 技术架构

本发明提出的技术架构如下：

```
本体定义层（Ontology Layer）
    │ 定义表单结构、字段约束、枚举值、业务规则
    ↓
场景识别层（Scene Recognition Layer）
    │ 识别用户意图，匹配对应的场景和表单类型
    ↓
LLM推断层（LLM Inference Layer）
    │ 加载本体信息构建提示词，LLM完成字段提取和推断
    ↓
推荐引擎层（Recommendation Engine Layer）
    │ 确定性值优先，多策略并行推荐，置信度加权决策
    ↓
约束校验层（Constraint Validation Layer）
    │ 应用字段约束和业务规则，确保数据一致性
```

### 5.3 技术方法步骤

#### 步骤一：本体定义与加载

定义一个实体-字段两级层级的JSON Schema作为表单的本体定义，将表单结构、字段类型、枚举选项、校验规则、业务规则全部外部化为配置文件。本体定义包含以下要素：

（1）**表单元数据**：formCode（表单唯一编码）、formName（表单显示名称）、description（功能描述）

（2）**实体定义**：entityCode（实体编码）、entityName（实体名称）、fields（字段数组）

（3）**字段定义**：每个字段包含如下属性：
- fieldCode：字段编码（唯一标识）
- fieldName：字段显示名称
- fieldType：字段类型（string/integer/number/date/select/boolean等）
- required：是否必填
- enumConfig：枚举选项配置（options列表，每个option包含value和label）
- ruleDescription：填写规则说明
- description：字段描述
- constraints：约束条件（最小/最大值、字符串长度限制、正则表达式模式等）
- dependsOn：字段依赖关系（联动字段）
- dataRange：数据范围约束
- pattern：正则表达式校验模式
- default：默认值
- businessRules：业务规则描述

（4）**业务规则定义**：在实体级别和字段级别定义业务规则描述，用于指导LLM进行符合业务逻辑的推断

#### 步骤二：场景识别与意图分类

接收用户的自然语言输入，通过多级匹配机制确定用户意图对应的表单类型和场景：

（1）**关键词匹配**：根据预配置的场景映射表（scene_mapping.json），通过场景名称、关键词列表进行初步匹配

（2）**优先级排序**：每个场景配置优先级（priority）字段，当多个场景匹配时选择优先级最高的场景

（3）**场景提示词加载**：根据匹配到的场景编码加载对应的场景提示词文件（.txt），该提示词定义了该场景下的业务流程和执行规则

（4）**表单本体加载**：根据场景配置加载对应的表单本体定义（ontologies/{form_code}.json）

#### 步骤三：LLM驱动的字段推断（核心步骤）

将本体定义和用户输入构建为结构化提示词，由大语言模型完成字段值的提取和推断。具体包含以下子步骤：

**子步骤3.1：确定性值收集**

从多个确定性来源收集已有字段值：
- 工具调用结果（最高优先级）：如果工作流执行过程中调用了外部工具，工具返回的结果字段直接作为确定性值
- 上下文变量：系统上下文中的已有变量值
- LLM直接提取：从用户输入文本中明确提到的字段值

确定性值的优先级排序为：工具结果 > LLM提取 > 上下文变量

**子步骤3.2：字段类型感知的LLM推断**

针对不同类型的字段，LLM在提示词指导下执行差异化的推断逻辑：

（a）**编码类字段**（fieldCode包含code/id/no/number/bossid等关键词）：从用户输入中提取符合特定格式的编码，如套餐编码（P+数字格式）、订单号、手机号等

（b）**枚举/选择类字段**（fieldType为select/enum/radio）：根据用户输入的关键词匹配本体定义中的枚举选项（options列表），如用户说"新增备案"→action_type="A"（新增）

（c）**数值类字段**（fieldType为number/integer/float）：从用户输入中提取数值，自动处理单位转换（如"5万"→50000、"100M"→100）

（d）**日期时间字段**（fieldType为date/datetime）：将自然语言日期转换为标准格式（date→YYYY-MM-DD、datetime→ISO 8601），支持"今天"、"明天"、"下周一"等自然语言表达

（e）**关联字段推断**：基于已提取的字段值进行关联推断，如用户提到"畅享套餐"→name="畅享套餐"、type1="1"(公众)

（f）**文本类字段**（fieldType为string/input/textarea）：直接提取用户描述的原始文本内容

**子步骤3.3：批量AI推断**

对未被确定性值覆盖的字段，通过一次LLM调用批量推断多个字段的候选值。构建增强版批量推断提示词，包含：
- 表单编码和用户输入
- 已确定的字段值（用于关联推断）
- 需要推断的字段定义（包含约束信息、枚举选项、业务规则）
- 字段联动关系
- 实体级约束
- 业务规则描述
- 严格的JSON格式输出指令

**子步骤3.4：多策略并行推荐**

对LLM推断后仍未确定的字段，并行执行以下四种推荐策略：

（a）**历史频率策略**：根据历史填写频率排序，优先推荐高频值

（b）**用户个性化策略**：同一用户的历史填写记录优先排序

（c）**时间衰减策略**：近期数据的权重高于长期数据，按时间衰减函数加权

（d）**静态配置策略**：无历史数据时使用配置文件中的默认值

四种策略通过线程池并行执行，结果互不阻塞，最后按优先级和置信度加权合并

#### 步骤四：置信度加权决策与约束校验

**子步骤4.1：分层决策**

按照以下优先级顺序为每个字段选择最终值：
1. 确定性值（优先级0-3）：直接使用，不做推荐
2. AI智能推断值（优先级10）：LLM结合本体的批量推断结果
3. 用户个性化推荐（优先级20）：基于同一用户历史数据
4. 历史频率推荐（优先级30）：基于全量历史数据的频率统计
5. 时间衰减推荐（优先级40）：基于近期数据的权重计算
6. 静态配置推荐（优先级50）：配置文件中的静态默认值
7. 兜底值（优先级90+）：字段默认值或枚举选项

**子步骤4.2：置信度加权计算**

每个推荐候选值携带以下属性：
- 来源类型（source）：标识值的来源
- 置信度（confidence）：0-1之间的置信度评分
- 策略权重（strategy_weight）：策略本身的权重配置
- 综合分数（final_score）= confidence × strategy_weight

按照来源优先级排序，同优先级按综合分数降序排列，选择最优值

**子步骤4.3：约束校验**

对决策后的表单数据应用约束规则：
- 日期约束：结束日期不得早于开始日期
- 分类约束：一级分类和二级分类的组合校验
- 业务规则约束：如删除操作必须填写序列号
- 字段类型约束：值必须符合字段类型定义
- 枚举值约束：值必须在预定义的枚举选项范围内

当约束冲突时，自动修正违规值（如清除冲突值、选择默认值等）

#### 步骤五：零代码扩展流程

新增表单类型的完整步骤如下，全程无需编写代码：

**步骤5.1**：在 `ontologies/{form_code}.json` 中定义表单本体（JSON Schema），包括实体结构和字段定义

**步骤5.2**：在 `scene_mapping.json` 中添加场景映射配置，包括场景编码、名称、关键词、优先级

**步骤5.3**：编写场景提示词文件 `prompts/scenes/{scene_code}_prompt.txt`，描述该场景下的业务流程和执行规则

**步骤5.4**（可选）：在意图识别提示词中补充该场景的字段推断规则

**步骤5.5**（可选）：在推荐配置中添加静态默认值

### 5.4 算法描述

**算法1：确定性值收集算法**

```
输入：字段编码列表 field_codes, 工具调用结果 tool_result, 上下文变量 context_values
输出：确定性值字典 definite_values

1. 初始化 definite_values = {}
2. 如果 tool_result 不为空：
3.     对于 field_codes 中的每个 field_code：
4.         如果 tool_result 包含 field_code 且值不为空：
5.             definite_values[field_code] = tool_result[field_code]
6. 如果 context_values 不为空：
7.     对于 field_codes 中的每个 field_code：
8.         如果 field_code 不在 definite_values 中且 context_values 包含它：
9.             definite_values[field_code] = context_values[field_code]
10. 返回 definite_values
```

**算法2：分层推荐决策算法**

```
输入：确定性值 definite_values, 推荐候选 recommendations, 本体 ontology
输出：表单数据 form_data, 决策日志 decision_log

1. 初始化 form_data = definite_values 的副本
2. 初始化 decision_log = {}
3. 获取所有字段编码 all_field_codes
4. 对于 all_field_codes 中的每个 field_code：
5.     如果 field_code 在 definite_values 中且值不为空：
6.         记录为"确定性值"，跳过推荐
7.     否则：
8.         获取推荐候选列表 field_recommendations
9.         按优先级（升序）→ 综合分数（降序）排序
10.        如果排序后列表不为空：
11.            选择第一个候选作为最优值
12.        否则：
13.            使用空字符串兜底
14.     记录决策日志（来源、置信度、理由）
15. 对 form_data 应用约束校验
16. 返回 (form_data, decision_log)
```

## 六、有益效果

与现有技术相比，本发明具有以下有益效果：

**1. 新增表单类型零代码**

首次实现了表单类型的扩展真正零代码化。新增一个表单类型只需定义JSON Schema和编写场景提示词，无需修改任何Python代码、前段代码或数据库结构。测试表明，熟练业务人员完成一个中型表单（约30个字段）的配置耗时约30分钟，而传统方式需要3-5个工作日。

**2. 字段推断准确率高**

利用大语言模型的自然语言理解能力，能够从非结构化输入中准确提取字段值。对编码类、枚举类、数值类、日期类等各类型字段的推断准确率显著高于规则引擎。特别是对模糊表达（如"大概5万左右"）、自然语言日期（如"下周一"）、单位转换（如"100M"）等复杂场景，准确率达到95%以上。

**3. 统一的字段处理框架**

所有类型的字段（编码、枚举、数值、日期、文本、关联）统一由LLM处理，无需为不同类型编写独立的提取逻辑。新增字段类型只需在本体定义中声明fieldType，无需修改字段提取代码。

**4. 确定性值与推荐值的分层决策**

通过"确定性值优先、推荐值候补"的分层决策机制，确保明确指定的值不会被覆盖，同时为不确定的字段提供智能推荐。避免了单一来源可能带来的错误决策。

**5. 多策略并行推荐**

四种推荐策略的并行执行和置信度加权合并，既保证了推荐的准确性，又保证了系统的响应性能。并行执行架构使得推荐引擎的平均响应时间控制在500ms以内。

**6. 约束感知的智能修正**

自动识别并修正字段间的约束冲突（如日期顺序、分类匹配等），确保表单数据的逻辑一致性，减少了因数据不一致导致的表单驳回率。

**7. 极高的扩展性和适应性**

由于字段提取逻辑完全由LLM承担，系统对新的业务领域和表单类型具有极强的适应性。目前已在通信行业资费备案、内部审批流程、外部API对接等多种场景中得到验证。

### 实施例1：通信行业资费备案场景

#### 8.1.1 场景描述

本实施例以通信行业的"资费备案公示"场景为例，对本发明进行详细说明。该场景需要用户填写一份包含16个必填字段和15个可选字段的资费备案表单，字段涉及套餐编码、备案主体（枚举）、操作类型（枚举）、资费标准（数值）、上线日期（日期）等多种类型。

#### 8.1.2 本体定义（示例）

在本体定义文件 `tariff_filing_publicity.json` 中定义表单结构。核心字段定义如下：

```json
{
  "formCode": "tariff_filing_publicity",
  "formName": "资费备案公示",
  "entities": [
    {
      "entityCode": "tariff_info",
      "entityName": "资费备案信息",
      "fields": [
        {
          "fieldCode": "bossid",
          "fieldName": "省内套餐编码",
          "fieldType": "input",
          "required": true,
          "ruleDescription": "BOSS系统内的省内套餐唯一编码，示例：P000111"
        },
        {
          "fieldCode": "reporter",
          "fieldName": "备案主体",
          "fieldType": "select",
          "required": true,
          "enumConfig": {
            "options": [
              {"value": "BJ1", "label": "北京电信"},
              {"value": "BJ2", "label": "北京移动"},
              {"value": "GD2", "label": "广东移动"}
            ]
          }
        },
        {
          "fieldCode": "action_type",
          "fieldName": "操作类型",
          "fieldType": "select",
          "required": true,
          "enumConfig": {
            "options": [
              {"value": "A", "label": "新增"},
              {"value": "M", "label": "修改"},
              {"value": "D", "label": "删除"}
            ]
          }
        },
        {
          "fieldCode": "fees",
          "fieldName": "资费标准",
          "fieldType": "number",
          "required": false
        },
        {
          "fieldCode": "online_day",
          "fieldName": "上线日期",
          "fieldType": "date",
          "required": true
        },
        {
          "fieldCode": "offline_day",
          "fieldName": "下线日期",
          "fieldType": "date",
          "required": false
        }
      ]
    }
  ]
}
```

#### 8.1.3 场景映射配置

在 `scene_mapping.json` 中配置场景映射：

```json
{
  "sceneCode": "tariff_filing_publicity",
  "sceneName": "资费备案公示",
  "keywords": ["资费备案", "公示", "套餐备案"],
  "priority": 8,
  "isActive": true,
  "promptCode": "tariff_filing_publicity_prompt"
}
```

#### 8.1.4 执行过程

**步骤1：接收用户输入**

用户输入："备案套餐P000111，新增备案，公众套餐，资费标准5万元，上线日期今天"

**步骤2：场景识别**

系统通过关键词匹配识别到场景为 `tariff_filing_publicity`（匹配关键词"备案"），加载对应的本体定义 `tariff_filing_publicity.json` 和场景提示词 `tariff_filing_publicity_prompt.txt`

**步骤3：LLM确定性值提取**

构建确定性值提取提示词，将用户输入和本体定义一同发送给LLM，LLM输出：

```json
{
  "bossid": "P000111",
  "action_type": "A",
  "type1": "1",
  "fees": 50000,
  "online_day": "2026-05-29"
}
```

- `bossid`：从用户输入中提取符合"P+数字"格式的编码
- `action_type`："新增备案"→enum选项"A"（新增）
- `type1`："公众"→enum选项"1"（公众）
- `fees`："5万元"→数值转换50000
- `online_day`："今天"→当前日期"2026-05-29"

**步骤4：确定需要推荐的字段**

共31个字段，已确定5个，剩余26个字段需要推荐

**步骤5：批量AI推断**

构建增强版批量推断提示词，包含剩余26个字段的定义、约束、联动关系、业务规则，LLM输出候选值：

```json
{
  "fields": {
    "reporter": ["BJ1", "BJ2", "GD2"],
    "name": ["畅享套餐", "尊享套餐"],
    "type2": ["1", "2"],
    "tariff_attr": ["2"],
    ...
  }
}
```

**步骤6：并行本地推荐**

四种推荐策略并行执行：
- 历史频率策略查询数据库获得每个字段的历史填写频率统计
- 用户个性化策略筛选该用户的历史填写记录
- 时间衰减策略对近30天数据加权
- 静态配置策略加载配置文件默认值

**步骤7：分层决策**

以 `reporter` 字段为例：
1. 无确定性值
2. AI推断候选：[BJ1(0.8), BJ2(0.7), GD2(0.6)]
3. 用户个性化候选：[BJ1(0.9)]——该用户历史记录中常用"北京电信"
4. 历史频率候选：[BJ1(0.85), GD2(0.6)]——整体统计BJ1出现频率最高
5. 时间衰减候选：[BJ1(0.88)]——近期数据中BJ1占比高
6. 合并排序：BJ1（用户个性化，优先级20，综合分0.9）→ BJ1（时间衰减，优先级40，综合分0.88）→ ...
7. 最终决策：`reporter = "BJ1"`

**步骤8：约束校验**

校验组合约束：
- 分类约束：type1="1"(公众) 要求 type2 必须在 ["1"(套餐)、"2"(加装包)、"3"(营销活动)] 范围内
- 如果 type2 的候选值中包含非范围内的值，自动排除
- 日期约束：如果离线日期和上线日期同时存在，离线日期不得早于上线日期

#### 8.1.5 输出结果

最终输出包含31个字段的表单数据，以及每个字段的决策日志，供用户查看和确认。

      {"fieldCode": "employee_id", "fieldName": "工号", "fieldType": "input", "required": true},
      {"fieldCode": "leave_type", "fieldName": "请假类型", "fieldType": "select", "required": true,
       "enumConfig": {"options": [
         {"value": "annual", "label": "年假"},

         {"value": "personal", "label": "事假"}
       ]}},
      {"fieldCode": "start_date", "fieldName": "开始日期", "fieldType": "date", "required": true},
      {"fieldCode": "end_date", "fieldName": "结束日期", "fieldType": "date", "required": true},

在 `scene_mapping.json` 中新增一条映射，耗时约2分钟

创建 `leave_apply_prompt.txt`，描述请假审批的业务流程，耗时约5分钟
