# AI 原生前端交互设计 — 产商品研发/运营助手

> 版本：v3.2  
> 更新：2026-08-27  
> 变更：由 v2.x「删除所有右侧面板」修正为「**操作全在对话 + 右侧保留场景感知的只读汇总面板**」，新增「长对话设计」「批量配置对话化」「会话状态实时汇总」三章；v3.1 新增「移动端交互设计」并全篇注入移动优先约束；v3.2 新增「可逆操作与执行态」（建议/已执行 + 撤销回退），并将第三章澄清为「静态分块 vs 时间线渐进」。

## 一、设计原则

### 核心原则：对话即界面

```
传统模式：             AI 原生模式：
┌──────────────┐      ┌──────────────────────────┐
│ 左侧菜单导航  │      │ 对话是唯一的操作入口       │
│ 中间表单填写  │      │ 自然语言驱动一切           │
│ 右侧操作面板  │      │ 结构化结果内联在消息中     │
│ 页面跳转审批  │      │ 操作全部在对话内完成       │
└──────────────┘      │ 右侧只读汇总（信息驾驶舱） │
                      └──────────────────────────┘
```

**三条铁律**：
1. **所有操作在对话中完成** — 新增/删除/入库/修正/建工单/热重载等动作，一律由自然语言 + 追问建议触发，不提供独立操作面板。
2. **结构化结果内联展示** — 表格、卡片、趋势图、批次清单都内联在聊天消息里；用户不用在消息与面板之间来回切换找结果。
3. **渐进式信息流** — 思考过程 → 工具执行 → 正文报告 → 结构化数据 → 追问建议，自上而下自然流出。

**重要澄清（区别于 v2）**：右侧**保留**，但职责从「操作面板」收敛为「**场景感知的只读实时汇总信息面板**」。它是用户的**信息驾驶舱**，帮助其在对话过程中快速、准确地掌握重要信息与当前状态——**汇总信息随场景不同而不同**，操作一律放对话。

### 移动优先（Mobile-First，v3.1 新增）

未来将支持移动端，因此设计方案须**遵循移动优先**：桌面端是移动端的增强，而非相反。

1. **核心是单列对话流**：对话本身天然单列、适合移动端。所有结构化结果、批次清单、汇总信息都必须**能独立在消息流内完整呈现**，不依赖任何侧栏/右侧面板。
2. **面板为可选增强层**：左侧边栏、右侧汇总面板、历史侧栏都应是**渐进增强**——移动端默认收起/折叠，按需以抽屉（Drawer）或底部标签调出；桌面端才常驻展开。
3. **布局容器适配**：当前 `AssistantShell` 的三区布局（左/中/右）在窄屏不成立，需按断点优雅降级（见第七章）。
4. **输入与手势**：输入框适配移动键盘（安全区）、支持语音、触控友好（热区≥44px）、避免 hover-only 交互。
5. **性能优先**：移动端网络与算力受限，流式 Markdown、关系图、长清单需按需加载/懒渲染，避免一次渲染大量节点。

## 二、界面布局（三区 + 右侧信息驾驶舱）

```
┌────────────────────────────────────────────────────────────────┐
│  导航栏：产商品研发 · 配置与合规                    [模型配置]   │
├──────────┬──────────────────────────────────────────┬───────────┤
│          │                                          │           │
│ 历史对话  │           对话消息区域                     │ 场景汇总  │
│          │  ┌────────────────────────────────┐      │ 面板(常驻) │
│  · 分析.. │  │ AI 思考过程 (时间线动画)       │      │           │
│  · 筛查.. │  │  ① 理解需求 → ② 确认意图 → ③ 执行 │      │ ┌───────┐ │
│          │  ├────────────────────────────────┤      │ │智读批次 │ │
│ 快捷场景  │  │ 正文报告 (流式打出)             │      │ │ 通过2    │ │
│          │  ├────────────────────────────────┤      │ │ 待修1    │ │
│  · 智聊  │  │ 工具执行结果 (内联卡片)          │      │ │ 可入库1  │ │
│  · 智读  │  ├────────────────────────────────┤      │ └───────┘ │
│  · 智查  │  │ 结构化结果 (内联卡/清单/趋势图)   │      │ ┌───────┐ │
│  · 智检  │  ├────────────────────────────────┤      │ │配置状态 │ │
│          │  │ 追问建议: [入库] [修正] [对比]   │      │ │ 草稿2   │ │
│ 使用提示  │  └────────────────────────────────┘      │ │ 已备案1 │ │
│          │                                          │ └───────┘ │
│          │  ┌────────────────────────────────┐      │           │
│          │  │ 📎 文件  [输入消息...]  [发送]  │      │  可折叠    │
│          │  └────────────────────────────────┘      │           │
├──────────┴──────────────────────────────────────────┴───────────┤
│ (无操作面板；右侧只读汇总)                                       │
└────────────────────────────────────────────────────────────────┘
```

**保留三区**：
- **左侧窄边栏**：历史对话 + 快捷场景 + 使用提示（可折叠）。
- **中央对话区**：唯一的主工作区，承载全部操作与结果。
- **右侧汇总面板**：常驻、场景感知、只读实时汇总（本设计重点，见第五章）。

**右侧职责界定**：
- ✅ 展示场景相关的实时汇总信息（批次进度、配置状态、风险分布、工单/告警、归因结论摘要等）。
- ✅ 随会话切换 / 最近意图自动切换卡片集。
- ❌ 不承载具体操作（入库、修正、建工单、热重载、表单编辑等）——这些全部走对话。
- ❌ 不再是互斥的多个操作面板。

**移动端布局降级（断点策略，详见第六章）**：
- ≥1024px（桌面）：三区常驻（左/中/右）。
- 768–1023px（平板）：右侧汇总面板默认收起，可点导航栏「汇总」图标以抽屉调出；左侧作抽屉。
- <768px（手机）：单列对话流占满全屏；左/右侧栏均收起，经顶部按钮以全屏抽屉调出；输入框沉底并适配安全区与键盘。

## 三、消息结构（单条消息承载整轮交互）

```
单条 AI 消息 = 思考过程 + 工具执行结果 + 正文报告 + 结构化数据 + 追问建议
```

### 3.0 静态分块 vs 时间线渐进（重要澄清）

> **当前现状（v3.1）**：各层面板已按 1→5 的位次**自上而下排布**（`ChatMessageList.vue` 已实现），但多数情况下是**「静态分块」**——思考过程、工具结果、结构化数据在对应 SSE 阶段到达时**整块一次性出现**，仅正文 `streamText` 为逐字打字机。**尚未实现「时间线渐进」**：即各层按后端事件到达的时间顺序逐段抵达、边到达边渲染。

**验收标准（正式要求，纳入 Step 7 回归）**：`useChatStream.js` 需将 `reasoning / tool / text / intent / done` 五类 SSE 事件与消息各层按序对接，做到：

1. 思考过程步骤**逐条**随事件到达实时出现/勾选；
2. 工具结果**逐工具卡**随执行完成逐个渲染（含耗时）；
3. 正文在工具流与思考流就绪后开始逐字流式；
4. 结构化数据与追问建议在正文结束后追加出现；
5. 任一事件缺省时降级为「直到 done 才整块渲染」，不阻塞会话。

消息渲染顺序（自上而下，时间线渐进，目标状态）：

```
┌─ 1. 思考过程面板 ────────────────────────────────┐
│  思考过程 3步                              进行中 │
│  ① 正在理解您的需求...                            │
│  ② 已确认业务意图：异动归因  把握度: 92%          │
│  ③ 正在分析异动原因...                            │
└──────────────────────────────────────────────────┘

┌─ 2. 工具执行结果面板 ─────────────────────────────┐
│  ┌─ sparql_query ──────────────────────── 1.2s ─┐ │
│  │ ✅ 查询完成  结果: 15 条记录                 │ │
│  └──────────────────────────────────────────────┘ │
│  ┌─ swrl_root_cause ──────────────────── 3.5s ─┐ │
│  │ ✅ 推理完成  主因: 渠道A贡献度40%            │ │
│  └──────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────┘

┌─ 3. 正文报告 (流式 Markdown) ──────────────────────┐
│  ## 异动根因分析                                     │
│  家庭融合畅享128本月收入下滑30%，主要原因是...        │
└──────────────────────────────────────────────────┘

┌─ 4. 结构化数据 (内联卡片，ProductOpsPanel 等) ──────┐
│  📊 归因结论：主因 渠道A 40% / 次因 渠道B 25%        │
│  📚 智读批次：通过 2 · 待修 1 · 可入库 1              │
└──────────────────────────────────────────────────┘

┌─ 5. 追问建议 ──────────────────────────────────────┐
│  下一步可以: [入库通过项] [修正待修正项] [和上月对比] │
└──────────────────────────────────────────────────┘
```

### 消息数据结构

```typescript
interface AssistantMessage {
  id: string;
  role: 'assistant';

  // Layer 1: 理解层 — 思考过程
  reasoning: ReasoningStep[];
  intentType: string;              // 意图标签（驱动右侧汇总场景）

  // Layer 2: 执行层 — 工具结果
  toolResults: ToolResult[];

  // Layer 3: 表达层 — 正文 + 结构化数据
  streamText: string;
  content: string;
  intentData?: any;                // 结构化数据（ProductOpsPanel 消费）
  nextSteps: string[];

  // 长对话：文件/批次引用锚（v3 新增）
  fileRef?: { fileId?: string; batchId?: string; fileName: string; counts?: object };

  // 状态
  loading: boolean;
  done: boolean;
}
```

## 四、关键交互设计

### 4.1 输入框 — 唯一的操作入口

```
┌────────────────────────────────────────────────────────┐
│ 📎 文件  [输入业务诉求...]                        [发送] │
└────────────────────────────────────────────────────────┘
```

- 无场景切换按钮、无快捷操作芯片；用户直接说需求，Agent 自动识别意图。
- 支持文件上传（拖入 / 粘贴 / 点击），文件上传成功得到 `fileId` 供后续引用。

### 4.2 思考过程 — 透明化 Agent 推理

用户能看到 AI 在做什么，每步完成显示结果标签，完成后可一键收起（`ThinkingProcessPanel`，已实现）。

### 4.3 工具执行结果 — 证据可追溯

每个工具一张卡，显示状态、耗时、结果摘要，可展开查看证据/原始数据（`ToolResultPanel`，已实现）。

### 4.4 正文报告 — 流式自然语言输出

流式打字机效果，含表格/代码块，正文结束后才出现追问建议（已实现）。

### 4.5 结构化结果卡 — 关键数据一目了然

在正文后展示，只展示关键摘要，可点击展开详情（`IntentPanel`→`ProductOpsPanel` 按 intentType 内联分发，已实现）。

### 4.6 追问建议 — 自然引导下一步

点击即填入输入框；基于上下文动态生成；支持维度下钻、时间对比、后续动作（已实现）。

### 4.7 可逆操作与执行态（v3.2 新增）⭐

> AI 原生操作（入库/建工单/热重载/删除等）具备破坏性或影响在架状态，业界（ChatGPT、Agentforce、Copilot 等）已把**「撤销/回退」与「建议态 vs 已执行态」**视为基本盘。本产品为任务型、不可逆成本高的系统，**必须**显式区分并支持回退。

**a) 建议态 vs 已执行态**

任何触发变更的操作，交付时**默认以「建议（suggested）」呈现**，经用户确认后才转为「已执行（executed）」，失败标记「failed」：

- 消息与结构化卡增加 `actionState: 'suggested' | 'executing' | 'executed' | 'failed'` 状态标记（色块/徽标）。
- 合规、入库、删除、建工单、热重载等一律走「AI 给出建议 → 消息内确认按钮 → 执行 → 回写执行态」。
- 结构化卡内联展示本条对应的执行按钮（in-dialog，不进右侧只读面板）。
- 任一动作可附 `undoable: boolean` 与 `undoAction` 说明。

**执行态流转：**

```
suggested ──用户确认──▶ executing ──成功──▶ executed
                              │              │
                              └──失败──▶ failed（可重试/撤销）
executed ──撤销──▶ reverted（回退到建议前状态）
```

**b) 撤销 / 回退**

- 已执行动作在消息/卡上提供「撤销」chip（`nextSteps` 追加 `{"label":"撤销","action":"undo",...}`）。
- 撤销按钮触达后端**幂等**接口（如 `deleteConfigDraft`、工单关闭、状态回滚），文案提示影响面后再确认。
- **删除注意**（沿用 7.2）：草稿项直接撤销/删；已备案（submitted）项撤销将影响在架，提示「建议走下线/停售流程」，仅在对话内说明，不直接执行破坏性回退。
- 撤销后追加一条 assistant 消息回写结果，右侧「会话常驻兜底卡」随之更新。

**c) 落地归属（新增/修改组件）**

| 组件 | 说明 |
|---|---|
| `ChatMessageList.vue` / `ProductOpsPanel.vue` | 渲染 `actionState` 徽标 + 消息内确认/撤销按钮 |
| `useProductConfig.js` | 增加 `actionState/undoable` 状态；新增 `executeAction/undoAction` 承接后端接口 |
| `useChatStream.js` | SSE `intentData` 透传 `actionState`/`undo` 信息 |
| 后端各动作接口 | 保证**幂等**，供重复确认/重试不重复执行 |

## 五、右侧场景感知汇总面板（v3 核心）⭐

### 5.1 定位

**场景感知的只读实时汇总信息面板**（信息驾驶舱）。目标：让用户在与 AI 对话过程中，**快速准确地掌握重要信息和当前状态**，提升使用效率。汇总内容**随场景/意图不同而不同**。

### 5.2 行为规则

- **常驻实时显示**：面板常驻右侧，随对话/会话自动刷新；所有汇总基于响应式状态（computed），无需轮询。
- **随会话/场景切换**：切换会话后，从历史消息恢复意图与汇总状态。
- **以场景为核心定制**：每个场景一套汇总卡片，当前处于哪个场景就显示哪套。
- **只读**：面板不加操作按钮，具体操作全部落在对话内。
- **按最近意图自动切换**：取消息列表中最后一条 `role==='assistant' && done` 的 `intentType` 计算当前场景 key；空会话/欢迎态显示默认兜底卡。

## 六、移动端交互设计（v3.1 新增）

> 设计以「移动优先」为底线：**移动端可用的功能才是完整功能**。桌面端所有能力都必须在移动端单列对话流内可达，面板一律为可选增强层。

### 6.1 布局断点与收敛策略

| 断点 | 形态 | 左右栏 | 汇总面板 |
|---|---|---|---|
| ≥1024px 桌面 | 三区（左/中/右）常驻 | 常驻 | 常驻 |
| 768–1023px 平板 | 双区（对话 + 汇总） | 左侧收为抽屉 | 默认展开，可收起 |
| <768px 手机 | 单列全屏对话 | 左侧收为全屏抽屉 | 收为抽屉，经顶部/按钮调出 |

**实现要点**：
- `AssistantShell` 布局容器按断点降级：横向三栏 → 双栏 → 单栏；当前 `.workbench-body` 的 flex 需改为响应式（右侧两栏用 `@media` 收拢）。
- 抽屉（Drawer）承载：历史对话、快捷场景、右侧汇总。
- 触控优先：可点区域 ≥44×44px，屏蔽 hover-only 交互（当前 `ChatMessageList` 的操作栏依赖 hover 显隐，移动端需常显）。

### 6.2 汇总信息在移动端的可达性

- 右侧汇总面板在移动端**不占常驻空间**，改为抽屉；为保证"随时掌握状态"，提供**会话内紧凑状态条**（消息区顶部一条可点入抽屉的「会话汇总」栏，含最新关键计数）。
- 抽屉内汇总卡沿用第五章场景卡片集，可横向滚动/折叠，点击某项→回到对话并展开对应消息。

### 6.3 输入与消息体适配

- 输入框：沉底、适配 `env(safe-area-inset-bottom)` 与软键盘弹出（`visualViewport` 高度变化）；支持语音输入。
- 长清单/关系图：移动端**懒渲染 + 分段加载**，批次清单、趋势图、风险列表等高密度内容默认折叠，「展开更多」增量加载，避免一次渲染大量 DOM。
- 表格适配：`.data-table` 等宽表在窄屏改横向滚动或卡片化；`ProductOpsPanel` 的表格需响应式处理。
- 消息操作栏：由 hover 显隐改为常显/长按菜单。
- 追问建议芯片：允许横向滚动，避免换行堆叠占用太多纵向空间。

### 6.4 移动端的性能约束

- 流式 Markdown 渲染防抖/节流；`ThinkingProcessPanel` 时间线动画在移动端可降级（`prefers-reduced-motion` 已支持）。
- 关系图谱 `SparqlResultGraph` 大图在移动端懒加载或降级为表格摘要。
- 会话历史加载分页，避免一次拉取全量消息。

### 6.5 与其它章节的协同

- 长对话（见第八章）的记忆与文件引用锚天然适合移动端（单列内联信息锚），无需额外侧栏。
- 批量配置（见第七章）的批次清单卡本就是内联表单，移动端友好，仅需折叠/展开优化。
- 「纯对话、无表单」方向**高度契合移动端**——避免在窄屏做复杂表单，是移动优先的正确解。

## 七、批量配置对话化（v3 新增）

### 7.1 场景：智读·文件配置（`file-parse` / `rd.import`）

**完整链路（已有的数据流，UI 改为对话内联）：**
1. **投喂**：粘贴方案正 / 上传文件（`fileId`）→ 后端解析（`batchFromDocument / batchFromUploadedFile / batchFromUpload`）。
2. **映射+合规**：返回 `batch`（items、passedCount、pendingCount、confirmableDrafts、scenario）。
3. **对话化清单**：`buildBatchPlaybook` 产出 playbook → 消息内展示批次摘要 + 逐条清单（名称/月费/状态/命中规则）。
4. **修正**：`applyBatchFix`（contract12/internal/fee19/dependBb 预设修复）→ 重跑合规。
5. **入库/提交**：`confirmPassedDrafts` → 逐条 `submitConfigDraft` → 生成商品编码+工单，结果追加回消息。

### 7.2 批量配置的具体操作（全部对话内）

| 操作 | 对话表达 | 承接逻辑 |
|---|---|---|
| 新增一个配置 | 「新增家庭融合套餐，月费99，30G流量」 | `generateProductFromChat` → AI 生成 → 内联配置卡 + 追问「校验/保存/提交」 |
| 新增批量 | 粘贴文档 / 上传文件 | `simulateFileParse` → 批次清单卡 |
| 删除一个配置 | 「删除刚才文档里的‘家庭融合128’」 | 定位 fileRef/batch → 内联确认卡 → 用户确认 → `deleteProduct`（`deleteConfigDraft`） |
| 修正待修项 | 「修正待修正项后重跑合规」 | `applyBatchFix` / 对话重述 |
| 入库通过项 | 「确认通过项入库」 | `confirmPassedDrafts` |
| 复制复用 | 「把 OF-xxx 复制为草稿」 | `copyAsDraft` / `discoverConfigs` |

**删除注意**：草稿项直接删；已备案（submitted）项删除将影响在架，提示「建议走下线/停售流程」，本次仅处理草稿与未提交项。

### 7.3 批量配置状态（内联批次清单卡展示）

```
状态机：草稿 → 待修正(合规FAIL) → 合规通过 → 已备案(submitted)
批次汇总：通过 N / 待修 M / 可入库 K
```

- 状态以标签/色块呈现于消息内的批次清单卡。
- 每次状态变化以追加消息回写（不跳转），可就任一状态下钻（「这几条为什么没通过」→ 命中规则/证据）。

## 八、长对话交互设计（v3 新增）

目标：**上传一个文件后，后续不断交互对话**时，系统能稳定地记住、引用并延续上下文。

### 8.1 现状能力

| 能力 | 载体 |
|---|---|
| 会话持久化 + 消息恢复 | `ChatPersistenceService` + `/chat/history/...`、`useChatStream.loadMessages/switchSession` |
| LLM 对话上下文 | 发送时携带最近 20 条消息文本（`useChatStream`） |
| 文件落盘 + 按需解析 | `ConfigDocumentStorage`（fileId）→ `batchFromUploadedFile` |
| 草稿按会话持久化 | `persistCurrentDraft` / `listConfigDrafts(sessionId)` |
| 会话消息搜索 | `/chat/history/search?keyword=` |

### 8.2 关键缺口

1. **文件/批次索引未结构化进会话**：`fileId` 与解析出的 `batch/batchItems` 不在会话持久化的结构化数据里，刷新/切会话后难以稳定引用。
2. **消息历史只有纯文本**：`getSessionMessageMaps` 返回消息不含结构化对象（批次、工具结果、意图数据），长对话时 LLM 看不到上一轮清单/证据。
3. **`batchItems` 不随会话恢复**：`loadPersistedDrafts` 只恢复 `products`，不恢复批次归属。

### 8.3 设计：三级落地

**L0 — 纯前端（本迭代优先）**
- 消息层为每次文件解析生成 `msg.fileRef`（fileId/批次名/计数/关键摘要），内联展示「已引用文档」条，作为对话记忆锚。
- 追问建议追加跨轮续接项：基于这份文件分析 / 修正待修项 / 对比这批套餐 / 导出结论。
- 引用消解：用户说「这份文件/刚才那批」，前端向上查找最近 `fileRef`/`batch`，带上 fileId 重发或重解析。

**L1 — 会话级结构化记忆（后端配合）**
- 将「文件→批次」引用关系持久化进会话 Metadata；`getSessionMessageMaps` 额外返回每条的 metadata（fileId、intentData 摘要、toolResults 摘要）。
- 下一轮上下文构造时注入结构化摘要，让 AI 记住上一轮文件与工具结果。
- `batchItems` 随会话序列化，`loadPersistedDrafts` 一并恢复批次归属。

**L2 — AI 原生「对话即记忆」（进阶）**
- 会话内「上下文卡」：每条约涉文件/批次的消息自带可折叠信息锚（沿用 ThinkingProcessPanel/ProductOpsPanel 内联折叠风格）。
- 后端 SessionManager/意图理解加入对「上次上传/上一份文档」的指代消解。
- 会话历史页重建「文件解析时间线」供回溯。

## 九、会话状态实时汇总（v3 新增）

### 9.1 定位
在长对话过程中，实时汇总并展示**会话级全局状态**（已上传文件、已生成配置、各状态计数、批次/工单进度），作为右侧场景汇总面板的「会话常驻兜底卡」与消息内联内容的补充。

### 9.2 可聚合数据源（前端响应式，已具备）

| 类别 | 来源 |
|---|---|
| 配置总数/状态分布 | `products[].status / auditStatus / compliancePass` |
| 批次概况 | `batch?.passedCount / pendingCount / confirmableDrafts` |
| 引用文件 | 消息中的 `fileRef` / `batch` |
| 工单/告警（Ops） | `monitorWorkOrders[]`、风险稽核计数 |
| 审计 trace | `lastConfigTraceId` |

- **实时性**：全部为 `ref/reactive` 响应式聚合，随状态自动更新，无需轮询。
- **持久化恢复**：刷新/切会话后调用 `GET /config/drafts?session_id=` 重建 `products`，恢复汇总。
