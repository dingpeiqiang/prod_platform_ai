# 产品智能配置助手 - 三大演示场景脚本实施计划

## 概述

基于现有"AI驱动动态表单底层框架",实现产品智能配置助手的三大演示场景(可演示MVP),三场景并行实施,由开发者创建演示数据。

- **场景一:智查・一键复制** - 存量配置语义检索、差异预览、一键克隆
- **场景二:智读・批量生成** - 方案文档上传、AI解析、批量生成配置
- **场景三:智聊・对话式配置** - 多轮对话、可视化画布、拖拽编辑

### 第二部分:后端API实现

#### 2.1 场景一API - 智查・一键复制

**新增文件:** `backend/app/api/demo_search.py`

| 端点 | 方法 | 功能 |
|------|------|------|
| `/api/v1/demo/search/semantic` | POST | 语义检索历史配置 |
| `/api/v1/demo/search/config/{package_id}` | GET | 获取配置详情 |
| `/api/v1/demo/search/clone` | POST | 一键克隆配置 |
| `/api/v1/demo/search/diff` | POST | 配置差异对比 |
| `/api/v1/demo/search/submit` | POST | 提交新配置(含本体校验) |

**核心逻辑:**
- `semantic` 端点:接收自然语言查询,调用`ai_inference_service`做语义向量化,与`demo_data_service`中的套餐做相似度匹配,返回Top5结果及相似度分数
- `clone` 端点:根据package_id深拷贝配置数据,生成新package_id,状态标记为"草稿"
- `diff` 端点:对比源配置与克隆配置,输出差异字段列表
- `submit` 端点:调用`ontology_service`做本体校验,返回校验结果

**请求/响应示例:**
```python
class SemanticSearchRequest(BaseModel):
    query: str  # "查找面向高校学生、200M宽带+手机号融合的历史在售套餐"
    top_k: int = 5

class SemanticSearchResponse(BaseModel):
    success: bool
    results: List[Dict]  # [{package_id, name, similarity, key_fields, ...}]
    
class CloneRequest(BaseModel):
    source_package_id: str
    modifications: Dict[str, Any]  # 差异修改字段

class DiffResponse(BaseModel):
    success: bool
    source_config: Dict
    cloned_config: Dict
    diff_fields: List[Dict]  # [{field, source_value, target_value, category}]
```

#### 2.2 场景二API - 智读・批量生成

**新增文件:** `backend/app/api/demo_doc.py`

| 端点 | 方法 | 功能 |
|------|------|------|
| `/api/v1/demo/doc/upload` | POST | 上传方案文档 |
| `/api/v1/demo/doc/parse` | POST | AI解析文档提取套餐 |
| `/api/v1/demo/doc/batch-generate` | POST | 批量生成配置草稿 |
| `/api/v1/demo/doc/batch-submit` | POST | 批量提交稽核 |

**核心逻辑:**
- `upload` 端点:复用chat_v2的文件上传能力,保存文档到`uploads/demo/`
- `parse` 端点:读取文档内容,调用`llm_service`用结构化Prompt提取多个套餐要素(带宽/月租/合约期/受理限制/优惠活动),返回结构化JSON列表
- `batch-generate` 端点:对每个解析出的套餐,调用`ontology_service`映射到商品本体,生成5套配置草稿
- `batch-submit` 端点:批量校验并提交,返回每个套餐的校验结果

**Prompt设计(嵌入`backend/app/prompts/demo_doc_parse.txt`):**
```
你是一个电信产品配置专家。请从以下方案文档中提取所有套餐信息,输出JSON数组。
每个套餐包含: package_name, bandwidth, monthly_fee, contract_period, 
acceptance_restrictions, promotional_activities, target_audience
文档内容: {document_content}
```

#### 2.3 场景三API - 智聊・对话式配置

**新增文件:** `backend/app/api/demo_dialog.py`

| 端点 | 方法 | 功能 |
|------|------|------|
| `/api/v1/demo/dialog/start` | POST | 开始对话配置会话 |
| `/api/v1/demo/dialog/chat` | POST | 多轮对话(SSE流式) |
| `/api/v1/demo/dialog/canvas/{session_id}` | GET | 获取画布配置数据 |
| `/api/v1/demo/dialog/update-node` | POST | 更新画布节点 |
| `/api/v1/demo/dialog/validate` | POST | 实时本体规则校验 |

**核心逻辑:**
- `start` 端点:创建演示会话,初始化空画布配置,返回session_id
- `chat` 端点:复用`configure_handler`的AI推理流程,但增加:1)意图识别(需求描述/补充信息/修改指令) 2)配置框架拆解 3)缺失字段追问 4)画布数据同步更新。返回SSE流(思考过程+文本+画布更新事件)
- `canvas` 端点:返回当前会话的画布配置树(节点列表+连接关系)
- `update-node` 端点:前端拖拽修改节点后,更新画布数据并返回校验状态
- `validate` 端点:调用`ontology_service`校验当前画布配置,返回冲突/错误列表

**画布数据结构:**
```python
class CanvasConfig(BaseModel):
    session_id: str
    nodes: List[CanvasNode]
    edges: List[CanvasEdge]
    validation_status: str  # pending/passed/failed
    
class CanvasNode(BaseModel):
    node_id: str
    node_type: str  # product/tariff/constraint/discount
    label: str
    fields: Dict[str, Any]
    position: Dict[str, float]  # {x, y}
    
class CanvasEdge(BaseModel):
    source_id: str
    target_id: str
    relation: str  # contains/refers_to/constrains
```

## 假设与决策

### 技术决策

1. **MVP策略**: 三场景均为可演示MVP,核心流程跑通,部分AI推理结果可预置模拟数据以保证演示流畅性
2. **数据存储**: 演示数据以Python模块形式存储(非数据库),便于部署和重置;会话状态使用内存+chat_v2数据库混合
3. **画布实现**: 使用SVG实现(非Canvas/第三方库),降低依赖,满足MVP拖拽需求
4. **SSE流式**: 场景三对话复用现有SSE模式(`text/event-stream`),与chat_v2保持一致
5. **本体校验**: 复用`ontology_service`现有校验能力,不新建校验逻辑
6. **样式**: 复用现有Element Plus + CSS变量,保持UI一致性

### 范围边界

- **不包含**: 真实Word文档解析(用.txt模拟)、真实向量数据库(用内存相似度计算)、真实用户认证(使用默认用户)
- **包含**: 三场景完整前端UI、后端API、演示数据、AI调用(复用现有LLM配置)
