# 产商品配置模板化扩展方案

## 1. 背景与问题

产商品研发助手当前配置链路：`智聊对话 → 槽位抽取 → 字段推理 → 合规校验 → 表单预览 → 报文投影`。
该链路目前仅支持"家庭融合/校园/5G"等预设场景，扩展任意业务产品（政企专线、物联网卡、权益包等）需修改多处代码。

### 1.1 现状诊断

| 环节 | 实现位置 | 现状 | 扩展障碍 |
|------|---------|------|---------|
| 字段 Schema | `resources/ontologies/offering_config.json` | 已配置化，但仅一套字段，品类枚举静态 | 新产品字段无法增量定义 |
| 槽位抽取 | `OpsExtractionService.extractSlots` | 正则词典与 LLM 提示词硬编码，SLOT_KEYS 固定 | 新字段无法被抽取 |
| 字段推理 | `ProductOntologyService.inferFields` | 场景分支硬编码（`"家庭融合".equals(scenario)`） | 新场景需新增 Java 分支 |
| 合规校验 | R-C* 规则 | 规则开关在 `ops_rules.json`，规则逻辑在 Java | 规则集无法按产品类型裁剪 |
| 前端表单 | `frontend/src/data/productMockData.js` | 本地 mock 生成 schema，未消费后端 offering_config.json | 后端 schema 变更前端不感知 |
| 报文投影 | messageProjector | 已按 categoryCode/messageRootKey 多品类投影 | 无障碍，保持不动 |

**结论**：扩展一类新产品当前需改 4 处代码（抽取提示词、推理分支、合规规则、前端表单）。

---

## 2. 设计目标

1. **零代码扩展**：新增一类业务产品 = 新增一份模板配置（JSON），不改 Java 与前端代码
2. **存量兼容**：家庭融合等既有场景行为与报文契约不变
3. **流程复用**：模板管"数据 Schema + 规则"，复杂校验/审批环节复用《工作流配置规范》节点编排
4. **渐进迁移**：家庭融合作为第一份模板从存量代码平移抽出，双品类验证后再推广

---

## 3. 总体架构

```
用户话术
   │
   ▼
┌─────────────────────────────────────────────────┐
│ 抽取层  产品类型识别（matchers）                    │
│         → 加载模板 → prompt/正则词典模板化拼装       │
├─────────────────────────────────────────────────┤
│ 推理层  derive_rules 规则引擎（默认值/推导/联动）    │
│         + compliance_bindings 规则集裁剪           │
├─────────────────────────────────────────────────┤
│ 表达层  /config/template/{type} 下发渲染 schema    │
│         → 前端 schema-driven 表单                  │
│         → message_projection 报文投影              │
└─────────────────────────────────────────────────┘
   模板层（模板仓库 templates/*.json，版本管理、继承）
```

## 4. 产品配置模板 Schema 规范

模板文件存放于 `backend-app/src/main/resources/ontologies/templates/{template_id}.json`，
JSON 字段统一 snake_case（对齐《工作流配置规范》第 9 节）。

### 4.1 模板整体结构

```json
{
  "template_id": "family_fusion",
  "template_name": "家庭融合套餐",
  "version": "1.0.0",
  "extends": null,
  "status": "published",
  "matchers": {},
  "fields": [],
  "derive_rules": [],
  "compliance_bindings": {},
  "message_projection": {}
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `template_id` | string | 是 | 模板唯一标识（snake_case），如 `family_fusion` |
| `template_name` | string | 是 | 模板显示名称 |
| `version` | string | 是 | 语义化版本号 |
| `extends` | string | 否 | 父模板 ID，字段/规则继承合并，子模板覆盖同名项 |
| `status` | string | 是 | `draft` / `published` / `deprecated`，仅 published 参与运行时匹配 |
| `matchers` | object | 是 | 产品类型识别与槽位抽取素材，见 4.2 |
| `fields` | array | 是 | 字段定义列表，见 4.3 |
| `derive_rules` | array | 否 | 声明式推理规则，见 4.4 |
| `compliance_bindings` | object | 否 | 合规规则集绑定，见 4.5 |
| `message_projection` | object | 否 | 报文投影配置，见 4.6 |

### 4.2 matchers（类型识别与槽位抽取）

```json
{
  "matchers": {
    "keywords": ["融合", "家庭", "宽带"],
    "priority": 10,
    "few_shot": [
      {
        "text": "给家庭用户做一个融合套餐，月费158，带500M宽带，全渠道销售",
        "slots": {
          "bizScenario": "家庭融合",
          "targetUser": "家庭",
          "offeringType": "fusion",
          "monthlyFee": 158,
          "includeBroadband": "500M",
          "channelScope": "全渠道"
        }
      }
    ]
  }
}
```

| 字段 | 说明 |
|------|------|
| `keywords` | 类型识别关键词（命中越多优先级越高） |
| `priority` | 多模板同时命中时的裁决优先级，数值大者优先 |
| `few_shot` | 槽位抽取示例，运行时拼装进 LLM 提取提示词；示例中的 slots 键必须存在于 fields |

抽取提示词由运行时按激活模板自动拼装：字段清单取自 `fields`，示例取自 `few_shot`，
`SLOT_KEYS` 动态生成，替代 `OpsExtractionService` 中的硬编码提示词。

### 4.3 fields（字段定义）

```json
{
  "field_code": "includeBroadband",
  "label": "宽带速率",
  "type": "select",
  "required": false,
  "unit": "",
  "default_value": "500M",
  "slot_aliases": ["带宽", "几M", "速率"],
  "extract_hint": "用户说 500M/千兆 时归一化为 500M/1000M",
  "enum_config": {
    "type": "static",
    "options": [
      { "value": "300M", "label": "300M" },
      { "value": "500M", "label": "500M" }
    ]
  },
  "visible_when": { "field": "categoryCode", "in": ["familyBasePrc", "broadBandMainPrc"] },
  "rule_description": "对应报文 prodPrcInsts 中的宽带速率要素"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `field_code` | string | 是 | 字段编码，与存量草稿字段名保持兼容（如 `offeringName`/`monthlyFee`） |
| `label` | string | 是 | 业务展示名 |
| `type` | string | 是 | `input` / `number` / `select` / `switch` / `date` / `textarea` |
| `required` | boolean | 否 | 是否必填（驱动 R-C06 校验与表单标红） |
| `unit` | string | 否 | 单位（元/M/分钟等，表单展示用） |
| `default_value` | any | 否 | 默认值 |
| `slot_aliases` | array | 否 | 正则/关键词抽取别名，供槽位抽取词典生成 |
| `extract_hint` | string | 否 | 抽取归一化提示，拼装进 LLM 提取提示词 |
| `enum_config` | object | 否 | 选项枚举（`static` 静态 / `remote` 远程字典） |
| `visible_when` | object | 否 | 条件显隐（表单联动，`in`/`eq`/`not_eq`） |
| `rule_description` | string | 否 | 字段语义与报文映射说明 |

说明：`field_code` 沿用存量 camelCase 草稿字段契约（后端报文投影与前端表单均依赖），
模板**元数据层**统一 snake_case，两层通过 `field_code` 关联，互不影响。

### 4.4 derive_rules（声明式推理）

```json
{
  "derive_rules": [
    { "when": { "categoryCode": "familyBasePrc" }, "set": { "messageRootKey": "familyBasePrc" } },
    { "set": { "mutexGroup": "MAIN_PKG" }, "unless_field_filled": "mutexGroup" },
    { "set_default": { "channelScope": "全渠道" }, "if_missing": true },
    { "when": { "targetUser": "校园" }, "clear": ["bindExistingMainPkg"] }
  ]
}
```

| 规则形态 | 说明 |
|---------|------|
| `when` + `set` | 条件成立时写入字段 |
| `set_default` + `if_missing` | 仅当字段为空时补默认值（对应现 inferFields 的 scenario_default） |
| `unless_field_filled` | 字段已被用户填写时不覆盖 |
| `clear` | 条件成立时清空指定字段（对应 clearBindExisting 逻辑） |

规则按声明顺序执行；`inferFields` 中的场景 Java 分支按此规范逐步平移为配置，
复杂规则（如互斥校验依赖在架数据查询）保留在 Java 规则集，通过 4.5 绑定。

### 4.5 compliance_bindings（合规规则绑定）

```json
{
  "compliance_bindings": {
    "rule_ids": ["R-C01", "R-C06", "R-C08"],
    "workflow_ref": null
  }
}
```

| 字段 | 说明 |
|------|------|
| `rule_ids` | 本模板适用的 R-C* 规则清单；合规引擎执行前按此过滤，未绑定的规则跳过 |
| `workflow_ref` | 可选，复杂校验/审批流程引用《工作流配置规范》的工作流 ID |

### 4.6 message_projection（报文投影）

```json
{
  "message_projection": {
    "root_key_by_category": {
      "familyBasePrc": "familyBasePrc",
      "broadBandMainPrc": "broadBandMainPrc"
    }
  }
}
```

报文根键按品类映射，与 messageProjector 现有多品类投影能力对接；
未声明时回退存量投影逻辑。

### 4.7 校验规则

| 校验项 | 规则 |
|--------|------|
| template_id | 非空、snake_case、全局唯一 |
| fields.field_code | 模板内唯一；继承合并后仍需唯一 |
| few_shot.slots 键 | 必须存在于 fields.field_code |
| derive_rules 引用字段 | 必须存在于本模板或父模板 fields |
| compliance_bindings.rule_ids | 必须存在于 ops_rules.json 已注册规则 |
| version | 语义化版本格式 |
| extends | 父模板必须存在且 status != deprecated，禁止循环继承 |

### 4.8 命名规范

- 模板元数据字段、模板 ID：snake_case
- field_code：沿用存量草稿字段契约（camelCase），保证报文/前端兼容
- 模板文件名：`{template_id}.json`

## 6. 接口设计

### 6.1 模板渲染 schema 下发

```
GET /api/v1/product-ontology/config/template/{productType}
```

响应：模板 fields + derive_rules 的表单渲染视图（字段/枚举/显隐/必填/单位），
前端 DynamicForm 直接消费。

### 6.2 模板清单

`GET /api/v1/product-ontology/meta` 响应新增：

```json
{
  "productTemplates": [
    { "template_id": "family_fusion", "template_name": "家庭融合套餐", "version": "1.0.0", "status": "published" }
  ]
}
```

### 6.3 翻译层工具入参

`rd_config_chat` 入参新增可选 `product_type`；理解层（RD 提示词）在计划阶段识别产品类型并写入 plan params，
未识别时由抽取层 matchers 兜底判定。

## 7. 与工作流配置规范的关系

| 维度 | 产品配置模板 | 工作流配置 |
|------|-------------|-----------|
| 解决问题 | 一类产品的字段/规则/抽取/投影 | 一段流程的节点编排 |
| 配置形态 | 声明式 Schema + 规则 | 节点 + 连接 + 变量引用 |
| 交叉点 | `compliance_bindings.workflow_ref` 引用工作流 | `workflow.condition` 可按 `{{flow.draft.categoryCode}}` 做品类分支 |

两者通过 `workflow_ref` 组合：模板负责"配什么"，工作流负责"怎么审/怎么算"。

| 阶段 | 内容 | 验收标准 |
|------|------|---------|
| P1 元模型 + 双品类验证 | 改造点 1/2/7 + family_fusion 模板平移；新增宽带单产品模板（纯配置） | 两类产品均跑通 智聊→推理→合规→预览→入库，家庭融合行为回归不变 |

## 9. 兼容性与风险

| 风险 | 应对 |
|------|------|
| 家庭融合行为回归 | 模板平移采用"先并存后切换"：derive_rules 引擎结果与存量 Java 分支对比灰度 |
| 报文契约破坏 | field_code 不改名，投影映射保持；P1 阶段 message_projection 仅观察不接管 |
| LLM 抽取质量随模板漂移 | few_shot 强制校验（4.7），模板试运行提供抽取 diff 报告 |
| 多模板命中歧义 | matchers.priority + 命中关键词计数裁决，歧义时走 CLARIFY 澄清链路 |

## 10. 本体技术结合路径

项目已具备本体基础设施：RDF 图存储（`resources/ontology/*.json`）、SPARQL/SWRL 推理引擎（运营侧
SPARQL_QUERY / SWRL_INFER 已在生产链路使用）、本体元数据接口（`/meta` 暴露 classes/relations）。
配置侧当前是"JSON 图配置 + Java 规则"的伪本体，本方案可与本体技术深度结合，把配置侧也纳入
「本体负责推理，大模型负责表达」的既有理念。

### 10.1 模板元模型 → 本体构造的映射

| 模板概念 | 本体构造 | 说明 |
|---------|---------|------|
| 模板 `extends` 继承 | `owl:subClassOf` | 宽带单产品 ⊑ 家庭融合，继承合并交由推理机完成 |
| `fields` 字段定义 | OWL 数据属性 + 基数约束 | `hasMonthlyFee(xsd:integer)`，required → `sh:minCount 1` |
| `enum_config` 枚举 | `owl:oneOf` / SKOS 概念方案 | 产品品类体系（personMainPrc…）即 SKOS 分类树 |
| `derive_rules` | SWRL 规则 | `FamilyFusion(?x) ∧ hasCategory(?x,"familyBasePrc") → hasMessageRootKey(?x,"familyBasePrc")`，复用现有 SWRL 引擎 |
| R-C* 合规规则 | SHACL 约束 | 必填/互斥/依赖 → `sh:minCount` / `sh:in` / `sh:sparql`；SHACL 校验报告直接映射为 issues（ruleId/field/level/message） |
| matchers 类型识别 | SPARQL 分类查询 | 关键词命中升级为语义分类，多模板歧义由推理裁决 |
| 槽位抽取 | 本体驱动 schema prompt | 属性 label / rule_description 下发 LLM 作抽取约束，抽取结果即 ABox 断言 |
| message_projection | 本体→报文映射（R2RML 风格） | messageRootKey 映射即属性级映射配置 |

### 10.2 收益

1. **更彻底的零代码扩展**：新增一类产品 = 向 TBox 增加一个类断言，推导/校验由推理机执行，无需任何规则引擎代码
2. **配置侧与运营侧同源**：共用同一套 TBox（品类、关系已在 `/meta` 暴露），配置草稿即 ABox 实例，入库后天然可被运营侧 SPARQL 查询（智查/归因直接覆盖新产品）
3. **可解释性**：字段填充在 fillSources 之上叠加推理链回放，可回答"为什么月费默认补了500M"（命中哪条规则/哪个场景）
4. **合规自解释**：SHACL 校验报告携带约束路径与违反值，直接生成面向研发的修正建议

### 10.3 务实落地建议（分档）

| 档位 | 形态 | 建议 |
|------|------|------|
| 轻量档（P1/P2 推荐） | JSON 模板为源，结构按本体语义设计（类/属性/约束对应 10.1 映射）；新增"模板→OWL/SHACL 编译器"，校验走 SHACL、推导走 SWRL | 团队无需 RDF 工程化经验，JSON 可读易校验；避免自研规则引擎 |
| 完整档（P3 演进） | 模板仓库以 JSON-LD 为源（既是 JSON 又是合法 RDF），SPARQL 做类型匹配、SHACL 做合规、SWRL/SHACL rules 做推导；模板继承 = owl:subClassOf | 模板本身成为知识图谱节点，与运营图谱合并 |

**风险提示**：避免一步跳到纯 Turtle/OWL 工程化形态——调试门槛与团队学习成本显著高于 JSON；
JSON-LD 是兼顾两者的载体，前端照常按 JSON 消费，本体侧按 RDF 消费。
