## 六、场景 1 深入：异动归因的建模与推理

> 本节是本文件唯一的实现级说明，行号均指 `backend-app/src/main/resources/ontology/product.ttl` 与 `OpsSwrlReasoner.java`（运行时版本，非 `docs` 设计稿）。
>
> **图示版**：`docs/ontology/model/scene1-root-cause-build-and-reason.html`（类层次图 + 规则图 + 装配/执行时序图）。

### 6.1 建模设计（`product.ttl` 内联段）

**1. 证据实体类**：`:Metric`（指标快照，携带异动判据）、`:Channel`、`:Promotion`、`:Competitor`、`:UserBehavior`。

**2. 归因结论类 —— 核心设计**（:1053-1072）

结论类是**证据实体自身的子类**，而非 `Offering` 的子类：`ChannelRootCause ⊑ Channel`、`PromotionRootCause ⊑ Promotion`、`CompetitorRootCause ⊑ Competitor`、`BehaviorRootCause ⊑ UserBehavior`。语义是"根因落在哪条渠道 / 哪个促销 / 哪个竞品 / 哪种行为上"，回读时按结论类取实例即可直接定位到具体证据对象，而不是只得到"这个商品有问题"。

唯一的 Offer 侧结论类是 `:AnomalyOffering ⊑ :Offering`（点火标记）。

**3. 归因链对象属性**（:1143-1152）

`hasMetric`、`soldOn`、`participatesIn`、`competesWith`、`influencedBy`，全部 domain=`:Offering`。

**4. 证据字段数据属性**

`metricDelta`、`orderDelta`、`contribRatio`、`daysToExpire`、`drivenOrderRatio`、`priceGapRatio`、`penetrationDeltaPp`、`weightHint` 等，类型 `xsd:decimal`。

**5. 命名阈值个体**（:1702-1710）

`:th_RA01_metricDeltaLte`、`:th_RA02_orderDeltaLte`、`:th_RA02_contribRatioGte`、`:th_RA03_daysToExpireLte`、`:th_RA03_drivenOrderRatioGte`、`:th_RA04_priceGapRatioGte`、`:th_RA04_penetrationDeltaPpGt`、`:th_RA05_minWeightHint`，均为 `:ThresholdHolder` 实例并带默认 `:thresholdValue`。**阈值进图而不是写死在规则体**，规则骨架恒定、阈值可运行时覆写。

**6. SWRL 规则**（`swrl:Imp`，:1749-1812）

R-A01.delta / R-A01.flag / R-A02 / R-A03 / R-A04 / R-A05，形如：

```
AnomalyOffering(?o) ∧ soldOn(?o,?c) ∧ orderDelta(?c,?d) ∧ contribRatio(?c,?r)
∧ thresholdValue(:th_RA02_orderDeltaLte,?td) ∧ thresholdValue(:th_RA02_contribRatioGte,?tr)
∧ swrlb:lessThanOrEqual(?d,?td) ∧ swrlb:greaterThanOrEqual(?r,?tr)
→ ChannelRootCause(?c)
```

硬约束：**R-A02~A05 的 body 首原子一律是 `AnomalyOffering(?o)`**，即强依赖 R-A01 点火成功；未确认异动就不做根因猜测，避免"没事找因"。

### 6.2 事实装配（`OpsSwrlReasoner.reasonRootCause`，:159-206）

1. 新建 `OWLOntologyManager`，`loadBaseOntology` 载入 `classpath:ontology/product.ttl`；
2. 断言 `Offering` 实例及 `offeringId` / `offeringName`；
3. 逐条 `node.metrics` 断言 `Metric` 实例并挂 `hasMetric`，写 `metricCode` / `metricDelta` / `metricDeltaPp`，`anomaly=true` 时断言 `anomalyFlag`；
4. `assertChannels` / `assertPromotions` / `assertCompetitors` / `assertBehaviors` 挂四类证据实例及其数值字段。

数据源为事实图 `opsGraph[oid]` 节点；入口 `POST /api/v1/product-ontology/ops/root-cause` → `ProductOntologyService.analyzeRootCause` → `OpsRiskAuditEngine.analyzeRootCause`（:338 起）。`offeringId` 缺失时先 `resolveOfferingId` 用 `text` 反查，解析不到直接返回 `success:false`。

### 6.3 推理执行（:208-320）

1. **规则开关**：`enabled(a01..a05)` 读 `ops_rules.json#/rootCause`；关闭项进入 `disabledRules`，由 `disableRules`（:1263）从本体**物理移除对应 `SWRLRule` 公理**，剩余规则才交给推理机；
2. **阈值覆写**：`applyThresholds`（:1245）把 `ops_rules` 阈值写回 `:th_*` 个体的 `thresholdValue`，替换 TTL 默认值；
3. `honorAnomalyFlag=false` 时单独禁用 `R-A01.flag`（只认数值越阈，不认上游标记）；
4. `OpenlletReasonerFactory.createReasoner(ontology)` → `prepareReasoner()` 执行推理；
5. **回读**：`reasoner.getTypes(offeringInd, true)` 判是否命中 `AnomalyOffering`（:260）；命中后按 `instanceLocalIds(reasoner, df, "ChannelRootCause")` 等**按结论类取实例 ID**（:299-316），再与事实 map 拼装候选行，行内带 `ruleId` 与 `engine=openllet-swrl`；
6. 未点火则返回"SWRL 未点燃异动（R-A01）"，四类候选为空。

候选按类聚合、**不给单一路径加权排序**：主因/次因的叙述由 LLM 依据 `fired` 列表与证据数值组织，规则层只保证确定性。

R-A06（持续下滑）是唯一的非 SWRL 补充路径：`OpsRiskAuditEngine.appendSustainedDeclineCandidate`（:789-820）按 `metricFacts.anomaly.decline_days ≥ declineDaysGte`（默认 3）生成 `MetricTrend` 候选，`weight = min(0.5, decline_days × 0.08)`，`engine=java-rules`。该候选带权重，与 SWRL 候选的等权语义不同。

### 6.4 分层兜底与结论不可改写

- `swrl-enabled=false` → `disabled()`；规则配 java → `skipJava()`；推理抛异常 → `catch` 记 warn 并返回 `success=false, engine=fallback-java`（:333-338），由 `OpsRiskAuditEngine` 走纯 Java 同逻辑兜底；
- 阈值默认值在代码侧同源（`-0.10 / -0.20 / 0.30 / 7 / 0.25 / 0.15 / 0 / 0.08`），覆盖缺失时行为可预期；
- 结论不可被 LLM 改写：`ruleId` + `engine` 随行下发，界面按规则编号回显（`frontend/src/components/intent-panels/ProductOpsPanel.vue:528,546`），人工可复核。

### 6.5 已知局限

- 判定为单层原子条件组合，无多因加权打分与排序；
- `Metric` 实例 IRI 采用 `metric-{oid}-{idx}` 位置序号，跨次调用不稳定，无法做跨期事实对比；
- `resolveOfferingId` 只能解析 `opsGraph` 内存在的编码，图谱无该商品即整体失败，不做零事实推断；
- 归因结果未落库，无历史归因可比对。

## 七、场景 2 深入：风险稽核的建模与推理

> 行号均指 `backend-app/src/main/resources/ontology/product.ttl` 与 `OpsSwrlReasoner.java` / `OpsRiskAuditEngine.java`（运行时版本，非 `docs` 设计稿）。
>
> **图示版**：`docs/ontology/model/scene2-risks-audit.html`（需求对比 + 风险类层次图 + 三级推理图 + 可调接口）。

### 7.1 建模设计（`product.ttl` 内联段）

**1. 单点风险结论类**（:1075-1094）

五个单点结论类全部 `rdfs:subClassOf :Offering`——风险主体就是商品本身，没有第二类证据实体：`:ZeroFeeRiskOffering`（零元资费）、`:AbnormalDiscountOffering`（异常全额赠送）、`:ZeroFeeNoContractOffering`（零元在架无合约）、`:ZeroSalesOffering`（长期零销）、`:LowEffOffering`（低效产商品）。

**2. 归并层与升级类**（:1095-1102）

`:HighRiskOffering ⊑ :Offering` 单独建出来作归并层，`:UrgentReviewOffering ⊑ :Offering` 作升级动作。二者自身不带判据，只承接下级结论。

**3. 判据数据属性**

`monthlyFee`、`oneTimeFee`、`inWhitelist`、`discountPercent`、`repeatableFlag`、`emptyTargetGroup`、`onShelf`、`hasContract`、`salesCnt30d`、`shelfDays`、`lowEffCategoryFlag`、`lowRevenueFlag`、`strategicTagFlag`。布尔量与数值量分属 `xsd:boolean` / `xsd:decimal`。

**4. 命名阈值个体**（:1713-1715）

`:th_RB01_fullDiscountPercentGte`（100）、`:th_RB03_zeroSalesShelfDays`（180）、`:th_RB05_highRiskReviewDays`（30），均 `:ThresholdHolder` 实例。R-B01 零元、R-B02、R-B04 判据为常量比较，不挂阈值个体。

**5. SWRL 规则**（:1813-1882）

R-B01.zeroFee / R-B01.discount / R-B02 / R-B03 / R-B04 / R-B05 六条判定规则，外加 R-HR.b02 / R-HR.discount 两条**纯归并规则**：

```
ZeroFeeNoContractOffering(?o) → HighRiskOffering(?o)
AbnormalDiscountOffering(?o)  → HighRiskOffering(?o)
```

归并规则 body 只有一个类原子，不带任何数值条件——条件是上一级规则已经推出来的。R-B05 的 body 首原子即 `HighRiskOffering(?o)`，因此「零元无合约 → 高风险 → 紧急复核」是**跨三轮规则匹配才能得出**的结论，单看任一条规则都得不到。

硬约束：**R-B02 依赖 R-B01.zeroFee 先行成立，R-B05 依赖归并层先行成立**，跳级判定不成立。

### 7.2 事实装配（`OpsSwrlReasoner.reasonRiskOffering`，:360-404）

1. `isSwrlEnabled()` 关闭则直接 `fail("disabled")`；`offeringId` 空则 `fail("invalid")`；
2. 新建 `OWLOntologyManager`，`loadBaseOntology` 载入 `classpath:ontology/product.ttl`；
3. 断言 `Offering` 实例与 `offeringId`，逐项写入上列数据属性；`discountPercent` 缺省写 `-1`，`targetCustomerGroup` 空白折算为 `emptyTargetGroup=true`；
4. `onShelf` / `inWhitelist` / `lowEffCategoryFlag` / `lowRevenueFlag` 四项由调用方预计算后经 `flags` 传入，不在推理器里算。

入口 `POST /api/v1/product-ontology/ops/risk-audit` → `ProductOntologyService.auditRisks` → `OpsRiskAuditEngine.auditRisksOn`（:1001）。

### 7.3 前置筛选（`auditRisksOn`，:1003-1033）

1. 取 `shelfOfferings`，只保留 `state` 为空 / `上架` / `在售` 的商品（:1005-1010），`scannedCount` 记为筛选后在架总数；
2. 传入 `offeringIds` 时再按 ID 求交集，空清单即全量（:1013-1018）；
3. 白名单取 `equityGiftWhitelist`，按 `whitelistTag` 或名称包含匹配（:1020-1022, :1060-1061）；
4. 低效阈值按当前在架商品 `revenue30d` 升序取 `lowRevenuePercentile`（默认 0.05）分位值（:1026-1033），**每次调用现算，随货架浮动**。

### 7.4 推理执行（:1036-1113）

1. `preferSwrlAny("R-B01"..."R-B05")` 判定是否走 SWRL（:1036）；
2. 逐商品调 `reasonRiskOffering`，内部：`applyThresholds`（:1245）覆写三个 `:th_RB*` 个体 → `disableRules`（:1263）按 `enabled` 物理移除规则公理 → `OpenlletReasonerFactory` 建推理器；
3. **按规则逐一验证**：`ruleFired`（:1298）要求「实例确已归入该规则 head 类」且「本体中存在 label 命中该规则号且 head 指向该类的规则」双条件成立——因多个规则共用同一父类结论，不能只看类型；
4. 等级随命中抬升：零元无合约、全额赠送、紧急复核直接 `HIGH`，零销与低效仅在非 `HIGH` 时抬到 `MEDIUM`；任一为 `HIGH` 即 `suggestDelist` / `urgent` 置位；
5. 回读结果按 `riskFeatures` 拼装配处置动作与证据三元组，`reasonEngine` 逐行标注 `openllet-swrl`。

### 7.5 评分与兜底

- 评分 `riskScore`（`OpsRulesService:394`）：HIGH 92 / MEDIUM 70 / LOW 40，`urgent` 加 5 封顶 99，配置项 `risk.scoring`；结果按分数倒序（:1215）；
- 逐商品 SWRL 失败即落 Java 同逻辑分支（:1115-1176），两者判据一一对应；
- 全批失败且零成功 → `riskEngine=fallback-java`；部分失败 → `openllet-swrl+java-fallback`（:1209-1213），`swrlOkCount` / `swrlFailCount` 随响应返回。

### 7.6 已知局限

- 结论只到「商品有风险」，不定位到具体资费项或渠道，整改需人工拆解；
- 低效占比是相对排名，小货架下分位值易失真；
- 归并链只有一层（R-HR → R-B05），无更长的风险传导；
- 结果不落库、不建工单，`urgent` 仅为标记，处置靠前端下钻。
