## 0. 版本修订沿革（防止方向反复）

### v1.0 → v2.0：砍掉"AI vs 人工"对比展示

**v1.0 的问题**：把"业务驱动"做成了"向业务人员解释技术选型"——新增 techTier 档位徽标、whyAi 量化词典、"为什么用 AI？人工 vs AI"折叠块。

**纠偏依据**：
1. 思考过程的受众是**业务人员**，他们关心"这步做了什么业务动作、拿到什么结果、下一步是什么"，而不是"为什么用 AI 不用人工"。"为什么值得用 AI"的量化对比是**架构评审物料**，不是终端用户界面内容——把它塞进 UI 是受众错位。
2. "为什么不用人工"的答案其实已经在 goal 里了（如"避免带病提交被驳回"就是业务理由），再叠一层"人工 30 分钟 vs AI 1 分钟"的徽标，等于让技术又回到了展示舞台中央——与"技术只是工具"的哲学自相矛盾。
3. 档位（TechTier）是给**编排器**看的，不是给用户看的——它应该存在于编排逻辑里，体现在"这个意图编不编排本体环节"的行为差异上，而不是渲染成徽标。

### v2.0 → v3.0：砍掉兜底词典与演示脚本机制

**v2.0 遗留的问题**：保留了"前端兜底词典 + thinkingSchedule 演示脚本 + 三层兜底链"，并把它们制度化。

**纠偏依据**：
1. **兜底 = 写死的温床**。前端 ID_TITLES 这类"按 id 猜标题"的兜底词典，本质是用硬编码预测后端行为——后端每加一种步骤 id，前端就要猜一次；猜错就显示错误文案，猜不到就显示"处理步骤"这种无意义兜底。兜底链越长，系统越固化：数据应该来自唯一事实源（后端按真实编排下发），而不是多层的猜测回退。
2. **演示脚本 = 固化的双轨**。thinkingSchedule.js 用静态脚本"演出来"一条思考时间线，与后端真实链路并行存在——它演示的不是系统真实行为，而是写死的剧本。保留它意味着：每改一次真实链路，剧本就要同步演一次（P2 就是在还这个债）；且演示内容会让人对系统能力产生错误认知。
3. **业务驱动哲学的直接推论**：面向业务的是**流程的真实呈现**，不是兜底的体面、也不是演示的排场。真实链路下发了什么，就展示什么；下发了 0 步，就展示 0 步——不粉饰、不预演。

### v3.0 → v4.0：从"清理垃圾产物"上升为"AI 原生框架设计"

**v3.0 遗留的问题**：只回答了"删什么"，没回答"删掉之后靠什么撑起来"。演示脚本、兜底词典、意图→工具的写死映射、澄清文案模板——这些产物的共同本质是：**用人的预判代替系统的智能**。它们存在的唯一原因是"AI 还不够聪明/不够可信时的拐杖"，但拐杖不离手，系统永远不会学会自己走路：每加一个场景，先写剧本、再写词典、再写映射——扩张成本线性增长，且所有"智能"都发生在编码时而非运行时。

**v4.0 的核心命题**：AI 原生 = **系统的行为由 AI 在运行时决定，人只定义能力边界与安全底线**。具体落到本系统（见第 8 章）：
1. **能力自描述驱动**：工具通过 `AgentTool` 接口自述"我能做什么、要什么参数、产出什么"（已有基建），LLM 看着这份"能力清单"做意图路由与编排——新增工具只需实现接口，理解层 prompt 不用改
2. **自由编排 + 确定性守门**：LLM 负责理解与路径选择（智能），工具参数契约校验/澄清机制负责把关（准确）——两者各司其职，而不是用写死的 `switch(intent)` 把智能钉死在编译期
3. **垃圾产物的淘汰判据**：任何一段硬编码，若可被"运行时的 AI 判断 + 确定性校验"替代，即列入淘汰清单（见 8.4 分阶段路线图）

## 1. 背景与目标

### 1.1 设计哲学（已与需求方对齐）

> 技术只是工具手段，**业务流程驱动才是 AI 原生的目标**。每引入一项技术（AI / 本体 / SWRL），只回答三个问题：不用它，业务人员会怎么做、要多久、错多少？用了之后更快、更准、更便宜了吗？答出量化差距 → 用；答不出 → 砍掉或降级。
>
> v4.0 延伸：**演示脚本、兜底词典、写死的意图映射，都是"AI 没有真正智能化"时期的产物**——它们用人的预判代替系统的判断，让"智能"固化在编码时刻。AI 原生框架的目标是让判断发生在运行时：系统面对新问题时自己想"该怎么做"，人只守住能力边界与安全底线。

### 1.2 现状盘点：哪些环节是"AI 原生"的，哪些是"垃圾产物"

| 环节 | 文件 | 现状机制 | AI 原生判定 |
|---|---|---|---|
| 工具能力定义 | `AgentTool.java` 接口 | getName/getDescription/getParams/getOutputFields/getLabel **自描述契约** | ✅ **已是 AI 原生雏形**——LLM 可读这份能力清单自主路由 |
| 意图→工具映射 | `DefaultUnderstander.java:393-433` | `switch(normalized)` 写死映射 + 双份手写 system prompt 列举意图-工具对应 | ❌ **编译期智能**：新增工具/意图要改映射代码 + 改 prompt + 改白名单，三处同步 |
| 澄清追问 | `DefaultUnderstander.validateParams` + `DefaultPresenter.CLARIFY_LABELS` | 机制本身智能（契约驱动），但追问文案是 4 条写死模板 | ⚠️ 半原生：机制保留，文案模板可由 LLM 生成 |
| 思考文案 | `ThinkingCopy.java` | 10 工具×四要素人工词典，编排层查表注入 | ⚠️ 过渡态：业务语义需要人定义（这是合理的领域知识），但应对"词典未覆盖的工具"有 LLM 现场生成兜底 |
| 前端兜底 | `normalizeThinkingStep.js` ID_TITLES/LEGACY 模板/正则猜测 | 按 id 猜标题 | ❌ **垃圾产物**：猜测式硬编码 → 批次①②清理 |
| 演示脚本 | `thinkingSchedule.js` + `simulateReply.js` | 9 场景静态剧本 | ❌ **垃圾产物**：预演代替真实 → 批次③"演示即真实" |
| 表达层 | `DefaultPresenter.present` | LLM 汇总（结果→自然语言），无写死报告模板 | ✅ AI 原生 |

### 1.3 改造目标

1. **G3 · 编排按业务必要性收敛**（内部设计约束）：规则密集+可解释场景才上规则引擎，LLM 一步到位的不编排本体/推理——体现为行为差异，而非徽标
2. **清理线 · 去兜底、去演示**（第 4 章）：确认依赖后分批移除前端猜测式硬编码与静态剧本
3. **G4 · AI 原生框架演进**（第 8 章，新增）：把"编译期智能"（switch 映射、手写 prompt、文案模板）逐步迁移到"运行时智能 + 确定性守门"，使新增工具/场景的成本从"改 N 处代码"降为"实现 1 个接口"

## 2. 总体设计

```
┌─ ThinkingCopy.java ──────────────────────────────────────┐
│ 唯一事实源（title/goal/manualHint/category 四要素封顶）    │
│ 本方案零改动 —— 业务语义词典不再膨胀                       │
└──────┬───────────────────────────────────────────────────┘
       │ 既有字段（唯一数据来源）
┌──────▼──────────────┐                                    ┌─ 前端 ─────────────┐
│ DefaultUnderstander │  编排按业务必要性收敛（G3, 内部）     │ ThinkingProcessPanel│
│ AgentOrchestrator   │ ──────────────────────────────────▶│ 只渲染后端下发数据   │
│ (事件即业务流程)     │                                    │（去兜底/去演示）     │
└─────────────────────┘                                    └────────────────────┘
```

**数据流原则**：**单一事实源**。思考过程的每一步文案只来自后端按真实编排下发（ThinkingCopy 词典 + 工具自描述 label）；前端不做猜测式兜底、不做静态演示剧本。后端没下发的，就不显示——不粉饰、不预演。

## 3. 改动点详细设计（后端）

### 3.1 ThinkingCopy.java —— 不新增字段（明确不改）

**决策**：v1.0 计划的 TechTier 枚举、COST_JUSTIFICATION 词典、ToolCopy 6 字段化**全部取消**。理由：

1. 现有 ToolCopy 四要素（title/goal/manualHint/category）已完整回答业务人员的问题："这步干什么、为什么、人工怎么做、属于哪类业务动作"
2. "人工 vs AI 耗时对比"是评审物料，塞进词典会让词典从"业务语义词典"变质为"技术论证物料库"——单一职责被破坏
3. 字典零膨胀是维护成本最优解：不加字段 = 不需要 3.4 的构建方法拆分 = 不需要 ToolContractValidator 联动排查

**ThinkingCopy 保持 201 行现状，本方案零改动。**

### 3.2 AgentOrchestrator.java —— 不改动

**决策**：v1.0 计划的 techTier/whyAi 事件透传**取消**。thinking/tool 事件结构维持 P0/P1 交付现状。

事件结构已满足业务流程呈现：

- thinking：步骤标题/描述/goal/输入/输出/工作流（`AgentOrchestrator.java:350-388, 460-467`）
- tool：title/goal/manualHint + input（业务键过滤）/ output（结构化摘要）（`:630-655`）

### 3.3 DefaultUnderstander.java —— 编排必要性复核（G3 落点，行为层面）

**原则**：只收敛"无谓环节"，不砍真实依赖。逐意图核对现有编排：

| 意图 | 现有编排（`DefaultUnderstander.java`） | 业务必要性判定 | 动作 |
|---|---|---|---|
| product_ops_query / monitor / compare（`:394-395`） | 仅 `sparql_query` | 查数就是查数，无冗余环节 | ✅ 已收敛，不改 |
| product_ops_reason（`:396-397`） | `sparql_query` → `swrl_root_cause` | 事实→归因，两步都有业务产出 | ✅ 必要链路，不改 |
| product_ops_policy（`:398-403`） | risk_audit 走 `swrl_risk_audit`，否则降级 `sparql_query` | 降级本身即业务驱动的正确行为 | ✅ 已收敛，不改 |
| rd 5 意图（`:421-431`） | 单工具直连 | rd 工具不直接用 SPARQL/SWRL | ✅ 已收敛，不改 |

**结论：G3 通过复核确认——现有编排已符合"业务必要性"原则，本方案对编排层零代码改动**。这份对照表本身的价值是把"哪些环节业务上真的需要规则引擎/本体"显式化、可评审化，防止未来演进时无谓加环节。

> 档位判定若未来需要（如新增意图时决定是否编排推理环节），作为**编排侧的注释性决策记录**写在 `mapIntentToPlan` 的 case 分支注释里，不做成枚举/配置/展示——它是开发时的思考，不是运行时的对象。

## 4. 改动点详细设计（前端）：去兜底、去演示的渐进清理

> 总原则：**不是一次性删代码，而是确认依赖后分批移除**。每批移除前先跑全量场景回归，确认后端真实链路已完整覆盖，才允许删。

### 4.1 清理对象与依赖分析

| 清理对象 | 现状职责 | 被谁依赖 | 风险 | 清理动作 |
|---|---|---|---|---|
| `normalizeThinkingStep.js` 的 `ID_TITLES`（按 id 猜标题） | 后端未下发 title 时猜一个 | 所有消息渲染 | 后端真实链路已全量下发 title（P0 起 thinking/tool 事件必带）→ 兜底**理论上不可达** | **批次①**：加 @deprecated 注释 → 回归确认无触发路径 → 删表，未知 id 直接显示"处理步骤"通用词（不猜） |
| `normalizeThinkingStep.js` 的 `LEGACY_STEP_TEMPLATES`（旧格式 3 步模板） | 历史会话 reasoning_full 里无 title 的老数据 | 仅历史还原路径 | 老数据可能仍在库中 | **批次②（延后）**：先统计线上/库内命中量，命中为 0 或迁移完成后删除；有存量则保留并标 @deprecated，不再新增条目 |
| `thinkingSchedule.js` 演示脚本（9 场景静态剧本） | 研发助手本地 playbook 路径"演出来"的时间线 | `RdAssistantPage.vue` 的 resolveProductScenario 路由 + `simulateReply.js` | 属产品演示能力，删除影响演示功能 | **批次③（需产品决策）**：三选一 —— A) 演示路径改走真实后端 SSE（推荐：演示即真实）；B) 保留但移出主包（懒加载 + 明示"演示数据"水印）；C) 直接删除演示入口 |
| `simulateReply.js` 模拟播放器 | 配合 thinkingSchedule 播放 | 同上 | 同上 | 跟随批次③ 同步决策 |
| `normalizeThinkingStep.js` 的 `pickResultFromContent` 正则猜测 | 从文案里正则反猜结果摘要 | 结果摘要兜底 | 与兜底词典同性质（猜测式） | **批次①** 同步处理：后端 summary 字段已结构化下发，正则猜测不可达则删 |

### 4.2 批次①实施细节：删除猜测式兜底（低风险，先行）

**前置确认**（实施时逐项验证，任一不满足则该条暂缓）：

1. 后端 `AgentOrchestrator` 所有 thinking 事件（单意图/多意图/澄清分支）均带 title（`intentStepName`/`buildReadablePlan`/固定文案）——已确认成立（`:350-388, 460-467, 519-547`）
2. tool 事件 done 态均带 title（ThinkingCopy 查表或工具 label 兜底，`buildToolEvent :636-646`）——已确认成立
3. 前端 `normalizeThinkingStep` 中 `hasBackendTitle` 优先逻辑已存在（`:139-142`）——兜底仅在缺 title 时触发

**改法**（`normalizeThinkingStep.js`）：

```js
// 删除 ID_TITLES 表与查表逻辑，收敛为：
const title = hasBackendTitle
  ? String(raw.title).trim()
  : (type === 'ontology' ? '分析推理' : type === 'tool' ? '业务处理' : '处理步骤')
```

**收益**：后端新增步骤类型/工具时，前端**不再需要同步改任何词典**——写死路径被物理移除，而非靠纪律约束。

### 4.3 批次③实施细节：演示路径对齐真实链路（需产品决策，后行）

推荐方案 A（演示即真实）：`RdAssistantPage.vue` 的 playbook 场景（chat-generate/query/file-parse/confirm-batch/compare/config-trace/compliance/root-cause/risk-audit）点击后不再走 `simulateReply` 播放静态剧本，而是**向后端发真实请求、渲染真实 SSE**——演示话术保留（作为输入预填），演出改为真实。

若产品坚持保留离线演示（后端不可用时仍可 demo），选方案 B：thinkingSchedule + simulateReply 拆到独立懒加载 chunk，运行时明示"演示数据"标识，与真实链路代码隔离——防止双轨在主链路里隐性耦合。

### 4.4 不改动的文件

- `ThinkingCopy.java` / `AgentOrchestrator.java` / `DefaultUnderstander.java`（后端零改动，见第 3 章）
- `ThinkingProcessPanel.vue` 渲染逻辑（分类徽标/goal 行/人工做法折叠均为 P0/P1 已交付能力，保持）
- `businessLabels.js`（作为 tool 事件 input 键的业务翻译，属于"渲染层通用翻译"，非猜测式兜底，保留）

## 6. 可维护性与扩展性设计（防成本爆炸）

> 设计目标：**新增一个场景/工具/意图，只改 1 处词典 + 0~1 处编排，前端零改动**。
>
> v3.0 的核心收益：**砍掉兜底词典与演示脚本后，"新东西上线要同步改前端硬编码"这条隐性成本被物理移除**——唯一事实源（后端 ThinkingCopy）之外不再有任何需要同步的副本。

### 6.1 扩展路径分析：三类典型变更的"改动点数"

| 变更类型 | 需要改的地方 | 改动点数 | 说明 |
|---|---|---|---|
| **① 新增研发/运营工具**（如 rd_xxx） | ThinkingCopy.TOOL_COPY 加 1 条 ToolCopy（4 字段）→ 编排层自动透传 → 前端自动渲染 | **1 处** | 前端零改动（批次①清理后，前端无词典可同步） |

**成本约束红线**：任何新场景若改动点数 > 3 处，说明词典出现分叉或渲染层被硬编码侵入——评审必须打回，先收敛再加功能。

### 6.2 单一事实源（Single Source of Truth）

- **后端 ThinkingCopy 是业务语义唯一词典**：title / goal / manualHint / category 四要素同条目维护，禁止在任何其他类里再写"工具名→文案"映射（P0 已清理过 ACTION_DISPLAY 等三张重复词典，防止复辟）。
- **前端不留业务语义副本**：批次①清理后，前端不再维护"按 id 猜标题"的词典；`CATEGORY_LABELS` 仅作为分类枚举的显示名（5 个固定值，随枚举走，属枚举而非词典）；`businessLabels.js` 仅做 input 键名翻译（渲染层通用翻译，非业务语义）。
- **禁止新建任何兜底/演示词典**：未来任何"前端预置一份文案以防后端没发"的提议，默认答案是不做——后端漏发就修后端，这是唯一正确路径。前端兜底会把"后端的 bug"悄悄变成"前端的静态文案"，掩盖问题且固化文案。

### 6.3 渲染与透传全部通用化（已达成，保持即可）

既有链路（P0/P1 交付）已实现无名工具通用透传：

  → useChatStream（通用：字段透传，无 if(toolName) 分支）

**校验规则**：前端任何组件不得出现 `toolName === 'sparql_query'` 之类的工具名分支判断。新增字段时只允许"读字段→渲染"，不允许"认工具→写死"。

### 6.4 单轨制：真实链路是唯一的思考过程来源

P2 之前存在"后端 SSE 主链路 / 前端 thinkingSchedule 演示脚本"双轨，历史上曾完全脱节（P2 做了对齐，但双轨本身仍在）。v3.0 的制度化结论：

1. **演示即真实（方案 A 推荐）**：演示话术只作为输入预填，演出走真实后端链路——系统对外呈现的每个"思考"都必须是真实发生的行为。
2. **若必须保留离线演示（方案 B）**：懒加载隔离 + "演示数据"明示标识，且**不允许**演示脚本反哺主链路、也不允许主链路复用演示剧本——物理隔离防止再次合流。
3. **新增场景不需要写演示脚本**：场景的可演示性由真实链路保障，不存在"先写剧本再实现"的工作流——那是顺序倒置，会导致实现迁就剧本。

### 6.5 词典条目膨胀的控制手段

- **ToolCopy 用 record**：`buildToolCopy()` 保持现状（分域合并结构已在 P0 实现），新增工具=加 6 行条目，函数长度始终在 AGENTS.md ≤50 行约束内。

## 8. AI 原生框架设计（v4.0 新增）

> 命题：**让系统的"怎么做事"由 AI 在运行时决定，人只定义能力边界（工具契约）与安全底线（校验/澄清/白名单）**。
> 演示脚本、兜底词典、写死的意图映射，都是"AI 不够智能"时期的拐杖——拐杖不离手，系统不会自己走路。

### 8.1 现有链路的"非 AI 原生"病灶诊断

对照三阶翻译层逐层诊断：

| 层 | 现状 | 病灶 | AI 原生形态 |
|---|---|---|---|
| **理解层** | LLM 输出 `{intent, action, tools, params}` → `switch(normalized)` 映射为 QueryPlan（`DefaultUnderstander.java:393-433`） | LLM 表面在做决策，实际只许在 6 个枚举里选——**假智能**。新增工具要改：①switch 分支 ②白名单常量 ③system prompt 文字三处 | LLM 直接基于**工具自描述契约**输出 `{tools:[...], params:{...}}`——tools 是自由引用，映射表消失 |
| **理解层 prompt** | 两份手写大字符串（`:490-537`），人工列举意图-工具对应与参数说明 | prompt 是第二套映射词典，与代码里的 switch/白名单**三重冗余** | prompt 由工具注册表**动态生成**（遍历 toolMap 拼接 name/description/params），代码即文档，永不脱节 |
| **执行层** | ExecStep 依赖编排（`result:<tool>.<key>` 数据流通道） | ✅ 基本原生：编排声明来自理解层，执行器不认识具体工具 | 保持 |
| **表达层** | LLM 汇总（`DefaultPresenter:70-95`） | ✅ 已原生 | 保持 |
| **澄清** | 契约驱动（`getParams()` 必填校验→CLARIFY）✅；追问文案 4 条模板（`DefaultPresenter:32-37`） | 文案模板写死，新参数类型要加模板 | 机制保留；追问文案由 LLM 基于 `ToolParam` 的 name/description 现场生成 |
| **思考文案** | ThinkingCopy 人工词典查表 | 新工具未登记时无文案（回退工具 label） | 词典保留（人工定义的业务语义是**领域知识**，不是垃圾产物）；未登记工具由 LLM 基于 ToolCopy 同构字段现场生成一次并缓存 |

### 8.2 设计原则：智能与确定的分界线

```
┌────────────────────────────────────────────────────────────┐
│                    运行时智能（LLM 决定）                     │
│  ① 意图理解：用户要什么 → 引用哪些工具、传什么参数              │
│  ② 编排选择：多工具时先谁后谁、要不要串                       │
│  ③ 文案生成：未登记工具的思考文案、澄清追问话术                 │
│  ④ 结果表达：结果 → 业务结论                                  │
├────────────────────────────────────────────────────────────┤
│                    确定性守门（代码决定，不可交给 LLM）         │
│  ⑤ 参数校验：ToolParam 契约（必填/类型/枚举）→ CLARIFY        │
│  ⑥ 安全边界：白名单过滤（LLM 选了未注册工具→拒绝）             │
│  ⑦ 依赖执行：ExecStep result: 数据流通道（防 LLM 幻觉引用）    │
│  ⑧ 失败降级：上游失败→依赖链中止（已有语义）                   │
└────────────────────────────────────────────────────────────┘
```

**判据**：答案会随业务变化的（怎么理解、怎么表达）→ AI；答案恒定的（参数全没全、工具存不存在、数据流对不对）→ 代码。**准确率不靠 LLM 自觉，靠守门机制兜住**——这也是"更准确"的来源：不是让模型更聪明，而是让模型的自由度被约束在能校验的范围内。

### 8.2.1 任务适配判据：不能为了用 LLM 而用 LLM（补强）

与 1.1"不能为了用本体而用本体"同构：**LLM 也是工具，只让它做它最擅长的任务**。给每类任务做适配性判定：

| 任务类型 | 例子 | 适配 LLM？ | 理由与替代方案 |
|---|---|---|---|
| 自然语言→结构（意图/参数抽取） | "分析畅享128收入下滑"→{offering, metric, time} | ✅ 最擅长 | 槽位抽取是 LLM 主场 |
| 自然语言→自然语言（表达/追问） | 结果→业务结论、澄清追问文案 | ✅ 最擅长 | 语言生成本色 |
| 语义检索/模糊匹配 | 未登记工具的文案生成、历史方案语义查找 | ✅ 适合 | 模糊性高，规则枚举不完备 |
| **有限集合的确定性选择** | 工具白名单过滤、参数必填校验 | ❌ **不适合** | 一行 `contains()` 又快又准；让 LLM 判断"工具存不存在"是花算力买不确定 |
| **精确计算/比较** | 收益粗算、资费档位比较、风险分数 | ❌ 不适合 | 用确定性公式/规则引擎，LLM 算数会幻觉 |
| **格式转换/数据流传递** | `result:<tool>.<key>` 上游结果注入下游参数 | ❌ 不适合 | 代码直取，零误差零成本 |

**双判据合用**（v1.0 的技术判据 + 本节的 LLM 判据）：
1. 该环节用某技术（本体/SWRL/LLM）比人工更快更准吗？——不满足则砍
2. 该环节交给 LLM 比一行确定性代码更可靠吗？——不满足则用代码

> 8.3 的改造点均按此双判据筛过：prompt 动态生成/映射退役是**删掉不必要的确定性代码**（那些代码在模仿智能，效果差）；守门校验**保留为代码**（确定性是它的优势）；澄清文案交给 LLM（语言生成本色）。方向一致：**各归其位**。

### 8.3 改造点设计（后端，分三步走）

#### 第一步：prompt 动态生成（消灭三重冗余，低风险）

`DefaultUnderstander` 删除 `buildOpsSystemPrompt()` / `buildRdSystemPrompt()` 两份手写字符串，改为遍历注册表动态拼接：

```java
private String buildSystemPrompt(String scene) {
    StringBuilder sb = new StringBuilder();
    sb.append("你是产商品业务助手，根据用户需求从下列能力中选择工具并填参数。\n")
      .append("仅输出 JSON：{\"tools\": [\"工具名\"], \"params\": {...}}\n")
      .append("多步任务按执行顺序列出多个工具。\n可用能力：\n");
    for (AgentTool tool : toolsOf(scene)) {          // 按场景白名单过滤注册表
        sb.append("- ").append(tool.getName())
          .append("：").append(tool.getDescription());
        if (!tool.getParams().isEmpty()) {
            sb.append("（参数：").append(describeParams(tool.getParams())).append("）");
        }
        sb.append('\n');
    }
    return sb.toString();
}
```

**收益**：意图枚举、action 枚举、意图-工具对应表、工具说明——四类信息收敛为工具自描述一处；新增工具实现 `AgentTool` 接口即自动进入 LLM 视野，**理解层代码零改动**。

#### 第二步：意图映射表退役（中风险，需回归验证）

`mapIntentToPlan` / `mapRdIntentToPlan` 的 switch 删除，QueryPlan 直接由 LLM 输出构造：

```java
QueryPlan plan = new QueryPlan(
    planLabel(firstTool),                                  // 仅用于展示标签
    sanitizeTools(tools, List.of()),                       // 白名单守门保留（⑥）
    params, question);
```

- `intent` 字段语义弱化为**展示标签**（前端 segment 标题/ thinking goal 已由 ThinkingCopy 按工具生成，不依赖 intent 枚举）
- `sanitizeTools` 白名单是安全底线，**保留不撤**（⑧）
- 依赖编排：多工具时 LLM 在输出中给出顺序（tools 数组即顺序），ExecStep 按 `result:` 映射声明跨工具依赖——声明式编排已支持，无需改执行层
- **风险与对策**：LLM 选错工具组合 → 白名单过滤 + `ToolContractValidator` 启动校验兜住；多意图拆分逻辑（`parseMultiIntents`）保留——它解析的是 LLM 已输出的结构，不属于写死映射

#### 第三步：澄清文案与未登记工具文案的 LLM 化（低风险）

- `CLARIFY_LABELS` 4 条模板退役：追问文案由 LLM 基于 `ToolParam.getName()/getDescription()` 生成（参数契约本身就是最好的澄清素材）；LLM 失败时回退一句话模板"请补充：{参数业务名}"
- ThinkingCopy 未登记工具：`buildToolEvent` 发现 `toolCopy()==null` 时，调用 LLM 按 ToolCopy 四要素同构生成一次并**进程内缓存**（ConcurrentHashMap）——新工具上线当天即有业务文案，词典登记转为事后优化而非上线前置

### 8.4 垃圾产物淘汰路线图（与第 4 章清理批次合并）

| 产物 | 性质 | 淘汰方式 | 依赖 |
|---|---|---|---|
| 前端 ID_TITLES / 正则猜测 | 猜测式兜底 | 批次①：@deprecated → 确认不可达 → 删 | 后端 title 全量下发（已成立） |

### 8.5 演进后的扩展成本对比

| 变更 | 现状（v3.0 前） | AI 原生（8.3 完成后） |
|---|---|---|
| 新增工具 | 实现接口 + 改 switch + 改白名单 + 改 prompt + 登记 ThinkingCopy（5 处） | **实现 `AgentTool` 接口 1 处**（白名单按场景声明 1 行；ThinkingCopy 文案由 LLM 自动生成、人工事后润色可选） |

**准确性保障**：理解准确率由"枚举限制 LLM 选择"改为"守门校验拒绝非法输出"——前者牺牲泛化换准确，后者不牺牲泛化且错误可检测可澄清。这正是"更智能且更准确"的机制来源。

### 8.6 实施顺序与风险控制

```

```

每阶段独立可回滚：阶段三若回归不通过，switch 映射恢复（git revert 即可），阶段一/二成果不受影响。

## 9. 工具智能选择与流程/工具编排设计（v4.1 新增）

> 回答三个问题：**① 如何智能化选对工具达成目标？② 复杂业务流程如何可编排、工具如何可编排？③ 如何兼顾开发运维成本与复杂度？**
> 设计基调延续 8.2：LLM 做"选与排"，代码做"校与连"——但选与排不裸奔，靠结构化输出+守门机制保证准确。

### 9.1 问题一：如何智能化选择合适的工具

**机制：能力市场 + 需求匹配 + 守门确认，三层漏斗。**

```
用户问题
  │
  ▼
【第1层·能力市场】注册表中该场景可见的工具（白名单过滤后）
  │   LLM 看到的是"能力清单"：name + description + params 契约
  │   （8.3 第一步的动态 prompt 就是这份清单的载体）
  ▼
【第2层·需求匹配】LLM 基于语义匹配选工具 + 填参数 + 排顺序
  │   输出结构化 JSON：{tools: [...], params: {...}, order 隐含在数组序}
  ▼
【第3层·守门确认】确定性代码逐项校验（不改选择，只验证合法性）
     ① 工具已注册？未注册 → 剔除 + 告知 LLM 重新选择（一次重选机会）
     ② 参数契约？ToolParam 必填/类型/枚举 → 缺失走 CLARIFY（已有机制）
     ③ 能力冲突？同一参数两个工具都要写 → 按 LLM 给的顺序，后者依赖前者输出才允许
     ④ 循环依赖？DAG 校验（见 9.2.3），有环 → 拒绝该计划
     ✓ 全部通过 → QueryPlan 成立 → 执行层跑
```

**关键设计决策**：

- **选择依据是 description 的质量，不是更多的路由代码**。工具的 `getDescription()` 必须写清"解决什么业务问题、什么时候该用我、什么时候不该用"——这相当于给每个工具写了"招聘启事"，LLM 是面试官。**description 是 AI 原生框架里最高杠杆的一段文字**，值得人工精写（这是领域知识，同 ThinkingCopy 定性）。
- **不引入向量检索/embedding 选工具**：当前工具规模 10 个，全量清单直接放进 prompt 一次匹配即可准确完成。工具规模超过 ~30 个时才考虑两级检索（先 embedding 粗筛 top-K，再 LLM 精选）——**按 YAGNI 原则，现阶段不做**（见 9.5 成本账）。
- **选错的代价被守门兜住**：LLM 选了不存在的工具→剔除；参数缺失→澄清而非硬跑；DAG 有环→拒绝。错误不扩散到执行层，转化为"澄清/重选"，这正是 8.2"准确率靠守门不靠模型自觉"的落地。

### 9.2 问题二①：复杂业务流程如何可编排

**机制：流程=步骤序列的声明（ExecStep 已有），编排=依赖声明+顺序执行（DefaultExecutor 已有）。缺的不是引擎，是"谁来产出这份声明"。**

现有执行层已具备完整编排原语（`ExecStep.java` + `DefaultExecutor.java`）：

| 已有能力 | 机制 | 位置 |
|---|---|---|
| 步骤序列 | `plan.getSteps()` 有序 ExecStep 列表 | `ExecStep.java:20` |
| 跨工具数据流 | `paramMappings` 的 `result:<tool>.<key>` 源 | `DefaultExecutor.java:148-187` |
| 依赖失败中止 | `DependencyFailedException` → 下游中止、独立步骤照跑 | `:87, :184-187` |
| 参数多源解析 | direct/result/evidence/default 四种来源 | `resolveSource :165` |

**v4.1 补齐的一块：让 LLM 能产出这份声明（PlanSchema 扩展）**

LLM 输出格式从 `{tools: []}` 升级为可选的 `steps` 结构（向后兼容，只有多步复杂任务才用）：

```json
{
  "tools": ["sparql_query", "swrl_root_cause"],
  "params": { "offering": "家庭融合畅享128", "metric": "收入", "time": "本月" },
  "steps": [
    { "tool": "sparql_query" },
    { "tool": "swrl_root_cause",
      "inputFrom": { "offeringId": "sparql_query.entity_ids" } }
  ]
}
```

- `inputFrom` 即 `paramMappings` 的 LLM 可读形态，`<上游工具>.<输出键>` 引用 `getOutputFields()` 声明的字段——**引用合法性可静态校验**（守门④的一部分），防幻觉引用
- LLM 不给 `steps` 时，执行层按现有降级逻辑（tools 顺序逐个直跑）——**简单任务零编排负担，复杂任务才付声明成本**

**流程编排的边界（v4.5 修订）**：本系统的"复杂业务流程"分为两类，分别由两个入口承载（详见第 12 章入口职责划分）：
- **可变探索类**：单轮内的多工具链（如 查数据→归因、解析→合规→批量确认），由 Agent 对话入口（LLM 运行时编排）承担，本章 9.1~9.5 全部机制继续有效；跨轮状态由 `SessionContext`（cachedEvidence/resolvedParams 三级回填）承担。
- **固定刚性类**：步骤、顺序、条件分支在业务上确定（开单审批、批量稽核、备案提交等），要求可回归、可审计、可回滚——由**后端固定流程引擎**（v4.5 新增，见第 12 章）承担，流程定义即数据，LLM 只出现在 llm 节点内部。
- **仍然不做**：前端执行引擎（刷新丢失、结果不可信）、BPMN 全量规范、跨系统 ESB——v4.4 反对的"把简单系统做成 ESB 的歧路"依然成立；v4.5 修订的仅是"固定刚性流程需要确定性引擎"这一边界，与既有哲学（LLM 做选与排、代码做校与连）不冲突——固定流程引擎把"选与排"固化为流程定义，是守门哲学的极致形态。

### 9.3 问题二②：工具如何可编排（接入即能力）

**工具成为编排单元的门槛 = 实现 `AgentTool` 一个接口**，五个自描述方法就是全部接入成本：

| 方法 | 在编排中的角色 |
|---|---|
| `getName()` | 编排引用的唯一键（steps/`result:` 通道都用它） |
| `getDescription()` | LLM 选它的依据（9.1 第 2 层） |
| `getParams()` | 参数守门 + CLARIFY 澄清（③①守门） |
| `getOutputFields()` | 下游 `inputFrom` 引用的合法键集（防幻觉引用的静态校验） |
| `getLabel()` | 思考时间线展示名 |

**一个新工具从写完到被编排的路径**（8.3 三步完成后）：

```
实现 AgentTool → 注册进 toolMap + 场景白名单（1 行）
  → 动态 prompt 自动收录它 → LLM 即可选用
  → ThinkingCopy 未登记时 LLM 现场生成文案（8.3 第三步）
  → 合规/风险类工具同步登记 ThinkingCopy（人工润色，事后可做）
```

**复合编排单元（可选，二期）**：若出现"这组工具总是按固定套路一起用"（如 解析→合规→确认 三连），可引入 `ToolRecipe`（预置步骤模板，LLM 只填参数）。**判据**：同一组合在真实流量中出现 ≥3 种不同话术触达时才引入——出现 1~2 次就写模板，是过早固化（回到"剧本"老路）。

### 9.4 问题三：开发/运维成本与复杂度控制

**总原则：LLM 决策的成本是"写好 description"，代码守门的成本是"写好校验"，两者都是一次性的；坚决不为"可能的编排需求"预建引擎。**

| 成本项 | 方案 | 量化 |
|---|---|---|
| **开发·新工具接入** | 实现接口 + 1 行注册 | ~半天（含 description/契约精写） |
| **开发·新流程** | 无代码——LLM 在运行时组合 | 0（复杂度转移到 description 质量） |
| **开发·守门机制** | inputFrom 静态校验 + DAG 无环校验 + 一次重选 | ~3 个私有方法，各 ≤30 行 |
| **运维·可观测** | 理解层 LLM 原始输出已落盘（`understand-diagnosis.log` 已有）+ QueryPlan 进 `query_plan` metadata（已有） | 复用现有，0 新增 |
| **运维·失败定位** | 步骤级 durationMs/tool 事件（已有）+ DependencyFailedException 错误链（已有） | 复用现有 |
| **运维·LLM 成本** | 每轮 2 次 LLM 调用不变（理解 1 + 表达 1）；守门重选最多 +1 次，且仅触发于 LLM 选错时 | 上界可控：3 次/轮 |
| **运维·回滚** | 8.6 四阶段，每阶段独立 revert | 已定义 |

**三条复杂度红线**（新增场景/工具时评审检查）：

1. **不得为单个场景写编排代码**——编排逻辑只允许存在于"LLM 输出 + 通用守门"，出现 `if (scene == X) { 专用编排 }` 即打回
2. **不得新增第二套流程描述格式**——流程=ExecStep 序列，工具契约=AgentTool，任何新格式（YAML 流程文件/DSL）都是双轨
3. **LLM 调用次数上界**——单轮请求 ≤3 次（理解+表达+最多一次重选），超界说明工具 description 质量有问题，修 description 而非加重试

### 9.5 与 8 章的关系：9 章是 8.3 第二步的"编排深化"

8.3 第二步（映射退役）回答"LLM 可以选工具"；本章补齐"LLM 怎么选得准、选完怎么排、排完怎么便宜地跑"。实施上合并进 8.6 的阶段三（同一批回归验证），不单独立阶段。`inputFrom` 静态校验与 DAG 校验属于**新增守门代码**（约 +90 行，`DefaultUnderstander` 解析 steps 时执行），是本章唯一的新增开发量。

## 10. 一条消息的完整旅程：识别→规划→驱动（v4.2 新增）

> 用户在消息窗口发出一句话之后，系统内部发生了什么？**谁来识别业务需求、谁来规划反馈、谁来驱动业务流程一步步完成——分别用 LLM、本体/规则，还是其他？**
> 本章把 8/9 章的设计串成一条端到端的时间线，明确每个环节的技术归属。

### 10.1 全景时间线（以真实话术为例）

用户输入："分析家庭融合畅享128本月收入下滑原因"

```
T0 消息到达
 │
 ├─【E1 需求识别】LLM ────────────────────────── 智能环节
 │    输入：用户消息 + 会话历史 + 能力清单（工具自描述）
 │    输出：结构化理解 {tools, params, steps?}
 │    · 抽槽位：offering=家庭融合畅享128, metric=收入, time=本月
 │    · 识别现象：收入"下滑" → 需要归因，不是单纯查数
 │    · 选工具：sparql_query（先取事实）→ swrl_root_cause（再归因）
 │
 ├─【E2 需求澄清（条件触发）】契约校验 → LLM 文案 ─ 混合环节
 │    · 确定性校验（代码）：offering 为空？→ 走 CLARIFY
 │    · 追问什么（代码定）：缺哪些必填参数
 │    · 怎么问（LLM 定）：基于参数契约生成自然语言追问
 │    → 用户补话后回到 E1（resolvedParams 回填，已有三级回填机制）
 │
 ├─【E3 规划确认】确定性守门（代码） ─────────────── 确定环节
 │    · 工具注册校验 / 参数契约 / inputFrom 静态校验 / DAG 无环
 │    · 产出：QueryPlan（ExecStep 序列 + result: 数据流声明）
 │    · 同步向消息窗口推送思考时间线：识别出什么、计划做什么
 │
 ├─【E4 逐步执行】执行层（代码）+ 工具（各按其技术本质） ── 按步驱动
 │    · 步骤1 sparql_query：NL→SPARQL（LLM）→ 查本体事实库 → 事实数据
 │    · 步骤2 swrl_root_cause：事实数据 → SWRL 规则推理（R-A 系列）→ 根因路径
 │    · 每步开始/结束实时推送 tool 事件（含 goal/manualHint）→ 思考时间线逐步点亮
 │    · 某步失败：依赖链中止（DependencyFailedException），独立步骤照跑
 │
 ├─【E5 反馈规划】LLM（表达层） ─────────────────── 智能环节
 │    · 把步骤结果整合为业务结论：主因/次因/证据链/建议动作
 │    · 生成跟进话术（suggested_follow_ups）
 │    · 部分失败时：先给部分结论，再说明失败环节与建议（已有语义）
 │
 └─ T+1 回复完成，SSE done
      · 全程思考时间线 = 业务流程的真实呈现（第 4 章已去兜底/去演示）
      · 会话上下文缓存证据（cachedEvidence）→ 下一轮追问可复用
```

### 10.2 环节 × 技术的责任矩阵（谁该做什么，一句话说清）

| 环节 | 负责者 | 为什么是它 | 代码位置（现状） |
|---|---|---|---|
| E1 理解：抽槽位/选工具/排步骤 | **LLM** | 自然语言→结构是 LLM 本场；工具选择靠语义匹配（8.2.1 判据②） | `DefaultUnderstander.understandPlans`（8.3 改造后为自由引用+动态 prompt） |
| E2 校验：参数齐不齐 | **代码（ToolParam 契约）** | 恒定规则，一行 `isRequired()` 判定，比 LLM 可靠 | `validateParams :158-200` |
| E2 追问文案 | **LLM** | 怎么把"缺参数"问得像人话是语言生成 | `DefaultPresenter`（8.3 第三步 LLM 化） |
| E3 守门：计划合法性 | **代码** | 注册表查询/DAG 校验是确定性计算 | `sanitizeTools` + 9.2 新增校验 |
| E4 执行：步骤驱动 | **代码（执行层）** | 顺序/依赖/失败语义必须精确，不容幻觉 | `DefaultExecutor :75-97` |
| E4 工具内部 | **按工具技术本质各归其位**（见 10.3） | 工具内部用什么技术是各工具自己的事，编排层不感知 | `AgentTool.execute` |
| E5 反馈：结论与建议 | **LLM** | 结果→业务结论是理解+表达 | `DefaultPresenter.present :70-95` |
| E5 规则命中解释 | **规则引擎（SWRL）的输出** | 归因路径/规则编号由推理产生，LLM 只负责转述不负责编造 | `SwrlRootCauseTool` 输出 paths |

### 10.3 工具内部的技术选择（本体/规则/LLM 的最终分工）

编排层不感知工具内部技术；每个工具按 1.1 双判据自选内部实现，当前分工已经正确（附 1 对照表的浓缩）：

| 技术 | 承担的任务 | 为什么是它 | 承载工具 |
|---|---|---|---|
| **LLM** | 语言理解、语言生成、语义匹配 | 模糊性任务，规则枚举不完备 | rd_config_chat / rd_file_parse / Presenter / Understander |
| **本体（SPARQL）** | 业务事实的结构化检索（多实体关联） | 事实必须准确，查询必须可复现——LLM 查数会幻觉 | sparql_query |
| **规则（SWRL/R-A 系列）** | 归因/稽核的规则推理 | 规则密集+可解释要求高：结论必须能指出"命中了哪条规则" | swrl_root_cause / swrl_risk_audit / rd_compliance |
| **确定性代码** | 流程驱动、参数校验、数据流、失败降级 | 这些恰恰是"不容出错"的骨架，交给任何智能体都是风险 | Understander 校验段 / Executor / Orchestrator |

**一句话总结**：**LLM 负责"听懂与说清"，本体负责"事实可信"，规则负责"判定可解释"，代码负责"流程不走样"**。用户消息进来，LLM 先读懂、守门先验证、执行层按声明一步步驱动、每步用对各自的技术、最后 LLM 把结果说成人话——每个环节都是该环节最合适的技术。

### 10.4 反馈规划的三种形态（对应用户感知）

| 场景形态 | 触发条件 | 反馈内容 | 用户感知 |
|---|---|---|---|
| **即时反馈**（思考时间线） | E1/E3 事件即推 | "已明确要做什么 → 计划做什么 → 每步目标" | 提交后 1 秒内看到系统"听懂了" |
| **过程反馈**（工具事件流） | E4 每步开始/结束 | 步骤标题/目标/输入/输出摘要/人工做法 | 看着业务流程一步步完成，而非黑盒转圈 |
| **结论反馈**（正文+跟进） | E5 完成 | 业务结论、证据链、建议动作、追问话术 | 直接可用，或点击跟进话术继续下一轮 |

三种形态全部由真实链路事件驱动（SSE thinking/tool/text*），无任何预演内容——这是第 4 章清理工作的直接受益。

### 10.5 失败与补充信息的流程韧性

| 情形 | 机制 | 用户体验 |
|---|---|---|
| 必填参数缺失 | E2 CLARIFY：暂停执行 → 追问 → 补齐后整轮重来（三级回填：resolvedParams > cachedEvidence > defaultValue，超限防死循环） | 感觉系统"会问"，而不是瞎猜硬跑 |
| LLM 理解失败/超时 | 3 次重试 → 仍失败则明确报错（不做关键词兜底——假智能已移除） | 得到诚实的错误提示 |
| 某工具执行失败 | 依赖链中止 + 独立步骤照跑 → E5 部分结论 + 失败说明 | 拿到部分价值，知道哪里断了 |
| LLM 选错工具 | 守门剔除 + 一次重选（9.1 第 3 层） | 无感（内部消化） |
| 追问多轮仍不清 | 超过澄清上限按缺省值继续，向用户说明假设 | 流程不卡死，假设透明 |

## 11. 用户体验终局：懂用户，并引导用户达成目标（v4.3 新增）

> 前面 10 章回答的是"系统内部怎么运转"——但**架构的一切正确性，最终都要落在用户的使用体验上**。
> 用户体验只有两条验收标准：**① 懂用户**（我说的话它真的听懂了，包括没说全的部分）；**② 引导用户达成目标**（它不只是答，还带我把事情办成——哪怕我一开始不知道要办什么）。
> 本章定义这两条标准的实现机制与验收方式。

### 11.1 "懂用户"的四个层次（从字面到意图）

| 层次 | 用户说的 | 系统懂到的 | 支撑机制 |
|---|---|---|---|
| **L1 听懂字面** | "查一下在售5G套餐" | query + 品类=5G | E1 槽位抽取（LLM 本场） |
| **L2 听懂意图** | "查一下在售5G套餐的增长趋势**和风险商品**" | 双意图：先盘点（query）→ 再稽核（risk_audit）——一条消息两件事都要办 | 多意图拆分（`parseMultiIntents`）+ segment 分组呈现 |
| **L3 听懂上下文** | 上一轮归因后说"**那把它下架吧**" | "它"=上轮命中的商品（cachedEvidence 里的 BUSINESS_ENTITY）；"下架"=承接归因结论的动作 | 三级回填（resolvedParams > cachedEvidence > defaultValue）——**代词与省略靠证据缓存接住，而非追问** |
| **L4 听懂没说的** | "家庭融合畅享128收入下滑了" | 没说时间范围 → 按业务常识补"本月"（向用户透明标注假设）；没说维度 → 归因规则自动跑渠道/促销/竞品/客群四维 | defaultValue + E5 结论中明示假设；规则补全而非追问——**会补的不问，缺了才问** |

**懂的用户体验底线**：用户不应为一个本可以推断的信息回答两次追问。L3/L4 的存在使 CLARIFY 只在"真正无法推断"时出现——追问次数本身就是"懂不懂"的可测量指标（验收指标见 11.4）。

### 11.2 "引导用户"的四个触点（贯穿全程的导航）

引导不是单独的功能，是散布在交互全程的四个触点：

| 触点 | 时机 | 机制 | 用户感知 |
|---|---|---|---|
| **① 进门引导**（知道自己要什么） | 会话开始/切换场景 | 场景欢迎页 + 推荐话术（assistantModes 已有，保留）——**注意：欢迎页是静态场景说明，不是演示剧本**，两者边界：欢迎页说"这里能办什么"，剧本才是"演一遍结果" | 第一眼知道这个窗口能干嘛、怎么开口 |
| **② 过程引导**（跟着流程走） | E4 执行中 | 思考时间线逐步点亮 + 每步 goal（为什么做这步）+ manualHint（AI 不可用时人工怎么做） | 不是黑盒转圈，是看着一条业务流程被走完，随时可接手 |
| **③ 澄清引导**（信息不全时） | E2 触发 | 追问给出**可点击的选项**而非开放问答（如时间范围给"本月/近7天/自定义"），点击即回填 resolvedParams | 补信息从"回答问题"变成"做选择题" |
| **④ 目标引导**（办完这件事之后） | E5 完成 | suggested_follow_ups（已有）升级为**任务链感知的下一步**：归因完成 → 推"生成处置工单"/"对同类商品批量稽核"；稽核完成 → 推"导出稽核清单"/"对高风险项建单"；对比完成 → 推"把推荐方案写回草稿" | 事情办完不悬空，自然流向下一个业务动作——**这就是"达成目标"与"回答问题"的区别** |

**④ 的实现约束（防走样）**：跟进话术由 LLM 基于"本轮工具结果 + 工具描述中声明的业务承接关系"生成，守门校验生成的话术所指工具在本场景白名单内——引导是真实的业务衔接，不是随便编的三句话。

### 11.3 引导的业务本质：把孤立问答串成业务闭环

用户真实的目标从来不是"问一个问题"，而是"办成一件事"——而一件事往往横跨多个场景（归因→稽核→工单；解析→合规→提交）。引导机制的业务价值：

```
用户目标：把这批方案安全上线
   │
   ├─ 智读解析（rd_file_parse）──┐
   ├─ 智检合规（rd_compliance）──┼── 每一步都由触点④衔接，用户只做业务判断
   ├─ 对比择优（rd_scheme_compare）┤   （"要不要下架""选哪个档位"），
   └─ 生成工单/提交备案 ─────────┘   而非自己重新组织每一步的提问
```

**系统的角色定位由此清晰**：不是"更聪明的搜索框"，而是**陪跑业务流程的协作者**——用户掌舵（做业务决策），系统划桨（驱动流程、衔接环节、记住上下文）。

### 11.4 体验验收指标（让"懂与引导"可测量，防自嗨）

| 指标 | 定义 | 目标 | 对应机制 |
|---|---|---|---|
| 追问率 | 触发 CLARIFY 的轮次 / 总轮次 | 持续下降（L3/L4 补全生效） | 证据缓存 + defaultValue |
| 一次办结率 | 用户发出消息后**未补充信息**即拿到可用结论的比率 | 上升 | L1~L4 全链 |
| 跟进转化率 | 点击触点④跟进话术 / 展示次数 | >0 且稳定 | 话术质量（任务链感知） |
| 任务链完成度 | 从首轮到业务闭环（如归因→建单）的平均轮次 | 下降 | 触点②④衔接效率 |
| 人工接手成功率 | 按 manualHint 人工执行同流程的成功率（抽样验证） | 高（证明 SOP 有效） | P1 交付的 goal/manualHint |

**指标获取方式**：全部可从现有数据推导（CLARIFY 计数已有 `incrementClarifyRounds`；follow_ups 点击需前端埋点 1 处）——不为本章新建数据管道。

### 11.5 本章与全文的关系：验收锚点

- 8/9/10 章的架构设计（AI 原生/编排/消息旅程）是**手段**；本章 L1~L4 与触点①~④是**目的**——任何架构改动若不能映射到这两组机制的改善，即为过度设计（回到 1.1 双判据）
- 11.4 的指标是第 5 章回归清单之外的**长期验收线**：架构演进（如 8.4 各阶段）上线前后对比这组指标，而非只看功能是否跑通

### 11.6 不确定时的正确姿态：确认与补充优先于猜测（确定性原则）

> **当 AI 不清楚或无法判断用户的业务意图时，必须停下并请用户确认或补充——宁可多问一句，不可偏离意图硬跑。**
> 这是全篇体验设计的兜底原则：懂用户（11.1）靠智能补全，但补全的边界必须清晰——**能推断的推断（透明标注），不能推断的追问，绝不允许"猜错了还煞有介事地执行完"**。

#### (a) 现状盘点：确认/补充机制已有骨架，缺口在"确认意图"与"选择题化"

| 能力 | 现状 | 位置 | 缺口 |
|---|---|---|---|
| **补参数**（缺槽位追问） | ✅ 已有：必填参数缺失 → CLARIFY → 前端补参表单 → 结构化回传整轮重跑 | `validateParams :158-200`；前端 `ChatMessageList.vue:250-263` 补参区 | 追问是**开放问答**（文本框），应升级为可点选项（11.2 触点③） |
| **问意图**（需求本身模糊） | ❌ **缺口**：LLM 判定"理解不了用户要干嘛"时，理解层只能报错终止（`understandPlans :128-131`）或误映射 | `DefaultUnderstander` | 缺一条 **CLARIFY 的兄弟分支：CONFIRM 意图**——低置信度时列出"我理解你想做 A / B / C"让用户选 |
| **防偏离**（假设透明） | ⚠️ 部分：超澄清上限按 defaultValue 继续但**未向用户明示用了什么假设** | `exceedClarifyLimit` 分支 | 假设必须回显在结论中（"按时间范围=本月 推断执行"），否则用户不知道结论的前提 |

#### (b) 设计：意图确认分支（CONFIRM）——识别层的三态出口

E1 需求识别的输出从"两态"（能懂→执行 / 缺参数→CLARIFY）扩展为**三态**：

```
E1 需求识别（LLM）
  ├─ 置信度高（意图明确、槽位齐） ──→ E3 规划执行
  ├─ 槽位缺失（意图明确但信息不足）→ CLARIFY：追问缺的参数（已有）
  └─ 意图模糊（多种合理解读）     → CONFIRM（新增）：复述理解 + 列候选让用户确认
        输出示例：您是想——
        ① 查询家庭融合畅享128 的本月收入数据
        ② 分析它本月收入下滑的原因（归因）
        ③ 都要：先查数据再做归因
```

**机制设计**（复用现有骨架，最小增量）：

- **LLM 侧**：理解层 prompt 增加一条输出约定——当用户需求存在多种合理解读时，输出 `{"intent": "CONFIRM", "candidates": ["解读1", "解读2", ...]}`。这是 LLM 最擅长的事：**识别歧义本身是语义判断**（8.2.1 判据✅）
- **守门侧**：`CONFIRM` 与 `CLARIFY` 同构处理——不执行任何工具、不扣任何步骤，整轮暂停等用户表态（复用 CLARIFY 的"澄清前不执行任何子意图"语义，`DefaultUnderstander :138-149`）
- **前端侧**：CONFIRM 候选渲染为**可点击卡片**（复用 clarify-area 样式与 suggest 通道），点击即以该候选话术重发——用户从"重新组织语言"降为"点一下确认"
- **上限防死循环**：CONFIRM 连续 2 轮未收敛 → 合并候选为最优解读执行 + 结论中明示假设（同 10.5 的超限语义）

#### (c) 假设透明：防偏离的最后一道闸

所有"系统自行推断"的取值（defaultValue 回填、超限继续、L4 业务常识补全）必须满足**回显义务**：

- 结论正文或思考时间线中明示："本次按 [时间范围=本月] 推断执行，如不符请说明"
- 实现：推断取值时在 `SessionContext` 记录 `assumptions` 列表，E5 表达层 prompt 中注入"请向用户说明以下推断假设"——**假设从隐藏行为变为明示契约**
- 判据：用户看到结论时，能准确说出"系统把哪句话理解成了什么"——说不出来即为偏离风险未受控

#### (d) 三种不确定形态的处理速查（收口）

| 形态 | 例子 | 正确动作 | 错误动作 |
|---|---|---|---|
| 缺参数（意图明） | 归因但没说哪个商品 | CLARIFY 追问（选择题化） | 用 defaultValue 硬跑（除非超限且明示） |
| 意图模糊（多解读） | "看看畅享128"（查数？归因？稽核？） | **CONFIRM 列候选确认** | 挑一个最常见的直接跑 |
| 能力外（办不了） | "帮我调系统配置" | 诚实告知能力边界 + 指引最近场景 | 硬套相近工具给出误导结果 |

**判定优先级**：能力外 > 意图模糊 > 缺参数——先确认"这事我能不能办"，再确认"你要的是哪件事"，最后才追问"缺的参数"。

## 12. 生产流程引擎与入口职责划分（v4.5 新增）

> 回答三个问题：**① 为什么需要固定流程引擎（对 v4.4 立场的修订）？② Agent 对话入口与流程引擎入口如何分工？③ 引擎的稳定性底线是什么？**
> 技术细节（节点契约/状态机/DDL/表达式规范）见《固定流程引擎设计文档》，本章只定立场与边界。

### 12.1 立场修订：从"不做引擎"到"固定刚性流程必须有引擎"

v4.4 §9.2 反对持久化流程引擎的语境是：**防止把"单轮多工具链的对话编排"硬套成 BPMN**——这个警告依然有效（对话入口不引入引擎）。

但生产环境存在另一类需求，其特征与对话编排正交：

| 特征 | 对话编排（Agent） | 固定刚性流程（生产） |
|---|---|---|
| 步骤与顺序 | LLM 每轮动态决定 | 业务上固定，评审后不得漂移 |
| 条件分支 | LLM 语义判断 | 显式表达式，可单测、可审计 |
| 正确性验收 | 采样评估 | 回归测试（同输入=同路径） |
| 变更管理 | 改 prompt，灰度观察 | 流程定义版本化，发布/回滚 |
| 审计要求 | 整轮 metadata | 节点级：谁批的、走了哪条边、依据是什么 |

这类流程（开单审批、批量稽核提交、备案流转）在电信运营商生产环境是刚需，**"可控可运维"是其第一验收标准**——LLM 动态编排无法满足"同输入同路径"与"变更即版本"，因此立项后端固定流程引擎。

### 12.2 入口职责划分规范（两入口并存，边界刚性）

**一句话规范：可变探索走 Agent，固定刚性走引擎。**

| 判定维度 | Agent 对话入口（第 8~11 章体系） | 固定流程引擎入口（第 12 章体系） |
|---|---|---|
| 需求形态 | "帮我分析/查一下/看看"——探索、一次性 | "这批方案走完合规→提交"——流程固定、反复执行 |
| 步骤确定性 | LLM 运行时选与排 | 流程定义固化（JSON，版本化） |
| LLM 出现位置 | 理解/表达全链 | 仅限 llm 节点与工具内部 |
| 执行留痕 | 会话 metadata | 节点级执行记录（状态/耗时/入参出参/分支依据） |
| 失败语义 | 依赖链中止+部分结论 | 节点级重试/fallback 分支/挂起恢复 |
| 典型场景 | OPS-1 市场洞察、OPS-4 异动归因 | RD-4 批量合规提交、审批流转、备案流程 |

**评审判据（新增需求归属判定，写进需求评审清单）**：
1. 该流程的步骤顺序业务上是否允许每次不同？允许 → Agent；不允许 → 引擎。
2. 该流程是否需要"哪个节点谁批的、走了哪条分支"的审计？需要 → 引擎。
3. 该流程是否需要回归测试保障？需要 → 引擎。
4. 三问有任一"不允许/不需要"，且无刚性约束 → 默认 Agent（避免引擎被对话需求污染）。

**边界红线**：
- 引擎不做自然语言理解——流程入口的入参是结构化的（表单/上游系统传参），不接收自由文本（自由文本属于 Agent）。
- Agent 不承载固定生产流程——即使 LLM 每次都能"编排对"，也不作为生产刚性流程的载体（计划随模型/温度漂移，不可运维）。
- 两入口共享的工具层（`AgentTool` 注册表）、守门组件（契约校验/依赖中止）不重复建设——引擎复用，不另造。

### 12.3 引擎稳定性三条铁律（违反任何一条，生产承诺作废）

1. **全持久化状态机**：每个节点完成即落库（节点级执行记录），任何时刻进程终止都能从最近节点恢复；人工审批挂起不限时长（挂起 TTL + @Scheduled 清理兜底）。禁止内存态执行。
2. **LLM 只进节点不进引擎**：引擎调度、条件求值、参数解析全部是确定性代码。一旦允许"LLM 动态改流程图"，即退回 Agent 范式，失去"可控可运维"资格。
3. **定义期守门前置（发布即绿灯）**：无环校验、工具存在性校验、参数契约校验、变量引用校验在**保存/发布时**全部执行；运行期不再出现"图本身非法"的失败类别。

### 12.4 与既有资产的关系（复用清单）

| 引擎部件 | 复用来源 | 说明 |
|---|---|---|
| 工具执行 | `AgentTool` + `DefaultExecutor.getToolMap()` | tool 节点直调真实工具，零新建 |
| 参数编排协议 | `ExecStep.paramMappings` 四来源 | 引擎变量引用 `{{...}}` 与其语义对齐 |
| 守门校验 | `ToolContractValidator` + DAG 校验逻辑 | 抽公共组件，定义期执行 |
| 流程定义/版本 | `pd_ai_workflows` 三表 + `WorkflowService` 版本/发布/回滚 | 已有，直接沿用 |
| 前端编辑器 | `LangChainEditor.vue`（vue-flow） | 保留编辑能力，**执行入口改调后端引擎**（拆除前端 DFS 引擎） |
| 会话与 SSE | 现有 chat 基建 | 引擎执行进度经 SSE 事件流式推送（复用 thinking/tool 事件语义） |

**实施顺序**：P1 真实工具接通（执行端点 + tool 节点去模拟）→ P2 后端引擎（图遍历状态机 + condition + 挂起恢复 + 节点留痕）→ P3 编辑器切换后端执行 + Agent 侧守门组件抽公共 → P4 运维闭环（执行历史可视化/失败重试/告警）。详见《固定流程引擎设计文档》。
