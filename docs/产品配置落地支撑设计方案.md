# 产品配置落地支撑设计方案

> 本文融合三份权威输入，产出可落地的"产品配置"实现设计：
> - **报文规范**《产品结构化映射逻辑模型报文规范.xlsx》——六类产品模板的字段事实源（每类模板的 baseInfo/releaseInfo/optionalInfo 及组件资源节点）
> - **模板化方案**《产品配置模板化方案.md》——JSON 配置模板 Schema 与零代码扩展路线
> - **本体设计**《产商品研发助手本体设计.md》——SHACL NodeShape = 模板本体形态、模块化、R-C* 绑定、推理分档
>
> 三者关系：**报文规范给"配什么"，配置模板管"怎么配"，本体设计把模板固化为"可推理、可解释、可校验"的本体形态**。
> 本文以"落地支撑六类产品配置"为目标，给出模板 Schema 落地版、编译执行引擎、六大场景接入、接口与分阶段实施。

---

## 1. 背景与目标

### 1.1 现状

产商品研发助手当前配置链路为 `智聊对话 → 槽位抽取 → 字段推理 → 合规校验 → 表单预览 → 报文投影`。
当前字段 Schema 集中在 `ontologies/offering_config.json`（一套通用字段 + 静态品类枚举），
报文投影在 `ontology/config_message_projection.json`（六类品类的业务字段 → 报文节点路径），
合规规则在 `ontology/ops_rules.json`（R-C* 仍为 Java 实现）。

**核心断层**：`offering_config.json` 只有一套通用字段，未按"产品类型"细分；
而 `config_message_projection.json` 与 Excel 报文规范已含六类产品的**完整字段目录**，
但尚未反哺为可驱动"抽取→推理→表单→校验"的**按模板字段定义**。

### 1.2 目标

1. **以报文规范为事实源**：六类产品（personMainPrc / broadBandMainPrc / personAddPrc / broadBandOptSpeedPrc / familyBasePrc / familyAddPrc）的字段目录、元素类型、默认值/枚举、是否必填、取值口径、联动关系全部落为**产品配置模板**。
2. **零代码扩展**：新增一类产品 = 新增一份模板配置（JSON），不改 Java 与前端表单代码。
3. **本体承接**：模板经编译器固化为 `prod-spec` 的 SHACL NodeShape 与 SWRL 推导规则，校验走 SHACL、推导走 SWRL、表达归 LLM、流程归工作流。
4. **存量兼容**：`offering_config.json` 的通用字段、`config_message_projection.json` 的投影映射、R-C* 规则 ID、草稿 camelCase 契约全部复用，不造新词、不建转换层。

### 1.3 设计原则

| 原则 | 含义 |
|------|------|
| 报文即投影 | 报文节点（baseInfo/releaseInfo/…）不建 OWL 骨架，仅作为模板 `message_projection` 的投影目标 |
| 字段零转换 | 模板 `field_code` 对齐草稿 camelCase 与投影 business 字段，SHACL 属性 IRI 直接用字段名 |
| 模板为本体源 | JSON 模板为源，编译生成 NodeShape/SWRL；完整档演进为 JSON-LD（既是 JSON 又是合法 RDF） |
| 按产品类型建模 | NodeShape 不按页面建模，页面只是模板的消费视图 |

## 2. 总体架构与分层

```
                                  用户话术 / 文件 / 历史草稿
                                            │
        ┌───────────────────────────────────▼───────────────────────────────────┐
        │  执行层（运行时）                                                       │
        │  ┌──────────────┐   ┌──────────────┐   ┌──────────────┐  ┌───────────┐ │
        │  │ 抽取层        │   │ 推理层        │   │ 表达层        │  │ 合规层     │ │
        │  │ matchers命中  │ → │ derive_rules  │ → │ schema表单    │  │ SHACL校验  │ │
        │  │ prompt拼装    │   │ 默认值/联动    │   │ 报文投影      │  │ → issues  │ │
        │  └──────────────┘   └──────────────┘   └──────────────┘  └───────────┘ │
        └───────────────▲───────────────────────────────▲───────────────────────┘
                        │ 加载/继承/版本                    │ 编译注册（P2+）
        ┌───────────────┴────────────────────────────────┴──────────────────────┐
        │  编译层（构建期）                                                      │
        │  ProductTemplateRegistry（JSON 校验/继承合并/缓存）                     │
        │  TemplateToShaclCompiler（模板 → prod-spec NodeShape / SWRL 规则）      │
        └───────────────▲───────────────────────────────▲────────────────────────┘
        ┌───────────────┴───────────────────────────────┴───────────────────────┐
        │  模板层（配置源 templates/{template_id}.json，版本管理、继承）            │
        │  六类产品模板 ← 从报文规范逐字段抽取                                     │
        └────────────────────────────────────────────────────────────────────────┘
```

分档落地（对齐《产品配置模板化方案》10.3 与《本体设计》第 10 节）：

- **轻量档（P1/P2 推荐）**：JSON 模板为源，结构按本体语义设计（类/属性/约束对应映射）；`TemplateToShaclCompiler` 生成 NodeShape/SWRL；校验走 SHACL、推导走 SWRL；避免自研规则引擎。
- **完整档（P3 演进）**：模板仓库以 JSON-LD 为源，SPARQL 做类型匹配、SHACL 做合规、SWRL/SHACL rules 做推导；模板继承 = `owl:subClassOf`；与运营图谱合并。

## 3. 六类产品模板内容清单（从报文规范抽取）

以下为从报文规范每个 Sheet 抽取的**模板维度清单**，作为模板 `fields` 分组的依据。
公共节点（baseInfo 通用段 / releaseInfo / optionalInfo 通用段 / acctMonth / acctFav）跨品类复用，
品类特有节点按需挂载。

### 3.1 公共骨架（所有品类）

| 报文节点 | 字段（field_code → 报文 path） | 类型 | 必填 | 说明 |
|---------|-------------------------------|------|:---:|------|
| baseInfo | templateId → `baseInfo.templateId` | select(remote工单) | 是 | 需求管理平台工单 |
| baseInfo | prodPrcName → `baseInfo.prodPrcName` | input | 是 | 资费名称 |
| baseInfo | effRuleId → `baseInfo.effRuleId` | select(立即/预约) | 是 | 订购生效方式 |
| baseInfo | cancelRuleId → `baseInfo.cancelRuleId`（别名 expRuleId） | select(立即/预约) | 是 | 退订生效方式 |
| baseInfo | effDate → `baseInfo.effDate` | date | 是 | 销售开始，默认当前时间 |
| baseInfo | expDate → `baseInfo.expDate` | date | 是 | 销售终止，默认 20991231 |
| baseInfo | prodId → `baseInfo.prodId` | input(hidden) | 是 | 产品代码，自动生成 |
| baseInfo | prodPrcId → `baseInfo.prodPrcId` | input(hidden) | 是 | 资费代码，自动生成 |
| baseInfo | pricingId → `baseInfo.pricingId` | input(查询返回) | 是 | 拆分代码 |
| releaseInfo | chnClassLimit → `releaseInfo.chnClassLimit` | multi-select | 是 | 发布渠道（互斥校验见 §8） |
| releaseInfo | groupId → `releaseInfo.groupId` | select(全省/非全省) | 是 | 发布地市 |
| releaseInfo | groupIdMessage → `releaseInfo.groupIdMessage` | multi-select(22地市) | 是 | 发布地市明细 |
| optionalInfo | printContent.* （prcMonthFee/containResource/chargeStandard/limitCondition/otherEquity） | input | 否 | 免填单五要素 |
| optionalInfo | prcSmsCfg.opType / sysNoteNow / sysNoteNext / sysNoteCancle / sysNoteErke | 多选+input | 视子项 | 短信提醒 |
| acctMonth | calcMode / fixFee / acctItem / isSplitRate / splitRate9 / splitRate6 / fixValidity / fixValidityVAlue | 混合 | 是 | 月租计费 |
| acctFav | favCondition / favItemType / favGroup / favType / favDiscount / favFee / favValidity / favValidityVAlue / favDesc | 混合 | 是 | 账务优惠 |

### 3.2 品类特有节点

| 品类 | 特有 baseInfo 字段 | 特有可选/组件节点 |
|------|------------------|------------------|
| **personMainPrc** 个人主资费 | 无（主资费精简） | `dlowFavFee`(保底：fav1Method/fav1Fee/fav1ItemType/fav1Group/fav1Validity/fav1ValidityVAlue)；`billGprsCfg`(resourceType/theshold/unit/sid/adjust/carryFlag/outChargeMode/remindFlag)；`billVoiceCfg`(resourceType/theshold/adjust/outCharge/remindFlag)；`billSmsCfg`(resourceType/theshold/adjust/outCharge/remindFlag)；`SmsInstCfg`(SvcName/SmsInst/SmsContent/SmsCity/AccessNO/ProdPrcType/ProdPrcid) |
| **broadBandMainPrc** 宽带主资费 | domainName/downStreamId/upStreamId/ifAddFamily | 无组件资源；`wkBillCfg`(wkBillFlag 话单优惠，默认是) |
| **personAddPrc** 个人附加资费 | prcEffCycle/Type/Num/Date、effNum、planFlag、5GUser、unifiedQryCancle、reFeeFlag | `dlowFavFee`；`billGprsCfg`(+location/locationCodes/periodUnit/period/sid)；`billVoiceCfg`；`billSmsCfg`；`SmsInstCfg`；acctMonth.fixCircle |
| **broadBandOptSpeedPrc** 宽带加速包 | prcEffCycle/Type/Num/Date、downStreamId、upStreamId | 无组件资源、无保底、无话单优惠 |
| **familyBasePrc** 家庭基础套餐 | teamType/ifFloorsPrc/payFlag/dateLimit/powerCode/familyCata/roleMax/roleMin/canAddFamilyPrc | `phoneMbrInfo`(ifChangeBasePrc/inProdPrcId/outProdPrcId/phoneMbrMax/phoneMbrMin/freeMbrCnt/phoneMbrFee)；`broadBandMbrInfo`(kdMbrMax/kdMbrMin/mainKd/tvPrc/sencondKdPrc/thirdKdPrc)；acctFav.favObject；`dlowFavFee`；`billGprsCfg`；`billVoiceCfg` |
| **familyAddPrc** 家庭附加业务 | prodType/prcEffCycle/Type/Num/Date/effNum/reFeeFlag/canBaseFamilyPrc/familyUpIfEnd/chgYueIfCanDown/chgYue | `equityContent`(kdEquity/tvEquity)；acctMonth.fixCircle；`billGprsCfg`；`billVoiceCfg` |

### 3.3 字段三分类（模板内标注）

| 分类 | 用途 | 示例 |
|------|------|------|
| `draft` 草稿业务字段 | 智聊/智读抽取与推理目标 | prodPrcName/categoryCode/monthlyFee |
| `projection` 报文投影字段 | 投影到报文节点路径 | fixFee→acctMonth.fixFee |
| `readonly` 查询返回字段 | 智查/回显（拆分代码、附件条件等） | pricingId/prodPrc/subBillPrcIds/conditionCode |

> 报文规范中"查询返回字段"（拆分资费代码 prodPrc、二批代码 billPrcId、子记账资费 subBillPrcIds、附件条件ID conditionCode、子附件条件ID subConditionCodes）标注为 `readonly`，仅在智查/回显时返回，不作为抽取目标。

## 4. 产品配置模板 Schema（落地版）

模板文件存于 `backend-app/src/main/resources/ontologies/templates/{template_id}.json`，元数据 snake_case，`field_code` 沿用草稿 camelCase 契约。基于《模板化方案》4.x 扩展报文规范语义。

### 4.1 模板整体结构

```json
{
  "template_id": "familyBasePrc",
  "template_name": "家庭基础套餐",
  "version": "1.0.0",
  "extends": null,
  "status": "published",
  "category_code": "familyBasePrc",
  "message_root_key": "familyBasePrc",
  "matchers": {},
  "sections": [],
  "fields": [],
  "derive_rules": [],
  "compliance_bindings": {},
  "message_projection": {}
}
```

| 字段 | 说明 |
|------|------|
| `category_code` / `message_root_key` | 对齐 `config_message_projection.json`、`offering_config.json` 品类码；根键默认=品类码 |
| `sections` | 报文/表单分组（baseInfo/releaseInfo/optionalInfo/acctMonth/acctFav/billGprsCfg/…），驱动表单 Tab 与投影分组 |

### 4.2 sections（分组/报文节点）

```json
{
  "sections": [
    { "code": "baseInfo",     "label": "基础信息",   "message_path": "baseInfo" },
    { "code": "releaseInfo",  "label": "发布信息",   "message_path": "releaseInfo" },
    { "code": "optionalInfo", "label": "可选配置",   "message_path": "optionalInfo" },
    { "code": "acctMonth",    "label": "月租",       "message_path": "optionalInfo.acctMonth" },
    { "code": "acctFav",      "label": "账务优惠",   "message_path": "optionalInfo.acctFav" },
    { "code": "billGprsCfg",  "label": "流量资源配置", "message_path": "optionalInfo.billGprsCfg", "component": true }
  ]
}
```

`component: true` 标识**组件资源节点**（billGprsCfg/billVoiceCfg/billSmsCfg/SmsInstCfg/equityContent），
其下字段以"列表/子对象"方式建模，对应本体 `comprisesComponent` 关系。

### 4.3 field 定义（扩展版）

```json
{
  "field_code": "fixFee",
  "label": "套餐固定费（元）",
  "type": "number",
  "required": true,
  "unit": "元",
  "section": "acctMonth",
  "field_class": "projection",
  "precision": 2,
  "decimal_places": 2,
  "default_value": null,
  "slot_aliases": ["月费", "固费", "套餐费"],
  "extract_hint": "小数最多2位，默认单位元",
  "enum_config": null,
  "visible_when": null,
  "source": "dict",                    // 可选: fs(工单)/dict(码表)/remote(账务后台)/generated(自动生成)/hidden
  "message_path": "optionalInfo.acctMonth.fixFee",
  "rule_description": "提示：小数点后2位，校验最多2位小数"
}
```

| 扩展字段 | 说明（吸收报文规范列） |
|---------|----------------------|
| `section` | 归属分组（对应报文节点） |
| `field_class` | `draft` / `projection` / `readonly`（§3.3） |
| `precision` / `decimal_places` | 数值精度校验（报文"最多2位小数/4位小数/正整数"口径） |
| `source` | 取值来源：`fs`(需求平台工单下拉)、`dict`(码表下拉)、`remote`(账务科目/SID/小区弹窗)、`generated`(代码自动生成)、`hidden`(隐藏元素)；`remote` 对应 OWL 对象属性远程概念查询 |
| `enum_config` | 复用模板化方案：`static`(静态枚举，解析为 `owl:oneOf`/SKOS) / `remote`(远程字典/码表)；
   当枚举带"后台传输数字/展示中文"语义时，`enum_config.enum_map` 记录 显示值↔传输值（如 adjust/calcMode 报文规范）
| `message_path` | 报文投影目标（可直接衔接 `config_message_projection` 的 path） |

### 4.4 枚举默认值映射示例（吸收报文规范"默认值（枚举值）"列）

```json
{
  "field_code": "calcMode",
  "label": "收费方式",
  "type": "select",
  "required": true,
  "section": "acctMonth",
  "field_class": "projection",
  "source": "dict",
  "default_value": "首月全额收取，次月按月收取",
  "message_path": "optionalInfo.acctMonth.calcMode",
  "enum_config": {
    "type": "static",
    "enum_map": [
      { "display": "首月免费，次月按月收取",             "value": "2" },
      { "display": "首月按天折算，一次性收取，次月按月收取", "value": "a" },
      { "display": "首月区分上下半月，次月按月收取",       "value": "1" },
      { "display": "首月全额收取，次月按月收取",         "value": "R" }
    ]
  }
}
```

**enum_map 值域契约（抽取/草稿/投影三层约定）**：

1. **抽取与草稿统一存显示值**（display）——保证 LLM 抽取、表单回显与用户可见口径一致；
2. **报文投影时翻译为传输值**（value）——投影层按 `enum_config.enum_map` 做 display→value 映射，承接于 `ConfigMessageProjector` 现有通道，投影 JSON 契约不变；
3. **无 `enum_map` 的字段视为 display=value**（零转换透传）；
4. **合规/轻量约束校验一律按显示值域执行**——避免显示值/传输值双值域校验歧义。

### 4.5 derive_rules（默认值/联动，吸收报文规范"元素说明"联动）

报文规范含大量**联动/连带**语义（"是否5G资费选择是才展示"、"账务月租收费方式连带默认调整"、"月租有效期非长期时展示值"），
落为 `derive_rules`：

```json
{
  "derive_rules": [
    { "when": { "planFlag": "是" },         "visible": ["5GUser"] },
    { "when": { "favItemType": "指定科目" }, "visible": ["favGroup"] },
    { "when": { "favType": "送费" },        "visible": ["favFee"],   "hidden": ["favDiscount"] },
    { "when": { "favType": "打折" },        "visible": ["favDiscount"], "hidden": ["favFee"] },
    { "when": { "prcEffCycle": "长期有效" }, "hidden": ["prcEffType", "prcEffNum", "prcEffDate"] },
    { "when": { "calcMode": "多月收取" },     "visible": ["fixCircle"] },
    { "set_default": { "expDate": "20991231" },   "if_missing": true },
    { "set_default": { "channelScope": "全渠道" }, "if_missing": true },
    { "derive": { "fixValidityVAlue": "一期后自动隐藏" }, "when": { "fixValidity": "长期有效" } }
  ]
}
```

> **联动语义三级承载**：显隐(`visible`/`hidden`) 归模板渲染；连带默认值（如 adjust 随 calcMode）归 `derive_rules`；
> 数值派生（如 splitRate6 = 1 - splitRate9，月费=组件费用和）归 SHACL 高级规则/Java（对齐《本体设计》§6 数值聚合边界）。

## 5. 从报文规范到本体的映射

对齐《本体设计》§4/§5/§6，把模板字段目录映射为 `prod-spec` SHACL NodeShape 与 SWRL：

| 报文/模板概念 | 本体构造 | 落地说明 |
|--------------|---------|---------|
| 模板 `extends` 继承 | `owl:subClassOf` | 如 broadbandOptSpeedPrc/broadBandMainPrc 承继其同构段，裁剪由子 NodeShape 收紧 |
| `fields`（baseInfo/releaseInfo/acctMonth/acctFav 等） | OWL 数据属性 + 基数约束 | 属性 IRI=field_code；`required`→`sh:minCount 1` |
| `enum_config` 静态枚举 | `sh:in` / `owl:oneOf`、品类/用户/渠道入 SKOS | 品类码原样挂 SKOS 词表，三方同源 |
| `source=remote`（科目/SID/小区） | 对象属性 + 概念查询 | 远程概念由账务后台/码表供给，编译为对象属性指向概念类 |
| `derive_rules` 默认值/联动 | SWRL 规则 | `FamilyBaseOffering(?x) ∧ planFlag(?x,"是") → hasFiveGSpeed(?x, …)` |
| 数值聚合（月费=组件和、splitRate6=1-splitRate9） | SHACL 高级规则(SPARQL CONSTRUCT)/Java | SWRL 不支持聚合，明确划归此处 |
| R-C* 合规规则 | SHACL 约束（minCount/in/not/maxLength/…） | 校验报告 `focusNode/path/message` 映射为 issues(ruleId/field/level/message) |
| `message_projection` | 本体→报文投影（R2RML 风格） | messageRootKey 映射即属性级映射配置 |

### 5.1 prod-spec NodeShape 示例（familyBasePrc 片段）

```turtle
@prefix prod: <http://sitech.ai/ontology/product#> .
@prefix sh:   <http://www.w3.org/ns/shacl#> .
@prefix xsd:  <http://www.w3.org/2001/XMLSchema#> .

prod:FamilyBaseShape a sh:NodeShape ;
  sh:targetClass prod:FamilyBaseOffering ;
  sh:property [ sh:path prod:prodPrcName ; sh:minCount 1 ; sh:maxLength 60 ] ;
  sh:property [ sh:path prod:teamType ; sh:in ( "全家福" "F套餐" ) ] ;
  sh:property [ sh:path prod:ifFloorsPrc ; sh:in ( "是" "否" ) ] ;
  sh:property [ sh:path prod:payFlag ; sh:in ( "是" "否" ) ] ;
  sh:property [ sh:path prod:roleMax ; sh:datatype xsd:integer ; sh:minInclusive 1 ; sh:maxInclusive 9 ] ;
  sh:property [ sh:path prod:roleMin ; sh:datatype xsd:integer ; sh:minInclusive 1 ; sh:maxInclusive 9 ] ;
  sh:property [  # 手机+宽带成员数封闭（roleMax = phoneMbrMax + kdMbrMax）
    sh:path prod:roleMax ;
    sh:equals prod:phoneMbrMax ;
  ] .
```

## 6. 编译与执行引擎实现

### 6.1 ProductTemplateRegistry

- 加载 `ontologies/templates/*.json`，执行《模板化方案》§4.7 校验（template_id 唯一、field_code 唯一、few_shot 键存在、derive_rules 引用字段存在、compliance_bindings.rule_ids 已注册、extends 无环）。
- 继承合并：`extends` 父模板字段按 `field_code` 合并，子模板覆盖同名项；NodeShape 继承合并由推理机完成。
- 版本缓存 + `findByCategory` / `findByType` / `list`。
- 增量注册：新增产品只落地模板文件，Registry 热加载（对齐 B2 验收"新增产品零代码完成本体注册与校验"）。

### 6.2 TemplateToShaclCompiler

- 输入：模板 JSON；输出：`prod-spec` NodeShape(turtle) + SWRL 规则(SWRL 附录)。
- 规则：`required`→minCount；`enum_config.static`→sh:in；数值约束→min/max/exclusive/pattern；`visible_when`/互斥→sh:not/sh:property 组合；`section.component`→qualifiedValueShape(类)。
- 与 R-C* 对接：SHACL 校验报告逐条映射 issues（ruleId 取模板 R-C 绑定 + 断言类型推断）。

### 6.3 执行链路改造点（对齐《模板化方案》§5）

| # | 环节 | 现状文件 | 改造 | 量级 |
|---|------|---------|------|------|

## 10. 分阶段实施与验收

| 阶段 | 内容 | 验收标准 |
|------|------|---------|

### 10.1 风险与应对

| 风险 | 应对 |
|------|------|
| 家庭行为回归 | 模板平移"先并存后切换"：derive_rules 引擎 vs 存量 Java 分支灰度对比 |
| 报文契约破坏 | field_code/投影映射不改名；P1 阶段 message_projection 仅观察不接管 |

## 11. 可行性评估（对现状代码库逐点核验）

> 本节基于当前后端源码（`ProductOntologyService`/`ConfigMessageProjector`/`OpsExtractionService`/`OpsSwrlReasoner`/`Rdf4jOntologyStore`/`OpsRulesService`）、`pom.xml`、前端 `productMockData.js` 逐点核验，给出可行档位与改造量级。档位：🟢 高可行 / 🟡 需改造 / 🔴 需补依赖或降档。

### 11.1 投影片已模板化（重大利好，🟢）

- `ConfigMessageProjector.java` 读 `ontology/config_message_projection.json`，已含**全部 6 类品类**（categories + sharedMappings + categoryMappings + defaultsByCategory），与 Excel 报文规范 baseInfo/releaseInfo/acctMonth/billGprs/billVoice/billSms/equityContent 等一一对应。
- 已提供 `toMessage`（业务→报文）/`fromMessage`（报文→业务）/`applyCategoryDefaults`。
- **结论**：投影层无需大改，本方案的模板 `message_projection` 只需与现有 JSON **对齐**，不新增引擎。唯 `resolveMessageRootKey` 按 家庭/宽带/附加 启发式判定为**半硬编码**，接入新品类时需在模板中显式声明 messageRootKey。

### 11.2 抽取层硬编码严重（🟡，改造点 3 量级应上调）

- `OpsExtractionService.extractSlots`：固定 `SLOT_KEYS`（约 17 字段）+ 硬编码 LLM prompt（含固定字段清单 + 场景规则 家庭融合/校园/5G）+ `parseSlotsByRegex` 约 20 个硬编码正则。
- `ops_rules.json` 已外置 `extractionTriggers`（clearBindTriggers/bindTriggers），可复用，但字段清单与 prompt 仍硬编码。
- **结论**：模板化需同步三件事——prompt 动态拼装（按 field_class）+ 正则通用化（改为模板驱动正则可配置）+ SLOT_KEYS 动态化。可行但**非小改**，建议 P2 单独一批，纳入回归（家庭融合行为不得漂移）。

### 11.3 推理层 derive_rules 可平移但需回归（🟡）

- `ProductOntologyService.inferFields`：场景分支硬编码（`家庭融合`、校园 R-C02、addon 判 familyAddPrc），按 R-C* 门控补默认值——与方案 derive_rules 的语义**高度对应**，可平移。
- **风险**：家庭行为回归最高风险点。同 10.1，须"先并存后切换"灰度对比。
- 默认值已部分外置到 `OPSRulesService.configDefault*`（includeBroadband/campusMonthlyFee/channelScope/mutexGroup/monthlyFeeMin~max），模板 derives 可沿用同一取值通道，天然一致。

### 11.4 SHACL 校验：当前无引擎，需降档（🔴 最大 gap）

- `pom.xml` 已声明 RDF4J 4.3.4 + OWLAPI 5.1.20 + Openllet 2.6.5，但**无任何 SHACL 依赖**；全库 SHACL 零命中。
- 现合规引擎是 **Java 硬编码**：`checkComplianceSmart/checkCompliance` 中 R-C01~C09、R-D01~D05 全部 `issues.add(issue("R-Cxx",...))` 写死（R-C06=必填列表、R-C03=资费/关系冲突、R-C04=附加依赖、R-C05=零元高风险、R-C07=折扣100%+可重复、R-C09=资费区间），阈值读 ops_rules configDefault。
- **结论（关键调整）**：《本体设计》主张"校验走 SHACL NodeShape"当前**不可直接落地**。建议：
  - **P1/P2 务实档**：JSON 模板为唯一事实源 + 合规**继续走现有 Java R-C\***，用 `compliance_bindings`（模板声明哪些 R-C 规则适用/裁剪该品类）做规则裁剪；新增字段校验用轻量 Java 约束（必填/枚举/数值区间，直接从模板 field_class 生成）。
  - **P3 演进档**：引入 topbraid-rdf4j（`rdf4j-shacl`）或自研轻量 SHACL 校验器，`TemplateToShaclCompiler` 产出 NodeShape，与 Java 报告**等价对比**通过后再接管。

### 11.5 持久化：草稿走 JPA JSON，发布走 RDF4J 子集 ABox（🟡 B3 改造量明确）

- **草稿（draft）**：`saveConfigDraft` 将完整草稿 JSON 序列化进 `OntologyInstance.data[DRAFT_JSON_KEY]`（**JPA `@ElementCollection` 存 Map<String,String>**，非 RDF4J），`readDraftJson` 反序列化回 - 即 `OntologyInstance` **是草稿 JSON 载体而非 ABox**。
- **发布（publish）**：`publishConfigDraft` 先把 draft 沉淀为 `graphCache` 内存 `shelfOfferings`/`configSchemes` 行，再向 RDF4J `addInstance(uri, "ConfigScheme", facts)` **写入子集 facts**（schemeId/workOrderId/status/version/messageRootKey/categoryCode/fixedFeeAmount/channelScope/appliesScene/similarTo），**不含完整字段**。
- **结论**：B3「草稿 ABox 入 RDF」属**新增行为**而非改造既有——需为 publish/config 的 ABox 实例**扩列到完整字段**（或链 fullDraft），并补充 SWRL/SPARQL 联通。改造量中等、边界清晰；不影响既有 JPA 草稿闭环。

### 11.6 SWRL 推理真实可用但为硬编码、仅覆盖运营侧（🟡）

- `OpsSwrlReasoner` 用 Openllet 真推理，但规则是 Java 程序化构造（buildRa01DeltaRule 等），仅覆盖 R-A01~A05/R-B01~B05，**非数据驱动、不覆盖配置侧默认值推导**；`isSwrlEnabled()` 可开关，失败回退 Java。
- **结论**：SWRL 可作为配置侧推导的可选增强（把 derive_rules 部分编译为 SWRL），但不要依赖它做聚合/跨实例联动（SWRL 弱项，划给 Java/SHACL，同 10.1）。

### 11.7 翻译层/接口已完备（🟢 利好）

- 后端已有 5 个 RD AgentTool + `AgentOrchestrator.scene:"rd"` 分流 + `ToolOutputRenderer` 结构化输出，方案"6 大场景接入"可**复用现成工具**。
- `ProductOntologyController` 已有完整 CRUD（infer/compliance/chat/batch/discover/copy-as-draft/upload/publish/drafts/submit/compare/trace/explain）；**仅缺 `GET /config/template/{category}`**（本方案新增）。
- `ProductTemplateRegistry` 尚不存在，需新建（P1 第一项）。`TemplateToShaclCompiler` 在务实档简化为"模板→轻量约束元数据"。

### 11.8 前端表单：需消费后端动态 schema（🟡）

- `frontend/src/data/productMockData.js` 的 `createOfferingFormSchema` 是**硬编码单套 schema**（内嵌 6 类 categoryCode 下拉），未消费 `GET /config/template/`；`useProductConfig.js` 的 `buildProductFormCard`/`syncFormFromProduct` 驱动面板。
- **结论**：改造点 8 为真实必要改造——前端 `buildProductFormCard` 改为按所选 categoryCode 拉取模板 schema 渲染；保留降级为本地 mock（模板接口未就绪时）。发布渠道 checkbox（不可前端校验）与发布地市数量展示问题按方案移提交期校验。

### 11.9 可行性结论与调用建议

| 模块 | 档位 | 建议 |
|------|------|------|
| 投影层 message_projection | 🟢 | 仅对齐，不新增引擎 |
| 模板仓库 ProductTemplateRegistry + `GET /config/template` | 🟢 | P1 优先实现 |
| 抽取模板化（SLOT_KEYS/prompt/正则） | 🟡 | P2，纳入家庭回归 |
| derive_rules 平移 inferFields | 🟡 | P2，先并存后切换 |
| **合规校验 SHACL** | 🔴 | **降档**：P1/P2 走 Java R-C\* + compliance_bindings + 轻量约束；P3 引入 SHACL 等价接管 |
| 草稿 ABox 入 RDF（B3） | 🟡 | 新增行为，发布时 ABox 扩列 + SPARQL 联通 |
| SWRL 配置侧推导 | 🟡 | 可选增强，不强依赖 |
| 前端 schema 消费 | 🟡 | 改造点 8，模板未就绪降级 mock |
| translate 工具/接口 | 🟢 | 复用现成，仅新增 template 端点 |

**总体判断**：方案**总体可行**，但应把《本体设计》的 **"SHACL 为默认校验引擎"调整为准入原则的"Java 合规 + compliance_bindings 绑定 + 轻量约束"务实档**（SHACL 降为 P3 演进）。投影层与翻译层高可行可先行；抽取/推理硬编码是主要改造量，需严格回归。B3 ABox 化属新增，边界清晰。

## 12. 本体运维推演（同步纳入落地闭环）

> §3~§11 解决的是"**模板/本体怎么造、怎么被消费**"。本节补上另一半：**上线后怎么运维**——版本、发布审核、灰度、回滚、监控、升级兼容、死代码清理。核验现状后发现本体运维是当前**最薄弱**环节，且存在**现成可循但未接线**的设施。下面逐点给出档位与改造建议。

### 12.1 本体运维现状核验（对当前代码库）

**关键结论：本体运维能力近乎空白，且部分为"假阳性"（stub）。**

| 运维能力 | 现状核验 | 结论 |
|----------|---------|------|
| 本体 CRUD | `OntologyService.createOntology/deleteOntology` 等返回**硬编码 success**（`deleteOntology` 还伪造 backup id）；`AdminController /api/v1/ontologies*` 5 个端点接的就是这些 stub | 🔴 假阳性，无持久化、无版本 |
| 版本管理/回滚 | **无任何 ontology 版本表**；`数据库设计文档`无该表；`运营助手能力矩阵`已将"规则落盘与多版本/回滚发布"列为**缺口** | 🔴 缺失 |
| 实例历史 | `OntologyInstanceHistory` 实体+仓库**是死代码**（无任何 service/controller 引用） | 🔴 死代码，需接线或清理 |
| 热重载 | `reloadGraph`/`reloadOpsRules`/`ConfigLoader.reloadConfig` 全部**内存重读**，不落盘、不记版本 | 🟡 有入口无治理 |
| 运行时守卫 | 仅启动期 `OntologyDemoGuard` fail-fast + 查询层回退；**无 last-known-good 快照**——热重载失败直接抛异常，不回退上一可用版本 | 🟡 需补快照 |
| 监控/审计 | 审计日志/规则覆盖均为**内存 last-50**，重启即失；`HealthController` 纯信息展示 | 🟡 无持久化监控 |
| 双世界并存 | 活跃实为 `ProductOntologyService + Rdf4jOntologyStore + ops 服务`；`OntologyService` 的 admin CRUD 是**未接线的另一套** | 🔴 语义混乱，需收敛 |

### 12.2 运维与落地方案的耦合点

模板化落地（P1~P3）**天然放大本体运维负担**：研发自助"新增产品类型"若无运维护栏，会把"改一个模板 JSON"升级为生产事故。因此运维能力必须**与模板仓库伴生上线**，而非事后补：

1. **模板 = 新的运维对象**：六个品类模板 + `ProductTemplateRegistry` 生命周成本身就是新增运维面（draft/review/publish/deprecated/rollback）。
2. **ABox 扩列（B3）放大数据面**：发布时向 RDF4J 写入完整字段后，图谱数据量、SPARQL 联查、swrl 推理全受影响，需可观测。
3. **compliance_bindings 裁剪规则**：模板声明"该品类用哪些 R-C\*"——错了就是前端校验盲区或误拦，需能审计。
4. **回归护栏**：家庭/校园行为"先并存后切换"需要运行时可对比的基线与回退点（见 12.4 灰度）。

### 12.3 构建"实体化版本库"（解决最大缺口）

**建议新建轻量的 `ontology_version` 治理面，替代/收敛现有死代码 stub：**

- **载体**：新增 JPA 实体 `OntologyVersion`（代码/类型/版本号 semver/作者/状态 draft|review|published|deprecated/变更摘要/createdAt/migratedAt），配套唯一索引（code, version）。**迁移现有 `OntologyInstanceHistory` 死代码为本表动作日志**：把 `action/instanceId/createdAt` 并入 `OntologyVersionLog`，使历史表真正生效（"接线而非新造"）。
- **纳入对象**：模板文件、`config_message_projection.json`、`ops_rules.json`、`product-config.ttl`、抽象 ABox 快照——**凡注册进 `ProductTemplateRegistry` 或供给 `checkCompliance` 配置面的资源，都登记一个版本行**。
- **发布审核**：模板 `draft→review→published` 与本体版本状态机绑定；`POST /config/template/{id}/publish` 除编译 NodeShape 外，**同步登记版本行 + 写入变更摘要**（呼应 §9.3 模板管理 P3）。
- **回滚**：`POST /config/template/{id}/rollback?to={version}`——从版本库取目标版本资源，重载入 `ProductTemplateRegistry` + `graphCache`，并记 rollback 日志。**这直接补上"规则落盘与多版本/回滚发布"缺口，落地为空闲演示即可自证。**

### 12.4 运行时守卫升级：last-known-good 快照（补当前缺失）

当前热重载失败即异常、无回退——对"生产上新模板"是**不可接受的**。建议：

- `ProductOntologyService` 维护 **last-known-good 快照**（成功加载并过 `checkCompliance` 冒烟的最后一套模板/规则缓存副本，内存 + 可选序列化到 `ontology_version`）。
- 热重载（`reloadGraph`/`reloadOpsRules`/模板 publish/dryrun→publish）执行**加载→校验→冒烟**三步；任一步失败则**保留上一可用快照并拒绝切换**，返回 `success:false` + 差异报告，而非抛异常。
- dryrun（§9.3 sandbox）即为"不切换只试跑"的天然载体，与 last-known-good 配合形成完整安全发布路径。

### 12.5 灰度与回归护栏（对齐 §10.1）

- "先并存后切换"不只靠代码分支，**要在版本库记录并存窗口**：`status=published`（新模板）与回退指针（旧基线）并存，`derive_rules` 引擎输出与存量 Java `inferFields` 结果做 **diff 报告**（字段级），供评审确认后再下架旧基线。
- **回归基线固化**：把 家庭融合/校园/5G 的典型用例固化为**自动回归用例**（模板版本 + 期望字段 + 期望 R-C\* 命中），随模板 publish 触发，失败即阻断发布——这也是 P1"家庭行为回归不变"验收的工程化落地。

### 12.6 监控与可观测（补持久化缺口）

- 现有审计/规则覆盖均为**内存 last-50**，重启即失。建议将 `configTraces`、`riskRuleAuditLog`、`lastBatchAudit` **落盘到 `ontology_version` 配套日志表**（trace_id 外键），使"为什么这么判/谁改过阈值"可回溯。
- `HealthController /health` 增补：`lastTemplateDeployTime`、`activeVersion`、`graphVersion`（来源 `ontology_version` 最新 published）、模板总数/已发布数、ABox 实例数——把"本体健康"从纯信息变成可巡检信号。
- 合规裁剪（compliance_bindings）命中情况、抽取 diff 率、publish 频次作为**变更面指标**，接入现有 ops 监控（`/ops/alerts` 机制）告警。

### 12.7 收敛"双世界"：接线 or 清理（去旧留新）

依《AGENTS.md 去旧留新原则》：
- `OntologyService` 的 `createOntology/updateOntology/deleteOntology/toggleActive` 五个 **stub** 当前污染语义（前端若调用会误以为已落库）。建议：**接线到新版本库**（`OntologyVersion`）使其真实生效，或**加 `@Deprecated` 并标注替代**后由模板仓库接管。
- `OntologyInstanceHistory` / `OntologyInstanceService`（空文件）/ `OntologyInstanceController`（空文件）为**死代码**：**清理**（删除）或**接线**（本表 → 版本库动作日志，见 12.3）。避免"留着一套假实现"误导后续开发。

### 12.8 运维推演结论与分档

| 运维面 | 档位 | 建议 |
|--------|------|------|
| 实体化版本库（OntologyVersion + 日志） | 🔴→🟢 | 新建轻量表，**接线**现死代码 history 表，补规则回滚缺口 |
| last-known-good 快照 + 冒烟 | 🟡 | 热重载失败不抛异常，保留上一可用；与 dryrun 配合 |
| 模板生命周本（draft/review/publish/deprecated/rollback） | 🟡 | 伴生 P3 模板管理，登记版本行 |
| 灰度/回归基线固化 | 🟡 | 字段级 diff + 自动回归用例随 publish 触发 |
| 监控/审计持久化 + 健康增强 | 🟡 | 审计落盘、/health 带版本信号、变更指标告警 |
| 双世界收敛（stub 接线/清理） | 🟡 | 接线或 @Deprecated 清理，去旧留新 |

**总体判断**：本方案落地可行性（§11）与**本体运维能力（§12 现状近乎空白）之间严重不匹配**——"零代码新增产品"若没有版本/回滚/守卫，运维风险将随自助化放大。**建议把运维治理纳为与模板仓库伴生的前提里程碑**（§12.3~12.4 至少 P1 落地：实体版本库 + last-known-good 守卫），而非拖到 P3；否则 P2"零代码完成本体注册"上线即埋雷。SHACL 降档（§11.9）+ 运维护栏补齐后，方案可在**既有工程约束下稳步闭环**。具体表结构与挂点见 **§13**。

## 13. 运维落地具体设计（§12 的工程化细化）

> 本节把 §12 的运维结论落到**可实现的表结构、代码挂点、状态机与回归边界**，并逐点指明"改哪、怎么改、影响哪些既有行为"。核验参照：`OpsWorkOrder` 实体风格（snake_case 列、TEXT 存 JSON）、`product_graphCache/riskRuleOverrides/riskRuleAuditLog/configTraces` 等**内存态结构**、`Rdf4jOntologyStore.getGraphData()/clear()` 快照钩子。

### 13.1 实体化版本库：表结构设计

沿用 `OpsWorkOrder` 的 JPA 约定（snake_case、TEXT columnDefinition 存 JSON）。**新建两张表**，并将 `OntologyInstanceHistory`（当前死代码）**接线为第二张表的动作日志**。

**表 A：`pd_ai_ontology_version`（版本主表）**

| 列 | 类型 | 说明 |
|----|------|------|
| id | BIGINT PK | 自增 |
| asset_type | VARCHAR(32) | template / message_projection / ops_rules / ttl / abox_snapshot |
| asset_code | VARCHAR(64) | 资源标识（模板 id / 文件路径 / 品类 code） |
| version | VARCHAR(32) | semver |
| status | VARCHAR(16) | draft / review / published / deprecated |
| author | VARCHAR(64) | 操作人 |
| summary | TEXT | 变更摘要 |
| payload | TEXT | **源码 JSON**（模板全文 / 规则全文 / 投影全文 / TTL） |
| created_at / published_at / deprecated_at | TIMESTAMP | 生命周期 |
| → 唯一索引 (asset_type, asset_code, version) | | 幂等登记 |

- **payload 存资源全文**是回滚的唯一事实源：`rollback` 只需取目标版本 payload 重载，无需依赖外部文件当前态。
- **跨资源引用**：模板 payload 内含它的 `compliance_bindings`/`derive_rules`/`message_projection`，使"这一版模板对应哪些校验/推导/投影"可整体回放。

**表 B：`pd_ai_ontology_version_log`（动作日志，接线现死代码 `OntologyInstanceHistory`）**

| 列 | 类型 |
|----|------|
| id BIGINT PK / version_id BIGINT(外键 A) / action VARCHAR(32) | publish / rollback / deprecate / reload / override |
| operator VARCHAR(64) / detail TEXT(JSON) / created_at TIMESTAMP | |

> 实施：`OntologyInstanceHistory` 现仅有 `id/instanceId/action/createdAt` 且**无处引用**。将其改造成 `OntologyVersionLog`（列收敛为 version_id/action/operator/detail/created_at），替换 `ProductOntologyService` 里 `appendRiskRuleAudit/snapshotRiskRuleAudit`、`configTraces`、`lastBatchAudit` 的**内存承载为落盘**——"接线而非新造"，一次性清掉死代码并补上持久化监控双缺口（§12.6）。

### 13.2 last-known-good 快照守卫（挂点已定位）

现有 hook（`ProductOntologyService#reloadGraph` L154、`reloadOpsRules` L185、`publishConfigDraft` L1259、`loadGraph` L160）是守卫挂点。设计：

```
enum Phase { LOAD, VALIDATE, SMOKE }
switchVersion(assetType, newPayload):
  1. LOAD    : 解析 newPayload → 暂存 pending（不覆盖现行）
  2. VALIDATE: 复用 OpsGraphSchemaValidator.validateAndNormalize + 模板注册校验
  3. SMOKE   : 用 pending 跑典型用例（家庭/校园基线断言，见 13.4）
  4. COMMIT  : 全过 → 存 snapshot(last-known-good = 当前版本) → 切换生效
            任一步失败 → 抛"版本校验失败"返回 success:false，**保留现行版本**
```

- **内存快照**：`graphCache` 本身就是"上一可用图谱"，热重载失败时不置空即天然回退；仅需把重载改为**先校验后提交**（当前 `reloadGraph` 是 `graphCache=null; loadGraph()`，失败即空，需改为事务式）。
- **持久快照**：发布成功/失败都登记版本行（表 A + 表 B），失败行留 review 态供复盘。
- 配合 `Rdf4jOntologyStore.getGraphData()/clear()`：如需 ABox 回退，取 last-known-good 版本 payload 重建。

### 13.3 模板生命周期状态机（衔接 §9.3）

```
                    publish(dryrun通过)
 draft ──review──► review ────────────────► published
   ▲                  │   rollback(家庭回归失败)      │  deprecate / 下架
   │                  └─────────────────────────────┴──► deprecated
   └────────────── 编辑新 draft（版本号++）◄─────────────┘
```

- 状态流转**落在表 A 的 status**，`ProductTemplateRegistry` 只认 `published`。
- `POST /config/template/{id}/publish`：dryrun（§9.3 sandbox）→ 表 A 登记 published + 提交表 B → last-known-good 交换（13.2）。
- `POST /config/template/{id}/rollback?to={version}`：取表 A 目标版本 payload → 13.2 守卫三步 → 成功后记 rollback 日志。
- **并存窗口**：rollback 前旧基线保持 `published`，新版本进 `review`，灰度对比通过再切换（§12.5）。

### 13.4 回归基线与发布门禁（对齐 §10.1/P1 A/R）

- 固化 `familyBasePrc`/`broadBandMainPrc`/校园/5G 的**回归用例集**：每条 = {模板版本, 输入 draft, 期望推导字段, 期望 R-C\* 命中, 期望报文节点}。
- 13.2 的 SMOKE 阶段**自动执行**该集合；任一断言失败 → 阻断 publish/switch。
- derive_rules 引擎输出 vs 存量 Java `inferFields` 做**字段级 diff 报告**，随发布落表 B detail，供评审。
- 这让"家庭行为回归不变"从人工验收变为**随发布自动拦截**。

### 13.5 双世界收敛：接线 or 清理（去旧留新）

| 现状 | 处置 |
|------|------|
| `OntologyService.createOntology/updateOntology/deleteOntology/toggleActive`（stub 假成功） | **接线到表 A**：create=登记 draft 版本，delete=置 deprecated（保留历史），toggleActive=切 published/deprecated；`AdminController /api/v1/ontologies*` 恢复真实语义 |
| `OntologyService.listOntologies/getOntology`（硬编码两项） | 改为查表 A 聚合（按 asset_code 最新 published） |
| `OntologyInstanceHistory` 死代码 | 改造为 `OntologyVersionLog`（13.1 表 B），一次性接线 |
| `OntologyInstanceService`/`OntologyInstanceController`（空文件） | **删除**（无内容），避免占位误导 |
| 热重载 `reloadGraph/reloadOpsRules` | 改为 13.2 事务式，登记版本行 |

### 13.6 监控/健康增强（§12.6 落地）

- `HealthController /health` 的 ontology 块增补：`graphVersion`/`rulesVersion`（表 A 最新 published 的 version）、`activeTemplateCount`/`publishedTemplateCount`、`lastDeployAt`、`lastGoodSnapshotAt`。
- 审计类内存态（`riskRuleAuditLog/configTraces/lastBatchAudit`）**落盘到表 B**，`GET /config/trace`、`/ops/risk-rules` 的 audit 改为查表 B（保留内存视图做展示，落盘保证重启可追溯）。
- 变更面指标（publish 频次、rollback 次数、抽取 diff 率、compliance 命中裁剪数）接入现 `/ops/alerts` 告警机制。

### 13.7 实施边界与回归影响评估

| 改动 | 影响面 | 回归风险 | 缓解 |
|------|--------|---------|------|
| 新增 2 张表 + 实体 | 无侵入（纯新增） | 低 | 建表脚本独立，不碰存量表 |
| 热重载改事务式（13.2） | `reloadGraph/reloadOpsRules` 语义变化 | 中 | 保留 `graphCache=null` 兼容路径在失败时；dryrun 先行 |
| admin stub 接线（13.5） | `AdminController /ontologies` 从假成功变真实写库 | 中 | 现无前端依赖（stub 本不可信），改后以版本语义返回 |
| 审计落盘（13.6） | 内存 last-50 → 表 B | 低 | 视图兼容返回结构不变，新增持久化旁路 |
| 回归门禁（13.4） | publish 路径新增 SMOKE 断言 | 中 | 先对存量用例验证断言通过再启用阻断 |

**边界结论**：本运维改造**以新增表/新增路径为主**，对既有"智聊→推理→合规→预览→入库"主链路**无返回结构破坏**（compliance/draft endpoints 不动）。主要回归点在**热重载语义**与**publish 多一道门禁**，均可用 dryrun + 兼容路径缓解。运维治理（表 A/B + 守卫 + 门禁）与模板仓库**伴生落地、置于 P1/P2**，使"零代码新增产品"在可控的版本/回滚护栏内闭环。

| SHACL（降档 P3，可选） | 高（新引擎+编译+等价对比） | 全新依赖 | 🔴 若引入则显著增复杂度，建议维持 Java 档 |
| **版本库表 A/B + last-known-good 守卫（§13）** | 中-高 | 2 新实体 + 守卫逻辑 | 🟡 守卫改 `reloadGraph/reloadOpsRules` 事务式，触及最复杂类 |
| admin stub 接线 + 死代码清理（§13.5） | **负（净减）** | 收敛双世界 | 🟢 接线减 stub 假语义、删空文件 |

**关键判断：增量中"新建"类（模板仓库、版本库实体、守卫）大多可独立成类、不合并进 `ProductOntologyService`，可控；真正推高复杂度的是"改造存量"项——推导/抽取/合规/热重载全部落在**已经超限的 `ProductOntologyService` 与 `OpsExtractionService`** 上。**

### 14.3 净复杂度走向（两情景对比）

**情景 A（运维治理缺失，只做模板化 P1~P3）：**
- 新增模板仓库/编译器/前端消费，但**不改存量 stub、不清死代码、不建版本库**。
- 结果：`ProductOntologyService` 再叠模板注册/发布/回滚逻辑 → **复杂度单向爬升**，且无守卫兜底，运维风险放大。
- 净变化：**高增**，不可持续。

**情景 B（本方案 §11~§13 完整：模板化 + 运维治理 + 双世界收敛）：**
- 新增可独立成类的模板/版本库/守卫 + **接线 stub、删空文件、审计落盘**。
- 若在执行中坚持**从 `ProductOntologyService` 抽取独立子服务**（见 14.4 收敛建议），则可将大类的复杂度**摊薄**。
- 净变化：**先平后降**——短期因双份逻辑（derive_rules vs Java）小幅升，切换完成+清理后回落，并因清 stub/死代码而**净降**。

### 14.4 复杂度收敛建议（对标 AGENTS.md）

1. **拒绝往大服务继续堆**：模板注册/发布/回滚、守卫、版本登记**必须新建独立类/服务**（`ProductTemplateService`、`OntologyVersionService`、`LastKnownGoodGuard`），**禁止**在 `ProductOntologyService` 内再增方法——否则方法数 99→120+，彻底失控。
2. **处置存量超限类**：
   - `ProductOntologyService`（3758 行）：按 SRP 拆出 草稿持久化(迁移 `OntologyInstanceService` 非空文件)、审计、发布 三个子服务；每拆一个即回归一次（对齐 §12.5 门禁）。
   - `OntologyService` 双世界：stub 接线或 @Deprecated；空文件删除（§13.5）——**一次性消化存量泡沫**。
3. **灰度期双份逻辑设硬性 deadline**：derive_rules vs Java `inferFields` 并存只允许**一个迭代周期**，diff 报告通过后**删 Java 分支**，防止长期双维护（DRY/复杂度双原则）。
4. **SHACL 维持降档**（§11.4/11.9）：不引入新引擎，`compliance_bindings` + 轻量约束即可，避免再叠一套编译/ ENGINE 复杂度。
5. **每次模板/规则变更绑定回归门禁**（§13.4）：把"复杂度不回归"固化为发布检查项（新模板必过 家庭/校园 用例断言）。

### 14.5 复杂度评估结论

| 维度 | 现状 | 情景 B 落地后 |
|------|------|--------------|
| 核心大服务行数 | 3758（超限） | 拆分子服务后**单个回落** |
| 死代码/stub | 有（history 死代码、admin stub） | **清理/接线，净减** |
| 双世界语义 | 存在 | **收敛为单一** |
| 新功能复杂度 | — | 新增类独立可控 |
| 运维守卫 | 缺失 | last-known-good + 门禁 |
| **综合** | **存量泡沫 + 无护栏** | **可控增量 + 净降存量 + 护栏补齐** |

**总体判断**：本方案**本身不显著推高系统复杂度**——关键解法是"**新建独立成类、改造务必抽取、死代码清理、灰度设 deadline**"。真正的复杂度风险不在方案新增，而在**存量 `ProductOntologyService` 这类超限大类**继续被方案改造所累。因此把"**从大服务抽取子服务 + 双世界收敛**"列为与模板仓库伴生的强制工程动作（§13.5/§12.7），可使系统在落地方案的**同时**完成复杂度净降，符合《AGENTS.md》"去旧留新、定期清理"要求。
