本体通用设计：每个场景都复用的四套底座

下面 10 个场景共享同一套本体与引擎。先讲清这些底座，后面各场景只讲"它新增了哪些类、哪些规则"。

2.1 配置本体的四层类结构

研发配置场景的核心是 PricingProduct（可选商品），它通过对象属性挂接四层要素：销售策略层、计费权益层、约束合规层、场景字典层。

2.2 运营结论族：所有"判定"都是 :Offering 的子类

运营洞察场景的核心是 :Offering。不论是"异动""渠道根因""零费风险""P0 告警"还是"挽留建议"，在 OWL 里统一建模为 :Offering 的子类——命中后实例仍是那个商品/渠道，回读按类取实例即可定位到具体对象。

2.3 四套推理引擎与"规则双验证"

ops_rules.json（版本 OpsRules-v1.3）登记了四个引擎。每条规则声明由哪个引擎执行，同一规则可同时挂在 SWRL 与 Java 上做交叉验证。

引擎实现覆盖规则定位
openllet-swrl primaryOpsSwrlReasonerR-A01~A05 / R-B01~B05 / R-C03~C09本体规则主力，结论由 OWL 推理推出
java-rulesProductOntologyService再加 R-A06 / R-C01 / R-C02 / R-D01 / R-D05SWRL 关闭或异常时的同逻辑兜底 + 旁路规则
policy-javaOntologyServicePS_PRODUCT_ONLINE_V1 等 4 个策略集立项研判 / 风控 / 营销 / 退费策略集
condition-dsl deprecatedSwrlRuleEngine—名含 SWRL 实为字符串条件表达式，已废弃
规则双验证机制。同一规则号（如 R-A02）在 SWRL 与 Java 各有一份实现。推理结束后 ruleFired 按规则 label 核对"该点火的确实点了火"，比对不一致会写入日志；引擎字段 reasonEngine 标注本次到底谁算的（openllet-swrl / java-rules / fallback-java）。
两个易踩的误区。① TTL 里没有任何 Drools 规则——"立项研判的 PS_PRODUCT_ONLINE_V1"是 policy-java 策略集（OntologyService.decide），不是 Drools。② R-A06（持续下滑）不在 TTL，是 Java + MetricService 算出的旁路候选，文档里按实际写。

下面每个场景统一结构：一、需求（难点 vs 做法）→ 二、建模结构（一张类图 + 规则表）→ 三、推理过程（步骤表 + 兜底表）→ 四、体验（可直接打后端）→ 五、边界。

研发配置 ① 智聊配置

rd.chat · 手册 chat-configure · intent RD_CONFIG_CHAT

一、场景需求

产品经理口述一句"加个校园 59 元 30G 语音加宽带"，系统要把它变成一份可提交的配置草稿：落到哪个品类、槽位填什么、哪些合规项会挂、要不要开工单。

难点

  • 一句话缺失大量字段，靠猜会造出错配置
  • 品类判断错，后面所有必填都错
  • 合规项（互斥/折扣/零费）分散在多个规则里
  • 草稿必须能溯源到本体字段，不能凭空生成

做法

  • 先解析品类 → 再抽槽位 → 才生成草稿
  • 每步一个工具，缺字段就问，不硬填
  • 合规由 SWRL 规则 R-C03~C09 判定
  • 字段映射走声明式 propertyMapping

五步半结构性编排：rd_category_resolve → rd_slot_extract → rd_draft_generate → rd_compliance → rd_workorder_create。human_gate 在"品类不明"与"确认提交"两处停下等用户。

二、本体建模结构

步骤工具读/写本体关键判据
rd_category_resolve读 :ProductCategory口述特征词 → 品类；不明则 human_gate
rd_slot_extract读品类必填清单按 slotPatterns（月费/流量/宽带/语音/折扣/合约期）正则抽取
rd_draft_generate写草稿字段propertyMapping 声明式映射到本体数据属性
rd_compliance触发 SWRLR-C06 必填 / R-C03 互斥 / R-C05 零费 / R-C07 折扣 / R-C09 费率
rd_workorder_create写 :workOrderId合规通过或用户确认后建单

三、推理过程

#推理环节规则 / 来源输出
1品类解析LLM + 特征词匹配category 或「待澄清」
2槽位抽取extraction.slotPatterns月费/流量/宽带/语音/折扣/合约期
3别名归一extraction.aliases「畅享128 / 家庭融合128 / 99898653」→ 99898653
4草稿生成config.propertyMapping本体数据属性（含 default -1 缺省）
5合规判定SWRL R-C03~C09issues[] / appliedRules[]
6工单落地R-D01 批量映射workOrderId
非命中 / 兜底处理

SWRL 不可用走 Java 预计算布尔（存在性冲突）兜底

四、体验

接口 POST /api/v1/product-ontology/config/chat，请求体 {"text":"..."}。

五、边界

  • 品类库不全时易误判，需人工补品类；
  • 一句话信息量有限，超出一句能表达的多要素配置仍需多轮；
  • 草稿不自动提交，human_gate 必须人工确认。

研发配置 ② 智读批量导入

rd.import · 手册 doc-batch-import · intent RD_FILE_PARSE

一、场景需求

产品经理传来一份 Excel/Word 配置清单，里面有几十上百条配置。系统要解析成结构化草稿，逐条做合规，每条草稿生成一张工单。

难点

  • 文件格式五花八门，表头不固定
  • 超长文本一次喂不进模型
  • 一条不合格不能拖垮整批
  • 要能说清"哪几条没通过、为什么"

做法

  • 四级降级链，优先结构化 IR
  • 切片 ≤6000 字 × ≤5 片
  • 每条草稿一单，逐案合规
  • 汇总 issues / 通过率 / 品类分布

四步：rd_doc_parse → rd_draft_extract → rd_compliance → rd_workorder_create。"每条草稿一单"是硬规则。

二、本体建模结构

规则引擎职责
R-D01java批量字段映射到本体属性
R-D02java按 ProductCategory 补全必备要素
R-D03java逐案套 R-C* 合规
R-D04java汇总 issues / appliedRules / messagePreview
R-D05java通过率 / 待修正数 / 品类分布

三、推理过程

#环节来源输出
1文件解析/config/upload → /config/batch-by-file切片文本
2草稿抽取四级降级链drafts[]
3批量映射R-D01本体属性
4逐案合规R-D03（R-C03~C09）每案 issues
5汇总R-D04 / R-D05通过率、品类分布
6建单每条草稿一单N 张工单
非命中 / 兜底处理
文件超 5 片只处理前 5 片，提示剩余未处理
某条抽取失败跳过该条并记入 issues，不拖垮整批
表头无法识别降级到 LLM 抽取

四、体验

接口 POST /api/v1/product-ontology/config/batch，请求体 {"text":"..."}；文件上传走 /config/upload 再 /config/batch-by-file。

五、边界

  • 单次最多 5 片 × 6000 字，超大文件会截断；
  • 扫描件/图片需先 OCR，本体链不负责 OCR；
  • 抽取质量取决于原文档结构规整度。

研发配置 ③ 历史配置智查

rd.query · 手册 discover-history · intent RD_CONFIG_DISCOVER

一、场景需求

产品经理要查"以前有没有做过类似配置"。系统在历史配置库里检索同类方案，返回最多 20 条，只读、不改档。

难点

  • 历史配置命名不统一，关键词搜不全
  • 要按"相似度"而非精确匹配
  • 查历史是只读行为，绝不能误改

做法

  • 走 :similarTo 关系召回
  • 关键词 + 语义双路
  • 只读，结果上限 20 条

二、本体建模结构

步骤来源说明
rd_config_search ×2RdConfigSearchTool关系路（similarTo）+ 关键词路
上限手册常量最多 20 条

三、推理过程

#环节说明输出
1解析查询对象编码 / 名称 / 关键词目标方案
2关系召回:similarTo同类候选
3关键词召回名称/品类/场景匹配关键词候选
4去重封顶合并去重≤20 条

四、体验

接口 POST /api/v1/product-ontology/config/discover，请求体 {"text":"..."}。

五、边界

  • 只读，结果不落库；
  • similarTo 关系依赖历史图谱构建质量，新库召回少；
  • 上限 20 条，超出的热门候选会被截断。

研发配置 ④ 多方案对比

rd.compare · 无独立手册，工具直驱 ChatConfigureService.compareConfigSchemes（:810）

一、场景需求

产品经理给出几套候选资费方案，要系统比出"哪套更合规、谁预计年营收更高"，并给出推荐。

难点

  • 合规与营收是两个维度，不能简单加权
  • 方案补丁不一定结构化，得从文本里抽
  • 推荐必须有明确依据，不能拍脑袋

做法

  • 先合规分组，组内再按营收降序
  • 缺补丁时从「N 元」正则抽，再缺省 39/59
  • 推荐 = 首个合规项，否则首条并标注需修正

工具 rd_scheme_compare（RdSchemeCompareTool，Set.of("rd","query")，requires [rd_draft_generate, rd_compliance]）直接调 compareConfigSchemes。

二、本体建模结构

环节算法行号
补丁抽取空则从 \d+\s*元 抽候选，再空默认 39/59:828-871
marketScale默认 150000，可从 \d+\s*万 解析:873-877
换算率clamp(0.10 - fee/1000, 0.02, 0.12):901
年营收marketScale × conv × max(fee,0) × 12:902
排序先 compliancePass（true 在前），再年营收降序:917-924
推荐首个合规项；否则首条并标注"仍需修正合规项":926-929
trace_id"cfg-compare-" + epochMilli:949

三、推理过程

#环节输出字段
1逐方案补丁解析patches[]
2逐方案合规判定compliancePass
3逐方案营收估算estimatedAnnualRevenue
4排序 + 推荐comparisons[] / recommended
5生成解释explanation

返回体：{success, comparisons, recommended, explanation, trace_id, marketScale}。

非命中 / 兜底处理
补丁全空正则抽「N 元」；仍空则默认 39/59
无合规方案推荐首条并明确标注"仍需修正合规项"

四、体验

接口 POST /api/v1/product-ontology/config/compare，请求体 {"text":"..."}。

五、边界

  • 营收是估算值，非真实结算口径；
  • 只比月费维度，不含宽带/权益等复杂组合；
  • 合规与营收不做加权融合，合规优先是硬序。

运营洞察 ① 市场洞察

market_insight · 手册 market-insight · intents [PRODUCT_OPS_QUERY, PRODUCT_OPS_MONITOR]

一、场景需求

问"5G 套餐最近市场表现怎么样""竞品价格有什么变化"，系统要先用指标域取数，再查关系，必要时做风险审计。这是只读洞察，不建单、不改档。

难点

  • 同类问题有的要看指标数值，有的要看实体关系
  • 口径不统一，指标定义散落各处
  • 洞察不该被误当成要执行的决策

做法

  • 双轨：指标类先 metric_query，关系类走 sparql_query
  • 指标域 P0 前置，口径统一
  • human_gate: [] 全直出，不代做决策

三步 v2：metric_query → sparql_query → swrl_risk_audit。指标类问题由 metric_query 先出数，关系类问题直接 sparql_query。

二、本体建模结构

步骤工具取数路径说明
metric_query指标域（P0 前置）指标类问题先出数
sparql_query关系图竞品/促销/渠道关系
swrl_risk_auditSWRL 风险规则顺带做风险审计

三、推理过程

#环节来源输出
1判定指标类 / 关系类intent 特征选轨
2a指标取数metric_query指标值
2b关系查询sparql_query实体关系
3风险审计SWRL R-B*风险标签

四、体验

接口 GET /api/v1/product-ontology/ops/dashboard；营收概览另有 /ops/revenue-overview。

五、边界

  • 只读洞察，不产生处置动作；
  • 无事实数据的商品指标为空；
  • 风险审计仅作旁证，不代表最终结论。

运营洞察 ② 立项研判

online_check · 手册 online-check · intent PRODUCT_OPS_POLICY · policy-java

一、场景需求

新品要不要上、"5G 套餐"在低市场体量下该不该放行——要给出可解释的放行/拦截研判。系统"不代做决策"，只给策略判定与理由。

难点

  • 投决问题不该由模型拍板
  • 与"风险稽核"同为 PRODUCT_OPS_POLICY，容易走错链
  • 研判要能说清命中了哪条策略

做法

  • policy-java 策略集 PS_PRODUCT_ONLINE_V1
  • 与 risk-audit 同码不同手册，靠 intent_guide 特征词二跳
  • human_gate: [] + audit 表达"不代做决策"

三步 v1：sparql_query → rule_explain → ontology_explain。触发规则 R-ONLINE-001：marketSizeGte:100000、denyProductTypeOnLowMarket:"5G套餐"。

这是 policy-java，不是 Drools。策略集由 OntologyService.decide（:560）/ triggeredRules（:839）执行。

运营洞察 ④ 异动归因

root_cause · 手册 root-cause · intent PRODUCT_OPS_REASON

一、场景需求

商品掉量了，要说清是渠道、促销、竞品还是用户行为造成的，并给出可复核的证据数值。结论不靠打分模型，靠本体规则推导。

难点

  • 根因藏在不同类型的证据里，判据各不相同
  • 结论容易"合理但不可查"
  • 阈值要能随时调，不能改规则体
  • 没事时容易硬猜一个原因

做法

  • 四类证据各建一个根因类，判据写成 SWRL
  • 结论带规则号，模型改不了
  • 阈值做成命名个体，运行时覆写
  • 先确认异动，再找根因

输入只有一个商品（编码或名称）。三步 v1：sparql_query → swrl_root_cause → ontology_explain。

二、本体建模结构

规则前置判据默认阈值结论
R-A01—指标环比跌幅 / 上游异常标记-10%商品异动
R-A02已异动渠道订单跌幅 + 渠道贡献占比-20% / 30%渠道根因
R-A03已异动优惠将到期天数 + 驱动订单占比7 天 / 25%促销根因
R-A04已异动竞品价差比例 + 渗透率增幅15% / >0pp竞品根因
R-A05已异动行为权重提示8%行为根因
R-A06—连续下滑天数（Java 旁路，不推理）3 天持续下滑趋势
R-A02~A05 的前置都是"该商品已确认异动"。没异动就不猜根因——这条硬约束是"没事找因"的解法。

三、推理过程

推理机（Openllet）求值规则，得出结论类型后按结论类反查实例。R-A06 是 Java 旁路，共同构成完整判定。

四、体验

接口 POST /api/v1/product-ontology/ops/root-cause，请求体 {"offeringId":"..."} 或 {"text":"..."}。

五、边界

  • 单层条件组合，不做多因加权排序，weight 只作证据值透传；
  • 只能对事实图 opsGraph 中有数据的商品归因；
  • 指标与渠道间无直接公理，无法细分"某指标主要由某渠道造成"；
  • 归因结果不落库，只能现场复核。

运营洞察 ⑤ 风险稽核

risk_audit · 手册 risk-audit · intent PRODUCT_OPS_POLICY

一、场景需求

批量筛查在售商品是否有零费、异常折扣、零销售、低效、高风险等问题，给出风险分与建议。只读筛查，不改档。

难点

  • 风险类型多，判据各异
  • 与"立项研判"同 intent，易混
  • 稽核不能顺手把档改了

做法

  • SWRL 风险规则 R-B* 逐条判定
  • 风险分 high/medium/low 分级
  • 只读筛查，不落改动

三步 v1：sparql_query → swrl_risk_audit → rule_explain。与 online-check 同码不同手册，靠 intent_guide 特征词二跳判定。

二、本体建模结构

R-B03零销售在架天数180 天ZeroSalesOffering
R-B04低效（低营收分位）5%LowEffOffering
R-B05高风险复核天数30 天HighRiskOffering

运营洞察 ⑥ 规则运营

ops_rules · 阈值覆盖 + 规则目录 + 查询热度

一、场景需求

运营/研发要能查看当前生效的规则与阈值、临时调整风险规则、重载规则目录，并了解用户都在问什么（查询热度）。

难点

  • 规则阈值散落，改一次要重启才生效
  • 哪些规则在跑、由哪个引擎跑，说不清
  • 不知道用户真实关心哪些问题

做法

  • 阈值入 :ThresholdHolder，运行时覆写
  • 规则目录显式列出引擎与覆盖范围
  • 查询热度统计 top 问题/关键词
