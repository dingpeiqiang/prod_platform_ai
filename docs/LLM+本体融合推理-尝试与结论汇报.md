# LLM + 本体融合推理智能体：尝试与结论

## 一、尝试做了什么

### 场景描述

产商品"研发-运营"全流程的智能化改造，选取两个核心业务场景：

| 角色 | 痛点场景 | 现状 |
|------|---------|------|
| 产商品**研发**人员 | 配置一个套餐要查模板、抄相近套餐、逐项填表、翻规则手册自查 | 30-60 分钟/个，易错易漏；方案文档录入靠人工抄录，一批 2-4 小时 |
| 产商品**运营**人员 | 指标异动后凭经验逐维排因；风险产品稽核靠人工抽查 | 归因 1-4 小时且结论因人而异；稽核只能抽查，存在盲区 |

### 目标

1. **提效**：套餐配置从小时级到分钟级（目标提效 90%+），文档批量录入分钟级，异动归因分钟级；
2. **提质**：配置合规零漏判、风险稽核从抽查变全量、归因结论可复现（同数据同结论）；
3. **可信**：AI 进入生产必须解决幻觉问题——每个结论可追溯、可审计，满足运营商合规要求。

### 思路/方法

**核心思路：LLM 与本体分工，各干各的最擅长的事**

- **LLM 负责"听懂与说清"**：理解业务人员的自然语言、抽取业务要素、把推理结果表达成报告——只做翻译和表达；
- **本体负责"事实与裁决"**：建两张业务知识地图（配置 + 运营），实体、关系、规则全部显式建模，机器能查（图查询）、能推理（规则引擎）、能校验（约束校验）——结论由它裁决；
- **架构级防幻觉**：LLM 全程不产生业务结论。合规/归因/风险的裁决由规则引擎执行，AI 无权改判；LLM 抽取要素受知识模板白名单约束，编不出不存在的字段；
- **规则外置 + 双轨容错**：判定阈值全部外置可调（在线热更）；语义推理失败自动降级到等价规则引擎；LLM 不可用降级词典抽取——不依赖任何单一模型。

**技术路线**：知识图谱（RDF4J 本体库）承载事实与概念模型；SWRL/策略集承载判定规则（阈值外置、版本化）；Openllet 语义推理机执行归因/风险推理；Spring AI 集成大模型做理解与表达；SSE 流式输出过程透明。

### 安全管控

| 管控点 | 机制 |
|--------|------|
| **输入管控** | 用户输入经护栏过滤后才进入理解层；LLM 抽取要素受品类模板白名单约束，超范围自动拦截 |
| **结论管控** | 合规/风险/归因结论**只能由规则推理引擎产出**，LLM 无权改判——提示词层面明文约束"不得把不通过说成可提交" |
| **数据安全** | 假设推演在独立沙箱图执行，不写生产数据；事实数据热重载四步守卫（加载→校验→冒烟→提交），坏数据自动回退最近可用版本 |
| **全程审计** | 每个结论关联知识地图上的事实、命中规则编号、阈值版本，全程留痕可回放 |
| **变更安全** | 知识资产（模板/规则/本体）版本化发布/回退；改规则先过典型用例回归门禁再上线 |

## 二、结论是什么

### 结论

**方案已验证可行并落地**：LLM + 本体的融合架构在研发、运营两大场景端到端跑通，"AI 换效率、本体守底线"的设计目标达成。关键验证结果：

1. **双品类全链路验证通过**：6 类品类模板全部就绪，家庭融合/宽带两类产品走通"对话配置→要素抽取→知识推理→合规校验→预览→入库"完整链路；
2. **防幻觉机制有效**：模板白名单 + 规则裁决双重约束下，LLM 无法编造字段、无法覆盖合规结论；坏图谱注入被自动拦截回退；
3. **推理结论可复现**：归因/风险结论由显式规则 + 确定性推理机产出，同数据同结论，每条可回放到具体事实数值与阈值；
4. **回归质量**：50 个自动化测试 0 失败，六典型业务用例回归全过。

### 数据

| 指标 | 改造前 | 现在 | 提升 |
|------|-------|------|------|
| 套餐配置 | 30-60 分钟/个 | 1-2 分钟 | **~95%** |
| 方案文档批量录入 | 2-4 小时/批 | 分钟级 | **~98%** |
| 合规校验 | 人工翻手册 20-40 分钟，易漏 | 自动逐条+整改建议 | 秒级，零漏判 |
| 异动归因 | 1-4 小时，结论因人而异 | 分钟级，可复现 | **~97%，结论一致性 100%** |
| 风险稽核 | 人工抽查（有盲区） | 全量日扫 | **覆盖 100%** |

### 价值与意义

1. **业务价值**：研发人员从"填表工"解放为"做判断"——只决策"要不要、选哪个"，AI 干完其余的活；运营从"事后救火"变"日常防控"，风险产品日扫零盲区；
2. **技术价值**：验证了"大模型 + 知识图谱"融合的工程化路径——**大模型提供交互能力、本体提供可信裁决**，为其他业务域（如网络运维、客服）复制该模式提供了参照架构；
3. **组织价值**：品类模板、业务规则、历史方案沉淀为组织知识资产，版本化管理，**不随人员流动流失**；规则阈值业务可读可调，知识运营门槛大幅降低。

## 三、反思

### 做的好

1. **技术分工边界清晰**："LLM 只翻译不裁决、本体只裁决不表达"的铁律从第一天就定死并贯彻到提示词与代码双重层面——这是防幻觉能落地的根本原因，避免了"先放飞再补救"的弯路；
2. **知识资产化意识**：品类模板、规则阈值全部外置为配置而非硬编码，新增品类零代码、调阈值不发布——为后续规模化扩展打好了底座；
3. **回归文化**：典型业务用例固化 + 全链路回归门禁 + 坏图谱自动回退，知识资产的每次变更都有安全网，敢热更、敢迭代。

### 做的不好的

1. **本体构建仍靠人工**：两张知识地图、6 份模板、20+ 条规则均为人工编写维护，新品类扩展仍需研发介入——"知识建模"成为当前最大的持续性成本；
2. **数据链路依赖 mock**：部分场景的事实数据仍走演示数据源（demo-only），真实 BOSS/CRM 数据源尚未完全接通，部分能力（历史方案检索、批量稽核）在生产数据上的效果未经验证；
3. **效果评估体系缺失**：配置/抽取的准确率、归因命中率缺少系统化的量化评测与持续监控指标，目前主要靠回归用例保证"不变差"，缺少"变好"的度量；
4. **LLM 依赖单点**：意图抽取对单一模型有依赖，模型服务波动影响对话体验，多模型路由尚未全部生效。

### 后续改进目标

| # | 改进项 | 目标 | 时间 |
|---|--------|------|------|
| 1 | **本体自动构建**：LLM 从业务文档抽取概念/规则草稿 → 校验 → 人工确认入库 | 新品类知识建模从"研发工单"降为"业务配置"，建模成本降 70% | 2-3 个月 |
| 2 | **接通真实数据源**：BOSS/CRM 事实图对接，去掉演示数据依赖 | 稽核/检索在生产数据上验证并出效果报告 | 1-2 个月 |
| 3 | **效果评测体系**：建立要素抽取准确率、归因准确率、合规命中率的标注评测集与线上监控 | 核心环节准确率可量化、可追踪、月度报告 | 1 个月 |
| 4 | **多模型路由**：按场景/任务自动选择最优模型，消除单点依赖 | 模型故障自动切换，可用性 99.9% | 1 个月 |
| 5 | **场景外溢**：将"LLM+本体"模式复制到表单智能校验、知识库问答等平台场景 | 形成 2 个以上新场景落地案例 | 持续迭代 |
