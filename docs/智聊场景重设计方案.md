## 0. 版本沿革与纠偏依据

### v1.x 隐性方案（现状）→ v2.0 显式工作流方案

**v1.x（现状）的问题**：智聊链路（听懂→查历史→起草→合规→落库→开单）的编排权在 LLM 手里——`DefaultUnderstander` 每轮基于工具自描述自由选择 `rd_config_chat` 等工具，编排结果是模型/温度/提示词的函数，随时间漂移，不可复现。同时 `rd_config_chat` 内部「生成→落库→开单」一气呵成（唯一开关是 session_id 是否携带），用户没有「确认后再落库」的中间控制点；过程透明化靠 `WorkflowBuilder` 造的**伪工作流**（静态一轮对话视图），与真实链路无绑定。

**纠偏依据**（《业务驱动改造方案》§12.2 评判判据）：
1. 智聊的步骤顺序业务上是否允许每次不同？——**不允许**。需求→查历史→起草→合规→落库→开单是业务规约，LLM 每次重新「发现」这条链是伪智能，还引入漂移风险。
2. 是否需要「哪个节点谁批的、走了哪条分支」的审计？——**需要**。落库与开单是写操作，事故回溯要求节点级留痕。
3. 是否需要回归测试保障？——**需要**。同输入=同路径是验收标准。

三问全命中 → 执行域从「LLM 动态编排」迁到「固定流程引擎」。**LLM 不被边缘化**：理解（听懂）与表达（说清）仍由 LLM 全责，本体仍负责事实与判定，符合项目哲学「LLM 负责听懂与说清，本体负责事实可信、判定可解释，工作流负责确定性执行」。

## 1. 目标与非目标

### 1.1 目标

1. **链路固化**：智聊核心链路固化为 `FlowEngineService` 可执行的显式工作流定义（`pd_ai_workflows.workflow_data`），同输入=同路径，评审后不漂移。
2. **阶段门（写操作可控）**：起草（DRAFT）→ 人工确认（CONFIRM，human 节点）→ 落库（PERSIST）→ 开单（ORDER），写操作前必有显式确认点；「仅起草」成为一等公民而非「没带 session_id 的副作用」。
3. **多轮澄清状态机化**：澄清从「会话内 3 轮计数 + 内存 lastClarifyParams」升级为**持久化挂起**（human 节点 + resume_token），断线/重启/跨设备可续谈，追问渐进式（每轮最多 3 问，带选项）。
4. **过程透明**：引擎节点执行实时推送 SSE（复用 thinking/tool 事件语义 + 新增 `flow_progress` 事件），用户看到「正在查历史 → 正在起草 → 正在合规校验」，前端时间线 = 真实节点留痕，删除伪工作流渲染。
5. **可审计**：节点级执行记录（pd_ai_workflow_node_logs）含输入快照、分支依据、重试次数；对话轮与执行实例双向关联（session_id ↔ execution_id）。
6. **query 场景扶正**：修复 scene='query'/'compare' 空白名单裂缝，query 获得正式场景声明与工具集（复用 rd_config_discover / rd_scheme_compare / sparql_query），纳入统一路由。
7. **双轨灰度**：新增显式工作流链路与现有 LLM 动态编排并行，`prodai.chat-workflow.enabled` Feature Flag 切流，随时回退。

### 1.2 非目标（明确不做）

- 不做 BPMN 全量规范、跨系统 ESB、分布式事务（saga 补偿只做「落库失败不开单」级别的防孤儿，继承现状）。
- 不做循环节点（引擎 DAG 铁律不变；澄清循环用「human 挂起 + 恢复后继续」表达，不引入回边）。
- 不拆 `AgentOrchestrator` 的理解/表达层——这是三要素架构的既有资产，本次只让渡**执行域**。
- 不新增中间件（无 Redis/MQ），全部基于 MySQL + Spring 现有设施。
- 不改变 SSE 既有事件（thinking/tool/text/done/warning/error）的字段契约，只做**增量扩展**（前端向后兼容）。

## 2. 总体架构

### 2.1 三要素职责再划分（v2）

```
┌─────────────────────────────────────────────────────────────────┐
│ 理解层（LLM 全责，保留）                                          │
│  DefaultUnderstander + IntentPromptAssembler + ParamCompletionGate│
│  输出：结构化 QueryPlan（不再是「工具列表」而是「场景路由判定」）    │
├─────────────────────────────────────────────────────────────────┤
│ 路由层（新增薄层 SceneFlowRouter）                                │
│  QueryPlan → workflow_code 解析（确定性，无 LLM）                  │
│  rd 场景主对话 → chat_configure_v2 / 检索意图 → config_discover_v2 │
│  ops 场景主对话 → ops_analysis_v2 / query 场景 → query_reuse_v2   │
│  未命中（CHAT/自由探索）→ 走现有 LLM 动态编排（双轨兜底）           │
├─────────────────────────────────────────────────────────────────┤
│ 执行层（工作流引擎全责，新增接线）                                 │
│  FlowEngineService.startExecution(workflowCode, version, ...)    │
│  + FlowEventListener（新增：节点级事件回调 → SSE）                 │
│  + ChatHumanBridge（新增：human 节点 ↔ 对话消息桥接）              │
├─────────────────────────────────────────────────────────────────┤
│ 本体层（不变，被 tool 节点调用）                                   │
│  ProductOntologyService.chatConfigure / checkCompliance          │
│  TemplateDeriveEngine / ComplianceRuleEngine / SWRL 推理          │
├─────────────────────────────────────────────────────────────────┤
│ 表达层（LLM 全责，保留）                                          │
│  DefaultPresenter + ThinkingCopy + ToolOutputRenderer            │
│  输入 = 执行层终态 output_data；输出 = 业务文案 + 跟进话术          │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 一条消息的完整旅程（智聊主链路）

```
用户："帮我配一个面向校园学生的融合套餐，月费 59 含宽带"
  │
  ├─① AgentController（SSE 建立，入口不变）
  ├─② DefaultUnderstander：LLM 理解 → QueryPlan{intent=RD_CONFIG_CHAT,
  │    params{product_type=融合, target_user=校园, monthly_fee=59, ...}}
  ├─③ SceneFlowRouter：RD_CONFIG_CHAT → workflow_code=chat_configure_v2
  │    → startExecution（版本锁定，Feature Flag 开启时）
  │       ├─ flow.start        承接 params（输入快照落库）
  │       ├─ flow.tool 查历史  rd_config_discover(question) → items
  │       ├─ flow.condition    命中度高？→ 走复用建议分支 / 低 → 起草分支
  │       ├─ flow.llm  起草    prompt 外置（继承 IntentPromptAssembler 机制）
  │       │                     输出 JSON 契约（结构化校验，失败重试）
  │       ├─ flow.tool 合规    rd_compliance(draft) → compliance_pass/issues
  │       ├─ flow.condition    compliance_pass == true ?
  │       │    ├─ false → flow.human 澄清/整改（form_spec 下发合规 issue 选项）
  │       │    └─ true ↓
  │       ├─ flow.human 确认门 【阶段门】展示草稿 + 合规结论，等用户"确认落库"
  │       │    （SSE 推 done(intent=AWAIT_CONFIRM, execution_id, form_spec)，
  │       │      挂起持久化，进程重启不丢）
  │       ├─ flow.tool 落库    rd_draft_manage(action=update→persist) 
  │       ├─ flow.tool 开单    createWorkOrder(source=rd_config_draft)
  │       └─ flow.end          output_data{draft, work_order_id, conclusion}
  ├─④ 表达层：DefaultPresenter 汇总 → text 事件 → done
  └─⑤ 落库：chat_message.metadata 记录 execution_id（回溯锚点）
```

**挂起恢复旅程**（用户回复"确认落库"）：

```
用户："确认落库"（或点击表单确认按钮）
  ├─① ChatHumanBridge.resume(executionId, resumeToken, formData)
  │    （对话内恢复入口，复用 /flow-engine/executions/{id}/human-resume 语义，
  │      但由对话层代持 token，用户无感知 executionId）
  ├─② FlowEngineService.resumeFromHuman → 从确认门节点继续推进
  ├─③ 落库/开单节点执行（每节点 SSE 推送 flow_progress）
  └─④ 终态 → 表达层总结 → done(work_order_id)
```

### 2.3 与现有体系的关系（复用清单）

| 现有资产 | 本方案处置 |
|---|---|
| `DefaultUnderstander` + `ParamCompletionGate` + `AgentCapabilityRegistry` | **保留全量**。理解层职责从「选工具链」收窄为「场景路由判定 + 参数抽取」，提示词能力清单部分换成场景工作流清单 |
| `DefaultPresenter` + `ThinkingCopy` + `ToolOutputRenderer` | **保留全量**。表达输入从 ExecutionResult 换成引擎 output_data + node_logs |
| `FlowEngineService` 7 类节点 + `FlowDefinitionValidator` G1~G4 | **直接复用**。需 3 处能力增强（见 §3） |
| `FlowIntentRouter`（关键词快路径）| **保留**，作为零 LLM 快路径；与 SceneFlowRouter 并列，快路径优先级不变 |
| `FlowExecuteTool`（LLM 语义慢路径）| **保留**，作为双轨兜底的进入方式 |
| `SessionManager` / `ChatPersistenceService` | **保留**；增加 session↔execution 关联字段 |
| `WorkflowBuilder`（伪工作流）| **退役**（§7 清理项）。SSE workflow 事件改由引擎定义真实图 + 实时节点态驱动 |
| `AgentTool` 注册表 | **复用**，tool 节点零新建（引擎已接线 ToolExecutionService） |

## 3. 引擎能力增强（3 项，最小改动）

> 以下缺口已由现状调研确认（《固定流程引擎设计文档》未覆盖对话侧需求）：

### 3.1 节点级事件监听器（`FlowEventListener`）

**缺口**：引擎完全阻塞、无 SSE 集成，前端只能整单等待或 HTTP 轮询。

**设计**：

```
FlowEngineService 注入 Optional<FlowEventListener>（List<FlowEventListener>，Spring 事件解耦）：

interface FlowEventListener {
    void onNodeStarted(FlowNodeEvent event);    // nodeId/nodeType/name/attempt
    void onNodeCompleted(FlowNodeEvent event);  // + output 摘要 + durationMs
    void onNodeFailed(FlowNodeEvent event);     // + errorMessage + 重试提示
    void onBranchTaken(FlowNodeEvent event);    // condition 命中分支 id + 表达式
    void onSuspended(FlowNodeEvent event);      // human 挂起（form_spec + resume 信息）
}

FlowNodeEvent：executionId / workflowCode / nodeId / nodeType / nodeName /
               status / attempt / branchTaken / formSpec / timestamp
```

- 引擎内每个节点事务提交**后**发布事件（避免事务回滚后前端看到假成功）；实现侧异步投递，不阻塞状态机主线程。
- 事件发布失败仅 log.warn，绝不影响执行（引擎可靠性 > 通知可靠性）。
- 对话侧监听器 `ChatFlowProgressBridge` 将事件翻译为 SSE：
  - `onNodeStarted/Completed/Failed` → `flow_progress` 事件（§5.1）
  - `onBranchTaken` → flow_progress 附 branch 字段（前端时间线显示「走了哪条边、为什么」）
  - `onSuspended` → done 事件变体 `intent=AWAIT_CONFIRM / CLARIFY`（复用既有语义）

### 3.2 LLM 节点结构化输出增强（`flow.llm` 扩展字段）

**缺口**：现有 llm 节点仅 `prompt → response` 单字符串，无法做「起草 JSON」这类结构化任务，也无法被 condition 可靠判定。

**设计**（`action_params` 增量字段，完全向后兼容）：

| 字段 | 必填 | 说明 |
|---|---|---|
| `system_prompt` | 否 | 系统提示词（支持 `{{ref}}` 注入；起草系统提示词外置到 `prompts/flow/`，与 IntentPromptAssembler 同机制） |
| `response_format` | 否 | `text`（缺省）/ `json` |
| `json_schema` | 否 | response_format=json 时输出契约校验（复用 `ToolContractValidator` 的轻量校验思想：必填键 + 类型），解析失败按 retry 语义重试 |
| `output_mode` | 否 | `raw`（缺省，现状）/ `flatten`（解析后的 JSON 顶层键平铺进 variables，供 condition/下游直接引用） |

约束：
- `json_schema` 校验失败 → 按节点 retry 重试（重试提示词附错误说明），超过 maxAttempts → onFailure 语义（fail/continue）。
- `flatten` 模式输出键自动加 `llm_` 前缀防覆盖（规避现状「输出顶层键平铺可能覆盖入参」的既有风险），condition 表达式引用形如 `${node-draft.output.llm_target_user}`。

### 3.3 对话内 human 挂起桥接（`ChatHumanBridge`）

**缺口**：human 恢复仅在编辑器 Web 端点，对话内无法续谈；澄清问题无法以自然语言+表单混合形式下发。

**设计**：

```
ChatHumanBridge（@Component）：
  onSuspended(execution, humanNode) 时：
    1. 依据 human 节点 form_code 经 FormSchemaPort 取 fields
    2. 将 form_spec 翻译为对话侧既有 clarify_contracts 契约
       （{param: {label, description, options}}，前端零新组件即可渲染）
    3. execution_id/resume_token 写入 chat_message.metadata（persistTurn），
       同时写入 SessionContext.executionBinding（新增字段）
  用户下一轮回复时：
    AgentOrchestrator 检测 session.executionBinding 存在 →
    走 ChatHumanBridge.resume（不再过理解层 LLM——挂起态的回复语义由流程定义，无歧义），
    文本回复经轻量意图判定映射为表单值（如"确认"→action=confirm，"改成 49 元"→回填参数），
    调 FlowEngineService.resumeFromHuman(executionId, token, formData)
```

- 跨轮上下文**不再依赖 30min 内存 TTL**：挂起态在 `pd_ai_workflow_executions`（status=waiting_human + context_data 全量快照），会话重建后由 executionBinding 反查恢复。
- TTL 兜底沿用引擎 72h sweeper；对话侧在挂起超 24h 后追问提示一次（体验项，可后置）。
- 澄清上限沿用 `SessionContext` 既有语义（clarify 3 轮 / confirm 2 轮），超限由流程定义内 condition 节点显式处理（如「按缺省值继续 + 记录 assumption」），防死循环责任在**流程定义**而非运行时计数。

## 4. 智聊工作流定义（chat_configure_v2）

**注**：
- `end-reuse` 为复用建议分支的 end 节点（复用建议文案由表达层基于 history_items 生成），上图中省略。
- `fix-human → compliance` 的回边**不是引擎运行时回边**——human 恢复是从挂起点**继续向后**推进，因此整改分支的图结构实为：`fix-human` 恢复后进入**第二次合规子流程**（`compliance-recheck`，复用同一定义通过 `flow.workflow` 拆子流程实现），避免 DAG 环。图示做了简化，实施时以子流程拆分为准（见 §4.2）。

### 4.2 回环的 DAG 化表达（澄清/整改循环的正确姿势）

> **【实施勘误 W3-2，2026-09-06】** 本节原设计经引擎实现验证，有 3 处与引擎现实约束冲突，落地形态以本勘误为准：
>
> 1. **子流程内不放 human 节点**：workflow 节点同步执行子流程且要求子流程终态=completed，
>    human 挂起（waiting_human）会断裂链路——原设计的 `fix-human → 重入 draft_and_check_v2` 不可行。
>    挂起确认门只放主流程（confirm-gate），可直接被 ChatHumanBridge 恢复。
> 2. **子流程不能重入自身**：引擎 `__workflow_chain` 防环机制对「同编码重入」直接拒绝，
>    原设计的「新实例重入」路径走不通。整改回环用**线性展开**表达：
>    fix-redraft → compliance-recheck → pass-check-recheck（二次仍不过走 rejected 终态，主流程继续）。
> 3. **跨流程引用只能用 `flow.<入参>`**：流程入参（flow 副本）仅在启动时注入一次，
>    节点渲染 `{{flow.x}}` 取的是入参快照；子流程 output 不能在主流程后续节点中作为上游引用。
>
> 落地后的实际结构见 `SceneWorkflowDefinitions`（chat_configure_v2 + draft_and_check_v2 线性整改）。

引擎定义期强制无环，智聊的「澄清→重新起草」「整改→重新合规」**不用**子流程重入表达（见上方勘误 1/2），改为：

```
chat_configure_v2（主流程）
  ├─ reuse-check ──reuse──→ end-reuse（复用历史）
  ├─ ──draft──→ workflow 节点 draft_and_check_v2（子流程，同步执行）
  │                ├─ draft-llm → compliance → pass-check
  │                ├─ pass-check──fix──→ fix-redraft → compliance-recheck → pass-check-recheck（线性整改）
  │                │        └─ 复检仍不过 → end-draft-rejected（子流程正常 completed 终态）
  │                └─ pass-check──ok──→ end-draft-ok
  ├─ draft-stage → confirm-gate（human，挂起等确认）→ confirm-check
  │        ├─ cancel → end-cancelled
  │        └─ proceed → persist → order → end-main
  └─ 防失控：整改只有一轮线性展开 + 确认门可取消，无重入环
```

- 整改「回环」以线性展开为代价换取确定性：每次整改是**有限且可审计**的（node_log 按 attempt 留痕），
  不存在重入实例链，DAG 校验天然通过。
- 澄清（缺参数）不经流程图：ParamCompletionGate 在理解层产出 CLARIFY 计划，
  由对话编排层与用户往返（每轮最多 3 问，选择题化），补参后**重新走一遍工作流**（新执行实例），不依赖流程内重入。
### 4.3 阶段门设计（写操作控制点）

| 门 | 节点 | 挂起产出（SSE done 变体） | 恢复动作 |
|---|---|---|---|
| 参数补全门 | `clarify-human` | `intent=CLARIFY` + clarify_contracts（复用现有契约） | formData 回填 → 重入起草 |
| 整改门 | `fix-human` | `intent=AWAIT_FIX` + issues 渲染 | 修改后草稿 → 重入合规 |
| 落库确认门 | `confirm-gate` | `intent=AWAIT_CONFIRM` + draft 全文 + 合规结论 + assumption 列表 | 确认 → persist；取消 → end(status=cancelled_by_user) |

- 三个门共用 human 节点机制，**用户视角只有一种交互**：对话中回复文字或点击内联表单（前端复用 InlineFormEditor/DynamicForm，经 clarify_contracts 渲染，零新组件）。
- 落库失败不开单（persist onFailure=fail → 流程终止；order onFailure=continue 记录告警）——继承现状防孤儿语义，但现在**留痕在节点日志**，审计可查。
- 「仅起草不落库」= 用户在确认门选择「只保存草稿」，persist 节点 inputParams 由 confirm-gate 输出驱动（formData.action=draft_only 时 persist 走 saveConfigDraft 不开单）。

## 5. 过程透明化（SSE 协议增量）

### 5.1 新增事件 `flow_progress`

现有事件契约**零改动**（thinking/tool/text/done/warning/error 原样保留，前端向后兼容）。新增：

```
event: flow_progress
data: {
  "execution_id": "exec-20260906-0001",       // 审计锚点
  "workflow_code": "chat_configure_v2",
  "node_id": "compliance",                    // 引擎真实节点 id
  "node_name": "合规自检",                     // 业务文案（ThinkingCopy 词典驱动）
  "node_type": "tool",
  "status": "running" | "done" | "error" | "suspended",
  "attempt": 1,
  "branch": { "id": "fix", "expression": "..." },   // 仅 condition 节点
  "progress": { "current": 4, "total": 8 },   // 引擎按 connections 可达路径估算
  "summary": "已检查 3 条合规规则，1 项不通过",  // 完成时给（ToolOutputRenderer 复用）
  "elapsed_ms": 3200
}
```

- 前端 `ThinkingProcessPanel` 时间线新增「流程进度」段：真实节点顺序渲染，不再用 `WorkflowBuilder` 伪图。
- 挂起时 `flow_progress(status=suspended)` 后紧随 `done(intent=AWAIT_*, form_spec, execution_id)`——**done 仍是收尾事件**，语义与现有 CLARIFY/CONFIRM 完全对齐，前端只加「等待确认」面板挂到 execution_id。
- 历史回放：`chat_message.metadata` 增加 `flow_execution_id` 键，`buildReasoningSnapshot` 增加从 node_logs 重建时间线的逻辑（恢复后的思考线与实时流同构）。

### 5.2 事件与既有语义的映射一致性

| 引擎事件 | SSE | 用户看到 |
|---|---|---|
| onNodeStarted | flow_progress(running) | 「正在合规自检…」 |
| onBranchTaken | flow_progress(branch) | 「历史配置命中，建议复用」 |
| onNodeFailed(可重试) | flow_progress(running, attempt+1) | 「超时，重试中…」 |
| onNodeFailed(终态) | warning + flow_progress(error) | 失败说明 + 后续建议 |
| onSuspended | done(AWAIT_*) | 表单/确认卡片 |
| 终态 completed | text → done | 表达层总结 |

## 6. 可观测与可审计

### 6.1 补齐节点输入快照与重试留痕

现状缺口（调研确认）：`pd_ai_workflow_node_logs.input_data` 字段存在但引擎从不写入；attempt 恒为 1。本方案纳入（引擎侧小改）：

- `persistNodeLog` 写入变量解析后的真实入参快照（脱敏策略与 toolInputView 一致：白名单键保留）。
- 重试每次尝试各写一条 node_log（attempt 递增），超时/失败原因落 error_message。
- 这同时是 §6.2 前端时间线「为什么失败」的数据源。

### 6.2 对话↔执行双向追溯

```
chat_message.metadata.flow_execution_id  ──→  pd_ai_workflow_executions
pd_ai_workflow_executions.trigger_type='chat', notes.session_id  ──→  chat_session
```

- 排障路径：用户报障（会话截图）→ 会话 ID → execution_id → node_logs 逐步回放（入参/出参/分支依据/耗时），定位到节点级。
- 审计路径：工单 ID → 反查 execution → 「哪个节点写的库、哪个门放行的、放行时用户看到了什么」（form_spec 快照存 node_log.output_data）。
- 运维端复用 FlowEngineController 既有端点（getExecution/getNodeLogs/listExecutions），不新增管理面。

### 6.3 与本体层 trace 的贯通

tool 节点执行的工具内部已有 `reasoningTrace`（本体推理留痕）与 `trace_id`（配置追溯）。贯通方式：`flow.tool` 节点的 node_log.output_data 收敛 ToolOutputRenderer 摘要 + trace 引用（trace 全文仍由工具侧按 trace_id 提供，避免 node_log 膨胀）。

## 7. 场景级工作流清单与路由

### 7.1 首批固化工作流（评审冻结后入库 pd_ai_workflows）

| workflow_code | 场景 | 覆盖业务 | 复用工具 |
|---|---|---|---|
| `chat_configure_v2` | rd | RD-1 智聊主链路 | rd_config_discover / rd_compliance / rd_draft_manage |
| `config_discover_v2` | rd/query | RD-3 智查·历史复用 | rd_config_discover（+copy-as-draft 建议） |
| `batch_parse_v2` | rd | RD-2 智读·文档转配置 | rd_file_parse（内含批量迭代封装） |
| `ops_analysis_v2` | ops | OPS-4/5 归因+稽核组合 | swrl_root_cause / swrl_risk_audit / sparql_query |
| `query_reuse_v2` | query | query.archive 正式化 | rd_config_discover |

### 7.2 路由决策（SceneFlowRouter，确定性代码）

```
输入：QueryPlan（理解层产物）+ session.executionBinding
判定顺序（短路）：
  1. executionBinding 存在（挂起态） → ChatHumanBridge.resume（不路由）
  2. FlowIntentRouter 关键词命中     → 快路径直达引擎（现状保留）
  3. plan.intent 映射表命中          → workflow_code（映射表为代码常量+配置覆盖，
                                       变更走评审，非 LLM 每轮决定）
  4. 未命中                          → 现有 LLM 动态编排（双轨兜底，flow_execute 仍可选）
```

- 意图→工作流映射是**编译期决策**（区别于现状 LLM 每轮运行时决策），这是「链路固化」的本质；但**理解层仍自由**——新意图出现时 LLM 仍可探索，成熟一条固化一条（AI 原生三步走：探索→评估→固化）。
- query 场景扶正：`AgentCapabilityRegistry` 增加 query 白名单（rd_config_discover / rd_scheme_compare / sparql_query 三工具声明 scene=query），修复 sceneToBackendScene 映射（'compare'→rd 或后端注册 compare 场景，实施期二选一）。

### 7.3 Feature Flag 与灰度

```
prodai.chat-workflow:
  enabled: true|false            # 总开关（false = 完全现状）
  scene-workflows:
    rd: chat_configure_v2
    query: query_reuse_v2
    ops: ""                      # 空 = 该场景暂不启用，走动态编排
```

- 开启且路由命中 → 引擎链路；否则 → 现状链路，**两轨共享工具层与本体层**，行为差异仅执行域。
- 观测指标：execution 终态分布 / 挂起恢复率 / 澄清轮次分布 / 节点 P95 耗时（node_logs 聚合即可，无需新基建）。
- 回退即关 Flag，无数据迁移风险（执行实例是追加数据）。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 工作流固化过死，长尾需求（LLM 本可灵活处理）被流程卡住 | 双轨兜底（路由未命中走动态编排）；固化判据 §0 三问，探索型需求永不固化 |
| 重入子流程导致执行实例膨胀 | __workflow_chain 上限 5 + 主流程 condition 重入计数兜底 + 澄清渐进式（每轮最多 3 问）降低重入次数 |
| human 挂起后用户流失（72h TTL 到期失败） | 24h 追问提示（体验项）；失败态可 resume 续跑（引擎既有能力） |
| LLM 节点 JSON 输出不稳 | json_schema 校验 + 重试附错误 + onFailure=continue 降级路径（合规节点兜底兜住错误草稿） |
| SSE 事件流增长（每节点 2+ 事件） | flow_progress 单事件多字段（不做多事件拆分）；前端按 nodeId 原地更新（复用既有原地更新语义） |
| 两轨行为不一致引发用户困惑 | 工具层/本体层共享（结果一致性由既有回归测试保障）；差异仅在过程呈现与确认点，灰度报告对齐 |
| 引擎事件发布影响主流程 | 异步投递 + 失败仅告警（§3.1）；Listener 可选注入，缺省零影响 |

## 11. 遗留决策点（需评审确认）

1. **整改分支形态**：§4.2 子流程重入 vs 引擎原生支持「回边」（后者违反 DAG 铁律，需改引擎校验器，不建议）。**建议子流程重入**。
2. **query.compare 映射修复方向**：前端改映射（'compare'→'rd'）vs 后端注册 compare 场景。**建议后端注册**（与「能力自声明」哲学一致）。
3. **重入计数载体**：system 变量注入（引擎扩展）vs 子流程 output 透传（零扩展）。**建议先 output 透传**，代价是定义略显繁琐。
4. **flow_execute 与 SceneFlowRouter 的长期关系**：Flag 全量开启后，flow_execute 保留为兜底通道还是退役？**建议保留**（探索型意图的出口）。
5. **ThinkingCopy 是否为新增节点（flow.human 的 AWAIT_* 状态）补词条**：需要（四要素词典扩展，工作量小）。
