# 产商品研发助手（RdAssistant）与运营助手（OpsAssistant）对齐改造方案

> 状态：**已完成**（阶段A展示层对齐、阶段B研发链路接入翻译层、阶段C清理收敛均已完成）
> 背景：运营助手已完成 LLM 智能体翻译层升级改造。本文档清点研发助手差异并提出分阶段 A→B→C 对齐方案，现已全部实施完成。

---

## 一、背景与核心差异

两个助手在「消息处理链路」上存在根本性差异：

| 维度 | 运营助手 OpsAssistant（已升级） | 研发助手 RdAssistant（未升级） |
| ---- | ------------------------------ | ------------------------------ |
| 查询入口 | 所有查询经 `scenarioToScene` 转换后**统一走翻译层** `sendAgentMessage` | 核心场景走**前端本地模拟 playbook**，仅无附件闲聊兜底走 `sendAgentMessage` |
| 底层能力 | 后端 AgentOrchestrator 翻译层（理解→执行→表达） | 前端 `productConfig.simulate*` / `playProductReply` mock playbook |
| 三阶产物 | 读取 `m.queryPlan` 生成 ContextBar 上下文标签 | 无 queryPlan 三阶产物 |
| 展示组件 | evidence 在 ProductOpsPanel 展示 | 无 evidence 展示 |

**关键点**：研发助手依赖的 `checkCompliance`、`submitCurrentDraft` 是真实后端调用，但核心「智聊配置生成、智读文件解析、智查、智检」仍是前端本地模拟，未接入后端翻译层，因此没有 queryPlan/evidence 三阶产物，也无法获得翻译层的统一上下文管理。

## 二、前端链路差异清单

### 2.1 消息处理入口对比

- **OpsAssistantPage.vue**：`onSend` → `scenarioToScene` → 统一 `sendAgentMessage`（第337行注释：统一走翻译层入口，三阶架构 理解→执行→表达），读取 `m.queryPlan` 生成 ContextBar 上下文标签（第78-109行）。

- **RdAssistantPage.vue**：`onSend`（第708行）→ `resolveProductScenario` 解析场景 → `runProductScenario`（第657行）→ `loadScenarioPlaybook`（第548行）→ 按场景分发到本地模拟：
  - `chat-generate` → `generateProductFromChat`（智聊·对话配置）
  - `file-parse` → `simulateFileParse`（智读·文件配置）
  - `query` → `simulateQuery`（智查）
  - `compliance` → `runComplianceCheck`（智检）
  - 仅无场景/无附件兜底走 `sendAgentMessage`（第743行）

### 2.2 展示层现状（重要发现）

- `QueryPlanCard.vue` 文件**存在**（渲染意图/工具/待补充/参数），但**未被任何组件 import 引用**。
- `EvidenceCard.vue` 文件**不存在**。
- `ContextBar.vue` 文件存在，且已在 `ChatInput.vue` 中引用（双助手共用），但仅运营助手通过 queryPlan 派生标签。
- 翻译层 queryPlan/evidence 数据已在 `useChatStream.js` 中透传并持久化（`chatApi.js` 的 `buildMessageMetadata` / `restoreMessageMetadata` 处理 `query_plan` / `evidence_summary`），但**消息渲染层 `ChatMessageList.vue` 未展示 QueryPlanCard / EvidenceCard**，仅在各页面计算属性里用 queryPlan 派生 ContextBar 标签。

### 2.3 前端差异结论

运营助手「链路打通 + 展示对齐」，研发助手「链路未打通 + 展示组件未接」。即便仅做展示层改造，也需要研发助手核心场景先接入翻译层，才能产出 queryPlan / evidence 数据。

## 三、后端缺口清单

### 3.1 翻译层已支持的能力

`AgentOrchestrator.java` 已支持意图：`query`、`root_cause`、`risk_audit`、`online_check`、`ops_monitor`、`compare`、`CLARIFY`、`CHAT`，流程为 理解→执行→表达，SSE 事件 `thinking`→`tool`→`text*`→`text_done`→`done`。流式入口 `POST /api/v1/agent/chat/stream`（AgentController.java）。

### 3.2 翻译层现有 AgentTool

`service/agent/tool/` 目录下的工具：

- `SparqlQueryTool`（sparql_query）
- `SwrlRootCauseTool`（swrl_root_cause）
- `SwrlRiskAuditTool`（swrl_risk_audit）
- `RuleExplainTool`（rule_explain）
- `OntologyExplainTool`（ontology_explain）

### 3.3 后端缺口

翻译层**没有研发场景对应的 AgentTool**，如：

- 对话配置生成（chat-generate）
- 文件解析生成产品配置（file-parse）
- 产品合规校验（compliance）

研发助手现依赖 `checkCompliance`（`productOntologyApi.js`）等前端直调接口。因此若要研发助手完整接入翻译层，需在后端新增对应 AgentTool，并注册到工具注册表与意图路由。

## 四、对齐改造方案（供评审）

### 阶段 A：展示层对齐（最小改动，纯前端，零后端改动）

目标：让助手消息能展示翻译层的 EvidenceCard / QueryPlanCard，统一双助手体验。

1. ✅ 新建 `EvidenceCard.vue`（结构：`{ count, items:[{label,value,contribution,highlight}], summary, severity, title }`）。
2. ✅ 在 `ChatMessageList.vue` 接入 `QueryPlanCard.vue` 与 `EvidenceCard.vue`（双助手共用）。

> **关键技术发现（决定阶段A不改后端）**：
> - 后端为公共/共享组件，尽量不改。
> - `msg.evidence` 在实时流（`done` 事件）与历史恢复时**都有值** → EvidenceCard 实时可用。
> - `msg.queryPlan` 后端只在**非流式**返回并持久化到会话历史 metadata，实时流不推（后端设计上改推送业务可读方案文本，避免透传内部码）→ QueryPlanCard 仅**历史会话恢复**时展示，实时会话为空。此为运营助手亦存在的现状。
> - 因此阶段A完全不动公共后端。

### 阶段 B：研发助手链路接入翻译层（核心改造）

目标：让研发助手核心场景走后端翻译层，获得三阶产物与统一上下文。

**完成情况（阶段B已完成，后端编译＋前端构建均通过）：**

1. ✅ 后端新增 5 个研发场景 AgentTool（`service/agent/tool/rd/`，`@Component` 自动注册、与运营工具解耦）：
   - 对话配置生成 `RdConfigChatTool`（rd_config_chat，包装 `chatConfigure`）
   - 文件解析配置 `RdFileParseTool`（rd_file_parse，包装 `batchFromUploadedFile` / `batchFromDocument`）
   - 合规校验 `RdComplianceTool`（rd_compliance，包装 `checkComplianceSmart`）
   - 配置发现 `RdDiscoverTool`（rd_config_discover，包装 `discoverConfigs`）
   - 多方案对比 `RdSchemeCompareTool`（rd_scheme_compare，包装 `compareConfigSchemes`）
2. ✅ 翻译层 `scene` 维度：`SessionContext` 新增 `scene`（不落库），`AgentController` 从请求透传（`/chat`、`/chat/stream`），`AgentOrchestrator` 新增 scene 重载。`DefaultUnderstander` 按 `isRdScene(context)`（scene=="rd"）分流：
   - RD 白名单 `RD_KNOWN_TOOLS` 与 `mapRdIntentToPlan`（RD_CONFIG_CHAT / RD_FILE_PARSE / RD_COMPLIANCE / RD_CONFIG_DISCOVER / RD_SCHEME_COMPARE）。
   - `buildSystemPrompt(rdScene)` 拆为 `buildOpsSystemPrompt` / `buildRdSystemPrompt`。
   - 运营路径（scene 为空）100% 原样保留（`KNOWN_TOOLS` / `mapIntentToPlan` / ops prompt 不变）。
3. ✅ 工具输出扩展：`ToolOutputRenderer.outputEntries` 改为遍历工具声明的全部输出字段，将完整结构化取值（`draft` / `compliance_pass` / `issues` / `items` / `batch` / `comparisons` / `recommended` 等）一并外泄到 tool 事件 `output`，前端据此驱动研发侧面板；对运营工具为增量暴露，不破坏既有 summary/count 语义。
4. ✅ 前端 `RdAssistantPage.vue` 对齐 Ops 模式：
   - `onSend` 所有核心场景统一 `sendAgentMessage({ text, scene: 'rd', params })`；文件解析经 `params.file_id` 透传附件；`onClarifySubmit` 补 `scene: 'rd'`。
   - `chatApi.sendAgentStream` / `useChatStream.sendAgentMessage` 支持 `scene` 透传；agent-stream `done` 后触发 `getPostProcessor(doneIntent)(doneMsg)`（与历史回放一致，直播流也能驱动面板）。
   - post-processor `applyRdToolToPanels(msg)` 按工具名读取 `toolResults[].output` 结构化数据，复用 `useProductConfig` 的 `buildProductFormCard` / `syncFormFromProduct` / `compareResult` / `showComparePanel` / `batchItems` / `showBatchPanel` 驱动 OfferingCanvas 表单卡 / 批次面板 / 对比面板。
   - 保留 `runProductScenario` / `loadScenarioPlaybook` / `finishProductReply` / `playProductReply`（仍被 `onQueryResultClick` / `handleConfirmSubmit` / 批次操作使用），仅 `onSend` 不再走 mock 分发。
5. ✅ 后端 `mvn -o compile -DskipTests` BUILD SUCCESS；前端 `npm run build` 通过。
6. ⏳ 待办：运行时冒烟测试（智聊/智读/智检/智查/对比各触发一次，确认 RD 工具路由、`output` 带出结构化数据、前端面板正确弹出）；阶段C 清理（阶段C 已完成，见下）。

### 阶段 C：全量对齐与清理（已完成）

1. ✅ 删除 mock playbook（`useProductConfig.js`）：`simulateQuery` / `simulateFileParse` / `generateProductFromChat` / `runComplianceCheck` / `runRootCauseAnalysis` / `runRiskAuditFlow` / `runCompareSchemes` / `loadConfigTrace` 共 8 个 mock 导出函数，及其仅被它们使用的专属辅助（`buildBatchPlaybook` / `buildChatPlaybook` / `buildNaturalChatReply` / `summarizeSlots` / `fieldCn` / `sourceCn` / `hasUploadAttachments` / `looksLikePlanContent` / `deriveDocMeta` / `needsServerParse` / `readAttachmentTexts` 等），并清理孤儿 import（从 `productOntologyApi.js` / `productOntologyLocal.js` / `ontologyLabels.js` 移除已无调用方的导入）。**保留**共享辅助（`draftToFormData` / `applyBatchFix` / `prepareProduct` / SSE 面板处理器）与被真实流程使用的 `evaluateHypothetical`；`runProductScenario` / `loadScenarioPlaybook` / `finishProductReply` / `playProductReply` 因仍被真实流程（`onQueryResultClick` / `handleConfirmSubmit` / 批次操作）复用而保留。删除后前端 `npm run build` 通过（主 JS 从 357.49kB 缩至 ~324kB）。
2. ✅ `ChatMessageList.vue` 统一渲染 QueryPlanCard / EvidenceCard 等共用展示收敛（阶段A 已接）。
3. ✅ 补充 `businessLabels.js` 研发助手意图/工具映射（`RD_CONFIG_CHAT` / `RD_FILE_PARSE` / `RD_COMPLIANCE` / `RD_CONFIG_DISCOVER` / `RD_SCHEME_COMPARE` 意图标签、`rd_config_chat` 等工具标签、`draft` / `text` / `offering_id` / `file_id` / `file_name` / `document_text` / `patches` / `compliance_pass` / `issues` / `comparisons` / `recommended` / `items` 参数标签、action 标签与 `toolOutputEntries` RD 工具输出条目）——前端无 lint/typecheck 脚本（`package.json` 仅 dev/build/preview），以 `npm run build` 为验证标准并通过。
