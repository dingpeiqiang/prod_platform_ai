# 超级助手统一入口与自主路由方案

> 状态：**方案评审稿**
> 目标：将「产品研发助手 / 产品运营助手 / 产品查询助手」合并为一个**超级助手**统一入口，由系统**自主路由**到对应能力域，支持**多轮连续路由**（一次会话内自动切换助手域，无需用户手动切换入口）。
> 原则：延续项目「LLM + 本体融合」与「理解 → 执行 → 表达」三层架构铁律，路由层保持**确定性可审计**，LLM 只做意图判定与表达，不产生业务结论。

---

## 一、现状盘点（改造的起点）

### 1.1 三个助手当前的真实差异

调研结论：三个助手在**后端**共用同一个 `AgentOrchestrator` 翻译层（理解→执行→表达），差异收敛在三处：

| 维度 | 载体 | 现状 |
|------|------|------|
| 场景键 `scene` | 前端 `assistantModes.js` → 请求体 `scene` 字段 → `SessionContext.scene` | `rd` / `ops` / `query` 三态；前端每个页面硬编码传入 |
| 角色提示词 | `prompts/intent/role_rd.txt` / `role_ops.txt` / `role_query.txt` | `IntentPromptAssembler.assembleSystemPrompt(scene)` 按 scene 选择 |
| 工具白名单 | 各 `AgentTool.getScenes()` 自声明 → `AgentCapabilityRegistry` 场景索引 | 工具按场景可见性守门（防跨场景调用） |

**关键发现：合并的物理基础已经存在。**

- 同一编排入口：`POST /api/v1/agent/chat/stream`（`AgentController`），三个助手本就共用；
- 能力注册表已是"场景→工具"单源（`AgentCapabilityRegistry`），且有跨场景工具先例：`RdConfigSearchTool`、`RdSchemeCompareTool`、`SparqlQueryTool`、`MetricQueryTool` 等声明了 `Set.of("rd","query")`；
- 意图归一化已存在（`IntentRecognitionSupport`），query 子场景（`query.ask/archive/compare`）已由前端统一归口 `scene=query`，后端自行分流——**这就是自主路由的雏形**；
- 路由体系多层齐备：`FlowIntentRouter`（关键词→固定流程）、`SceneFlowRouter`（计划→场景工作流）、`PlaybookRegistry`（触发词/意图→SOP 手册）、`ModelRouter`（场景→模型）。

### 1.2 阻碍合并的四个断点

1. **scene 只活一轮**：`SessionContext.scene` 注释明确"不落库"，每轮由前端硬传；历史会话恢复（`SessionManager.restoreFromPersistence`）不还原 scene → 会话级路由记忆缺失。
2. **表达层白名单硬编码兜底**：`DefaultPresenter.allowedToolsOf` 用 `rdScene ? "rd" : DEFAULT_SCENE`（ops）二值判定，query 场景在表达层会回落 ops 白名单——新增 `scene=auto` 会放大此问题。
3. **理解层角色提示词三选一静态选择**：`IntentPromptAssembler` 按 scene 切换角色文件，没有"一个角色看全域能力"的形态；`scene=rd` 才注入 `rd_rules_block.txt`。
4. **前端三个页面三份入口**：`RdAssistantPage / OpsAssistantPage / QueryAssistantPage` 各自硬传 scene（rd 页面还保留本地 mock playbook 链路残留），`/` 重定向到 `/rd`，无统一工作台。

## 二、目标架构

### 2.1 一句话

> 用户只看到一个「超级助手」；每轮消息进入**统一路由器**，由「规则快筛 + LLM 场景判定」决定本轮归属哪个能力域（rd/ops/query），并写入会话路由记忆；后续轮次在无明确跨域信号时**延续上一域**，命中跨域话术时**无缝切换**——用户全程无感知。

### 2.2 分层视图

```
┌─────────────────────────────────────────────────────────────┐
│ 前端超级助手工作台（/assistant 统一路由，替代 /rd /ops /query）  │
│  UnifiedAssistantPage = AssistantShell + 统一场景面板(合并)     │
└──────────────────────────┬──────────────────────────────────┘
                           │ scene="auto"（或不传）
┌──────────────────────────▼──────────────────────────────────┐
│ AgentOrchestrator（不变，仍为理解→执行→表达）                    │
│                                                              │
│  ★ 新增：SuperAssistantRouter（本轮能力域判定，确定性代码）      │
│   ├─ L0 会话路由记忆：上下文挂起/上一域延续判定（零成本短路）      │
│   ├─ L1 规则快筛：关键词注册表命中（复用 Playbook/Flow 注册表模式）│
│   ├─ L2 LLM 场景判定：与意图识别合并为一次调用（同一 prompt 两产物）│
│   └─ 输出：本轮 effectiveScene + 路由依据（可审计 trace）         │
│                                                              │
│  理解层 DefaultUnderstander：按 effectiveScene 组装提示词/白名单  │
│  执行层 Executor：能力注册表按 effectiveScene 守门（不变）        │
│  表达层 DefaultPresenter：修掉 ops 兜底硬编码（透传 effectiveScene）│
└─────────────────────────────────────────────────────────────┘
```

### 2.3 核心设计决策（为什么这样合并）

| 决策 | 结论 | 理由 |
|------|------|------|
| scene 取值 | 新增 `"auto"`（超级助手专用），保留 rd/ops/query 显式值 | 旧入口零破坏（兼容灰度），auto 才走路由器；符合"双轨并行、灰度接管"既有演进模式 |
| 路由判定位置 | **理解层之前、编排器内**独立组件 `SuperAssistantRouter` | 与 W2 挂起短路、手册触发词快筛同级——都是"进入理解层前的确定性前置判定"；LLM 判定并入理解层同一次调用，不增加 LLM 次数 |
| 路由判定方式 | L0 记忆延续 → L1 规则命中 → L2 LLM 判定 → 兜底延续/默认 | 三级瀑布与 PlaybookRegistry"触发词快筛→意图升级"同构；确定性优先，LLM 兜底，可审计 |
| 会话路由记忆 | `SessionContext` 新增 `routeState`（上一域 + 置信度 + 切换轮次），随 metadata 落库恢复 | 多轮连续路由的核心；复用 `restoreContextFromMetadata` 恢复通道 |
| 提示词形态 | 新增 `role_super.txt` 全域角色 + 三域"能力说明书"片段按 L1/L2 结果**动态注入** | 避免静态三选一；全域角色只列三域职责边界与判定规则，具体工具清单仍按判定结果域注入（白名单守门不放松） |

## 三、SuperAssistantRouter 详细设计

### 3.1 三级判定流水线

```java
@Component
public class SuperAssistantRouter {

    public record RouteDecision(String effectiveScene, String source,
                                String matchedKeyword, String reason) {}

    /**
     * 判定本轮 effectiveScene。仅当请求 scene=auto 时调用。
     * L0：会话挂起态/进行中事务（挂起工作流、待提交工单）→ 强制延续上一域；
     * L1：关键词注册表命中（三域各一张词表，命中即定域，确定性可审计）；
     * L2：LLM 判定（理解层同一次调用中额外输出 scene 字段）；
     * 兜底：有上一域 → 延续；无上一域 → 默认 ops（与 DEFAULT_SCENE 语义一致）。
     */
    public RouteDecision decide(String question, SessionContext context) { ... }
}
```

**L0 会话路由记忆（最高优先级，零成本）**

- 上一轮存在挂起工作流（`context.hasPendingExecution()`）→ 延续该工作流所属域；
- 上一轮产生 rd 工单/草稿且未终结（会话工单实时状态非空）→ 延续 rd（避免"提交它"这类跨轮指代被误路由）；
- 其余情况进入 L1。

**L1 规则快筛（词表外置 `prompts/intent/scene_routes.yaml`，支持热更，模式对齐 FlowIntentRouter 关键词注册表）**

词表设计示例（高置信度术语级命中，宁缺毋滥）：

| 域 | 命中词示例 |
|----|-----------|
| rd | 做一个套餐、生成草稿、合规校验、提交工单、方案对比（+创建意愿动词）、导入方案文档 |
| ops | 收入下滑、环比、归因、风险稽核、0元资费、告警、处置工单、规则运营 |
| query | 多少流量、包含什么、查一下…配置、对比…套餐、命名规范、备案公示 |

冲突消解：多域同时命中 → 交 L2 判定（把命中情况作为提示注入 LLM）。

**L2 LLM 场景判定（与意图识别合并，不增加调用次数）**

在 `base_prompt.txt` 的 JSON 契约中增加一个字段：

```json
{ "scene": "rd|ops|query", "intent": "...", "action": "...", "tools": [...], "params": {...} }
```

- 仅当 `scene=auto` 时要求 LLM 输出该字段（显式 scene 请求跳过，行为与现状完全一致）；
- 解析后与 L1 结果互相校验：L1 与 L2 一致 → 直接采信；冲突 → 采信 L2 但记录 `reason` 供审计与词表迭代；
- 判定结果回写 `routeState`。

### 3.2 多轮连续路由的状态机

```
              ┌────────────────────────────────────────────┐
              │            会话 routeState                 │
              │  lastScene / sinceTurn / lastSource        │
              └────────────────────────────────────────────┘
   新消息(scene=auto) ──► L0 延续判定 ──命中──► effectiveScene = lastScene
                              │未命中
                          L1 词表快筛 ──命中──► effectiveScene = 命中域
                              │未命中/多域冲突
                          L2 LLM 判定 ──► effectiveScene = LLM 结果
                              │
              与 lastScene 不同？ ──是──► 切换域（reason 落 trace，响meta透出 scene_switched）
                                    └─否──► 延续域
```

跨域指代处理（多轮连续路由的关键语义）：

- **延续优先**："再改一下月费"、"提交它"、"那它的档案呢" —— 代词/省略主语时 L0 延续上一域；
- **显式切换**："帮我查一下刚才那个套餐的收入表现"（rd→ops）、"这个套餐配置生成草稿"（query→rd）—— L1/L2 命中即切换，**上一域产物（草稿 ID/工单号/查询证据）仍在 SessionContext 缓存中跨域可用**（现有 `resolvedParams`/`cachedEvidence` 机制天然支持，无需改造）；
- **切换失败兜底**：切换后理解层产出 CLARIFY（参数不足），澄清轮延续新域，不弹回旧域。

### 3.3 可审计性（对齐项目铁律）

每次路由决策输出结构化 trace，随 `query_plan` metadata 落库：

```json
{ "route": { "scene": "ops", "source": "L2-llm", "keyword": null,
             "prevScene": "rd", "switched": true, "reason": "话术含『收入下滑/归因』" } }
```

前端收到 `scene_switched` 可在对话流中插入轻提示（如"已切换到运营分析能力"），用户保留知情权；后台管理中心可增加路由命中统计（L0/L1/L2 各占比、切换次数），驱动词表迭代。

## 六、分期实施计划

| 阶段 | 内容 | 验收标准 |
|------|------|---------|
| **P0（1~2 天）** | 修 `DefaultPresenter` 白名单兜底缺陷（改造点 #7）——它是合并的前提，也是现存 bug | query 会话表达层工具清单正确 |
| **P1（3~5 天）** | 后端 SuperAssistantRouter（L0+L1）+ routeState 落库恢复 + `scene=auto` 全链路打通；先只做"延续+词表"，LLM 判定兜底为"延续/默认" | 幂等回归：显式 scene 三入口行为零变化；auto 会话内同域多轮延续正确 |
| **P2（2~3 天）** | L2 LLM 场景判定（base_prompt 契约扩展 + 解析 + L1/L2 互校）；role_super.txt | 跨域切换话术用例集通过（rd↔ops↔query 各 5 例） |
| **P3（3~5 天）** | 前端超级助手工作台（SuperAssistantPage + 路由标签 + 切换轻提示）；旧路由保留 | 三域场景在单一入口完成全流程演示 |
| **P4（持续）** | 词表迭代（路由统计看板）、旧页面收编、多意图拆分预研 | L1 命中率 ≥ 阈值后逐步收缩 L2 调用 |

回归防线：现有显式 scene 链路（旧三入口）在 P1~P3 全程零行为变化（双轨并行），超级助手仅 `scene=auto` 新链路生效。

## 七、远期演进（不在本期）

1. **单消息多意图拆分**：一条消息含多域任务（"查A商品并归因它本月收入下滑"）→ LLM 输出多计划（`understandAll` 已支持多子计划），按子计划各自路由域并行执行、汇总表达。前置条件：P2 的 scene 判定下沉到子计划粒度。
2. **路由模型轻量化**：L2 判定可切到 `gpt-4o-mini` 级小模型（ModelRouter 已有 complexity/intent 规则位），甚至规则蒸馏本地模型。
3. **用户可见路由面板**：后台管理中心的注册表式路由配置页（对齐 FlowIntentRouter 的 `flow_router_register` 工具语义），业务管理员可自助调词表。
