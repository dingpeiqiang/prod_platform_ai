# 产商品研发助手本体设计

> 本文是《产品配置模板化方案.md》第 10 节（本体技术结合路径）的深化设计，
> 覆盖产商品研发助手五大场景（智聊/智读/智检/智查/方案对比）的本体建模。

---

## 1. 设计目标与原则

| 原则 | 说明 |
|------|------|
| TBox/ABox 分离 | TBox 描述"产品体系 + 约束"（稳定，配置扩展主战场）；ABox 记录"会话/草稿实例"（高频，每次智聊产生） |
| 对齐存量 | 品类码（personMainPrc 等）、R-C* 规则 ID、草稿字段名（camelCase）直接复用，不造新词、不建转换层 |
| 模块化 | 四个模块独立演进，避免单体 OWL 文件 |
| 职责边界 | 本体管确定性知识（结构/约束/推理），自然语言理解与权衡判断归 LLM，流程时序归工作流 |

---

## 2. 命名空间与模块划分

```turtle
@prefix prod:   <http://sitech.ai/ontology/product#> .        # prod-core / prod-spec
@prefix rds:    <http://sitech.ai/ontology/rd-session#> .     # rd-session
@prefix prov:   <http://www.w3.org/ns/prov#> .                # 溯源（复用 PROV-O）
@prefix skos:   <http://www.w3.org/2004/02/skos/core#> .      # 品类/用户/渠道词表
@prefix sh:     <http://www.w3.org/ns/shacl#> .               # 约束
@prefix owl:    <http://www.w3.org/2002/07/owl#> .
```

| 模块 | 内容 | 变更频率 |
|------|------|:---:|
| `prod-core` | 产品、组件、品类、资费、用户、渠道类层次与属性 | 低 |
| `prod-spec` | 每类产品的 SHACL NodeShape（= 配置模板的本体形态） | 中（新增产品 +1） |
| `rd-session` | 草稿、会话、批次、对比、合规报告等研发会话域 | 低 |
| `prov` | 字段填充来源与推理链（复用 PROV-O） | 低 |

---

## 3. 类层次（TBox 主干）

```
prod:ProductOffering（产商品）
├── prod:FusionOffering（融合套餐）
│   ├── prod:FamilyFusionOffering        ← 家庭融合
│   └── prod:CampusFusionOffering        ← 校园融合
├── prod:StandaloneOffering（单产品）
│   ├── prod:BroadbandOffering
│   ├── prod:IotCardOffering
│   └── prod:CloudDiskOffering
└── prod:ValueAddedOffering（增值/权益包）

prod:OfferingComponent（资费组件；产品由组件聚合而成）
├── prod:VoiceComponent（语音）
├── prod:DataComponent（流量）
├── prod:BroadbandComponent（宽带）
└── prod:SmsComponent（短信）

skos:ConceptScheme prod:ProductCategory   ← personMainPrc / familyBasePrc / broadBandMainPrc …
skos:ConceptScheme prod:TargetUser        ← 家庭 / 校园 / 政企 / 个人
skos:ConceptScheme prod:SalesChannel      ← 全渠道 / 线上 / 线下

研发会话域（rd-session，ABox 载体）：
rds:ConfigSession（智聊会话）→ rds:ConfigDraft（草稿）
rds:FileParseBatch（智读批次）→ rds:ParsedSchemeItem
rds:SchemeComparison（方案对比）
rds:ComplianceReport → rds:ComplianceIssue（R-C* 校验结果）
```

模板继承对应 OWL 分类：`prod:BroadbandOffering rdfs:subClassOf prod:FusionOffering` 的
裁剪关系由子类 NodeShape 收紧表达，继承合并交由推理机。

## 4. 关系与属性

### 4.1 对象属性

| 属性 | 定义域 → 值域 | 说明 |
|------|--------------|------|
| `belongsToCategory` | ProductOffering → skos:Concept | 复用存量关系，挂品类码 |
| `comprisesComponent` | ProductOffering → OfferingComponent | 产品↔组件 1..n |
| `bindsMainPackage` | FusionOffering → ProductOffering | 融合绑主套餐 |
| `soldViaChannel` | ProductOffering → skos:Concept | 渠道 |
| `draftOfSession` | ConfigDraft → ConfigSession | 智聊归属 |
| `parsedFromBatch` | ParsedSchemeItem → FileParseBatch | 智读归属 |
| `comparedIn` | ProductOffering → SchemeComparison | 对比成员 |
| `derivedFrom` | 任意 → 任意 | 溯源链（默认值/复制/解析来源） |

### 4.2 数据属性（关键决策：属性 IRI 对齐存量草稿字段）

| 属性 | 类型 | 约束 |
|------|------|------|
| `:offeringName` | xsd:string | 必填，≤50 字符 |
| `:monthlyFee` | xsd:integer | 必填，单位元，1..1000 |
| `:includeBroadband` | xsd:string | 枚举 300M/500M/1000M |
| `:channelScope` / `:targetUser` / `:bizScenario` | xsd:string | 枚举见对应 SKOS 词表 |

JSON-LD 形态下 `field_code` 即属性名，前端表单、报文投影、草稿字段零转换。

## 5. SHACL 约束规范（= 产品模板的本体形态）

每类产品一个 NodeShape，由配置模板（fields/enum/互斥）编译生成：

```turtle
prod:FamilyFusionShape a sh:NodeShape ;
  sh:targetClass prod:FamilyFusionOffering ;
  sh:property [
    sh:path prod:offeringName ; sh:minCount 1 ; sh:maxLength 50 ;
  ] ;
  sh:property [
    sh:path prod:monthlyFee ; sh:minCount 1 ;
    sh:datatype xsd:integer ; sh:minInclusive 1 ; sh:maxInclusive 1000 ;
  ] ;
  sh:property [
    sh:path prod:includeBroadband ; sh:in ( "300M" "500M" "1000M" ) ;
  ] ;
  sh:not [   # 互斥：绑主套餐 与 独立宽带组件 不可同时存在（对应 R-C 互斥校验）
    sh:property [ sh:path prod:bindsMainPackage ; sh:minCount 1 ] ;
    sh:property [
      sh:path prod:comprisesComponent ;
      sh:qualifiedValueShape [ sh:class prod:BroadbandComponent ] ;
      sh:qualifiedMinCount 1 ;
    ] ;
  ] .
```

**与 R-C* 合规引擎的对接**：SHACL 校验报告（`sh:focusNode` / `sh:path` / `sh:message`）
直接映射为现有 issues 结构（ruleId / field / level / message）。
`prod-spec` NodeShape 与 R-C 规则的对应关系在模板 `compliance_bindings` 中声明。

## 6. 推理规则与已知边界

| 推理类型 | 技术 | 示例 |
|---------|------|------|
| 默认值/派生 | SWRL | `FamilyFusionOffering(?x) ∧ belongsToCategory(?x, prod:familyBasePrc) → hasMessageRootKey(?x, "familyBasePrc")` |
| 类型识别 | OWL 分类推理 | matchers 关键词命中升级为语义分类，多模板歧义由推理机裁决 |
| 数值聚合 | SHACL 高级规则（SPARQL CONSTRUCT）或 Java | SWRL 不支持聚合；"月费 = 组件费用之和"必须划归此处，设计时即明确 |

## 7. 场景 → 本体能力映射

| 场景 | TBox 用途 | ABox 写入 | 查询/推理 |
|------|----------|----------|----------|
| 智聊·对话配置 | NodeShape 属性清单下发 LLM 作抽取约束 | 抽取结果实例化 `rds:ConfigDraft` | SHACL 即时校验 |
| 智读·文件配置 | 同上 | 批次实例化 `rds:ParsedSchemeItem` | SHACL 批量校验 |
| 智检·合规 | NodeShape | — | SHACL 全量校验 → `rds:ComplianceIssue` |
| 智查·历史复用 | — | — | SPARQL 按品类/场景/资费检索历史 draft |
| 方案对比 | — | `rds:SchemeComparison` | SPARQL 拉取要素 diff；结论由 LLM 解释 |
| 审计追溯 | — | `derivedFrom` / PROV-O 链 | SPARQL 回放推理链 |

## 8. 与存量系统的对接

| 存量资产 | 本体对接方式 |
|---------|-------------|
| mock_graph.json / rdf_seed.json | 作为 prod-core 初始 ABox/词表导入，品类码原样入 SKOS |
| R-C* 规则（ops_rules.json） | 规则 ID 保留；逐条评估 SHACL 化可行性，复杂规则保留 Java 并通过 compliance_bindings 绑定 |
| 草稿字段契约（camelCase） | 属性 IRI 直接使用字段名，JSON-LD 双向零转换 |
| 运营侧 SPARQL/SWRL 引擎 | 配置草稿入 ABox 后，运营侧智查/归因天然覆盖新产品，两侧同源 |

---

## 9. 建模陷阱

1. 不要把流程时序塞进本体——工作流管流程，本体管知识
2. 不要自造品类词表——SKOS 直接挂存量品类码，否则运营图谱与配置侧不同源
3. 聚合计算、跨实例联动是 SWRL 弱项，规划时划给 SHACL rule 或 Java
4. 属性 IRI 对齐草稿字段，避免引入转换层
5. NodeShape 不要按页面建模——按"产品类型"建模，页面只是消费视图

## 10. 分阶段实施

| 阶段 | 内容 | 验收标准 |
|------|------|---------|
| B1 本体骨架 | prod-core 类层次 + family_fusion NodeShape + SHACL 校验接入现有合规链路 | 家庭融合草稿走 SHACL 校验产出等价 issues |
| B2 模板编译 | 配置模板 → NodeShape/SWRL 编译器；宽带单产品纯配置验证 | 新增产品零代码完成本体注册与校验 |
| B3 图谱合并 | 草稿 ABox 入库存 RDF；运营侧 SPARQL 联通；溯源链回放 | 智查覆盖新产品；"为什么"可回答 |
