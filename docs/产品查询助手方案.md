## 0. 商用化差距总评（v2.0 新增）

**结论：架构骨架是生产级的，业务肉身是 Demo 级的。** 三阶翻译层、工具 SPI、手册机制、SSE 契约均已完备，但从业务场景实现看，当前 query 场景只是"一条链路 + 一个工具的皮"在跑，与生产商用要求存在系统性差距：

| 维度 | 当前状态 | 商用要求 | 差距评级 |
| --- | --- | --- | --- |
| 数据 | mock_graph.json 92 个演示商品；JDBC 源留口未联调 | 真实在架商品/存量用户/指标数据对接 + 数据时间戳透出 | ★★★ |
| 工具面 | 6 个只读工具，覆盖单域（移动商品） | 商品 360、存量用户套包、异网对比、地市政策、多域（宽带/终端/号卡）、政企目录 | ★★★ |
| 交互 | 单轮问答为主，无多轮条件收敛 SOP | 渐进式收敛（粗查→澄清→精查）、结果过载时的降维呈现 | ★★ |
| 权限 | 无数据行权限（用户→地市/渠道/敏感度） | 省内署必备的行级隔离与查询审计 | ★★★ |
| 知识 | 知识库内存实现 2 条种子文档 | 制度/资费文档规模化接入 | ★★ |

差距根因：架构先行、场景后补——三位一体设计均围绕研发写路径（草稿→合规→开单），query 仅是架构验证的"读侧样本"；演示导向的数据完备度不等于商用完备度。本章差距由 §5.6 逐项展开、§6 阶段 A/B/C 收敛。

## 1. 背景与定位

产品查询助手面向"找产品、看配置、比方案、查事实"的高频只读诉求。它继承本项目"LLM 听懂与说清、本体保证事实可信、工作流保证确定性执行"的三位一体哲学，是 LLM+本体架构在**只读查询**场景的落地形态。

**与另两个助手的关系**：
- 研发助手（rd）：面向"从需求到上架"的**写路径**（草稿 → 合规 → 开单 → 工单）；
- 运营助手（ops）：面向在架商品的**运维路径**（巡检、风险、根因）；
- 查询助手（query）：面向**读路径**，是前两者的"前置窗口"——查到的在架商品可一键"复制为草稿/复制即开单"转入 rd 流程，查到的经营异常可转交 ops 工具。

**设计基线（重要）**：本方案基于对现状代码的盘点而非凭空设计。query 场景在《智聊场景重设计方案》§7.2"场景扶正"中已基本落地，本文档第 3 章先盘点已实现能力，第 5 章再给出差距与改进路线。

## 2. 目标与非目标

### 2.1 目标

1. **一句话查产品**：自然语言（品类、资费、合约期、在架状态、时间窗口等条件组合）直达在架商品事实，回答附证据与来源；
2. **零工具改动扩展**：新查询工具实现 `AgentTool#getScenes()` 返回含 `query` 即自动进入场景能力集；
3. **只读安全**：query 场景默认无写操作，所有工具均为只读（查询、解释、对比、检索）；
4. **查询即流转**：查询结果可无缝衔接 rd（复制为草稿、复制即开单），形成"查—改—办"闭环；
5. **配置驱动**：手册（Playbook）、提示词、触发词、意图归一化全部配置化，禁止硬编码业务规则（AI 主导原则）。

**商用化目标（v2.0 增补）**：

6. **真实数据可用**：脱离 mock 数据，真实在架商品/指标数据可查且数据新旧可感知；
7. **数据权限合规**：查询范围随用户身份（地市/渠道/角色）隔离，查询行为可审计；
8. **商用高频场景覆盖**：商品 360、存量用户套包、多轮收敛查询等真实生产场景可用（§6 阶段 A/B）。

### 2.2 非目标

- 不做数据写入（上架、改价、下架等一律转交 rd/ops 或工单）；
- 不做通用 BI 报表（指标查询仅覆盖日宽表 `dwd_prod_metric_daily` 既有指标）；
- 不重复建设比对引擎（多方案对比复用 rd 场景的 `rd_scheme_compare`）。

## 3. 现状盘点（已落地能力）

### 3.1 端到端链路

```
用户输入（前端 QueryAssistantPage，scene=query）
  → POST /api/v1/agent/chat/stream（SSE，SseEmitter 300s）
  → AgentOrchestrator（三阶翻译层）
      ① Understander：触发词快筛 → 手册直达 / 意图升级 / 动态编排
         提示词 = base_prompt.txt + role_query.txt（IntentPromptAssembler 装配）
         意图归一化（IntentRecognitionSupport.normalizeIntentType）：
           compare / what_if / hypothesis → product_ops_query
      ② Executor：QueryPlan（intent=SPARQL_QUERY, tools=[sparql_query] 等）逐步执行
      ③ Presenter：工具结果 → 自然语言作答 + 建议追问
  → SSE 事件：thinking → tool → text → text_done → done（异常时 warning/error）
  → 会话持久化：pd_ai_chat_sessions / pd_ai_chat_messages / pd_ai_chat_message_metadata
```

### 3.2 工具清单（query 场景可见 6 个，全部只读）

| --- | --- | --- | --- |
| `sparql_query` | ops, query | 自然语言 → SPARQL 查 RDF 在架商品事实 | `OntologyService.nlDiscoverAndRetrieve`（LlmIntentExtractor + SparqlConfigDiscoverer） |
| `rd_config_search` | rd, query | 历史/相似配置检索 | `ProductOntologyService.discoverConfigs` → `ChatConfigureService` |

| `ontology_explain` | ops, query | 概念/制度问询 | `OntologyService.explain`（详见 §5.2 已知落差） |

### 3.3 手册（Playbook）

- 唯一 query 场景手册：`resources/playbooks/query-ask.yaml`
  - `scene: query`，intents：`[SPARQL_QUERY, PRODUCT_OPS_QUERY]`
  - 两步 SOP：`sparql_query` 查询 → 整理作答；纯只读，无写步骤；
- 触发词快筛（`PlaybookRegistry.matchTrigger`）零 LLM 成本直达；命中失败则回退意图升级（playbookUpgradePath）或动态编排三级瀑布；
- rd/ops 场景手册（discover-history、market-insight 等）中带 query 语义触发词的部分，对 query 用户同样可达（经意图归一化）。

### 3.4 前端

- `QueryAssistantPage.vue`（路由 `/query`）提供三个子入口：
  - `query.ask` 智能问答 → 后端 scene=`query`；
  - `query.archive` 档案调阅 → **当前转发到 scene=`rd`**（见 §5.1）；
  - `query.compare` 比对分析 → scene=`compare`（见 §5.3）；
- 查询结果卡片 `msg.queryResults`：支持"复制为草稿 / 合规检查 / 复制即开单"（`copyAsDraft`）跳转 rd 流程；
- 比对面板 `ComparePanel`：由 `rd_scheme_compare` 输出（comparisons / recommended / explanation）驱动；
- 助手清单 `assistantModes.js`：`{ key: 'query', route: '/query', icon: 'search', color: '#6d28d9' }`，与 rd/ops 并列。

### 3.5 数据层

- **事实源不在 SQL，在本体图**：
  - TBox：`ontology/product-config.ttl`（v2.2 四层架构本体）+ `product-ops.ttl`；
  - ABox：`ontology/mock_graph.json`（演示：92 个在架商品 + 7 套配置方案）；`FactGraphSyncService` 将 shelfOfferings 灌入 RDF4J（幂等先删后写）；
  - 生产数据源：`ontology.abox-source=jdbc` 时走 `JdbcOpsProductDataSource` 只读视图，30 分钟定时刷新（ABoxSyncScheduler），失败回退 last-known-good；
- SQL 仅承载会话/工作流/工单/指标：`pd_ai_chat_*`、`pd_ai_workflows*`、`pd_ai_ops_work_orders`、`dwd_prod_metric_daily` 等 22 张表；
- `LlmIntentExtractor`：NL → DiscoverIntent JSON（query_type / keywords / monthly_fee / fee_tolerance / state / time_window_days / limit），`SparqlConfigDiscoverer` 负责品类标签映射（TYPE_LABELS）与参数化 SPARQL 构建。

## 4. 架构设计

### 4.1 分层

```
┌────────────── 前端 Vue3 ──────────────┐
│ QueryAssistantPage / ComparePanel     │  ← sendAgentMessage（SSE）
├──────────────── API ──────────────────┤
│ AgentController  /agent/chat/stream   │
├──────────── 编排（翻译层）─────────────┤
│ AgentOrchestrator                     │
│  Understander → Executor → Presenter  │
│  PlaybookRegistry（触发词/手册/SOP）   │
│  AgentCapabilityRegistry（场景能力集） │
├──────────── 工具（SPI）───────────────┤
│ 6 个 query 只读工具（§3.2）           │
├──────────── 事实与数据 ───────────────┤
│ 本体图（TBox+ABox）/ 宽表 SQL / 会话库 │
└───────────────────────────────────────┘
```

### 4.2 请求处理决策序（Understander）

1. **触发词快筛**：命中 query-ask 手册触发词 → 零 LLM 成本进入手册 SOP；
2. **意图升级**：手册执行中发现范围外诉求 → `handoffs` 升级（如查询命中方案对比 → handoff 至 `rd_scheme_compare`）；
3. **动态编排**：以上均未命中 → LLM 依据场景能力集（工具名+描述+参数+输出字段）自行规划 QueryPlan；
4. **澄清门**（ParamCompletionGate）：关键参数缺失 → CLARIFY 事件反问，不臆造参数。

### 4.3 只读约束

- query 场景注册的工具均无写副作用；编排层按场景过滤能力集，query 用户不会看到 draft/compliance/workorder 等写类工具；
- 需要变更时，工具结果或建议追问引导"复制为草稿/复制即开单"跳转 rd，而非在 query 内直接写。

### 4.4 数据行权限设计（v2.0，支撑 §6-A2）

**原则：权限过滤在参数化层强制注入，不依赖 LLM 遵从提示词，工具入参不可覆盖。**

```
用户请求（携带登录态）
  → 网关/Controller：解析用户身份 → UserScope{cityCode, channelType, role, sensitivity}
  → SessionContext.attach(userScope)                 【身份上下文随会话流转】
  → Executor 调工具 → SparqlConfigDiscoverer.build(intent, userScope)
        ├── intent 条件（品类/资费/状态…）：来自 LlmIntentExtractor
        └── 权限子句（强制注入，后拼接，优先级最高）：
              FILTER(?cityCode IN (userScope.visibleCities))
              FILTER(?sensitivity <= userScope.maxSensitivity)
  → RDF4J 执行（物理上查询不到越权行）
```

要点：

1. **注入点唯一**：仅 `SparqlConfigDiscoverer`（及后续 `MetricQueryTool` 的 SQL 构建器）两个数据访问出口需要注入，工具数量增长不放大注入面；
2. **LLM 零参与**：DiscoverIntent schema 不含权限字段，LlmIntentExtractor 输出再"大"也进不了权限通道；
3. **userScope 不可伪造**：由后端从登录态解析，前端传入的 scene/message 体中的任何 scope 字段一律丢弃；
4. **metric_query 同构**：SQL WHERE 注入 `city_code IN (...)`，与 SPARQL 口径一致；
5. **审计对账**（A3）：每次查询落 metadata（userScope 摘要 + 命中范围 + 返回条数），支持事后"越权尝试"抽查。

### 4.5 多轮收敛查询 SOP（v2.0，支撑 §6-B1；✅ 已实施）

现状 query-ask 是"一步直通"；升级为**结果规模感知的收敛循环**。**实施落地（阶段 B1）**：判定收拢在 `QueryRefinePolicy`（model 包，纯确定性组件），接线点为编排层手册链路（`runPlaybookPath` / `runPlaybookStream`）粗查落袋后：

```
① 粗查：手册链路 sparql_query 执行（上限默认 20 个实体）
② 规模判断（QueryRefinePolicy.judge，确定性代码，非 LLM）：
      hits ≤ 5   → 直接呈现全部（OK）
      5 < hits ≤ 20 → 呈现 + refine_suggest 收敛建议（不阻断）
      hits > 20（或触顶）→ 走③
③ 澄清（复用 CLARIFY 响应契约：clarify / clarify_contracts，前端零改动）：
      优先级：地市 > 资费档位 > 时间窗 > 关注维度（REFINE_DIMENSIONS）
      首轮问 2 项；第二轮跳过已答维度；至多 2 轮（SessionContext.meta.refine_rounds 独立计数）
      轮次达上限 judge 回落 OK → 强制降维呈现
④ 精查：澄清答案经 applySuppliedParams 写入 resolvedParams，mergeAnswer 拼接收敛子句进问题重查
⑤ 降维呈现：summaryPrompt 注入 TOP 10 + 排序依据 + "共 X 条"总量声明
```

设计约束（实施核验）：

- 澄清至多 2 轮，第 3 轮强制降维呈现兜底（`MAX_REFINE_ROUNDS=2`，与参数补全门 MAX_CLARIFY_ROUNDS=3 独立计数）；
- 规模判断是确定性代码（DRY：`QueryRefinePolicy` 单一实现，手册与动态编排共用；无 LLM、无 Spring 依赖）；
- query-ask.yaml SOP 增 refine 步骤（规模判定与收敛语义）+ 护栏补充（收敛上限降维/总量如实声明），YAML 驱动、无硬编码业务规则；
- 仅对手册工具链含 sparql_query 的查询类手册生效（非查询手册零感知）。

### 4.6 新增工具 SPI 定义（v2.0，支撑 §6-A4/B2/B3）

新增工具遵循既有 SPI 契约（参照 `SparqlQueryTool`：name / description / label / scenes / handoffs / outputFields / params / execute）。定义先行，供评审后开发。

**`product_360`（商品 360 视图，阶段 A4）**

```java
getName()    → "product_360"
getDescription() → "按商品 ID 或名称聚合呈现单商品全景：资费、订购量、投诉、合约到期分布、状态变更历史"
getLabel()   → "商品全景"
getScenes()  → Set.of("ops", "query")           // 运营也受益，场景自声明
getHandoffs() → List.of("rd_scheme_compare", "metric_query")
getParams()  → [ offering_id(required, 有 id 走精查) |
                 offering_name(required, 无 id 走名称匹配) ]
getOutputFields() → [
    summary        : nl_answer(SUMMARY, "商品全景摘要"),
    profile        : basic_profile(OTHER, "基础档案：品类/资费/状态/上架时间"),
    subscriptions  : metric_trend(COUNT,  "近30天订购量走势"),
    complaints     : risk_signal(OTHER,   "投诉热点与趋势"),
    contract_expiry: risk_signal(OTHER,   "合约到期分布（未来6个月）"),
    sources        : data_source(OTHER,   "数据来源与截止时间戳")
]
```

**`user_plan_query`（存量用户套包查询，阶段 B2；✅ 已实施）**

实施落地与 SPI 定义差异说明（去旧留新）：

- `getHandoffs()` → `List.of("sparql_query", "product_360", "rd_config_search")`（查到套包后承接商品详情/相似配置，比单承接更贴客服链路）；
- 增 `user_masked`（OTHER，打码标识）与 `sources`（OTHER，数据来源）输出字段；
- 数据源 v1 为 mock 确定性生成（订购面演示数据，同指标域 mock 模式），生产接 CRM 只读视图时替换数据供给，工具编排与门控零改动；
- 敏感度门控在 `execute()` 入口强制执行（`UserScopeContext.current().canAccess(SENSITIVITY_SENSITIVE)`），非全量权限账号直接拒绝，不返回降级数据。

```java
getName()    → "user_plan_query"
getDescription() → "按用户标识（脱敏）查询其当前订购套包、合约期、可选包与生效变更记录"
getLabel()   → "用户套包查询"
getScenes()  → Set.of("query")                   // 仅查询助手，客服/渠道口径
getHandoffs() → List.of("sparql_query", "product_360", "rd_config_search")
getParams()  → [ user_id(required, "脱敏用户标识，后端解析为内部 ID"),
                 include_history(optional, boolean, 默认 false) ]
getOutputFields() → [
    summary      : nl_answer(SUMMARY, "套包概览"),
    current_plans: plan_list(OTHER, "在订套包（主套包/可选包/增值包）"),
    contract     : basic_profile(OTHER, "合约期与到期日"),
    history      : plan_list(OTHER, "近6个月变更记录（include_history=true 时）")
]
// 硬性约束：输出不含完整号码/证件信息；入参 user_id 经 UserScope 校验归属地市权限（§4.4）
```

**`market_benchmark` / `city_policy_query`（阶段 B3；✅ 已实施）**

结构同 user_plan_query SPI 契约，实施落地要点（去旧留新）：

- `getScenes()` → `Set.of("query", "ops")`（查询助手主口径；运营定价参考/铺市排期跨场景自声明）；
- **来源与截止时间必透出**（方案 §6-B3 硬性约束）：sources 面必含 `data_as_of`（数据截止日期），nl_answer 摘要尾缀同步提示"数据截至"——竞对资费/政策时效性强，不可让用户把演示数据当真实行情；
- 数据敏感度 = INTERNAL（目录级情报，行权限内可见，无需 SENSITIVE 门控，与 user_plan_query 区分）；地市维度行权限过滤在数据接入后按 scope 叠加；
- 数据源 v1 为 mock 确定性生成（MarketBenchmarkTool：2 竞对 × 档位分箱 low/mid/high，本网对标对齐真实货架 shelfOfferings；CityPolicyQueryTool：地市字典四类型政策 + policy_type 过滤 + 未覆盖地市拒绝不冒充），生产接竞对资费情报库/政策库时替换数据供给，工具编排与契约零改动。

实现要点：

1. 每个工具一个 `@Component`，构造注入数据服务（CRUD 数据访问在 service 层，工具仅做参数校验与编排翻译）；
2. `execute()` 内部**必须**透传 SessionContext 的 userScope 到数据层（§4.4 注入点），不新增权限旁路；
3. outputFields 的 Role 标注（SUMMARY/COUNT/OTHER 等）供 Presenter 生成卡片与降维呈现复用。

### 4.7 query-ask 手册多步化样例（v2.0，支撑 §6-B1）

现有 `query-ask.yaml` 为两步直通 SOP（query → present，见 §3.3）。按 §4.5 收敛循环改造为多步手册（示意，保留原元数据结构）：

```yaml
applies_to:
  scene: query
  intents: [SPARQL_QUERY, PRODUCT_OPS_QUERY]
  triggers: ["月费多少", "资费", "套餐内容", ...]   # 原触发词保留

steps:
  - id: query
    do: 知识库粗查
    how: 提取查询要素转 SPARQL；limit 由 QueryRefinePolicy 决定（初值 20）
    tool: sparql_query

  - id: refine            # 新增：规模感知分支
    do: 结果规模判断与澄清
    how: hits≤5 直接进 present；>20 触发 CLARIFY（优先级：地市>资费档>时间窗，
         选项取粗查结果维度分布 top）；澄清至多 2 轮后强制进 present
    tool: sparql_query
    policy: 澄清选项必须来自真实结果分布，不臆造选项

  - id: present
    do: 降维呈现
    how: TOP N + 排序依据 + "共 X 条，已按…筛选"；数字结论标注数据来源与截止时间
    tool: sparql_query
    policy: 只读不改档（原护栏保留）
```

护栏与 audit 区块不变；`QueryRefinePolicy` 作为确定性组件被 `how` 文案引用，规则本身不写进 YAML（配置表达"做什么"，代码保证"怎么算"，与本项目 AI 主导原则一致）。

## 5. 已知落差与问题

### 5.1 子场景路由不一致（P1）

`assistantModes.js` 的 sceneToBackendScene 将 `query.archive` 转发到后端 `rd` 场景而非 `query`。后果：archive 入口享受的是 rd 提示词与 rd 场景能力集，与"查询助手"的定位、审计口径（会话场景标记）不一致。
**修正**：评估 `rd_config_search` 已声明 scene 含 query，archive 应改发 `query`；若历史原因必须保留转发，需在前端注释说明并纳入回归。

### 5.2 `ontology_explain` 语义错位（P1）

工具描述为"概念/制度问询"，但 `OntologyService.explain` 实际返回的是**归因评估审计记录**（评估流水），并非 TBox 概念解释。用户问"什么是融合套餐"时得到的是评估记录列表，体验落差明显。
**修正**：新增 TBox 概念/关系解释通道（基于 product-config.ttl 的 rdfs:label / rdfs:comment / 类层级），原审计查询能力拆分为独立工具（如 `attribution_query`）。

> **✅ 已修正（2026-09-09，B5）**：ontology_explain 改造为 TBox 概念解释（SPARQL 检索 label/comment/类层级/关联属性，三级解析：本地名精确→前缀→中文包含；未命中拒绝不冒充）；审计流水拆分为独立工具 `attribution_query`（承接 OntologyService.explain 语义，traceId+audience 参数化）。详见 §6-B5。

### 5.3 compare 场景边界模糊（P2）

前端 `query.compare` 发送 scene=`compare`，而后端意图归一化已将 compare/what_if/hypothesis 收敛进 `product_ops_query`（W5 意图收敛）。compare 作为独立 scene 在能力注册表中无自声明工具，实际依赖 rd/ops/query 工具的场景覆盖兜底。
**修正**：统一收敛——`query.compare` 直接发 scene=`query`，比对诉求由意图归一化路由至 `rd_scheme_compare`；删除前端对 compare scene 的特殊分支。

### 5.4 ThinkingCopy 覆盖不全（P3）

`metric_query` 未登记工具文案词典，thinking 阶段文案由 LLM 现场生成，与已登记 5 个工具的风格一致性不可控。**修正**：补登记（如"查询经营指标"）。

### 5.5 知识库能力薄弱（P2）✅ 已修正（B6）

`KnowledgeBaseService` 为内存实现，种子仅 2 条演示文档。制度/资费类问询（当前由 ontology_explain 兜底）回答深度不足。**修正**：见 §6 阶段 B（B6）。

**实施状态（B6 完成）**：新增 `InMemoryVectorSearch` 内嵌向量检索——中文字符 bigram + 英文/数字词段，TF-IDF + 余弦相似度，Top-K 降序，synchronized 线程安全；`KnowledgeBaseService` search/qa 改走向量检索，真实相似度替换固定 0.85 伪值，种子加载/增删同步维护索引；kb_seed.json 扩充 2 → 10 条（备案/命名/资费口径/合约违约金/可选包叠加/上下线流程/退市迁转）。外部向量库以同 API Bean 替换扩展（javadaoc 声明扩展位），编排与门控零改动。测试：InMemoryVectorSearchTest 7 例，全量 545/545。

**C5 查询→行动中间态缺失（P2）**

**C6 多域与 B2B 空白（P2）**

## 7. 风险与对策

| 风险 | 对策 |
| --- | --- |
| NL→SPARQL 生成错误查询 | 参数化 SPARQL 模板 + DiscoverIntent 结构化约束，禁止自由拼接；失败时 CLARIFY 澄清而非臆造 |
| ABox 同步失败/数据陈旧 | 30 分钟定时刷新 + last-known-good 回退，前端提示数据时间戳（✅ 已落地：导航栏 DataFreshnessBadge"数据截至"徽标，同步失败黄色降级提示） |
| 意图归一化误收敛（把查询误判为对比） | 归一化规则配置化 + 触发词快筛兜底；归一化仅收敛不扩散 |
| 子场景路由改动引发回归 | 阶段 0 第 5 项测试先行；前端改动灰度开关（assistantModes 配置项） |
| 工具描述与实际行为漂移（如 ontology_explain） | 工具 description 纳入评审清单；能力注册表与文档同步更新 |
| **行权限被绕过（v2.0）** | 行级过滤在 SparqlConfigDiscoverer 参数化层强制注入，不依赖 LLM 遵从提示词；权限子句不可由工具入参覆盖；审计对账抽查 |
| **真实数据质量差于 mock（v2.0）** | 阶段 A1 联调时并行核对视图字段空值率/口径一致率；脏数据白名单告警而非静默吞掉 |
| **存量用户数据涉敏（v2.0）** | user_plan_query 强制脱敏（号码打码、仅呈现套包维度）；叠加行权限；纳入 A3 审计范围 |

## 8. 验收口径

**基线验收（v1.0 保留）**：

1. query 场景下用户问题 100% 由只读工具应答，无写操作入口；
2. "一句话查产品"：品类+资费区间+状态组合查询，返回结果含商品名/资费/状态及数据来源；
3. 查询结果可一键转入 rd（复制为草稿/复制即开单）且上下文（sessionId、requirement）完整携带；
4. SSE 事件序列符合契约（thinking → tool → text → text_done → done）；
5. 新增一个 query 只读工具（含 getScenes 声明）接入成本 ≤ 半天，编排层零改动。

**商用化验收（v2.0 增补）**：

6. 真实数据源下查询可用，前端可见数据截止时间戳（✅ 时间戳呈现层已落地，验收待真实数据联调）；
7. 两个不同地市账号执行同一查询，各自仅见权限范围内数据，且行为在审计视图中可追溯；
8. 结果 >20 条时自动触发澄清/降维呈现（TOP N + 依据），不直接甩全量列表；
9. 存量用户套包查询走通且号码等敏感字段已脱敏。
