# 思考步骤出入参规范（v1）

> 单一事实源：本文档。后端生产（AgentOrchestrator / TraceSnapshotBuilder）与前端消费
> （ThinkingProcessPanel.vue / businessLabels.js）均以本规范为准。
> JSON 传输统一 snake_case（AGENTS.md 约定），步骤 IO 内业务字段沿用工具契约既有驼峰键（不二次转换）。

## 1. 步骤 IO 统一结构

每个思考步骤（thinking 事件 `steps[]` 项）可选携带 `io`：

```json
{
  "id": "sop-step-0",
  "type": "thinking",
  "title": "第1步 解析文档提取文本",
  "io": {
    "input":  { ... 输入视图 ... },
    "output": { ... 输出视图 ... }
  }
}
```

## 2. io.input 键域（封闭集）

| 键 | 类型 | 语义 | 生产方 |
|---|---|---|---|
| `from_step` | string | 上游步骤 id。值域固定：`intent` / `plan` / `execute` / `sop-step-<N>` / `tool_<工具名>` | 所有承接型步骤 |
| `requirement` | string | 本步骤的处理需求描述（业务可读一句话）。手册步骤=上一环节产出概括；意图缺失回退=用户话术截 40 字 | plan / sop / clarify |
| `structured_intent` | object | 结构化意图：**统一为 `{action: 动作名, <业务要素键>: 值}`**。手册快筛链路同样放业务要素（不放 playbook 内部码，playbook 走步骤顶层 `metadata`） | intent 产出的下游 |
| `upstream_outputs` | array | 汇总步骤输入：`[{from_step: "tool_<名>", summary}]`，每项**只带 from_step + summary 两键** | generate |
| `missing_params` | **string[]（数组）** | 澄清步骤的要素缺口清单（v1 起从顿号连接字符串改为数组，前端 `join('、')` 展示） | clarify |
| `question` | string | 用户原话。仅 intent 步骤（首步）携带；回放快照同实机不置空 | intent |

其余业务参数键（text/draft/product_type/offering 等）按工具入参契约透传，经隐藏键清单过滤（见 §6）。

## 3. io.output 键域（封闭集）

### 3.1 通用键（所有步骤）

| 键 | 类型 | 语义 |
|---|---|---|
| `summary` | string | 输出行主文案（结论先行，≤60 字）。**唯一的事实性摘要出口** |
| `branch_taken` | string | 命中的工作流分支标签。实时流与回放快照**均下发**（v1 起对齐） |

### 3.2 计数键（语义统一）

| 键 | 语义 | 取代 |
|---|---|---|
| `total` | 本环节处理条数（命中/抽取/校验/开单统一用 total） | ~~hitCount~~ |
| `passedCount` / `pendingCount` | 通过 / 待修正条数 | — |
| `workOrderCount` | 开单数（保留业务专名） | — |
| `scannedCount` / `highCount` / `mediumCount` / `suggestDelistCount` | 稽核场景专用计数（保留） | — |
| `extractedChars` | 解析字符数 | — |

### 3.3 明细键（结构化对象数组，单一载体）

> v1 起**废除预渲染字符串行**（`draftRowLine` 等后端拼文案逻辑删除），明细一律结构化对象数组，
> 前端按统一 schema 渲染。每条明细行 schema：

```json
{ "seq": 1, "title": "条目主名", "state": "通过|未通过|待修正|已创建|失败|null", "extra": "次要补充（可省）" }
```

| 键 | 载体 | 条目内容 |
|---|---|---|
| `parse_details` | array | `{seq, title: 文件名/表格名, extra: "引擎 csv，抽取 172 字"/"表格 N 列"}` |
| `draft_details` | array | `{seq, title: 套餐名, extra: "月费 198 元｜原文：…", state: 预判通过/待修正}` |
| `compliance_details` | array | `{seq, title: 套餐名, state: 通过/未通过, extra: "问题规则 R-B01、R-B02"}` |
| `work_order_details` | array | `{seq, title: 工单标题, state: 已创建/稽核未通过, extra: "工单号 WO-…"}` |
| `referenced_rules` / `issueRules` | string[] | 规则编号清单（截 8） |
| `workOrderFailures` | object[] | 失败原始条目（截 8，前端 JSON 兜底渲染） |

明细截断统一 `DETAIL_LIMIT = 8`。

### 3.4 结构化实体键（面板渲染用，保持工具契约）

`parseEngine` / `extractEngine` / `ruleId` / `compliancePass` / `issueRules` /
`workOrders`（对象数组，工单卡直链用）/ `items`（对象数组，配置卡片用）——
这些是**数据键**（供前端面板消费），与 §3.3 的**展示键**（`*_details`）并存不冗余：
展示键只含面板渲染所需最小字段，数据键保留完整契约。

## 4. from_step 值域（固定）

| 值 | 含义 |
|---|---|
| `intent` | 承接意图识别 |
| `execute` | 承接执行层整体（汇总步骤） |
| `sop-step-<N>` | 承接第 N 个手册步骤（0 起） |
| `tool_<工具名>` | 承接某工具（upstream_outputs 项内层） |

## 5. 各步骤类型的 IO 契约

| 步骤 | io.input | io.output |
|---|---|---|
| intent | `{question}` | `{summary, structured_intent}` |
| plan | `{from_step:"intent", structured_intent \| requirement}` | `{summary, branch_taken}` |
| sop-step-N | `{from_step:"sop-step-(N-1)", requirement?}`（首步无 from_step） | `{summary, <计数键>, <明细键>, branch_taken}` |
| generate | `{from_step:"execute", upstream_outputs}` | `{summary, branch_taken}` |
| clarify | `{from_step:"intent", missing_params: string[], structured_intent \| requirement}` | `{summary, branch_taken}` |
| 失败（任何步骤） | 原输入 | `{summary: "执行失败：<原因>"}` |

> sop 步骤 v1 起补 `branch_taken`（固定「按手册执行」），保证与 plan/generate 步骤行结构一致。

## 6. 隐藏输入键清单（前后端同源）

后端 `ThinkingCopy.HIDDEN_INPUT_KEYS`（唯一事实源）：
`question, intent_type, action, config, maxEntities, limit, file_id, file_ids, file_name, document_text, session_id`

前端 `HIDDEN_INPUT_KEYS` **必须与后端一致**（前端可额外防御别名：sessionId/session/intentType/fileId，但不得漏后端声明的键，也不得隐藏后端放行的业务键）。

## 7. 实时与回放同构要求

1. intent 步骤：实时与回放的 `input.question` 均为**用户原话**（回放不再置空串）。
2. plan 步骤：实时与回放的 output **均含 `branch_taken`**。
3. 手册链路（sop-step-N）：回放快照**必须**包含 sop 步骤（与实时同构），不再退化为普通 tool 卡。
4. FLOW_EXEC 链路：回放时间线由 `flow_progress_timeline` 承载（现状保留，不在本规范范围）。

## 8. 前端消费规则（对齐实现）

- 「输出」行：`output.summary` 优先 → 徽标（toolOutputEntries）→ result 兜底；同一事实不在三处重复。
- 「明细」块：仅消费 §3.3 的 `*_details` 结构化数组，按 `seq. title（extra）[state]` 渲染。
- 徽标键：`total` 统一标签为「处理条数」（不再写死「风险命中」；稽核场景由 summary 承载风险语义）。
- `offeringName` 徽标只出一处（「分析对象」），删除重复的「草稿名称」分支。
