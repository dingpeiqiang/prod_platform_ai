需求建模结构推理过程体验

运营指标异动归因：需求 · 本体建模 · 推理过程

商品掉量了，得说清楚是渠道、促销、竞品还是用户行为的问题。结论不靠打分模型，靠本体规则推导。

一、场景需求

运营看到某商品指标下滑，需要一份可复核的归因：谁造成的、凭哪些数值判定的。LLM 能组织语言，但"到底算不算根因"必须由确定性规则说话。

难点

  • 根因藏在不同类型的证据里，每种证据判据不同
  • 结论容易"合理但不可查"，模型一改口就无从追责
  • 阈值需要业务随时调，改一次就得改规则体
  • 没事时喜欢硬猜一个原因

做法

  • 四类证据各建一个"根因类"，判据写成 SWRL 规则
  • 结论是推理推出来的类型，带规则号，模型改不了
  • 阈值做成命名个体，运行时覆写，规则骨架不动
  • 先确认异动，再找根因，没有异动就闭嘴

输入只有一个商品（编码或名称）。指标、渠道、促销、竞品、行为全由服务端从事实图取，阈值读配置，用户不传任何数据。

二、本体建模结构

关键决策：结论挂在证据上。四类根因类都是证据实体自己的子类，命中后实例仍是那条渠道、那个促销，回读时按类取实例就能直接定位到具体对象。

判据写成六条 SWRL 规则，结构统一为点火 → 取一条证据 → 数值越阈 → 该证据归入根因类。阈值挂命名个体，运行时按 ops_rules.json 覆写，规则体不动。

规则前置判据默认阈值结论
R-A01—指标环比跌幅 / 上游异常标记-10%商品异动
R-A02已异动渠道订单跌幅 + 渠道贡献占比-20% / 30%渠道根因
R-A03已异动优惠将到期天数 + 驱动订单占比7 天 / 25%促销根因
R-A04已异动竞品价差比例 + 渗透率增幅15% / >0pp竞品根因
R-A05已异动行为权重提示8%行为根因
R-A06—连续下滑天数（Java 旁路，不推理）3 天持续下滑趋势
R-A02~A05 的前置都是"该商品已确认异动"。没异动就不猜根因——这条硬约束是"没事找因"的解法。

三、本体推理过程

推理机（Openllet）求值规则，得出结论类型后按结论类反查实例。以下三类外加 R-A06 的 Java 旁路构成完整判定。

同一份事实会同时触发多条规则，四类候选独立产出、互不干扰。

非命中 / 兜底情形处理
商品解析不到，或图谱无该商品直接失败，附带原因
R-A01 未点火只返回"未检出异动"，四类候选为空
SWRL 关闭 / 规则配置为 java跳过 SWRL，走同逻辑 Java
推理抛异常后端日志告警，整次降级为 Java 兜底，引擎字段标注 fallback-java

四、体验

需后端已启动（默认 localhost:6174）。两个通道二选一：填商品编码，或直接说商品名。

五、边界


    
  
  • 单层条件组合，不做多因加权排序，weight 只是证据值透传。
    • 
  
  • 只能对事实图 opsGraph 中有数据的商品归因，无事实直接失败。

  • 指标与渠道间无直接公理，无法细分"某指标主要由某渠道造成"。

  • 归因结果不落库，只能现场复核。
