场景 ① · 风险识别

零元资费在架无合约 → 高风险 → 紧急复核（4 跳长链）

全库最长推理链，跨越「事实判定 → 状态组合 → 风险升级 → 处置动作」四个语义层。规则编号与业务 SOP 一一对应。

输入事实 · :probe_rb01ZeroFee
a :Offering ;
:monthlyFee    0 ;
:oneTimeFee    0 ;
:inWhitelist   false ;
:onShelf       true ;
:hasContract   false ;
:shelfDays     100 .  # 不加则 R4 断链
阈值个体（运行时可由 reasoner 覆写）
:th_RB05_highRiskReviewDays
  :thresholdValue 30
R-B01/R-B02/R-HR 为纯布尔判定，不依赖阈值个体
轮次规则前件（AND）结论
R1R-B01.zeroFeemonthlyFee=0 ∧ oneTimeFee=0 ∧ inWhitelist=falseZeroFeeRiskOffering
R2R-B02ZeroFeeRiskOffering ∧ onShelf=true ∧ hasContract=falseZeroFeeNoContractOffering
R3R-HR.b02ZeroFeeNoContractOfferingHighRiskOffering
R4R-B05HighRiskOffering ∧ shelfDays(100) > th_RB05(30)★ UrgentReviewOffering
链式推理必须迭代到不动点

HermiT / Pellet 会自动跑多轮；若用 OWLAPI 手写 SWRL 执行器且只跑一轮，只能得到 ZeroFeeRiskOffering，后续 3 跳全部丢失。

漏写 shelfDays 会「静默断链」

R4 前件无法绑定 ?v_rb5d，链停在 HighRiskOffering，且不报任何错误——SWRL 无类型校验，这是开放世界假设的代价。

同一结论存在多条到达路径

旁支 R-B01.discount（折扣 100% + 可重复订购 + 空目标群）→ AbnormalDiscountOffering → R-HR.discount → HighRiskOffering，可与主链对比。

规则编号即业务 SOP

零元在架无合约 → 高风险 → 在架超 30 天 → 紧急复核，可直接对着业务流程给业务同事讲解，无需翻译。

场景 ② · 指标归因

异常感知 → 渠道根因（跨实例导航 + 阈值外置）

归因的本质是「先发现异常品，再定位根因来源」。R-A02 是全库唯一同时约束「对象属性跳转 + 双阈值比较」的规则，且结论主体与入口主体不同。

输入事实 · 三实例结构
:probe_metric  a :Metric ;
  :metricDelta -0.20 .

:probe_channel a :Channel ;
  :orderDelta   -0.30 ;
  :contribRatio 0.50 .

:probe_offering a :Offering ;
  :hasMetric :probe_metric ;
  :soldOn    :probe_channel .
阈值个体（运行时由 OpsSwrlReasoner 覆写）
:th_RA01_metricDeltaLte      -0.10
:th_RA02_orderDeltaLte       -0.20
:th_RA02_contribRatioGte     0.30
改阈值个体即可调参，规则本体（约 600 行）无需重建
轮次规则前件（AND）结论
R1R-A01.deltaOffering ∧ hasMetric→Metric ∧ metricDelta(-0.20) ≤ th_RA01(-0.10):probe_offering ∈ AnomalyOffering
R2R-A02AnomalyOffering ∧ soldOn→Channel ∧ orderDelta ≤ -0.20 ∧ contribRatio ≥ 0.30★ :probe_channel ∈ ChannelRootCause
主体可以换：入口 Offering → 结论 Channel

R2 的入口变量 ?v_o3 是 AnomalyOffering，但结论断言在 ?v_c3（Channel）上，靠对象属性 :soldOn 完成导航。学员必须理解这一点才能读懂归因结果落在哪个实例上。

阈值个体 ≠ 变量，是命名个体

:th_RA02_orderDeltaLte 是 :ThresholdHolder 实例，规则通过 :thresholdValue 把它的值绑到 ?v_tod。改它只需一次断言，规则本体无需重建——这是全模型的核心设计。

两个阈值条件是与关系

只满足 orderDelta ≤ -0.20 但 contribRatio < 0.30（渠道量小）不点火。业务语义：滑块要「跌得多」且「占比大」才算根因。

四类根因的触发指纹不同

R-A03 促销看 daysToExpire + drivenOrderRatio；R-A04 竞品看 priceGapRatio + penetrationDeltaPp；R-A05 行为看 weightHint。可放在一起对比训练。

场景 ③ · 配置合规

零固费无合约：声明式映射 → 5 个与条件 → 违规族归集

这是全链路最完整的一条：库表原始字段经 ops_rules.json 声明式映射翻译为本体属性，SWRL 按 5 个 AND 条件判定，命中后归入 ConfigViolation 违规族。Java 侧没有逐字段硬编码。

原始事实（表字段 / 草稿 Map）
fixedFeeAmount 0     # 或 monthlyFee / chargePlan.fixedFeeAmount
oneTimeFee     0
hasContract    false
bizScenario    "普通销售"   # 未命中权益赠送白名单
channelScope   "全渠道"     # 非「内部验证」
映射后断言的本体属性（OpsSwrlReasoner:1517）
a :Offering ;
:monthlyFee     0^^xsd:decimal ;
:oneTimeFee     0^^xsd:decimal ;
:hasContract    false^^xsd:boolean ;
:exemptionFlag  false^^xsd:boolean .
属性名、来源、类型、转换算子全部来自 ops_rules.json → config.propertyMapping（17 条）
轮次规则前件（全为 AND，缺一不可）结论
R1R-C05monthlyFee=0 ∧ oneTimeFee=0 ∧ hasContract=false ∧ exemptionFlag=false ∧ monthlyFee=th_zeroFeeC05HighRiskZeroFee
R2R-C08实例不属于 ConfigViolation（查询违规族结果）C08Compliant
「与」条件的教学样本

5 个条件缺一不可。现场把 hasContract 改成 true，或把 channelScope 设为「内部验证」，结论立即消失——很适合演示「白名单 / 内测 / 合约任一豁免即可放行」。

SWRL head 必须显式断言父类

Openllet 不会因为 head 里断言了 C05HighRiskZeroFee 就自动补齐它的父类 ConfigViolation。每条违规规则的 head 都必须同时写两个 ClassAtom，否则违规族查询会漏掉这条规则——合法合规链路静默失效。

声明式映射是唯一定义点

属性名、取值来源、类型、转换算子全部来自 ops_rules.json → config.propertyMapping。Java 侧没有逐字段硬编码；同一属性多条映射按 OR 合并（如 exemptionFlag 的两条来源）。

违规命中 + 违规族查询成对出现

C05（违规命中）与 C08（合规判定）构成一对，能讲清 SWRL「只能表达存在性，不能表达不存在性」的表达力边界，是合规模块最值得讨论的点。

场景 ③ · 补充 · 实例数据从哪来

实例不存本体：库表实时读取 → 声明式映射 → OWL 断言

本体（TBox）只描述规则与概念，不含任何实例。实例事实（ABox）在推理前从 pd_ai_ontology_instance 实时读取，由 ops_rules.json 声明式翻译为本体属性后断言进内存模型，推理结束即丢弃——不写回本体。

本体与实例严格分离

TBox（product.ttl）只含类、属性和 SWRL 规则，不含任何实例。ABox 每次推理前从库表装载，推理结束即释放。这样本体文件可独立版本化与评审，不受业务数据变动影响。

职责三分

OntologyInstanceFactsService 只负责「库 → Map 读取」；OpsSwrlReasoner.assertMappedFacts 只负责「Map → OWL 断言」；product.ttl 只负责「SWRL 规则」。三层之间无硬编码耦合。

映射缺失不报错，只是不触发

若某属性在 propertyMapping 中缺失，规则会因缺少前件原子而静默不点火。这是开放世界推理的正常行为，但排查时容易误以为规则失效——先核对映射表。

场景 ④ · 告警分级

分级 → 派单（双跳闭环），及 P0/P1 级别重叠

告警模块的完整业务动作是「定级 → 派单」。R-E02 定级、R-E04 派单构成处置闭环；同时暴露 OWL 开放世界假设与业务封闭优先级的经典冲突。

正常样例 · :probe_re02P1
a :Offering ;
:errorCount 3 .

# R-E01(≥10) ✗ / R-E02(≥1) ✓
重叠样例 · errorCount = 15
a :Offering ;
:errorCount 15 .

# R-E01(≥10) ✓ 且 R-E02(≥1) ✓
# 同时属于 P0 与 P1
阈值个体
:th_RE01_errorCountGte   10
:th_RE02_errorCountGte   1
:th_RE01_feeErrorRateGte 0.05
:th_RE02_feeErrorRateGte 0.01
轮次规则前件（AND）结论
R1-aR-E01.errerrorCount(3) ≥ th_RE01(10)✗ 不点火
R1-bR-E02.errerrorCount(3) ≥ th_RE02(1)P1AlertOffering
R2-aR-E04.p0P0AlertOffering（未命中）—
R2-bR-E04.p1P1AlertOffering★ NeedWorkOrderOffering
双跳闭环：定级 → 派单

P1 定级后由 R-E04.p1 派单。结合 P2「不派单」（R-E04 只接 P0/P1），正好讲清「P2 只观察不建单」的运营规则。

级别重叠：OWL 开放世界 vs 业务封闭优先级

errorCount=15 时同时命中 R-E01(P0) 与 R-E02(P1)。规则层面两者并存不矛盾——OWL 没约束 P0/P1 互斥。业务上必须靠 :alertLevel 写回取最高级。这是整个模型最经典的建模冲突，建议作为讨论题。

趋势类 P2 的特殊性

orderTrendDown / errorTrendUp 是预计算布尔，SWRL 不算趋势，只在「趋势为真」时归 P2。与 R-C05 的预计算布尔是同一条设计原则，可串起来复习。

阈值个体成对出现

P0/P1 各自有 errorCount 与 feeErrorRate 两组阈值个体。演示覆写其中一组即可让级别流转，强化「阈值外置」记忆点。

培训总结

四类场景的共性推理时序

所有规则共享同一套执行模型：预计算事实进入工作内存 → 规则引擎多轮匹配 → 阈值个体提供可调参数 → 结论类进入下一轮前件 → 直到不动点。

场景跳数是否需迭代关键机制
① 风险识别4必须规则链 + fixpoint 收敛
② 指标归因2必须跨实例对象属性导航 + 阈值个体
③ 配置合规1否多条件 AND + 违规族归集
③补充 实例读库0否库表 → 声明式映射 → OWL 断言（不含推理）
④ 告警分级2必须分级 + 派单 + 级别不互斥
建议授课顺序（由简到繁）

③ 配置合规（单规则，建立信心）→ ④ 告警分级（引入「链」与「矛盾」）→ ② 指标归因（跨实例导航）→ ① 风险识别（4 跳长链综合演练）。每级新增一个概念：AND 条件 → 链 → 跨实例 → 不动点迭代。

三个必讲陷阱

① 单轮推理导致链断；② SWRL head 漏断言父类 ConfigViolation，违规族查询静默漏判；③ 映射表缺项时规则不点火却不报错，误判为规则失效。
