系统是怎么自己发现问题的

过去，资费上架是否违规、销量下滑该怪谁、告警要不要半夜叫人，全靠人逐个翻表格、凭经验判断。
现在，这些判断被写成了 一套可复用的业务规则，系统每天自动跑一遍，把结论直接送到对应的人手上。
下面四页，用业务语言讲清这套判断是怎么一步步得出结果的。

场景 ① · 风险识别

一个「不收钱还挂在架子上」的套餐，是怎么被自动揪出来的

某天运营配置了一个新套餐：月费 0 元、一次性费用 0 元，而且直接挂上了架。
这个套餐既不在白名单里，也没有签任何合约——这意味着客户可以零成本订购，公司一分钱收不到。
更麻烦的是，它已经在架上超过 30 天，说明问题存在了很久却一直没人发现。

系统是怎么一步步想明白的
1
先发现「它不收钱」
系统扫到：月费 0 元、一次性费用 0 元，并且不在白名单。
→ 判定：这是一个零元套餐
2
再确认「它还在卖」
接着核对：它正在架上，而且没有合约兜底。
→ 判定：这是零元套餐，且无合约保护，放任在卖
3
升级为「高风险」
符合公司对 高风险资费 的定义——零元、在架、无合约三者同时成立。
→ 判定：标记为高风险资费
4
最后看「晾了多久」
已在架 100 天，超过 30 天 的容忍上限。
→ 判定：必须紧急复核
最终结论
紧急复核 · 最高处置等级
直接派给资费管理员，要求当天核实并下线或补签合约。整个过程没有任何人工参与，从配置上架到被系统挑出，不需要等任何人想起来去查。
为什么一定要「一步步来」

这四步是有先后顺序的：先知道它零元，才能判断它在卖零元；先知道它在卖零元，才能定性为高风险。系统会反复扫描，直到没有新结论产生才停下。如果偷懒只跑第一遍，系统最多只能告诉你「这是个零元套餐」，后面的严重性判断全部丢失。

最容易被忽略的一环

第 4 步要读取「在架天数」这个数据。如果这个字段没被采集，系统不会报错，也不会提醒——它只是悄悄停在「高风险」，永远不会升级成「紧急复核」。这是自动化最危险的地方：它不会告诉你它漏了。

同一个问题，可能有多种走法

除了「零元」这条路，系统还有另一条平行的判断路径：如果套餐折扣打了 100%、还允许重复订购、又没指定目标客群，同样会被认定为高风险。两条路殊途同归，避免漏网。

对业务的价值

这类「漏收钱」的配置，过去靠月度抽查，平均要几十天才能发现，期间每天都在流失收入。现在当天就能被发现并派单，相当于把稽核从「事后统计」变成了「事中拦截」。

① / 四类业务判断
场景 ② · 指标归因

销量掉了，系统是怎么定位到「具体是哪个渠道」的

月底复盘，发现某款产品销量下滑。
「下滑」本身是结果，管理者真正要的是：为什么会跌，我该去找谁。
系统会自动从「哪个产品出问题了」，顺藤摸瓜找到「是哪个销售渠道拖了后腿」。

两步定位法
1
第一步：找出「生病的产品」
系统逐个比对每款产品的销量变化，超过预警线的就打上标记。
本例中，这款产品销量跌了 20%，而预警线是跌 10%。
→ 判定：这是一款「异常产品」
2
第二步：顺藤摸瓜找「渠道」
一款产品往往在好几个渠道卖。系统沿着产品的销售渠道逐一排查，两个条件同时满足才认定是「元凶」：
跌得够狠（跌 30%，超过 20% 线）
占得够大（占该产品销量 50%，超过 30% 线）
→ 判定：这个渠道就是根因
系统输出
根因渠道已定位，直接指向责任方
管理者拿到的不是「销量下滑 20%」这种废话结论，而是「某某渠道销量跌 30%，占该产品一半，去查它」——可以直接转给对应渠道负责人跟进。
为什么要两个条件同时满足

只看「跌得狠」会误伤：有些小渠道虽然跌了 50%，但本来就只占 3% 的量，对大盘毫无影响。只看「占比大」也不对：占比大的渠道可能压根没跌。
又跌得狠、又占得大，才是真正的元凶——这是业务经验，被固化进了规则。

预警线可以随时调整

「跌 20%」「占 30%」这些数字都单独存放，业务要收紧或放宽口径，改个数字就行，不用找技术改系统。比如旺季放宽到跌 30%，淡季收紧到跌 10%，当天改当天生效。

除了渠道，还有三类常见原因

系统同时支持另外三种归因：促销没做好（快过期了还没卖动）、被竞品抢了（价格差拉大、份额下滑）、用户行为变了。四种原因各有各的识别条件，可并行跑。

对业务的价值

把「复盘会上互相猜、各说各话」变成「系统给出证据链，大家直接谈怎么补救」。归因周期从「周」压缩到「天」，且结论可复现、可追溯。

② / 四类业务判断
场景 ③ · 配置合规

上架前，系统怎么自动判断「这个定价违规了」

资费上架是风险最高的环节之一：定错一次价，可能被大量用户订购，损失巨大且难以追回。
系统会在上架流程中自动做一次合规检查，把违规配置拦在门内。

违规的判定：五个条件必须同时成立
✓
① 固定费为 0
套餐的固定费用是 0 元
✓
② 一次性费用为 0
开通费用也是 0 元，等于完全不收费
✓
③ 没有合约
不绑定任何合约期，随时可退
✓
④ 不在白名单
不是经过特批的特殊资费
✓
⑤ 不是内部测试
不是研发测试用的临时配置
五项全中 → 判定为「高风险零固费资费」
这是一条明确的红线：既不收钱、又无合约约束、还不是特批或测试，就是必须拦下的违规定价。
拦截效果
上架即告警，配置方当场修正
不需要等财务月结、也不需要等稽核抽查，在配置的那一刻就被系统指出来。风险从「事后追损」变成「事前拦截」。
为什么要「五个条件同时」

因为每一个都对应一种合理豁免：白名单 = 领导特批；内部测试 = 研发用；有合约 = 有对价。只要有一条成立，就说明这个零元是事出有因的，不该拦。五个条件全中，说明什么理由都没有。

边界一：合规结论靠「排除违规」得出

系统只能判断「命中了某条违规红线」，无法自动证明「不存在任何违规」。所以「合规」是把 7 类违规逐一排除后得到的结论，而不是一条独立的正向判定。这是这类推理技术的固有边界，实施时须配套校验流程。

边界二：两项豁免靠外部预判

「是否特批」和「是否内部测试」这两项，系统不会自己去查系统、也不做数据清洗。其中「内测」按渠道直接判定；「特批」因为技术上无法证明「不存在白名单单号」，只能由前置程序按「查不到就当没有」算好一个豁免标志传进来。两条映射规则都写在配置文件里，业务方可自行查看与调整，但该标志不是系统推理出来的——这是明确的建模妥协。

顺带拦下的其它红线

同一套机制还可以覆盖：折扣超限、赠送资源超量、价格倒挂等配置红线。只需按同样方式新增一条判断条件，不需要改系统架构。

③ / 四类业务判断
场景 ④ · 告警分级

出了故障，系统怎么决定「谁来处理、有多急」

告警最大的痛点不是「发现不了」，而是「天天响、没人信、真出事了反而漏掉」。
系统把这套事分成两步：先定级，再派单。

第一步：定级 —— 按严重程度分三档
P0
错误数 ≥ 10 次
或计费错误率 ≥ 5%
→ 重大事故，最高级别
立刻响应
P1
错误数 ≥ 1 次
或计费错误率 ≥ 1%
→ 一般故障，需处理
当日响应
P2
只是趋势不好
销量在跌 / 错误在涨，但未达红线
→ 仅观察，不派单
不打扰任何人
第二步：派单 —— 只有 P0、P1 才建工单
P0
派「紧急工单」
按重大事故流程走，通知到值班负责人和管理层
P1
派「常规工单」
进入日常工单队列，按 SLA 时限处理
举例说明
错误 3 次 → 判 P1 → 自动开工单
3 次没到 P0 的 10 次线，但已经超过 P1 的 1 次线，所以判 P1 并派常规工单。不用人判断、不用人建单，判断和派发一次完成。
为什么要分三档、而不是一刀切

如果所有异常都当重大事故处理，一周就会把人拖垮，最后所有人都开始无视告警。分级的意义是让「该紧张的紧张，不该打扰的不打扰」，P2 只观察不派单，正是为了保住告警的可信度。

已知的边界：级别可能重叠

如果错误数是 15 次，它同时满足 P0 和 P1 的条件。系统层面这不算矛盾（两个判断都成立），但业务上必须只取一个。目前靠最后按最高级收敛来处理。
建议：后续在业务规则里显式声明「P0 与 P1 互斥」，让结论更干净。

趋势判断不做预测

P2 里的「销量在跌」「错误在涨」，是前置程序算好后传进来的结论，系统不负责预测趋势。这和大屏上的趋势图是两回事，不要把两者混谈。

对业务的价值

值班同事从「每天翻几百条告警逐个甄别」变成「只看系统派过来的工单」。工单数量可能只有原来的十分之一，但真正该处理的都没有漏。

④ / 四类业务判断

一页看完全部四个场景

所有判断共享同一套逻辑：把数据准备好 → 按规则一步步推 → 得出可执行的结论。差别只在步骤多少和判断条件的复杂程度。

场景需要几步最终交付给谁业务上解决什么问题
① 风险识别4 步资费管理员漏收钱的在架套餐，当天被挑出并要求复核
② 指标归因2 步渠道负责人销量下滑直接定位到责任渠道，不用开会猜
③ 配置合规1 步配置操作人违规定价在上架那一刻被拦下
④ 告警分级2 步值班 / 管理层该紧张的最紧张，不该打扰的不打扰
三条管理层需要牢记的事

1. 规则是可以调的资产，不是一次性开发。业务口径变了，改阈值即可，不用重新开发系统。

2. 自动化最怕「静默失败」。数据没进来，系统不会报错，只是得不出结论。必须配套数据完整性监控。

3. 系统只负责「判断有没有违规」，不负责「证明不存在违规」。「合规」是由排除 7 类违规反向得出的；另有「特批」「内测」两项豁免依赖外部传入的标志（已声明在配置中）。流程设计上要补齐这两环。

建议的推进节奏

先跑通一个场景（建议从场景 ③ 配置合规开始，单条规则、见效快、风险低），验证「规则改写 → 数据接入 → 结论派单」整条链路。

再复制到其它场景，此时只需要业务专家参与定义条件，技术侧几乎零开发。

最后评估扩展边界：哪些判断适合规则化，哪些必须靠人工经验，提前划清，避免过度承诺。
