本体能帮业务干什么：5 个真实场景讲明白

不用懂技术也能看。下面 5 件事都是日常运营、资费、运维里真会碰到的活儿。每件事都按三句话讲：难在哪 → 系统心里怎么盘算 → 自己能点一下试。

先打个比方，本体就是给系统装了一本「业务常识册」：
  • 册子里写清楚了「这个平台上有哪些东西」——商品、渠道、促销、竞品、用户行为、风险、告警。
  • 也写清楚了「它们之间怎么扯上关系」——谁卖在哪个渠道、参加过哪个促销、被哪个竞品压着。
  • 还写清了一些「行规」——什么算异动、什么算高风险、什么配置算违规。
有了这本册子，系统遇到一件具体的事，就能顺着册子里的关系一条条往下捋，最后告诉你「问题出在哪、归哪一类」。普通程序只能照事先写死的 if 去判断，册子没写到的就傻了；本体是把常识摆在那里，让系统自己推。
这页怎么用：顶部按钮一件一件切过去看。每个场景页面底下都有体验区，前后端跑起来后点按钮就能看到真实结果，不用自己填参数。

系统到底是怎么跑起来的（白话版）

五个场景是同一套路子：你给一个商品编号，系统去库里把这件商品的真实情况捞出来，临时拼成一张「关系网」，拿册子里的行规在上面推一遍，把推出来的结果（比如「因为 XX 渠道掉单」）告诉你，然后把这网扔掉。

为什么跑完就扔？因为推出来的结论只对这一次有用，不留旧账；库里的数据和册子本身都只看不写，出事也弄不乱原始资料。

这样设计的好处：判断标准变成可调的「数字」，运营自己就能改档；跑一次不留残留，随便试不会污染数据；同一条线把「找原因 / 分类 / 校验 / 检索 / 定级」全包了，不用为每件事单独写一套。

怎么试

  • 先让后端在公司电脑上跑起来（默认 localhost:6174），这页直接双击打开就行。
  • 顶部按钮切换场景，每个场景点一下示例按钮，参数自动填好发过去。
  • 地址写错了或后端没开，页面会直接告诉你。
给技术看：接口、类名、代码位置

5 个场景共用同一条执行链：前端只发业务事实，本体与规则在后端现场装配、一次性推理、回读结论即销毁。核心在推理服务——它不靠硬编码分支，而是把请求数据塞进本体变成实例，调阈值、关规则、交给 Openllet 点火，再从推出来的类型反查命中了谁。

实例数据从哪来：页面只传一个商品 ID（至多带一句描述），不预存任何个体。后端先据 ID 从数据库取该商品的运行时事实，再翻译成 OWL 个体，并用 :hasMetric、:soldOn、:participatesIn、:competesWith、:influencedBy 挂回主商品。基础本体由 loadBaseOntology 按 productOpsOwlPath（告警走 ALERT_OWL_PATH）只读载入。DB 只读不回写。

所有类、属性、规则均指向运行时本体 backend-app/src/main/resources/ontology/product.ttl。docs/ontology/model/*.ttl 只是设计稿，改它不生效。

接口前缀 /api/v1/product-ontology、/api/v1/appstore，都在鉴权白名单里，不需要 token。

场景 1 · 这个包为什么突然卖不动了

业务天天问「为啥掉量」，以前只能凭经验猜、口径还各不相同。系统现在会先生判「到底算不算掉」，真掉了才顺着渠道、促销、竞品、用户行为四路去找，最后指名道姓说是哪个渠道、哪个竞品。

难在哪

现实里的麻烦

  • 掉量的原因太多，全靠人猜，十个人十个说法
  • 只说"有问题"没用，得说清是哪个渠道、哪个竞品拖的
  • 只是小波动也会被硬凑原因，白折腾

系统怎么做

  • 先看波动够不够大，不够大就到此为止，不瞎归因
  • 够大才分四路排查，原因直接落到具体渠道、促销、竞品、行为上
  • 结论能点开看到是哪一条，不是一句空话

系统心里有本账

系统心里有张「这件商品摊了什么摊子」的清单：卖在哪些渠道、参加了哪些促销、被哪些竞品抢单、受哪类用户行为影响。「原因」不是另写一句话，而是直接标在清单里的某个具体渠道 / 促销 / 竞品 / 行为上——标了谁，谁就是根因。四路排查各有一条行规，比如「这条渠道掉单超过 30% 而且在总掉量里占比够高，就算它的锅」。

红线值（掉多少算掉、占比多少算数）是写死的数字，可以改。改了不用动程序。

系统一步步怎么走

对业务的意义：不用先学怎么看报表，把编号丢进去就能拿到「是 XX 渠道、被 XX 竞品抢单」这种能直接拿去处理的结论；不是异动的那天，系统也会明确告诉你"没事"，省掉空跑。
给技术看：类结构、规则、执行时序

结论类是证据实体自身的子类而非商品子类（:1053-1072）：:ChannelRootCause ⊑ :Channel、:PromotionRootCause ⊑ :Promotion、:CompetitorRootCause ⊑ :Competitor、:BehaviorRootCause ⊑ :UserBehavior。唯一的商品侧结论类是点火标记 :AnomalyOffering ⊑ :Offering。

四类证据靠对象属性（domain 全部 = :Offering，:1143-1152）从商品出发：:soldOn 指渠道、:participatesIn 指促销、:competesWith 指竞品、:influencedBy 指行为。阈值进图而非写死：:th_RA01_metricDeltaLte…:th_RA05_minWeightHint（:1703-1710）。

R-A02 示例（:1770-1777）：

AnomalyOffering(?o) ∧ soldOn(?o,?c) ∧ orderDelta(?c,?d) ∧ contribRatio(?c,?r)
∧ thresholdValue(:th_RA02_orderDeltaLte,?td) ∧ thresholdValue(:th_RA02_contribRatioGte,?tr)
∧ swrlb:lessThanOrEqual(?d,?td) ∧ swrlb:greaterThanOrEqual(?r,?tr)
→ ChannelRootCause(?c)

硬约束：R-A02~A05 的 body 首原子一律是 AnomalyOffering(?o)，强依赖 R-A01 点火成功；R-A01 自身有两条交替入口——.delta 走 metricDelta ≤ 阈值，.flag 走 anomalyFlag = true。

场景 2 · 哪个包有风险、该先处理谁

零元卖、乱送、一挂大半年一个没卖出去——这些情况系统会自己认出来、归进「风险」，几个风险叠在一起就自动升级成「高风险」，再叠就催「紧急复核」。不用人一条条对表打分。

难在哪

现实里的麻烦

  • 风险好几种，判断标准各不相同，散在一堆台账里
  • 单个风险感受不深，几个凑一起才严重，可没人帮你合起来看
  • 分好类还得能按类批量捞出来处置

系统怎么做

  • 每种风险各有一条自己的判断标准，认出来就归进那一类
  • 几条严重风险会自动并到「高风险」这层，一并了就升级要紧急复核
  • 分类结果是现成的清单，按类一捞就是一批待处理

系统心里有本账

每种风险都是商品身上贴的一张「标签」：零元卖、异常赠送、零元又没合约、长期零销、低效在架。标签不全靠人贴，是系统按标准看到情况就自己贴上去的。其中两条最严重的（零元又没合约、异常赠送）一被贴上，商品就自动多出一张「高风险」大标签；已经是大高风险、又在架太久，系统再贴「紧急复核」，相当于自己举手喊人。

这个链条是一环扣一环的：前面没认出来，后面就不会升；所以掺不了假，也不会跳过中间步骤直接喊紧急。

系统一步步怎么走

对业务的意义：风险自己会叠、会升级、会排队，人只需要接「紧急复核」的单子就行；不严重的自动落在中等，不会被杂事淹没。按风险类别一筛就是一整批，能批量下架或复核。
给技术看：类结构、规则、执行时序

五个单点风险类全部 rdfs:subClassOf :Offering（:1075-1094），风险主体就是商品本身：:ZeroFeeRiskOffering、:AbnormalDiscountOffering、:ZeroFeeNoContractOffering、:ZeroSalesOffering、:LowEffOffering。另有归并层 :HighRiskOffering 与升级动作 :UrgentReviewOffering（:1095-1102），二者自身不带判据。阈值个体 :th_RB01_fullDiscountPercentGte（100）、:th_RB03_zeroSalesShelfDays（180）、:th_RB05_highRiskReviewDays（30）。

规则分三层（product.ttl:1813-1882）：

ZeroFeeNoContractOffering(?o) → HighRiskOffering(?o)        # R-HR.b02
AbnormalDiscountOffering(?o)  → HighRiskOffering(?o)        # R-HR.discount
HighRiskOffering(?o) ∧ shelfDays(?o,?d) ∧ thresholdValue(:th_RB05_highRiskReviewDays,?t)
∧ swrlb:greaterThan(?d,?t) → UrgentReviewOffering(?o)       # R-B05

硬约束：R-B02 依赖 R-B01.zeroFee 先行成立，R-B05 依赖归并层先行成立。因多规则共用同一父类结论，回读不能只看类型，要用 ruleFired（实例确已归入 head 类 ∧ 存在 label 命中该规则号且 head 指向该类的规则）双条件逐条验证命中。

场景 3 · 这个配置有没有坑

新配置送上后台先过一道自动体检：该填的没填、自相矛盾、资费越了线，统统逐条挑出来，还告诉你踩的是哪条规矩。

难在哪

现实里的麻烦

  • "格式对不对"和"内容合不合规"是两码事，混在一起没法管
  • 合规口径全埋在程序里，改一条规矩就得发版等排期
  • 报错只说"有错"，不说是哪条规矩哪一项，改不动

系统怎么做

  • 格式归格式查，业务归业务查，两拨分开各管一摊
  • 业务规矩从册子里读，改规矩不碰程序
  • 每个违规都标明是第几条规矩、哪一项，照单改就行

系统心里有本账

体检分两关，互不掺和：

  • 第一关看长相——必填的三项（名称、固定资费、适用渠道）有没有缺，同一个互斥组有没有重复勾选。相当于表单的"格式检查"。
  • 第二关看合不合规矩——折扣和赠费撞车没有、加了附加包却没配依赖、高风险情况下还收零元、折扣砍太狠、固定资费超出范围。相当于"业务审核"。

两关都跑完，命中什么就报什么，每条都带规矩编号和具体字段。白名单里的特批配置会被直接跳过，不冤报。

系统一步步怎么走

对业务的意义：规矩写进册子，运营和产品自己就能加、能改，不排队等开发；报出来的话能照着改，不用来回问"到底哪错了"。
给技术看：SHACL/SWRL 分工、规则、执行时序

两类约束互不重叠、各管一层：结构层用 SHACL（compliance-shacl.ttl），:OfferingShape 以 sh:targetClass :Offering 挂在商品节点上，含 R-C06 三必填（sh:minCount 1）、R-C03 互斥组 sh:maxCount 0。业务层用 SWRL：R-C03 折扣/赠费冲突、R-C04 附加缺依赖、R-C05 高风险零固费、R-C07 异常折扣、R-C09 固费越界，命中都归入 :ConfigViolation。

R-C05 示例（:2082-2094）：

Offering(?o) ∧ monthlyFee(?o,?m) ∧ oneTimeFee(?o,?ot) ∧ hasContract(?o,?c)
∧ thresholdValue(:th_RC05_zeroFee,?t) ∧ swrlb:equal(?m,?t) ∧ swrlb:equal(?ot,?t)
∧ swrlb:equal(?c,"false") ∧ exemptionFlag(?o,?e) ∧ swrlb:equal(?e,"false")
→ C05HighRiskZeroFee(?o) ∧ ConfigViolation(?o)

豁免白名单的草稿在 draftToStatements 投影时直接跳过。已迁 SWRL 的规则以 SWRL 为准，未迁或 SWRL 抛异常的才回退 Java 同逻辑（ComplianceRuleEngine）。

场景 4 · 用大白话把包找出来

"有哪些 0 元的校园包？"就这么问，不用学查询语法。系统认得出话里的关键词，自己去库里翻，翻出清单给你。

难在哪

现实里的麻烦

  • 业务不会写查询，看关系图也头大
  • 名字和标签写法五花八门，关键字死搜漏一堆
  • 想顺着「这个品类」「这个资费」找，平表比不出来

系统怎么做

  • 册子里每个东西都有中文说明，正好当"能问什么"的对照表
  • 话里的片段对上哪一个，就在库里去比哪一个
  • 对不上的词直接忽略，不会因为多说一句就查不出

系统心里有本账

系统手里还是那本册子，但这次只用来「认词」：册子里写了哪些东西、每样东西怎么称呼。你说「校园」，它翻到「所属品类」这一条；你说「0 元」，它翻到「月费」这一条；你说「包」，它知道要找的就是商品。认出来的词都变成条件，去库里一次性筛完。

认不出来的词（比如"最近挺火的"）不报错，直接略过——所以随便怎么说话都不会失败。什么都不说，它就干脆把库里有什么全列出来，帮你先对个眼。

系统一步步怎么走

对业务的意义：不用背字段名、不用找技术同学代查，一句人话就能了解市场上有哪些包、什么价位、哪个品类，查起来没有门槛。
给技术看：词表映射、接口、执行时序

本体在这里的角色是"结构化词表"：类给出"能问哪类对象"（统一落在 :Offering，:1039），对象属性给出"能沿什么边找"——:belongsToCategory（品类，:24）、:hasMetric（指标，:1143）；数据属性承载可过滤的字面值，如 :monthlyFee（:1240）、:offeringName（:1158）、:channelScope（:307）。类/属性上的 rdfs:label、rdfs:comment 是给 LLM 的语义提示。

抽词后每个片段找最近的类/属性，拼成 SELECT ?o WHERE { ?o a :Offering ; :belongsToCategory :personMainPrc ; :monthlyFee 0 . } 一次取回。接口只读：POST /sparql（:343）非空 query 走 sparqlSelect，空 query 回全量实例列表。

场景 5 · 这摊子事到底有多急

单量掉、报错涨、资费出岔子，系统直接判成 P0 / P1 / P2 三档，最急的两档自动开单，不给人拖到第二天。

难在哪

现实里的麻烦

  • 监控指标一大堆，哪个算事谁也说不准
  • 靠值班眼睛看，同一摊事换个人就换了档
  • P0 要是拖过夜，就是事故

系统怎么做

  • 每种异常都有明确的红线，够线就归到那一档
  • 档位是系统自己判的，不靠人拍脑袋
  • P0、P1 自动开单并写明多久必须处理，P2 只观察

档位不是打分，而是三个抽屉：P0 最急、P1 次急、P2 先看着。每种异常对一档红线——报错数、出错率一律比 P0 线：超了扔进 P0 抽屉；没超但超了 P1 线，扔 P1；只是趋势在往上爬，扔 P2。同一件事同时够好几档，就按最急那档算。

扔进 P0 或 P1 抽屉，还会自动触发一个动作：开单，并约定多久内必须处理。P2 只躺在抽屉里，不惊动任何人。红线数字写在外头，随时能调。

系统一步步怎么走

对业务的意义：不用再为半夜判断吵一架，同一摊事谁来判都是同一档；P0、P1 自动落到工单上，有处理时限兜着，不至于过夜变事故。想看有多少 P0，按档一捞就是一份名单。
给技术看：等级类、规则、执行时序

等级不是数字，是类：:P0AlertOffering / :P1AlertOffering / :P2AlertOffering，加上归并动作类 :NeedWorkOrderOffering。指标异常是商品自身的数据属性：:feeErrorRate、:errorCount、:errorTrendUp、:feeTrendUp、:orderTrendDown。阈值个体 :th_RE01_feeErrorRateGte（0.05）、:th_RE01_errorCountGte（10）、:th_RE02_errorCountGte（1）、:th_RE02_feeErrorRateGte（0.01）。

规则头直接写等级类，判定即归类；建单由 R-E04 推 :NeedWorkOrderOffering：

Offering(?o) ∧ errorCount(?o,20) ∧ thresholdValue(:th_RE01_errorCountGte,10)
∧ swrlb:greaterThanOrEqual(20,10) → P0AlertOffering(?o)        # R-E01.err
P0AlertOffering(?o) → NeedWorkOrderOffering(?o)               # R-E04.p0
