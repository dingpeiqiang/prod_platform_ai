## 1. 目标与非目标

### 1.1 目标

1. **流程即数据**：流程定义是 JSON（`pd_ai_workflows.workflow_data`），评审/单测/发布/回滚均针对确定物。
2. **图即真相**：编辑器画的图 = 引擎执行的图 = 监控展示的图，三者同源。
3. **节点级可观测**：每个节点的状态/耗时/入参出参/分支判定依据落库，可审计可回放。
4. **确定性执行**：同流程同输入 = 同路径；条件分支为显式表达式，可单测。
5. **持久化状态机**：每节点完成即落库，进程重启可续跑，人工挂起不限时长（有 TTL）。

### 1.2 非目标（明确不做）

- 不做自然语言理解入口（自由文本属于 Agent 对话入口，见方案 §12.2）
- 不做 BPMN 全量规范、跨系统 ESB、分布式事务
- 不做循环节点（确有批量迭代需求时封装为 `AgentTool`，见方案 §12.1 判据）
- 不引入新中间件（无 Redis/MQ 依赖，全部基于 MySQL + Spring 现有设施）

```
┌─ 前端编辑器（LangChainEditor.vue，vue-flow）────────────┐

│  执行/监控面板 → /api/v1/flow-engine/*（新增）            │
└──────────────┬──────────────────────────────────────────┘
               │ JSON 流程定义（workflow_data）
┌──────────────▼──────────────────────────────────────────┐

               │
```

## 3. 节点契约

### 3.1 节点类型集（首发 7 种，收敛自编辑器现有 14 种）

| 类型 | action 值 | 语义 | 执行器 |
|---|---|---|---|
| 开始 | `flow.start` | 入口，承载结构化入参 | 引擎内置 |
| 结束 | `flow.end` | 出口，声明流程输出 | 引擎内置 |
| 工具 | `flow.tool` | 调用 `AgentTool`（真实工具） | ToolNodeExecutor |
| LLM | `flow.llm` | 调用 LlmService（prompt 模板 + 变量注入） | LlmNodeExecutor |
| 条件 | `flow.condition` | SpEL 表达式，多出边按分支条件选择 | ConditionEvaluator |
| 人工 | `flow.human` | 挂起等待人工确认/填写后恢复 | 状态机内置 |
| HTTP | `flow.http` | 调外部系统接口 | HttpNodeExecutor |

编辑器已有的其余节点类型（code/loop/variable/form/validate 等）**暂不进入引擎**：variable/set_variable 的能力由变量解析器承担；code 节点涉及沙箱安全（二期单独评审）；form 并入 human 节点（挂起时下发表单 schema）。

### 3.2 节点定义结构（对齐《工作流配置规范》v1.0，扩展执行语义字段）

```json
{
  "id": "node-tool-001",
  "type": "flow.tool",
  "name": "合规校验",
  "position": { "x": 300, "y": 200 },
  "action": "flow.tool",
  "action_params": {
    "toolName": "rd_compliance",
    "inputParams": [
      { "name": "draft_id", "value": "{{node-start.output.draft_id}}" }
    ],
    "timeoutMs": 30000,
    "retry": { "maxAttempts": 2, "backoffMs": 1000 },
    "outputParams": [
      { "name": "compliance_result", "source": "data.result", "type": "object" }
    ]
  }
}
```

**新增执行语义字段（与纯 UI 字段区分）**：

| 字段 | 必填 | 说明 |
|---|---|---|
| `timeoutMs` | 否 | 节点执行超时（默认 30000）；超时按失败处理，走 fallback 或标 failed |
| `retry.maxAttempts` | 否 | 失败重试次数（默认 0，即不重试——重试策略必须显式声明） |
| `retry.backoffMs` | 否 | 重试退避间隔 |
| `onFailure` | 否 | `fail`（默认，流程失败）/ `continue`（记录失败继续）/ 边路由到 fallback 节点 |

### 3.3 condition 节点定义

```json
{
  "id": "node-cond-001",
  "type": "flow.condition",
  "action": "flow.condition",
  "action_params": {
    "branches": [
      {
        "id": "high-risk",
        "expression": "${node-tool-001.output.compliance_result.riskLevel} == 'HIGH'",
        "label": "高风险 → 人工审批"
      },
      {
        "id": "pass",
        "expression": "default",
        "label": "通过 → 自动提交"
      }
    ]
  }
}
```

- 多条分支按声明顺序求值，首个为 true 的命中；`expression: "default"` 为兜底分支（必须声明，防止无分支命中导致流程悬挂——定义期校验强制）。
- 分支命中依据（表达式原文 + 求值结果）**写入节点执行记录**——审计时"为什么走这条边"有据可查。

## 4. 状态机与执行模型

### 4.1 执行实例状态

```
running ──┬──→ waiting_human ──（人工恢复/超时）──→ running
          ├──→ failed（可 resume 重跑，从失败节点续）
          ├──→ cancelled
          └──→ completed
```

### 4.2 节点执行状态

`pending → running → completed / skipped / failed`

- `skipped`：condition 分支未命中路径上的节点、或上游 `onFailure=continue` 失败后的下游——**skipped 不触发依赖中止**（与 Agent 的 fail 语义区分）。

### 4.3 推进模型（每节点一个事务）

```
① 取 next 节点（按边+condition 求值）
② UPDATE 节点状态 → running（乐观锁，version 字段）
③ 执行节点（NodeExecutor 分派，带超时）
④ 事务：INSERT node_log + UPDATE execution.context + UPDATE 节点状态
⑤ 循环 ① 直到 end 节点 / 挂起 / 失败
```

**关键决策——上下文全落库**：每节点完成后，其 output 合并写回 `pd_ai_workflow_executions.context_data`（JSON）。恢复执行时从库读上下文，引擎无内存态。代价是每节点一次 UPDATE，换来"kill -9 任意时刻可恢复"。

### 4.4 human 节点挂起/恢复

- 挂起：execution 置 `waiting_human`，节点记录 `pending_form_schema`（表单定义），生成 `resume_token`（UUID，一次有效）。
- 恢复：`POST /api/v1/flow-engine/executions/{id}/resume` 携带 token + 表单数据 → 校验 token → 数据写入节点输出 → 状态机继续推进。
- TTL：节点定义 `ttlHours`（默认 72h），`@Scheduled` 扫描过期挂起 → 走 `onTimeout` 分支（默认标 failed，可路由到降级节点）。
- 无 Redis/MQ 约束下的并发控制：恢复请求以 DB 行锁（`SELECT ... FOR UPDATE` on execution 行）防双提交。

## 5. 条件表达式规范（SpEL 沙箱）

### 5.1 求值上下文

| 变量 | 来源 | 示例 |
|---|---|---|
| `node_<id>.output` | 节点输出 | `${node_tool_001.output.riskLevel}` |
| `flow` | 流程入参 | `${flow.applyReason}` |
| `system` | 系统变量（timestamp/executionId） | `${system.timestamp}` |

### 5.2 安全约束（硬性）

1. 使用 `SimpleEvaluationContext`（禁类型引用、禁构造器、禁 bean 访问）——防 SpEL 注入。
2. 表达式长度 ≤ 500 字符；定义期校验时**空跑求值一次**（用占位上下文）确保语法合法。
3. 禁止出现 `T(`、`new `、`#this` 之外的标准上下文引用；定义期正则预检 + 运行期沙箱双保险。

### 5.3 变量引用对齐

流程定义中的 `{{node-id.output.field}}` 引用语法（《工作流配置规范》§5）由 `VariableResolver` 解析，语义与 Agent 侧 `ExecStep.paramMappings` 的 `result:<tool>.<key>` 对齐（上游输出→下游入参）；`VariableResolver` 从 `DefaultExecutor.resolveSource` 抽取复用，两入口共用一份参数解析实现（DRY）。

## 6. DDL 变更

```sql
-- 1. 执行实例表扩展（已有表加列）
ALTER TABLE pd_ai_workflow_executions
  ADD COLUMN context_data    JSON NULL COMMENT '运行上下文（各节点输出合并，恢复执行的数据源）',
  ADD COLUMN current_node_id VARCHAR(64) NULL COMMENT '当前推进到的节点',
  ADD COLUMN resume_token    VARCHAR(64) NULL COMMENT '人工节点恢复令牌（一次有效）',
  ADD COLUMN status_version  INT NOT NULL DEFAULT 0 COMMENT '乐观锁版本',
  ADD COLUMN workflow_version INT NULL COMMENT '执行时锁定的流程定义版本（回滚安全）';

-- 2. 节点级执行记录（新增）
CREATE TABLE pd_ai_workflow_node_logs (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  execution_id  VARCHAR(64) NOT NULL COMMENT '执行实例 ID',
  node_id       VARCHAR(64) NOT NULL COMMENT '节点 ID',
  node_type     VARCHAR(32) NOT NULL COMMENT '节点类型',
  status        VARCHAR(16) NOT NULL COMMENT 'running/completed/skipped/failed',
  attempt       INT NOT NULL DEFAULT 1 COMMENT '第几次重试',
  input_data    JSON NULL COMMENT '节点实际入参（变量解析后）',
  output_data   JSON NULL COMMENT '节点输出',
  error_message TEXT NULL,
  branch_taken  VARCHAR(128) NULL COMMENT 'condition 命中的分支 id 及表达式原文',
  started_at    DATETIME(3) NOT NULL,
  ended_at      DATETIME(3) NULL,
  duration_ms   BIGINT NULL,
  KEY idx_exec (execution_id),
  KEY idx_exec_node (execution_id, node_id, attempt)
) COMMENT '流程节点级执行记录（审计与断点恢复依据）';
```

**要点**：`workflow_version` 在启动执行时锁定定义版本——流程定义被回滚/更新后，**在途执行实例继续按锁定版本跑完**，避免"跑到一半图变了"。

## 7. API 设计（新增 `/api/v1/flow-engine`）

| 端点 | 方法 | 语义 |
|---|---|---|
| `/executions` | POST | 启动执行：`{workflowCode, version?, inputData}`；缺省 version 取已发布最新版 |
| `/executions/{id}` | GET | 执行详情（状态+节点记录+上下文） |
| `/executions/{id}/resume` | POST | 人工节点恢复：`{resumeToken, formData}` |
| `/executions/{id}/cancel` | POST | 取消（仅 running/waiting_human 可取消） |
| `/executions/{id}/retry` | POST | 从失败节点续跑（复用锁定版本） |
| `/executions` | GET | 执行列表（按 workflowCode/status 过滤） |

前端编辑器的"执行"按钮与监控面板全部改调上述端点；`executionEngine.js` 的前端 DFS 逻辑在 P3 拆除。

## 8. 实施顺序（P2 拆解，每步可独立验证）

| 步骤 | 内容 | 验收 |
|---|---|---|
| P2-1 | DDL 变更 + FlowDefinitionValidator（定义期守门：无环/工具存在/引用合法/condition 兜底分支必填） | 单测覆盖非法定义全拒 |
| P2-2 | 状态机 + start/tool/end 三节点线性执行 + 节点留痕 | 一个含真实 AgentTool 的三节点流程跑通，kill -9 可续 |
| P2-3 | ConditionEvaluator（SpEL 沙箱）+ condition 节点 + 分支审计字段 | 分支判定依据落库可查 |
| P2-4 | human 节点挂起/恢复/TTL | 挂起→重启进程→恢复续跑成功 |
| P2-5 | llm/http 节点 + timeout/retry | 超时按声明走 fallback |
| P2-6 | SSE 进度推送（复用 thinking/tool 事件语义） | 编辑器执行面板实时点亮节点 |
| P2-7 | 编辑器执行入口切换后端 + 拆除前端 DFS | 前端不再有执行语义代码 |

## 9. 风险与应对（承接可行性评估结论）

| 风险 | 应对 |
|---|---|
| SpEL 注入 | SimpleEvaluationContext 沙箱 + 定义期正则预检（§5.2） |
| 无 Redis 的并发恢复 | DB 行锁 + resume_token 一次有效（§4.4） |
| 长挂起堆积 | TTL + @Scheduled 清理（§4.4） |
| 外部系统卡死 | 节点级 timeoutMs + retry 声明式配置（§3.2） |
| 定义更新与在途执行冲突 | workflow_version 启动锁定（§6） |
| 两入口边界漂移 | 方案 §12.2 评审判据进需求评审清单；引擎入口不收自由文本 |

## 10. 与 Agent 体系的组件共享边界

| 组件 | 归属 | 共享方式 |
|---|---|---|
| `AgentTool` 注册表 | Agent 体系 | 引擎 ToolNodeExecutor 注入复用 |
| 参数解析（四来源） | **抽公共**：`ParamResolver`（从 DefaultExecutor 抽取） | 两入口共用 |
| 工具契约校验 | `ToolContractValidator`（已有） | 引擎定义期校验复用 |
| DAG 无环校验 | 从 DefaultUnderstander 抽取为静态工具类 | 定义期校验复用 |
| LLM 调用 | `LlmService` | llm 节点复用 |

抽取原则：只抽"纯函数式"校验与解析逻辑（无状态、无 LLM 依赖），不抽 Agent 的编排语义（steps 顺序执行/CLARIFY 流程）——两范式保持各自的执行模型，共享点收敛在工具层与校验层。
